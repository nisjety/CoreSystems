- P1 risk: the run-end and start-failure revokes of both grants reuse the ingress browser bearer, which auth-core mints as a 300-second plane token by default (PLANE_TOKEN_TTL_BROWSER_BROKER_SECONDS) and the gateway caches for 240 seconds, and the broker enforces exp with a 30-second leeway, so a run that outlives that bearer has its revokes refused and both grants end at their TTL (the parent at most 600 seconds after issue) rather than at run end; the fix is a browser-broker bearer that covers the run limit (a deploy TTL or an owner ruling) or a fresh bearer at run end.
- P1 bug: keyed_run_key (model-gateway browser_run.rs) folds the parent grant id into a room run's key and the gateway issues a new parent on every attempt, so a retry with the same client_send_id starts a second run while one is live (the Space cap of two admits it), contrary to WS20-S3's comment that a replayed decision "names the same run"; this predates D5, needs an owner ruling (key room runs by org, user and decision key only) and was not changed here.
- P2 gap: a dispatch that never ends the run (an ExecuteStep transport error, an unknown lifecycle status, a heartbeat error, or a pause nobody cancels) revokes neither grant, so both end at their TTL, the stated ten-minute bound; a stop is seen when the dispatch returns or at the five-minute heartbeat.
- P2 deviation: the plan's WS20-S2 text says POST /v1/browser/grants cannot set a TTL, so this slice adds an optional ttl_s to that route (session kind only, 30 to 900 seconds, otherwise 400 invalid_ttl) forwarded to the existing AcquireGrantRequest.ttl_seconds (field 13); the broker proto is unchanged.
- P2 decision: the parent is revoked from revoke_derived_run_grant, which every terminal point and the capacity and liveness refusals already reach, rather than from the gateway relay, because the gateway sees a run's end only when it is polled; the gateway's existing revoke of the parent on every non-success start answer and on an idempotent replay stays, and each revoke cascades to the derived grant.
- P2 risk: the parent is now an ordinary session grant, so the org site policy (applySitePolicy, Enforce mode) applies at issuance, a dropped host makes the derive refuse widening, and any issuance failure reaches the SPA as 502 browser_grant_unavailable because issue_parent_grant maps every error to that code (UNVERIFIED: the Enforce narrowing rules were read from broker comments only).
- P2 risk: UNVERIFIED execution-core is assumed to validate the browser grant during a step with the bearer captured at ExecuteStep start (not read); if it re-validates after the bearer expires, runs past the bearer's life already fail, which makes the first bullet more visible.
- P2 test-gap: nothing was compiled or run; the cascade that the derived revoke relies on (revokeSubtree in postgres.go, RevokeScoped in grant.go for the in-memory store) was read, not executed, and the owed tests are in the unit file.
- P3 risk: in a rolling deploy with a new gateway and an old model-gateway, the old route ignores ttl_s (it has no deny_unknown_fields), so the parent gets the broker default lifetime and no run-end revoke until both sides are new; the gateway's start-failure revokes still work.
- P3 decision: the parent lives the full ten minutes (RUNTIME_MAX_S) whatever the run's max_runtime_s, as the brief fixed; a per-run lifetime (max_runtime_s plus 60, capped at 600, the derived grant's formula) would shorten the window for short runs and is a follow-up.
- P3 gap: a request future dropped between issuance and model-gateway's answer, or a panic in the dispatch task, skips the revoke, which leaves the parent to its TTL.
