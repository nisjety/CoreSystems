- P0 deviation: DEVIATION: WS04-S4's PublishSpaceMembershipEvent published to "aqencia.controlplane.space.membership_changed", a legacy prefix that user-core-shared may not publish to (control-shared-nats.conf allows only controlplane.space.membership_changed) and that Session Core does not subscribe to, so every S4 event was dropped; S10 fixed the subject to controlplane.space.membership_changed in shared_publisher.go.
- P1 risk: the inline handler publish (fire and forget) and the outbox worker both publish each event when the sweeper is on; the payload states the current fact so the duplicate is a no-op, but the inline one carries no Nats-Msg-Id and is not deduplicated at the broker.
- P1 risk: the claim reads the current membership fact at claim time, not publish time; a change landing in between is corrected by the next change event or the 10-minute re-announce, not instantly.
- P1 gap: the Session Core consumer is still a plain subscribe (no JetStream durable consumer, needs audit-core provisioner work), so a consumer outage still loses events; only the 10-minute/24h re-announce heals it.
- P2 gap: space_membership_events has no worker health metric (pending count, oldest pending age, last_error); add to the GDPR-style delivery health view.
- P2 risk: the re-announce sweep republishes every user membership updated in 24 h (up to 5000 rows per sweep, 10 pages of 500); a large org-room sync could exceed the cap and the tail waits for the next sweep.
- P2 risk: all replicas run the sweep; Nats-Msg-Id is stable per 10-minute bucket so the broker dedups within its duplicate window, but a leader lock would be cleaner.
- P2 follow-up: agent (service subject) ledger rows are never published (Session Core revocations are user-scoped); WS17 cascade may need them.
- P3 follow-up: the "reannounce" action and the lease/backoff constants are not configurable by env.
