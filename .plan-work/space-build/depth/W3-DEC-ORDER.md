- P1 decision: The ordering key is Control's `space_seq`, the Space authority revision, which Control bumps under the Space revision row lock in the same transaction as each user-row membership write and ledger row (`commitChange`, the ReplaceMemberships path). The outbox, the inline publish and the re-announce all state it, so no Control change was made; the global ledger `seq` is not in the payload, `event_id` is random and `_published_at` is publish time.
- P1 decision: The stored ordering lives in a new table, `space_membership_fact_order` (migration 0132), not a column on `space_membership_revocations`, because re-activation deletes that revocation row and the ordering must outlive it. It is keyed (space_ref, subject_id) like the revocation projection, with org_id as data.
- P1 bug: The stale `active=true` clear (RETRACT depth P2, pre-existing) is fixed: the membership consumer applies a fact only when its `space_seq` is newer than the stored one, clearing and setting alike, in one transaction with the stored value.
- P1 deviation: The retraction consumer skips only a fact strictly older than the stored value, so an equal fact still retracts. The membership consumer may have applied the same fact first, and a skip on equal would lose the retraction and the re-announce retry for a demotion. A removal records its `space_seq` after its revocation commits; a demotion records nothing, because it changes no revocation.
- P1 risk: A removal or demotion whose retraction would run after a newer fact for the subject has been applied is skipped, so the copies it targeted stay when the member is re-added before the retraction runs. The alternative, always retracting removals, over-retracts copies shared after the re-add (fails closed). This follows the brief's "skip stale facts"; the lead should confirm the trade-off.
- P2 risk: The two consumers run on separate subscriptions, so the retraction consumer can act on a removal before the membership consumer has seen a newer re-add. The copies are then retracted (fails closed, the owner re-shares), as before this slice.
- P2 risk: Declassify's revocation check (`LOCK_MEMBER_SQL` in `space/memory_declassify.rs`, outside this lock group) is not serialised with the membership consumer's revocation write, which takes the ordering lock only. A share committed before the revocation is removed by the retraction that runs after it under the declassify lock, and a share started after it is refused; a share racing the revocation is closed only by that retraction. The lead should confirm this is acceptable.
- P2 UNVERIFIED: Nothing was compiled or run. Unverified: `query_scalar` inference to `Option<i64>` through `?` on `fetch_optional(&mut **tx)`; `Option::is_some_and`; tracing's bare-identifier field `space_seq`; the retraction holding one pool connection while `retract_removed_subject` takes a second (main pool max 20); the `hashtextextended` lock key.
- P2 UNVERIFIED: Assumed and checked only by reading the user-core writers (every `space_memberships` INSERT, UPDATE and DELETE and the ledger writers): every user-row change bumps `authority_revision` in its own transaction, and `space_ref` is never reused (a recreated Space would restart at revision 0 and be ignored until its revision passed the stored value). Not grepped across the other services.
- P2 risk: A fact without `space_seq` is applied unordered, as before; none is live, since `PublishSpaceMembershipChanged` has no callers. A non-integer `space_seq` fails decode and the fact is dropped, as any malformed fact is today. The table starts empty at deploy, so a subject's first fact applies with no stored value; a stale `active=true` for a subject removed before deploy can clear once until the next re-announce (at most 10 minutes).
- P3 gap: The re-announce's `space_seq` is the Space's current revision, not the subject's last change, so the stored value can run ahead of the subject's own last change. This is correct (the snapshot already holds every earlier change for the subject), but an older fact for that subject is then skipped as superseded.
