### F-t2-018 · Make scrape, crawl and batch schedules actually execute (Temporal schedules)
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-control, quarry-orchestrator, quarry-edge); Frontend gateway trims its UI | W2 | Medium |

**What to build.** Persist the full schedule definition (name, config such as url/urls, max_pages and schema, overlap policy, timezone), map the crawl, scrape and batch target kinds to the already-registered Temporal workflows, and make trigger and backfill work. Write skipped and failed reasons as job events and send failure notices through the Application Plane. Until this ships, stop the gateway UI offering overlap, trigger and backfill controls the backend cannot honour.

**Why it matters.** Scheduled re-crawls keep tracked sources fresh, and the UI already lets users create such schedules. Today only `change_monitor` schedules run, so a user-created scrape, crawl or batch schedule either fails at creation or never fires, which erodes trust and leaves knowledge stale.

**What the references do.** Scheduling is in 2 of 4 references (Firecrawl, Apify) and is table-stakes for crawl platforms. Firecrawl's scheduler tick claims due monitors through a database RPC with a worker id, limit and 60 s lease, defers each fire by a deterministic jitter of `sha256(id) mod min(interval/2, 5 min)`, records `skipped_overlap` when the previous check is still active, marks checks stale after 60 min (10 min for search-only) and releases them, and supports IANA timezones and a plain-English phrase parser with a 5-minute minimum [SRC]. The credit check happens at run time in the runner through a credit lock, recorded as `skipped_no_credits`, not before dispatch [SRC]. Note that this scheduler drives change-tracking monitors, not generic scheduled scrape or crawl jobs, and the claim SQL is not in the open repo, so `FOR UPDATE SKIP LOCKED` is a Verevon design choice rather than an observed mechanism [SRC; INF]. Apify schedules are timezone-aware cron with per-run input overrides, a 10 s minimum and a default email when a scheduled run fails to start through misconfiguration, not on every failure [DOC]. Timezone-aware cron exists in both references [SRC; DOC]. Firecrawl monitoring is recent and partly behind a billing rollout, and requires the DB-backed deployment [SRC].

**Verevon today.** `workflowFor` maps only `change_monitor` (apps/Ingestion Plane/Quarry-v2/services/quarry-control/internal/resources/schedule_wire.go:39-51); the orchestrator skips workflowless schedules (apps/Ingestion Plane/Quarry-v2/services/quarry-orchestrator/internal/schedules/schedules.go:158-163); `MountScheduleAliases` receives a nil Temporal client so trigger and backfill return 501 (quarry-control/cmd/control/main.go:177-192). `CrawlJobWF`, `BatchJobWF` and `ScrapeJobWF` are registered (quarry-orchestrator/cmd/orchestrator/main.go:94-116) and `Manager.Trigger`/`Backfill` exist unused (schedules.go:365-398). The gap is larger than "skipped": the edge's non-preset create path forwards keys (kind, config, overlap_policy, name) that do not exist on `store.Schedule` (quarry-control/internal/store/store.go:333-355), validation requires `org_id` and `target_ref` (store/schedule_validate.go:39-55) while the create handler never reads the org parameter (resources/resources.go:113-130), so creation most likely fails with 400 [INF from reading the code, not executed]. Reuse the `ChangeMonitorWF` replay-safe `run_id` derivation (workflows.go:296-320), the orchestrator reconcile loop as the single writer of Temporal schedules, native Temporal `ScheduleSpec` overlap, jitter and `TimeZone`, and the preset create path in schedule_routes.rs that stamps org and `created_by` from the claim.

**How to build it in Verevon.** Persistence first: extend `store.Schedule` and the control schema, map kind to `target_kind` and config to `target_ref`/args in the edge, and require the org from the signed query in the control create handler. Then extend `workflowFor` for the three workflows, derive `run_id` from the workflow execution as `ChangeMonitorWF` does, and set overlap policy and `TimeZone` in schedules.go create/update. For trigger and backfill, prefer reaching the orchestrator's existing `Manager.Trigger`/`Backfill` through a pull-model request row or an internal orchestrator endpoint over a second Temporal client in quarry-control; record the choice in an ADR (architecture decision record) because the control-side interface was designed for an SDK client. The Ingestion Plane owns schedules end to end; failure notices go through Application Plane notification-core by API, and entitlement is re-checked at fire time against the Control Plane with no cross-plane DB reads ([F-t2-008](#F-t2-008)). Durable jobs are refused under ZDR (quarry-edge/src/routes.rs:563-588), so refuse schedule creation for ZDR orgs and re-check posture at fire time. Existing rows must not all start firing after the fix: require an explicit enable step. Sequence after crawl scoping so recurring crawls do not repeat off-site walks.
