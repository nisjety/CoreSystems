### F-t2-023 · Scrape-time page actions plus screenshot and PDF formats, under one bounded, grant-gated action policy
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-core, quarry-runtime, quarry-browser, quarry-edge); Frontend renders outputs | W2 | High |

**What to build.** Two deliverables. Formats: make `screenshot{fullPage, clip, quality, viewport}` and `pdf` first-class scrape formats captured on the scrape session, stored as artifacts under the claim's org, inline-only under ZDR, with tile-and-stitch only past the single-capture height limit. Actions: carry a validated, capped `Vec<Action>` on the scrape request and run it on the same page before extraction, returning per-action outputs in order, with Firecrawl-style caps (about 50 actions, 60 s total wait). Evaluate inside actions follows the [F-t2-002](#F-t2-002) policy.

**Why it matters.** Declarative actions and screenshot or PDF output are table-stakes for scrape APIs, and the runtime pieces already exist in Quarry on the agent path, but scrape cannot reach them: the screenshot and pdf formats are always `None` [SRC]. Agents and users need a page after consent dismissal, a scroll or a click, and a visual artifact for review.

**What the references do.** Scrape-time actions are in 2 of 4 references (Firecrawl, Apify); screenshot capture is in 3 of 4 (Firecrawl, Codex, Aside), and Apify likely offers it too [INF, not re-checked]. Firecrawl's request schema allows nine action types (wait, click, write, press, scroll, screenshot, scrape, executeJavascript, pdf) with `MAX_ACTIONS=50`, a 60 s total wait, screenshot quality 1-100 and a 7680x4320 viewport cap; outputs are grouped into per-type arrays (`screenshots`, `scrapes`, `javascriptReturns`, `pdfs`), not one ordered list, so an ordered per-action result is a Verevon improvement [SRC; INF]. Execution happens only in the closed hosted fire-engine; the open-source Playwright engine declares `actions:false`, so self-hosted Firecrawl cannot run actions [SRC]. The scrape `executeJavascript` action has no script-size cap; the 100,000-byte and 1-300 s limits belong to the separate hosted-browser `/execute` endpoint [SRC]. Codex captures JPEG at quality 80 with `captureBeyondViewport` plus clip and uses a screencast timestamp to guarantee a fresh frame for hidden pages [SRC]. Aside always scroll-stitches: it plans vertical tiles with CSS-pixel overlap, scrolls to each, waits 150 ms plus two animation frames, captures PNG with `captureBeyondViewport:false` and composes the tiles; element shots use the box model as clip and default to webp; PDF goes through `Page.printToPDF` [SRC, scratch copy of the daemon blob]. Apify's page actions are DOC-only, declarative per-Actor options rather than a general action DSL [DOC]. Firecrawl's OpenAPI spec lists eight types without pdf, so the spec has drifted [SRC].

**Verevon today.** `ScrapeRequest` has only `render.waitFor*` hints (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/routes.rs:346-373); the pipeline hard-codes `screenshot: None` and `pdf: None` (quarry-runtime/src/pipeline.rs:702-703); `signals.actions`, `screenshot` and `pdf` are planning hints only (quarry-runtime/src/driver_plan.rs:13-20). Screenshot via `capture_beyond_viewport` and PDF via `PrintToPdfParams::default()` exist on the agent path (quarry-browser/src/chromiumoxide.rs:2392-2445). `ActionRuntime` (quarry-runtime/src/action_runtime.rs:62-110) has no production caller and acquires its own session instead of the scrape session used by `BrowserDriverAdapter::do_fetch` (quarry-runtime/src/browser_driver.rs:128-240). docs/OSS_PARITY_BACKLOG.md:21-23 marks both as parity, which is overstated. Reuse `do_fetch`, the `Action` enum and `ActionScript` with `on_error` (quarry-browser/src/actions.rs:1-80; it includes Navigate and Evaluate, so both need explicit policy), `driver.screenshot`/`driver.pdf`, `put_artifact_if_allowed` (observation.rs:525-545), the unpopulated `OutputFormats.screenshot/pdf` fields (quarry-core/src/output.rs:140-147) and the tenant-bound artifact read (quarry-edge/src/resource_routes.rs:157).

**How to build it in Verevon.** Formats (M): capture inside `do_fetch` after goto and wait_for, return the bytes through the fetch response so the pipeline fills `OutputFormats.screenshot/pdf` as artifacts, with ZDR no-store, cache bypass and the clip, quality, viewport and fullPage options. The vision sidecar's tiles (quarry-runtime/src/vision.rs) are OCR preprocessing, not capture, so do not reuse them. Actions (M): carry the capped list on `RenderHints`/`FetchHints`, extend `ActionRuntime` to take an existing session, and run it in `do_fetch` on the same page so the scrape's host-pinned egress policy and cookie context are kept; a second `ActionRuntime` page would lose both. The Model proposes scrape actions and Quarry validates, caps and executes them; selectors and scripts from model output are untrusted. Evaluate stays denied until the [F-t2-002](#F-t2-002) gate exists. Cache admission must exclude requests with actions, headers or screenshot options ([F-t2-003](#F-t2-003)); the format registry is [F-t2-005](#F-t2-005). Frontend: render the artifacts in the timeline through the owner-gated gateway route and correct the stale tenant-scoping comment in browser.rs. Risks: memory on very tall pages, stitched seams on sticky or lazy content, and screenshots of authenticated pages, which must stay behind the owner gate and never persist under ZDR.
