### F-t2-008 · Enforce cost and runtime budgets in the Quarry executor, meter browser time, and clamp crawls to the remaining entitlement
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (enforcement) + Model Plane cost-core (ledger) + Control Plane (entitlements) | W2 | High |

**What to build.** Slice 1 (S): add a spend accumulator and start time to RunEntry, add the per-step cost already computed for receipts, and replace enforce_step_budget with an enforce_budget covering steps, cost and wall clock that returns a typed budget-exhausted error. Apply it only to agent-initiated runs or steps, or stop the gateway passing 12 steps and 120 s for manual sessions and use an idle TTL instead. Slice 2 (M): emit a browser-second UsageEvent on close_run, clamp crawl and batch page limits and request rate to the remaining entitlement and return the clamped value, and have cost-core carry the remaining budget in the BrowserBroker grant and reconcile once per run id.

**Why it matters.** Agents with live browsers and paid providers can run up unbounded cost. docs/WEB_AGENT_ROADMAP_EXECUTION.md:50-53 says max_cost_usd is enforced; the HTTP step path does not enforce it [SRC]. Both crawl platforms enforce in the executor, which is where Quarry must do it.

**What the references do.** Executor-side budget enforcement is 2 of 4 references (Firecrawl, Apify). Firecrawl's browser-session create runs a credit check for the full TTL (402 if short) and reserves only a concurrency slot (429); a debit-ahead exists only for keyless use. On stop it locks the session row with SELECT ... FOR UPDATE, settles the actual duration exactly once, and a periodic sweep settles sessions whose stop was missed [SRC]. Rates are plain browser versus a session that used a prompt, plus a ZDR surcharge. Its CostTracking class can throw on a limit, but no open-source caller sets one, so it is dormant [SRC; hosted enforcement INF]. At crawl submit, limit becomes min(requested, remaining credits) and only the clamped value is stored; maxConcurrency is capped to the team limit; results expire after `crawlTtlHours` (default 24) [SRC]. Apify lets an Actor call charge(event, count) within a caller-set maximum total charge and aborts the run automatically when reached; "finish the step and persist partial results" is a Verevon proposal [DOC; proposal INF]. Caveats: the Apify half is documentation only; Firecrawl sessions need the hosted Hangar service.

**Verevon today.** enforce_step_budget checks max_steps only (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes.rs:446-451, called at 2294); default_constraints (433-440) leaves cost and runtime unbounded; max_runtime_s only becomes the lease ttl_s (1446). Cost and runtime logic exists in the library AgentLoop (quarry-runtime/src/agent_loop.rs:154-163), which has no HTTP caller. Per-step cost_usd is computed for receipts (agent_routes.rs:2346-2362) but never accumulated; usage.rs has no browser metric. Crawls are bounded only by max_pages, where absent means unlimited (quarry-orchestrator/internal/workflows/workflows.go:456), plus a 30-minute Temporal timeout (jobs/dispatcher.go:254). execution-core enforces steps and runtime on its own clock but never checks max_cost_usd (browser_agent.rs:320-330, 666). Reuse the receipt cost functions, AgentLoop over_budget, UsageEvent and UsageMeter, and the quarry-control credit-usage read model.

**How to build it in Verevon.** Enforcement belongs in the Quarry step admission path; cost-core owns model spend only; Control Plane owns entitlements, which quarry-control does not model as a ceiling today. The gateway creates every manual session with max_steps 12 and max_runtime_s 120 and human actions share `/step` (gateway/src/domains/browser.rs:481-488, 663-732), so naive enforcement would cap human browsing [INF]. Resolve caps as min(request, grant claim, org default) and fail closed. Under ZDR, receipts are skipped, so accumulate in memory and keep usage events content-free. Depends on [F-t2-001](#F-t2-001), [F-t2-006](#F-t2-006), [F-t2-022](#F-t2-022), [F-t2-046](#F-t2-046) and [F-t2-014](#F-t2-014). Risks: double counting between Quarry and cost-core (one ledger key per run), flat-table estimates stopping runs early (label estimated versus provider-billed), and silent clamping (always return the clamped value).
