### F-t2-020 · Harden persistent browser profiles: complete snapshots, per-org envelope encryption at rest, ordered saves, ZDR enforced inside Quarry
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-browser, quarry-runtime, quarry-edge) + Control Plane (key API) | W2 | High |

**What to build.** Two independent slices. Snapshot completeness: capture all cookies of the browser context with expiry and SameSite, local and session storage for every visited origin, and an IndexedDB export, and re-apply them on restore. Encryption and ordering: envelope-encrypt the snapshot row and the cached payload with a per-org data key obtained through a Control Plane key API (environment master key first, KMS later), add a monotonic `saved_at` upsert and deletion tombstones, extend the purge consumer to profiles, and apply the ZDR and owner checks to the `/v1/profiles` routes.

**Why it matters.** Persistent profiles hold live session cookies for users' signed-in sites. Today snapshots miss most of the state and are stored as plaintext, so restores fail silently and a database read exposes credentials [SRC]. Encryption is specified in Quarry's own contract (apps/Ingestion Plane/Quarry-v2/docs/CONTRACTS.md:185-199) but not implemented [DOC].

**What the references do.** Some form of persistent browser state exists in 3 of 4 references (Firecrawl through Hangar, Codex, and Aside [INF]), with only a weak analogue in Apify, but no reference encrypts browser profiles per org: Firecrawl keeps only a profile listing while the profile contents live in the closed, hosted Hangar service, and no encryption code exists in its repo [SRC]; Codex keeps browser storage in persistent `persist:codex-browser-*` partitions with a storage id and a profile importer [SRC]; Aside is a full Chromium browser with profiles [INF]; Apify's SessionPool pins cookies to a proxy session, which is only a weak analogue of a named profile [DOC]. The reusable mechanism is Firecrawl's save ordering: a save is ignored unless its `savedAt` is newer than a deletion tombstone, `saved_at` is set to the greater of the stored and new values, and delete removes rows saved at or before the tombstone; the tombstone is a key-value entry keyed by team hash and name, not a column [SRC]. Firecrawl rejects profiles under lockdown and ZDR and answers 409 while a session is still saving [SRC]. Firecrawl seeds caller cookies through Playwright `context.addCookies` with a "last two host labels" domain heuristic, which is wrong for `co.uk`-style suffixes; do not copy it [SRC]. The envelope-encryption pattern (random AES-256-GCM data key wrapped by a per-(user, tool) RSA key, ciphertext only in logs) is Apify's secret Actor input mechanism, not profile encryption, so it is borrowed as a security baseline, not parity [DOC]. The full snapshot specification is Verevon's own intent from CONTRACTS.md [DOC].

**Verevon today.** `capture_snapshot` (apps/Ingestion Plane/Quarry-v2/crates/quarry-browser/src/chromiumoxide.rs:1771-1832) calls `Page::get_cookies`, which in chromiumoxide 0.9.1 returns only cookies matching the tab's current URL, sets `expires` to `None`, reads storage for the current origin only and hard-codes `indexed_db` to empty. Snapshots are plaintext JSON through a last-write-wins upsert with no ordering (quarry-runtime/src/postgres_profile_store.rs:30-92), cached unencrypted in Redis (quarry-edge/src/main.rs:597-600), and `S3ProfileStore` is never constructed (quarry-runtime/src/lib.rs:166). The purge consumer handles page images only (quarry-runtime/src/page_image.rs:43-61). ZDR refusal is already enforced inside Quarry at run creation (quarry-edge/src/agent_routes.rs:527-533, 1466-1476), but the `/v1/profiles` routes check org id only, with no ZDR or owner check, and `GET` returns raw cookie values (quarry-edge/src/profile_routes.rs:102-125, 268-296). Reuse the `ProfileStore` trait as the single serialization boundary, `zdr_forbids_persistent_profile` and `Claims::zdr_floor`, the restore probe and `ProfileScope`, and the migrations directory.

**How to build it in Verevon.** In quarry-browser, use `Storage.getCookies` or `Network.getAllCookies` for the whole context, iterate visited origins for DOMStorage, add IndexedDB through the CDP (Chrome DevTools Protocol) domain, and restore emulation overrides with the hooks from [F-t2-007](#F-t2-007). In quarry-runtime, add the encryption layer below the Redis cache so the cache holds ciphertext, with envelope `{enc_v, key_id, nonce, aad = org|profile|snapshot, ciphertext}`, lazy re-encryption on next save plus a one-off backfill. Keys come from a Control Plane key API; Quarry never reads Control Plane tables, and erasure is crypto-shredding driven by a Control Plane erasure event. Skip the S3 store in the first slice since production already requires Postgres. The store has no owner column, so owner and Space isolation stay enforced above it and a Space must never widen a profile's owner ACL; do not widen the routes' audience before an owner check exists. Decide whether `GET /v1/profiles/:id` should ever return raw cookie values. The Model Plane must never see cookie values. Main risks: master-key loss destroys all profiles; nonce handling in a new Rust AES-GCM implementation needs review; stale restores can look like hijacks to the origin. Profile pinning for scrape is [F-t2-058](#F-t2-058).
