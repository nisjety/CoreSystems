### F-t2-017 · Public async job lifecycle: status, paginated results, per-URL errors, cancel/pause/resume, origin and live tail
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-edge, quarry-control, quarry-orchestrator) + Frontend gateway | W2 | High |

**What to build.** Add authenticated, org-checked routes on the Quarry edge for crawl and batch jobs: `GET /v1/crawl/:id` (status, completed/total, warnings, expiry), `GET /v1/crawl/:id/errors` (per-URL failures including robots-blocked URLs), `GET /v1/crawl/ongoing`, `DELETE /v1/crawl/:id` and `POST /v1/crawl/:id/pause|resume`, with `/v1/batch` aliases. Turn `GET /v1/jobs/:id/events` into a live tail that sends a catch-up snapshot first and honours `Last-Event-ID`. Record a run origin (user, agent, schedule, webhook, api) on the job record and surface the controls in the crawl UI and as proposable Model Plane actions. Treat cursor-paged result data as a separate sub-item.

**Why it matters.** A user or agent who starts a crawl of up to 5000 pages has no way to stop, pause or inspect it from the product. Agents need one poll call and a cancel to honour budgets, and the audit model needs to know who started a run. Status and cancel are also the dependency for webhooks, waiters and monitors.

**What the references do.** Job status and cancel exist in 2 of 4 references (Firecrawl, Apify); a live stream with catch-up exists in 1 of 4 (Firecrawl). Firecrawl's `GET /crawl/:jobId` returns status, counts, credits, `expiresAt` and a page of documents that ends at 100 documents or 10 MiB, with a `next` cursor that advances by what was actually returned; `/errors` returns `[{id, timestamp, url, code, error, requiresAction}]` plus `robotsBlocked[]`; `DELETE` marks the crawl cancelled, cancels the queue group and answers 409 when already complete; results expire by a per-team TTL (time to live), 24 h by default [SRC]. Its WebSocket sends a `catchup` status message, then each finished document, then `done`, but it has no resume cursor, polls once a second server-side and there is no SSE (server-sent events) route in the source [SRC]. Apify runs have a persisted status, a graceful abort with a 30 s grace period, resurrection of a finished run with the same storage ids and a recorded `meta.origin`, but no pause [DOC]. Pause and resume are not a reference capability: Firecrawl has them only for monitors, not crawls, so they come from Quarry's own Temporal signals [SRC]. `Last-Event-ID` resume over an event history is a Verevon recommendation, not a reference mechanism [INF]. The step timeline idea comes from Firecrawl's legacy multi-page extract, not from crawl jobs [SRC, medium confidence].

**Verevon today.** The edge exposes only `POST /v1/crawl` and `/v1/batch` (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/routes.rs:133-134), a generic jobs list and an events route that drains once and ends with a done frame (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/resource_routes.rs:1057-1127). Pause, resume, cancel and state queries exist only in `CrawlJobWF` (apps/Ingestion Plane/Quarry-v2/services/quarry-orchestrator/internal/workflows/signals.go:87-146); `BatchJobWF` has no handlers (workflows.go:359-383), and nothing sends the signals: quarry-control's Temporal client is a `NoopClient` (apps/Ingestion Plane/Quarry-v2/services/quarry-control/internal/temporal/client.go:91-130) and only the orchestrator dials Temporal (cmd/orchestrator/main.go:66), starting workflows as `quarry-job-<jobID>` (internal/jobs/dispatcher.go:246). The gateway proxies start, discover, list and events only (apps/Frontend Plane/verevonv3/apps/gateway/src/domains/knowledge.rs:179-196). Reuse the control `GET`/`PUT /v1/jobs/{id}` record (resources.go:24-31, 486-530), the `page_failed`/`page_blocked` events (workflows.go:174-202), the gateway `crawl_run_events` proxy that already forwards `Last-Event-ID` (knowledge/quarry.rs:1098-1120) and the `ingestions.*` action registry (src/shared/actions/action-registry.ts:1320, 2563-2590).

**How to build it in Verevon.** Do not wire a Temporal client into quarry-control. Follow the repo's reconciler pattern: the edge writes a desired state (cancel, pause, resume) to the control job record via the existing `PUT`, and the orchestrator `jobs.Manager`, which already holds the client and the deterministic workflow id, sends the signal. Add control-signal handlers to `BatchJobWF` or document batch as non-cancellable. Build `/errors` from existing `page_failed` and `page_blocked` events, and implement the live tail in the edge handler by polling control with `after_seq`, with a per-org cap on open streams. Every route needs an org check from verified claims; the Model may propose cancel or pause as registry actions but Quarry executes. Crawl and batch are refused under Zero-Data-Retention (ZDR) today, so no ZDR content handling is needed now; any future ZDR crawl must be status-only. Surface the fixed 30-minute `WorkflowExecutionTimeout` (dispatcher.go:254) as a typed terminal state. Result pagination needs a data-source decision first: crawl output is not stored per job today (events carry excerpts; pages go to artifacts or the Data Plane when ingest is on). Cancel must be idempotent against finished workflows and must not leave a half-written ingest. Shares the signal path with [F-t2-018](#F-t2-018).
