### F-t2-001 · Production BrowserBroker grants and delegated bearer forwarding (unblocks every browser path)
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Model Plane (BrowserBroker) + Frontend Plane gateway; Quarry validates only | W1 | High |

**What to build.** Give the Model Plane BrowserBroker a durable (Postgres) grant store and an issuance path the Frontend gateway can reach. The gateway obtains a user-session grant when it creates a browser session, sends `grant_id` on `POST /v1/agent/runs`, forwards `x-browser-authorization`, and derives a narrower run grant for AI runs instead of the interim `session:{id}` string. Add one prod-mode contract test across gateway, model-gateway, execution-core and quarry-edge that fails on 401 or 403.

**Why it matters.** Prod-mode Quarry requires a broker grant on every run and step and refuses to boot without a validator, yet nothing in production issues a grant and the broker store is in memory [SRC]. Until this lands, the in-app browser, the AI step loop, co-browsing, the credential bridge, grant-carried budgets and per-origin consent cannot work in production [INF from the code paths below; not runtime-tested]. It is the highest-leverage item in the audit.

**What the references do.** No reference implements a durable, org-scoped grant issuer; it is a Verevon design requirement, not a parity feature [INF]. The closest mechanisms are single-user, local-device trust checks. Aside's browser-control endpoint refuses unauthenticated clients: a client fetches a challenge, signs it with an installation key and receives a short-lived session token, and commands travel over a bridge routed per account, profile and mode that rejects stale connections [SRC, from a scratch copy of the daemon blob]. Codex runs a signed, nonce-bound per-turn browser-access check tied to a "Work settings" toggle [SRC; enterprise gating INF from an error string]. Codex also hardens every guest attach in its Electron main process, forcing partition, session and preload and deleting dangerous flags; that is 1 of 4 references (Codex) and Electron-specific, so it says nothing about Aside [SRC]. Firecrawl's hosted sessions take `ttl` and `activityTtl`, enforced by the external, closed Hangar service; Firecrawl's own 15 s reconciler settles billing and is not a reaper [SRC; enforcement INF].

**Verevon today.** The broker implements AcquireGrant, ValidateGrant and RevokeGrant with org and owner scoping, a host list of at most 32, a 15-minute TTL and sensitive child grants, but the store is in memory (apps/Model Plane/go/services/browser-broker/internal/grant/grant.go:61-71) and no production code calls AcquireGrant. create_session posts to Quarry with no grant_id (apps/Frontend Plane/verevonv3/apps/gateway/src/domains/browser.rs:483-506), which prod Quarry rejects with 403 (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes.rs:1377-1412), and start_ai_run sends `session:{id}` (browser.rs:1235) without the browser bearer that model-gateway's VerifiedBrowserBearer extractor requires (apps/Model Plane/rust/services/model-gateway/src/auth.rs:427-437). Reuse the grant package, browser.proto, resolve_browser_grant, the declared BrowserBroker audience (audience_tokens.rs:27-42) and Quarry's GrpcGrantValidator.

**How to build it in Verevon.** Slice it: issuance, gateway wiring and the contract test on the in-memory store first, then Postgres. Prefer a model-gateway HTTP endpoint wrapping AcquireGrant over teaching the gateway gRPC. Only `x-browser-authorization` is missing from the bearer set; add it to proxy_model_json_with_delegations (chat/shared.rs:629-690). Both create_session and start_ai_run need the grant; deriving a run grant from a session grant is a new broker API. The Model Plane owns issuance and the gateway must never mint authority; domains come from the broker, never the client; ZDR grants are never persisted; a Space must never widen a grant. The 15-minute TTL caps session length until [F-t2-011](#F-t2-011) adds renewal. Risks: scope creep, restart semantics for in-flight sessions, and user-session issuance bypassing the cross-domain approval gate.
