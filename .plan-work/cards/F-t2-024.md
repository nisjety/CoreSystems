### F-t2-024 · Credential handoff where the model never sees secrets: executor-side fill_secret and email OTP via integration-corev2
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Absent | L | Ingestion Plane (Quarry executor + integration-corev2) + Model Plane (approval) | W3 | Medium |

**What to build.** OTP (one-time password) first: a `fill_otp` sensitive action beside `upload_ref` and `download_ref`, issued as a single-use child of the run grant bound to one origin and frame after user approval, plus an executor-only integration-corev2 (IC) `mail.otp.read` action that returns only the code. Quarry re-checks origin and field type, fills the value in the page, masks the field in observations and stores only a boolean in receipts. Password and vault-secret references (`secret://` handles) follow later, behind a secret-custody ADR.

**Why it matters.** Aside and the hosted Codex Cloud Browser (not the shipped desktop in-app browser) keep secrets out of the model. Verevon's only fallback today is human takeover into a scoped profile, which works for attended runs but blocks unattended agents and routines. Keeping the model blind to the value is what makes autonomous sign-in acceptable under prompt-injection risk.

**What the references do.** Secret handoff is in 2 of 4 references (Aside, Codex) and is a differentiator; Codex's variant is cloud-only. Codex's `browserAuth` flow lets the model request a handoff on a tab; the runtime proceeds only when the origin is https, the frame origin equals the top origin, exactly one required non-password input is present, there are no options or QR, the credential-observation gate is on and the conversation id is bound, otherwise it answers `unavailable` [SRC]. It then raises an elicitation of kind `browser_email_otp` that a guardian cannot auto-approve, stating the model cannot see the code and the user may type it instead; on approval the value is delivered natively and the model receives only a status, and AX, DOM and screenshot reads of that document are denied until navigation [SRC]. That the host fetches the code from a mail connector is inferred from the elicitation text, not observed [INF]. This flow is wired only to the hosted Codex Cloud Browser through a broker socket; the shipped desktop in-app browser does not advertise the capability, and the socket env is forwarded only in Dev builds [SRC]. Aside fills passwords from opaque password-manager references without a UI form, returning generated-password plaintext only to its trusted agent-manager extension, never to the model [SRC]. Firecrawl and Apify have no equivalent in this record set.

**Verevon today.** `AgentAction` (apps/Ingestion Plane/Quarry-v2/crates/quarry-core/src/contracts.rs:636-700) has only plaintext `Type`, `TypeRef`, `FrameTypeRef` and `TypeSemantic`; typed text is persisted verbatim for non-ZDR runs (quarry-runtime/src/step_receipts.rs:185-200; quarry-edge/src/agent_routes.rs:2346-2362). No secret store with opaque references is reachable from Quarry: IC's vault is AES-GCM at-rest encryption for provider tokens (apps/Ingestion Plane/integration-corev2/internal/crypto/vault.go:1-40), `/internal/connectors/token` leases raw provider tokens to an allow-list that excludes quarry (internal/api/server.go:1315-1345; internal/config/config.go:335-350), IC has mail read operations but no OTP action (internal/actions/mail_read.go:100-175), and BrowserBroker sensitive approvals cover only `respond_dialog`, `upload_ref` and `download_ref` (apps/Model Plane/go/services/browser-broker/internal/grant/grant.go:20-130). Reuse Quarry's sensitive-approval machinery (agent_routes.rs:196-312), `CreateScopedSensitiveApproval` (grant.go:96-130), the `RiskCategory::Login` HITL (human-in-the-loop) gate (execution-core/src/browser_agent/browser_risk.rs:25-45), the orchestration approvals surface (gateway/src/domains/browser.rs:1190-1210) and IC's Gmail and Microsoft mail read capabilities (internal/providers/catalog.go:254, 431). The fill_secret plan exists only in a document (QUARRY_V2_BROWSER_AUTOMATION_IMPROVEMENTS_2026_OWNERSHIP_RECONCILED.md:1106-1127) [DOC].

**How to build it in Verevon.** Add the `fill_otp` variant to the existing sensitive-approval path and reuse the Login risk gate and orchestration approvals for the approval card, naming origin and connection and offering "I will type it myself", instead of a new elicitation channel. Add the IC `mail.otp.read` action with sender, age and pattern filters, audited through the existing outbox, kept off every Model-callable tool surface; give Quarry a distinct identity or manifest row toward IC, since IC internal auth is one shared API key (server.go:170-173), and do not add quarry to `INTEGRATION_TOKEN_LEASE_CONSUMERS`. The Ingestion Plane owns execution and secret resolution; the Model only sees opaque references and proposes, Quarry executes. Secrets are scoped to user or org and never widened by Space access. ZDR forbids persisting values or frames that show credentials, and non-ZDR receipts store typed text today, so [F-t2-021](#F-t2-021) redaction must land first; trusted input is [F-t2-015](#F-t2-015), takeover is [F-t2-013](#F-t2-013), and production grant issuance is [F-t2-001](#F-t2-001). Defer password references until the custody ADR and those items are in place; the full scope would be XL. Main risks: exfiltration through a phishing page or injected iframe, an OTP requested by a page the agent was lured to, and accidental logging; mitigate with https-only, top-origin equality, single-use approval that shows the origin, and receipts that carry a boolean only.
