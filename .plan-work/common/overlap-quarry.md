## B. Interfaces each side needs from the other

**#1 Grants (the keystone).**
- *Model -> Quarry:* `ValidateGrantResponse` v2 fields (kind `run|human_browse|origin_ext`, `action_classes`, `read_only`, `budget{max_cost_usd,max_runtime_s}`, `policy_revision`, `session_key`/parent) added to `browser.proto` **and the vendored copy** (identical today); executor must treat unknown kind as deny. `AcquireGrant` today fixes owner = caller, so user-issued grants need the user's `aud=browser-broker` bearer; unattended runs have no such bearer (T2 ADR9, T3 ADR5: draft-only), so they stay out of scope.
- *Quarry -> Model:* a Quarry service identity to the broker (registry row `quarry-edge -> browser-broker` scope `browser:read`, manifest row, drop the dev-bypass-only bearer attach) so `ValidateGrant` works for both user-token and service-token callers (service principals see any owner in org).
- *Issuance path:* model-gateway HTTP endpoint wrapping `AcquireGrant`, called by the gateway with the forwarded `x-browser-authorization` (add it to `proxy_model_json_with_delegations`); response carries `grant_id`; gateway never constructs grant fields. Same bearer must reach `RunAgent` for Do mode (execution-core re-validates it).
- *Contract test:* one prod-mode test gateway -> model-gateway -> execution-core -> quarry-edge failing on 401/403, fixtures from Quarry.

**#2/#3 Agent path.** execution-core -> Quarry: `/v1/agent/runs` {`grant_id`, constraints, profile, `zdr`}, `/step` one `AgentAction`; Quarry returns typed denials (`browser_action_denied`, `USER_TOOK_OVER`, budget-exhausted) with `decision_source`; `driver_capabilities` forwarded to the model. Quarry -> Model: `ChallengeSignal`/block taxonomy as an event the Model turns into `human_assist`. Gateway projection: owner-gated frame/control/receipt routes (`owned_orchestration_run`, per T2 L519, not re-opened).

**#4 Takeover.** Quarry stamps `control_epoch` + initiator on receipts/events; Model Plane run reads epoch on `USER_TOOK_OVER` and pauses (not aborts, `gate_risky_action` aborts today per T2 L825).

**#5 Events.** Envelope owner adds `producer_seq`, `origin`, `agent` (fields 14-20 are reserved, `events.proto:55`); Quarry publishes `browser.session`, `step.receipt`, `egress.decision`, `artifact` on NATS (persisted unless ZDR); `x-request-id` is correlation only.

**#6 Policy.** org-core `GET` (fail-closed, revisioned) read by broker at issue (embeds resolved tighten-only fields in grant), by execution-core/model-gateway for loops (sends `policy_revision`), and by Quarry for scrape/search by service token. User-token callers: signed claim optional. Needs one Control registry grant per reader (quarry-edge has none to org-core today).

**#7 Credentials.** `fill_otp` single-use child grant (origin+frame bound) from broker; IC `mail.otp.read` with its own identity (IC internal auth is one shared key; do not add quarry to the token-lease consumers); Quarry masks field, receipt stores a boolean; Model sees status only.

**#9 Invoke grant.** Registry row `quarry-edge -> model-gateway` (`model:invoke` family), flip `granted` in the manifest together; `ModelPlaneInvokeRequest` adds `structured_output_schema` + `zdr`; org-bound, metered; ZDR from body flag (service-token zdr claim is ignored by design, `auth.rs:105-123`).

**#10 ZDR.** Quarry matrix emits `zdr_feature_not_supported` + feature from the Model catalogue (copied under a conformance test, not a shared crate); SPA text then works unchanged.

## C. Contradictions between the documents

1. **Who mints grants.** T3 F-t3-008 (L458) "the gateway mints" vs T2 F-t2-001 (L331) "the gateway must never mint authority", prefer a model-gateway endpoint. T3's own how-to (L466) agrees with T2; fix T3 wording.
2. **Grant store.** T2: Postgres (F-t2-001 L323). Model Plane docs: Redis target (`apps/Model Plane/docs/ARCHITECTURE.md:36`). Neither audit mentions the other.
3. **Policy delivery.** T2 F-t2-022: signed claims + grant fields; T3 F-t3-055 (L1084): service endpoint + policy revision, "not a bearer claim"; T3 F-t3-032: Control-signed registry.
4. **Where per-site decisions persist.** T2 F-t2-032: Control user settings; T2 F-t2-033: capability-core rules, "not BrowserBroker"; T3 F-t3-008: per-user site table; T3 F-t3-006: session scope until confirmed in settings.
5. **Secret custody.** T3 F-t3-043 names a Control secret store; T3 F-t3-057 and T3 ADR8 put keys in integration-corev2; T2 ADR2 leaves both open.
6. **`@` trigger.** T2 F-t2-028 `@tab`; T3 F-t3-010 `@connector`; T3 F-t3-052 says use a trigger other than `@` (reserved for Space agents, `DashboardComposer.tsx:3870-3885`).
7. **Run origin.** T2 F-t2-014 adds an origin enum; T3 F-t3-064 "origin in run metadata, do not widen the six-value CHECK"; T3 F-t3-018 adds a run-level tag.
8. **Reviewer-model screening.** T2 F-t2-049 layer 2 (reviewer model before fetch) vs T3 ADR9/F-t3-097 (no LLM on the permission path, tighten-only after ADR).
9. **Takeover authority.** T2 F-t2-013 (Quarry does not enforce) vs T3 F-t3-026 L736 (Quarry control-mode "already covers" it). Code confirms T2.
10. **Quarry-to-broker auth.** Both audits assume validation works once grants exist; code says Quarry cannot authenticate in prod (section 0).
11. **Wave mismatch for one piece.** F-t2-001 W1 vs F-t3-008 W2; F-t2-013-ph2 W2 vs F-t3-026 W3; F-t2-022 W2 vs F-t3-055 W3; F-t2-014 W2 vs F-t3-050 W4.
