### E4.1 Result sets and saved job definitions

- **Audit items:** F-t2-052 (result sets, export), F-t2-053 (saved jobs; packs).
- **Owner:** Ingestion Plane (quarry-edge Rust for routes, quarry-control Go for sources/schedules); Frontend Plane for the Ingestions page and gateway proxy.
- **Effort:** F-t2-052 M (about 11 engineer-days); F-t2-053 shrinks from L to M (about 6 days) because its phase 1a is WS15 S2. Epic about 17 days.
- **Hard dependencies:** WS15 (control `jobCols` refactor and `ForJobTypes` event read, D14b L1; schedule execution S2); WS5 Epic E1 (scrape options embedded in crawl/batch) plus WS16 for a true dataset. ADR 4 (ZDR per durable resource) for retention wording. Soft: WS7 (`RunPolicy` becomes `JobPolicy`), WS14, WS4 (shared ZDR refusal call site).
- **Gating and park:** build. Decide D14b D9 first (results are an index, not content). Park the QuarryPack manifest and schema-driven forms; there is no second consumer.
- **Scope.** (1) Add `run_id` to `ArtifactSummary` (`Q/crates/quarry-core/src/resources.rs:83-97` [C]; keys already carry org/run/page_hash/kind/id) and a `run_id` filter on `list_artifacts` (`Q/crates/quarry-edge/src/resource_routes.rs` [C], route `routes.rs:178` [M]). (2) Add `GET /v1/runs/{id}/items` (alias under `/v1/jobs`) in a new `Q/crates/quarry-edge/src/run_items_routes.rs` [NEW], reading `page_extracted` events through WS15's `jobResults` store method (`QCT:internal/resources/jobs_lifecycle.go` [NEW], `ForJobTypes(['page_extracted'], after_seq, 100)`), joined to artifact refs, with streamed `csv` and `jsonl`, field projection and D14b's 100-item / 10 MiB cap. Rows are `PageExtraction` today (`quarry-core/src/output.rs:81-104` [C]); they gain a `json` column once crawl embeds the `json` format. (3) Gateway proxy in `FE/apps/gateway/src/domains/ingestions/runs.rs` [C] and an action contract in `FE/src/shared/actions/action-registry.ts` [C] first, then a table view with an explicit "Ingest selected" action in `FE/src/features/ingestions/components/VerevonIngestionsPage.tsx` [C]. (4) For saved jobs, a saved definition is a `Source` (`resources.rs:27-43` [C], `config` is free-form JSONB) whose `config` becomes a typed, versioned options object validated by the D5/D14a request validators; schedules point at it through `target_ref`. (5) `GET /v1/presets` is mounted only on control (`Q/services/quarry-control/cmd/control/main.go:174` [C]); do not proxy it until D7's `JobPolicy` and the `robots.max_mode` ceiling enforce it, because the `fast` preset sets `RobotsIgnore` (`QCT:internal/resources/presets.go:60-75` [C]); otherwise delete the Go presets and rename the overloaded word to "saved job".
- **First slice:** `run_id` on `ArtifactSummary` plus the filter (S, 2 days, independent). Items route flag-off after WS15 L1.
- **Main risks:** a page index mistaken for a dataset (carry `kind: page_index|dataset`); result retention (follow control `QUARRY_RETENTION_DAYS`); artifact reads are org-bound, not actor-bound; `/v1/artifacts` list is closed to service principals (`auth.rs:504-545` [C]), so Model Plane reads go through the gateway; hotspots `routes.rs` [M], `KnowledgeComposer.tsx` [M].
- **ZDR and ownership:** crawl and batch are refused under ZDR (`routes.rs:559-588` [M]) so no ZDR result set exists, and pre-ZDR jobs refuse content-bearing reads; Ingestion keeps a retained working set, the Data Plane is touched only by the existing `ingest=true` contract.
- **Evidence:** the verified items route design in `designs/D14b-job-lifecycle-schedules.md` section D9; `PageExtraction` has no structured fields (`output.rs:81-104`).
- **Recommendation:** build.

### E4.2 Procedure store and run-as-procedure

- **Audit items:** F-t2-051.
- **Owner:** Ingestion Plane (postconditions, canonicalisation: quarry-runtime, quarry-core, quarry-edge) and Model Plane (store: capability-core; runner: execution-core); Frontend Plane via WS9 slice 4c.
- **Effort:** XL stands (about 30 engineer-days: postconditions 6, canonicalisation 6, store and runner 18).
- **Hard dependencies:** WS1 (replay needs a run grant), WS6 (budgets re-applied per replay), WS11 (the runner is a planner mode), WS3 S10 (trusted input so outcomes can verify), WS12 (typed text redaction). ADR 6 (stored actions are declarative, which fits "Quarry validates every call") and ADR 3 adjacent (a human-recorded session). Needs a ledger entry for the store owner.
- **Gating and park:** build staged after the ledger entry; postconditions can start earlier because they are Quarry-only.
- **Scope.** Keep the shipped compiler: `compile_procedure`, `compare_replay`, `assess_quality`, `analyze_impact` (`Q/crates/quarry-runtime/src/browser_procedure.rs:61, 114, 153, 188` [C]) behind `POST /v1/agent/runs/{id}/procedure` (`compile_run_procedure`, `Q/crates/quarry-edge/src/agent_routes.rs` near 2466 [C]) and three stateless checks (router near 3688 [C]). Version is hard-coded to 1 and the compiler rejects any receipt not `Verified` (`browser_procedure.rs:85-96`). Step 1, postconditions: `outcome_for_action` (`Q/crates/quarry-runtime/src/observation.rs:217-266` [C]) returns `Unknown("postcondition_required")` for click, type, press, scroll, select, evaluate, back and forward, so a form-driving run cannot compile. Add an optional step-level `expect` (URL pattern, element present or absent by ref, text in a region) on the action request in `Q/crates/quarry-core/src/contracts.rs` [C]; the Model proposes it and Quarry evaluates it. Step 2, canonicalisation: ref actions carry `snapshot_id`, `generation` and `ref_id` (`contracts.rs:650-654` [C]); map them at compile time to the existing `ClickSemantic`/`TypeSemantic` locators or an `ElementFingerprint`, fail closed with `TARGET_REPAIR_REQUIRED` on ambiguity, and replace typed text with a named slot bound at replay (WS12 redacts receipts to `[redacted:<kind>]`). Step 3, store and runner: a capability-core package `MP/go/services/capability-core/internal/procedures` [NEW] with a session-core migration (0048 or later, provisional; 0046 and 0047 are claimed by WS10 and WS11), immutable versioned builds with tags and the resolved version recorded per run; the runner is a deterministic planner mode in `MP/rust/services/execution-core/src/browser_agent.rs` and `quarry_agent.rs` [C] that proposes each stored step to Quarry's step endpoint under a fresh grant, runs `compare_replay` first, and hands back to the LLM planner or the user on mismatch. Naming collision: WS11's `browser_agent/procedure.rs` [NEW] and `QUARRY_BROWSER_AGENT_PROCEDURE` mean the planner prompt procedure `browse/1`; call the stored artifact a "saved recipe" in product and API, keeping `BrowserProcedure` as the wire type.
- **First slice:** `expect` postconditions behind a flag, surfaced in receipts (M), or the store-owner ledger entry.
- **Main risks:** never reuse a stored sensitive approval; procedures compiled from human receipts lose observations (D8 offers `HUMAN_RECEIPT_MODE=full` for recording only); stale recipes after a site change (`analyze_impact` quarantines); two meanings of "procedure".
- **ZDR and ownership:** ZDR runs write no receipts and cannot be saved; the store holds actions and locators only, never page text or typed secrets; rollout state lives in the Model Plane (Quarry's own doc comment says so), Quarry still executes or rejects every step.
- **Evidence:** `outcome_for_action` Unknown arms at `observation.rs:217-266`; compile route and checks exist but nothing stores output (`agent_routes.rs` router, `browser_procedure.rs`).
- **Recommendation:** build after ADR-lite (store owner), staged.
