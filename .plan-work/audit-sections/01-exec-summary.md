## 1. Executive summary

### 1.1 Goal

Verevon's web layer has two halves that must become one product: an acquisition API (scrape, crawl, batch, search, monitors, schedules) modelled on Firecrawl and Apify, and a remote, leased Chromium that users and the Model share, modelled on the Codex in-app browser and Aside. This audit reads the four references and the Verevon code at commit afb83928 to answer three questions: what every comparable product has that Verevon lacks or half has, what each reference does uniquely well and is worth adopting, and which Verevon strengths must be protected while the gaps close. The result is 77 recommendations in three tiers, five waves, and ten decisions that need an architecture decision record (ADR) before building.

### 1.2 Where Verevon stands today

The code-verified baseline holds 260 Verevon capabilities across ten categories: 142 shipped, 52 partial, 22 stub and 44 absent [SRC]. The picture is uneven. Integration-plane overlap is the strongest category (14 of 18 shipped), followed by output formats and content processing (16 of 26) and AI-browser control (22 of 38). The weakest are rendering and browser engines (9 of 24 shipped, 8 partial, 3 stub, 4 absent), orchestration and scale (8 of 20) and platform and ecosystem (10 of 19, with 5 absent). The user-facing browser shell is in the middle (19 of 34 shipped, 7 absent) [SRC].

Two readings follow. First, Verevon is ahead of every reference on search routing with Zero-Data-Retention (ZDR) gating, SSRF and egress containment, governed one-action-per-call execution, and evidence (step receipts, checkpoints, proof bundles, replay) [SRC]. Second, most of what is missing already exists as code that nothing calls: crawl scoping and robots enforcement, scrape actions, the DOCX parser, the retry helper, the secret redactor, the Temporal client and the LLM planner are all built and unwired [SRC]. After verification, 61 of the 77 recommendations are Partial, 11 Absent, 3 Stub and 2 Planned; none is already done.

### 1.3 Headline findings

1. **No browser path works in production mode.** The gateway starts sessions without a grant and sends `session:{id}` as the grant id, which production Quarry rejects with 403; BrowserBroker implements grants only on an in-memory store and no production code calls AcquireGrant (`apps/Frontend Plane/verevonv3/apps/gateway/src/domains/browser.rs:483-506`, `:1235`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes.rs:1377-1381`) [SRC]. See [F-t2-001](#F-t2-001).
2. **The gateway search cache is a confirmed cross-tenant and ZDR hole.** Its key carries no org and entries are stored without a ZDR check, while the Quarry search it fronts uses org-scoped private-corpus providers (`apps/Frontend Plane/verevonv3/apps/gateway/src/domains/search.rs:195-231`, `:285`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/search_routes.rs:495-530`) [SRC]. See [F-t2-003](#F-t2-003).
3. **Human takeover is enforced by the gateway, not by Quarry.** The Quarry step handler never reads `control_mode`, so a Model Plane run that calls Quarry directly keeps acting after the user takes over (`apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes.rs:2222-2310`) [SRC]. See [F-t2-013](#F-t2-013).
4. **Budgets are a contract, not an enforcement.** Only `max_steps` is enforced on the step path; cost and runtime are unbounded, browser time is not metered, and a crawl with `max_pages` 0 is unlimited (`agent_routes.rs:433-451`; `apps/Ingestion Plane/Quarry-v2/services/quarry-orchestrator/internal/workflows/workflows.go:456`) [SRC]. See [F-t2-008](#F-t2-008) and [F-t2-006](#F-t2-006).
5. **Crawl has no scope and no robots check.** The live crawl workflow enqueues every href after a depth check; CrawlFrontier, CrawlDenialReason and RobotsCache have no production caller (`workflows.go:385-620`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/routes.rs:817-840`) [SRC]. See [F-t2-016](#F-t2-016).
6. **The scrape contract is thin and the ZDR scrape path returns nothing.** `/v1/scrape` has no `formats[]`, no main-content controls and no unknown-field rejection; output is artifact references only, and under ZDR the pipeline writes no artifacts and returns html and markdown as None (`routes.rs:345-375`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-runtime/src/pipeline.rs:597-601`) [SRC]. See [F-t2-005](#F-t2-005).
7. **Raw script evaluation is ungated inside Quarry.** The sensitive-action gate covers only dialogs, uploads and downloads, and `evaluate` runs in the page's main world; the Model Plane side already refuses to offer it, so exposure is direct service callers (`agent_routes.rs:276-310`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-browser/src/chromiumoxide.rs:3003-3017`) [SRC]. See [F-t2-002](#F-t2-002).
8. **The shared user-plus-AI browser is half built.** Every user session is pinned to its first host with 12 steps and 120 seconds, the chat-side panel is read-only with no live frame, and no Model Plane run can attach to a user's session (`browser.rs:483-490`; `apps/Frontend Plane/verevonv3/src/features/chat/lib/chat-run-watch.ts:402-452`) [SRC]. See [F-t2-011](#F-t2-011), [F-t2-012](#F-t2-012) and [F-t2-013](#F-t2-013).
9. **Secrets reach receipts, snapshots and screenshots unmasked, and the model would see any credential it types.** AX values are copied verbatim, typed text is persisted in step receipts, `redact_sensitive` has no caller, and there is no `fill_secret` action or secret store reachable from Quarry (`chromiumoxide.rs:1096-1130`; `apps/Ingestion Plane/Quarry-v2/crates/quarry-runtime/src/step_receipts.rs:185-200`) [SRC]. See [F-t2-021](#F-t2-021) and [F-t2-024](#F-t2-024).
10. **One shared Chromium serves every session and restarts on a viewport mismatch.** Any viewport change closes the browser and clears pages, egress receipts and dialogs for all sessions; the agent path has no pool, cap, idle reaper or absolute TTL (`chromiumoxide.rs:185-270`; `agent_routes.rs:1425-1505`) [SRC]. See [F-t2-007](#F-t2-007) and [F-t2-006](#F-t2-006).

### 1.5 Decisions leadership must make

Ten topics need an ADR before the items that depend on them start. Each must respect the plane rules: no cross-plane database access, the Model proposes and Quarry executes or rejects, ZDR propagates, and Space access never widens an owner-plane ACL.

1. **Web policy of record and tighten-only claims.** Whether Control Plane org-core or Model Plane capability-core owns disabled, allowed and forced capability policy, delivered to Quarry only as signed claims. Items: [F-t2-022](#F-t2-022), [F-t2-032](#F-t2-032), [F-t2-008](#F-t2-008), [F-t2-025](#F-t2-025).
2. **Secret custody for browser credential use.** integration-corev2 holds secrets, Quarry resolves and fills them, and the Model sees only opaque references; no secret material may enter receipts or telemetry. Items: [F-t2-024](#F-t2-024), [F-t2-021](#F-t2-021).
3. **Shared human-plus-agent sessions.** How a grant binds a shared session, the control lease, and a broker-defined navigation policy for free human browsing that is not a single-host allowlist. Items: [F-t2-001](#F-t2-001), [F-t2-011](#F-t2-011), [F-t2-013](#F-t2-013), [F-t2-054](#F-t2-054).
4. **ZDR semantics per feature.** For caches, monitors, schedules, durable crawls and telemetry: refused, inline-only or hash-only, published as a ZDR capability matrix. Items: [F-t2-003](#F-t2-003), [F-t2-004](#F-t2-004), [F-t2-016](#F-t2-016), [F-t2-018](#F-t2-018), [F-t2-030](#F-t2-030), [F-t2-048](#F-t2-048).
5. **Anti-bot posture.** Confirm the honest-identity stance, decide whether to delete the stealth code, and define what policy-gated proxy escalation and robots override are allowed. Items: [F-t2-027](#F-t2-027), [F-t2-066](#F-t2-066), [F-t2-067](#F-t2-067), [F-t2-016](#F-t2-016), [F-t2-058](#F-t2-058).
6. **Script execution model.** Whether evaluate, scrape actions, code mode and generated extractors are acceptable when every binding call is still validated and executed by Quarry under grants and caps. Items: [F-t2-002](#F-t2-002), [F-t2-023](#F-t2-023), [F-t2-063](#F-t2-063), [F-t2-065](#F-t2-065).
7. **External agent exposure over MCP (Model Context Protocol).** Reverses the documented deferral; needs audience-bound OAuth and a ZDR-aware tool-call log. Items: [F-t2-064](#F-t2-064), [F-t2-042](#F-t2-042).
8. **Run trace envelope and sharing.** Model Plane trace versus Application Plane projections and Space grants, without letting a Space member see more than the owning plane allows. Items: [F-t2-014](#F-t2-014), [F-t2-038](#F-t2-038), [F-t2-072](#F-t2-072).
9. **Automation owner.** Application Plane versus Model Plane for completion-triggered follow-ups and routines, with per-fire browser grants for unattended runs. Items: [F-t2-031](#F-t2-031), [F-t2-061](#F-t2-061).
10. **Browser execution substrate.** Shared Chromium pool, per-session containers or VMs, governed remote providers, or a user-browser extension that gives up containment and ZDR evidence. Items: [F-t2-007](#F-t2-007), [F-t2-059](#F-t2-059), [F-t2-060](#F-t2-060), [F-t2-077](#F-t2-077).

The open questions that matter most, beyond the ADRs: was any org-private search result ever served across orgs (verification found that the Quarry search behind the gateway cache uses org-scoped private-corpus providers, so the cache is a cross-tenant exposure today); what idle timeout and navigation policy a human browsing session gets; whether enterprise tenants need a container or VM per browser session; and which claims need runtime confirmation first, namely the 401/403 failures on the AI paths, the viewport relaunch frequency, password masking in the accessibility tree, and the iframe sandbox flags in the search results viewer. A separate housekeeping decision is whether stale repo documents that claim robots handling, format parity, DOCX and budget enforcement are done should be retired wave by wave through the stale-document register.

### 1.6 What changed during verification

Tier calibration produced 24 Priority, 41 Recommended and 12 Nice to have. Two independent verification passes then ran: a Verevon-side pass that read the code behind all 77 items, and a reference-side pass that re-read the evidence behind 24 items. The Verevon pass kept 8 items as written, reworded 61 because the code showed a more precise gap, a better place to build or reusable parts, and recommended demotion for 8; six of those moved from Recommended to Nice to have ([F-t2-054](#F-t2-054), [F-t2-057](#F-t2-057), [F-t2-061](#F-t2-061), [F-t2-063](#F-t2-063), [F-t2-064](#F-t2-064), [F-t2-065](#F-t2-065)) and two were already Nice to have. The Priority count is unchanged at 24; the final split is 24, 35 and 18. Effort changed for 33 items, almost always upward, because items that looked like one-plane work turned out to span three or four services. The reference pass confirmed 2 items outright and corrected 22 in part; 14 prevalence counts were wrong and have been replaced or removed. No item remains unverified or low confidence, and no item was dropped as already built.
