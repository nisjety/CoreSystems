- D WS10.S6: `QueryEvents` serves only single-run reads: `filter.run_id` is mandatory, so the "cross-run" and `correlation_id`-only queries the proto describes are not served for the trace; the proto header comment says so only for the run path. A reader needing org-wide trace queries would need a second index and an authorization story (Space visibility, F-t2-072).
- D WS10.S6: the plan's "payload at most 8 KiB" is ambiguous; the table CHECK measures `payload::text`, which Postgres renders with `": "` and `", "` separators, so a compact 8,000-byte producer payload can exceed it. The validator measures the jsonb rendering (not the compact size) to avoid a permanent insert error being NAKed to MaxDeliver. Numbers that Postgres normalizes (`1e5`, `1.0`) are measured as serde prints them; a payload within a few bytes of the cap could still be refused by the CHECK and would then be NAKed five times and dropped (counted as `db_error`).
- D WS10.S6: a database error is NAKed with a 2 s delay and there is no breaker: a poisoned message the validator cannot see (a CHECK this table adds later) would be redelivered MaxDeliver times and then silently lost by the broker, with only the `db_error` counter to show it.
- D WS10.S6: identity-column commit-order skew (plan risk) is accepted as designed; `gap_suspected` is also raised for a plain out-of-order redelivery, so it is a suspicion counter, not a loss count. The exact loss figure is `published - rows` as the soak computes it.
- D WS10.S6: `next_cursor` is returned whenever a page has rows (the proto says "empty when exhausted"); lane B and the gateway/SPA must use `has_more` for exhaustion. If the owner prefers the proto wording, the change is one `if has_more` in `eventlog_grpc.rs`, but a poller of a live run then has no way to resume from the end of a short page.
- D WS10.S6: the consumer authorizes with `authorize_thread_owner` AND `authorize_run_owner` (the latter adds the revoked-Space-membership refusal). For a human caller on a Space run whose owner is someone else, the thread rule may admit the Space members (system-owned threads inside a Space are not org-readable, per `authorize_thread_owner_row`) while the run rule needs `runs.user_id` to match: the stricter of the two wins, which is owner-only as ADR-8 part 1 says, but Space co-members never see a trace in v1.
- D WS10.S9: C5's "new WS4 matrix rows" cannot go into `zdr-posture-matrix.json` (see MP-ASKS lane D batch 3); they are Quarry's `zdr_matrix::ROWS`. - D WS11.S7: the taint window is time-based (`messages.created_at` inside `[run.created_at, run.ended_at + 60 s]`), because messages carry no run id. Two runs of one thread that overlap in time (a background run beside a chat turn) taint each other's assistant messages; a long run's window also swallows a user's concurrent assistant-visible text. Conservative (more rows skipped), never looser.

- D WS11.S7: the marker is written even when `SESSION_CORE_DREAMING_SKIP_EXTERNAL_CONTENT` is off, so the kill switch is reversible without a backfill; a tenant that turns the filter off for a week and back on gets the week's tainted rows skipped on the next pass only if they were not yet dreamt (already-mined rows stay mined).
- D WS11.S7: the execution-core latch is not built here (later lane). Until it lands, `save_memory` in the SAME live run after a `web_fetch` is NOT refused; only Dreaming's derivation is guarded. The two halves are independent, so this is a gap in coverage, not a conflict.
- D batch 3: migration files are CRLF in this working copy but `.gitattributes`/autocrlf stores them LF (git warns "CRLF will be replaced by LF"), and the existing session-core migrations have the same property; sqlx checksums the file bytes, so a database migrated from a CRLF checkout and later booted from an LF checkout reports a checksum mismatch (the known fresh-checkout crash-loop). 0086 and 0087 are no worse than 0001-0085.
- lane D / WS11.S6: `compose_system_prompt` now reads `EXECUTION_CORE_ROUTING_GUIDANCE` per call and the park resume compares `prompt_digest_of(compose_system_prompt(..))` with the parked run's digest. Flipping the switch while a run is parked therefore changes the digest of the resumed prompt. Default off makes this inert; before turning it on in a deployment, either drain parked runs or fold the switch state into the park fold. Not tested: the park/resume mismatch path with the switch flipped between park and resume.
- lane D / WS11.S7 (execution-core): (1) the latch rebuild at cold resume reads `[source: ...]` tags from the restored transcript, but `compaction_budget::clear_stale_tool_results` can clear old tool payloads in the live history, and a Segment (stage-1 approval continuation) resume restarts from the goal with no history at all, so in both cases the latch can come back unset after an external read; session-core's durable `external_content_at` still guards Dreaming, but a later `save_memory` in the resumed run is not refused. Fix would be to carry the latch bit in the loop fold. (2) A `save_memory` rejected in the pre-pass never reaches session-core, so no `external_content_at` is involved; the refusal is visible only as a tool error line (no audit event). (3) The same-batch rule counts a batch-mate whose call is later rejected or fails, which is conservative by design. (4) Delegated children: a child with its own `save_memory` call is also refused by the shared latch; leaf children cannot run risky tools anyway.
