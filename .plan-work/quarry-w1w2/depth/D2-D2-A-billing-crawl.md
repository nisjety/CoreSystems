# D2-A-billing-crawl: findings not fixed

Format: `- [severity] [kind] what | where | why not fixed`

Decision 3.11 (BILLING-IDEMPOTENCY), crawl and batch only.

- [medium] [risk] Under-bill window: if the edge dies (or the NATS publish is never reached) between Control's 201 and the meter call, the client's retry is a replay (200) and is not billed, so that crawl seed or batch is never billed. The decision chose "skip on replay" over "bill the replay under the job id with Control's created_at", which would close this window because billing-core dedupes on the job-id key. ControlJob does not read `created_at` yet | `crates/quarry-edge/src/handoff.rs`, `routes.rs` (crawl_handoff, batch_handoff) | decided option; the alternative needs `created_at` read from Control's job and `occurred_at` overridden on the event. Cheap if finance wants no under-billing
- [medium] [decision] Sync routes keep billing every retry: search, search/similar, vertical search, map, legacy extract, answer. Each retry re-does real work and mints a fresh id, so it is billed again. Nothing was built (no Redis first-seen scheme, by decision). Real idempotency needs a stored response replayed plus a body fingerprint | `search_routes.rs`, `map_routes.rs`, `extract_routes.rs` | decided: recorded only
- [medium] [kind evidence] Nobody has established which legacy metrics reach invoices today. If `quarry.crawl.seed` or `quarry.batch.url` do, finance may want a look-back at past over-billing (failed handoffs other than queue-full in `off`/`shadow` were billed) and under-billing (a reused X-Request-Id was billed once, ids over about 101 bytes were refused by billing-core) from the old request-id key | billing-core data | needs the billing owner; information only
- [low] [behaviour change] In `off` and `shadow` a crawl or batch that Control refused for any reason other than a full queue (control unreachable, a 5xx) used to be billed and is no longer. In every mode the event id changed from `quarry:<request_id>:<metric>` to `quarry:<job_id>:<metric>`; an event that was queued under the old id and is delivered later is a different row | `routes.rs` | intended by the decision
- [low] [risk] The replay test is a status test: `replayed` is "an Idempotency-Key was sent and Control answered 200". It relies on control's documented 200-versus-201 split (`services/quarry-control/internal/resources/resources.go`, createJob). If Control ever answers 200 for a fresh create with a key, the first call would go unbilled. No contract test pins the split on the Control side in this unit | `handoff.rs` `post_job` | a Control-side test belongs to the Go service owner
- [low] [kind evidence] Nothing ran against a stack: no real Control, no billing-core, no NATS. The two-organization case is covered by construction (the key is Control's job id, ids are unique across organizations and Control's idempotency index is per organization) and by a test that distinct jobs with one reused request id get distinct ids; the dev-bypass edge has one organization only, so no two-org request test exists | `tests/billing_handoff.rs` | needs real tokens for two orgs; stack session
- [low] [doc] The billing owner has not been told (step 5 of 3.11 is information only). Text for them: crawl seed and batch events now use `quarry:<job_id>:<metric>`; a replayed Idempotency-Key and a failed handoff emit no event; billing-core is unchanged | n/a | a message is not sent from a build unit
