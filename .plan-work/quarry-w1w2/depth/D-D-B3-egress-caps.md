## D2-017 (WS6.H plan-cap stamp)

- [high] [decision] A plan value of `0` for `quarry.cap.crawl_jobs` or `quarry.cap.job_backlog` cannot be stamped: control reads `params.admission.cap` below 1 as "none given" and applies its default (3 and 200), so a plan that says "no crawl jobs" would get the default instead. The edge stamps nothing for a zero | `crates/quarry-edge/src/handoff.rs` (`admission_stamp`); `services/quarry-control/internal/resources/admission.go` (`backlogCap`), `store/store.go`, `store/pg/resources.go` (cap >= 1) | needs a control-side meaning for an explicit zero, or an edge refusal (402 or 403); a product decision
- [medium] [risk] The stamp is inert today: the only limits source is `StaticFloor` (origin Floor), which stamps nothing, so no job carries `params.admission` until the WS6.D entitlement backend fills `PlanCaps.crawl_jobs` and `job_backlog` | `crates/quarry-edge/src/limits.rs` | no billing source yet (plan WS6.D); the two-plan test uses a stub resolver
- [medium] [kind evidence] Control only reads the stamp with `QUARRY_JOB_ADMISSION=on`; with it off the stamp is carried in `jobs.params` and ignored. Nothing was run against a stack: no control, orchestrator or Postgres test for a stamped cap in this unit | `services/quarry-control` | stack evidence round
- [low] [risk] `LimitsOrigin::Open` (fail-open) stamps nothing, so control uses its own default cap (3) for those jobs, while run capacity under `open` uses the process-wide cap. Probably right (fail-open should not raise caps), not decided | `handoff.rs` `admission_stamp` | confirm with the WS6 owner
- [low] [kind scope] Only the two handoff routes (`/v1/crawl`, `/v1/batch`) create jobs; scheduled jobs are created by control and carry no stamp | routes.rs, schedule path | out of this unit

## D2-013 (tab egress is a meet)

- [high] [behaviour change] The attach tab (`agent_routes/attach.rs`, `OpenTabOptions.egress_policy = from_allowed_domains(&allowed_domains)`) used to be governed by that policy alone, so it ignored the session's web-policy narrowing and deny list. It now answers to the session policy and that one. Intended, but it is a tightening that the live attach lane has never seen | `crates/quarry-edge/src/agent_routes/attach.rs:251` | not run against Chromium
- [high] [kind evidence] The WS8.E live Chromium tests (`per_tab_policy_blocks_third_host_in_agent_tab_only`, `human_tab_keeps_open_web_while_agent_tab_is_narrow`, both `#[ignore]`, `CHROMIUMOXIDE_TEST=1`) were not run here. They configure an open session policy and a narrow tab policy, which the meet leaves unchanged | `crates/quarry-browser/src/chromiumoxide.rs` (tests near 7080 and 7210) | needs the Chromium lane
- [medium] [behaviour change] A tab policy with no session policy is now deny-all (a session with no policy is deny-all, so a tab policy alone is not authority). `lifecycle.rs` configures the session policy before the first tab, so no caller depends on the old order; a future caller that opens a tab before the session policy exists will be refused | `tab_control.rs` `resolve_tab_egress_policy` | deliberate; stated in the doc comment
- [low] [doc] The trait docs of `configure_tab_egress_policy` and `OpenTabOptions` in `crates/quarry-browser/src/lib.rs` (hot file) still say the tab policy "governs" the tab; `tab_control.rs` has the corrected text | `lib.rs` ~1104 | shared hot file, comment only
- [low] [risk] The browserbase and browserless drivers have no per-tab guard (`per_tab_egress` is false there), so the meet is a chromiumoxide property only | `browserbase.rs`, `browserless.rs` | capability bit already says so

## D2-020 (Narrowed(empty))

- [medium] [hardening] `BrowserEgressPolicy::from_allowed_domains(&[])` is the unrestricted policy, so any caller that derives a list and may pass an empty one fails open. Only `egress_policy` is fixed here. A `from_narrowed(&[String])` constructor (empty = deny-all) in `quarry-browser/src/lib.rs` would remove the footgun; other derived-list callers: `agent_routes/attach.rs:251` (list is the attachment's validated non-empty list), `quarry-runtime/src/observation.rs` (empty means an unrestricted run by design) | `crates/quarry-browser/src/lib.rs` | hot file, API addition; no caller is wrong today
- [low] [evidence] `narrow_egress` never returns `Narrowed(vec![])` by inspection of `quarry-core/src/web_policy/mod.rs` and by the sample test added; it is an invariant of that function, not enforced by its type | `quarry-core/src/web_policy/mod.rs:785` | not this unit's file

## D2-018 (URL-fetching route sweep)

Route table of routes.rs: 75 `.route(` calls, 70 distinct paths, all classified in `tests/web_policy_routes.rs` (`route_manifest`). Gated and proved through the router with a denied host: `/v1/scrape`, `/v1/scrape/stream`, `/v1/crawl`, `/v1/batch`, `/v1/map`, `/v1/extract`, `/v1/search/similar`, `/v1/internal/run_page`. One gap found and fixed: `/v1/change/refresh` (postgres-queue build) queued a URL with no policy gate; it now gates before the enqueue (edit in `change_routes.rs`, outside the unit's file list: one hunk). Not fixed:

- [high] [other-plane] `POST /v1/audio` forwards a caller `audio_url` to the Model Plane, which fetches it; Quarry's web policy (`domains.deny`) is not applied and the edge does no SSRF check on it | `crates/quarry-edge/src/audio_routes.rs` | the fetch is the Model Plane's; the edge could gate the URL with `gate_url` before the forward, a one-hunk change in a file outside this unit; needs the owner to say whether `audio_url` is a web fetch under the policy
- [medium] [risk] `POST /v1/answer` and `/v1/answer/stream` fetch the pages their own search returned (`scrape_fn` in `quarry-runtime/src/answer.rs`); the edge handlers apply no `gate_url` to those result URLs, so a `domains.deny` host that the search returns can be fetched. Redirects inside a fetch are handled by `quarry-runtime/src/policy_gate.rs` (not re-verified here) | `crates/quarry-edge/src/answer_routes.rs`, `crates/quarry-runtime/src/answer.rs` | outside the unit's files; needs the pipeline to take a gate
- [medium] [design] `POST /v1/sources` and `/v1/schedules` (and trigger, backfill) store a URL with no create-time gate; the fetch happens later through the orchestrator's `/v1/internal/run_page`, which is gated at fetch time against the policy then in force. A denied host therefore registers and then fails at run time, instead of being refused at create. Reasonable (the policy can change in between) but the user sees the failure late | `resource_routes.rs::create_source`, `schedule_routes.rs` | product call whether to also refuse at create
- [medium] [risk] `/v1/internal/run_page` decides with `Principal::Autonomous` and the operator baseline only; there is no organisation layer (WS7.H and WS7.J not built), so an org's own deny list does not apply to crawl pages at fetch time | `routes.rs` ~1638 | WS7.H, WS7.J
- [low] [observation] `/v1/search/similar` returns 501 for "no vector index" before it gates the seed URL; harmless (nothing is fetched on that path). The test uses a counting index so the gate is what answers | `search_routes.rs` ~1290 | no change needed
- [low] [observation] `/v1/internal/queues/:queue_name/enqueue` and `enqueue_batch` (queue_routes.rs, service token) enqueues caller-given URLs for the durable queue; the consumer of the queue is not in this edge. Not gated here | `crates/quarry-edge/src/queue_routes.rs` | internal surface; check the consumer
- [low] [test] The `/v1/change/refresh` gate is in the `postgres-queue` build only; the default build answers 501 before any URL is read, so the route-level refusal case is not in the sweep. Compile-checked with `--features postgres-queue` only | `change_routes.rs` | needs the queue pool for a runtime test
- [info] [routes.rs for D-B3-scrape-actions' owner] No fetching route in routes.rs lacks a gate: `scrape` (decide + gate_url before the driver), `scrape_stream` (decide before the stream, gate inside it), `crawl_handoff`, `batch_handoff`, `internal_run_page`. This unit changed routes.rs in 4 spots only: `with_admission(..)` around the crawl and batch params.
