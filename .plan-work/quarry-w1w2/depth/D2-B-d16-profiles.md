# Depth findings left open by D2-B-d16-profiles (2026-10-28)

Unit: decision 3.5 D16-Q2 (option C): owner stamp at run start (people only), default scope user_private in every store, observe-mode counters, legacy-count script. Commits aa2f64988 (stores) and 3f9017d62 (edge); this file, RUNBOOKS and the scripts are in the docs commit.

- D2B16-01 (low, decision): a model-driven (service principal) run that persists a profile leaves an ownerless row, which is hidden under `enforce` (D16 Q2: "refused, or the row stays ownerless and hidden"; the stay-hidden branch was built). Nothing refuses it. `quarry_profile_owner_stamps_total{outcome="skipped_service"}` counts them. The owner chooses, after the observe week, between refusing a service run's persistent profile under enforce and waiting for an acting-user claim.
- D2B16-02 (low): a run that fails after the stamp (the run-checkpoint save, a later step of `start_run`) leaves an empty placeholder row owned by its person. It holds no cookies. It is listed with no name. The stamp sits after the caps, the policy and the lease, so a start that one of those refuses leaves no row. A cleanup (delete a row with `saved_at IS NULL AND rev = 0` when the start fails) was not built: it needs a delete that is tombstone-neutral, and the decision lists the placeholder as an open risk.
- D2B16-03 (low): the S3 profile backend has no tombstones, so `stamp_owner` there is the trait default (exists, then `save_metadata`): not ordered against a delete and not atomic (two starts of one new id can both write the metadata). Production uses Postgres. The older RUNBOOKS note that an S3 snapshot save stamps no owner is unchanged.
- D2B16-04 (low): the scope of the stamped row is the run's own `profile_scope`. Any member can therefore create an `org_shared` persistent profile by starting a run with `profile_scope: org_shared`, the same as `POST /v1/profiles/create` allows. The edge comment says the effective scope comes from the authenticated gateway; the edge does not re-validate it. Not new, but now visible in the stored row.
- D2B16-05 (info): a person's token that sends `initiated_by: agent` is still a person (user principal): its persistent run is stamped. Only the principal type decides, not the hint. That is what the decision says ("human users only"), and the gateway calls Quarry with the user's own audience token (`quarry_token` in domains/browser.rs), so the gateway's default persistent flow is stamped.
- D2B16-06 (info): the legacy count script (`scripts/evidence/d16-legacy-profile-count.{sql,sh}`) was run only against a throwaway Postgres 16 container with the migrations and six synthetic rows (counts matched, a DELETE inside it was refused), never against a stack. `psql` 12 or later is required (`\if :{?since}`).
- D2B16-07 (info, tests): the Postgres tests for the default scope and the stamp (`postgres_profile_store::tests`) compile under `--features postgres-queue` but skip without `DATABASE_URL`; the Redis-gated `metadata_methods_pass_through_to_inner_uncached` was corrected and skips without `REDIS_URL`. Neither ran against a service in this unit. The in-memory equivalents ran and pass.
- D2B16-08 (info): the first commit message names the changed quarry-browser test loosely ("list_attaches_metadata..."); the test is `session::tests::list_carries_name_and_scope_from_metadata`.
- D2B16-09 (info, hygiene): the files this unit touched are not rustfmt-clean on the base (`rustfmt --check` shows diffs in code this unit did not write); no whole-file reformat was done, because the hot-file rule forbids it.
- D2B16-10 (decision, not made here): `QUARRY_EDGE__PROFILE_OWNER_ENFORCE=enforce`. It needs the legacy count on the stack, the observe week, and the owner's choice between a manual org-confirmed rescue and a backfill from run records (user actors only). The scripts and counters for the first two are built; the third is not.
