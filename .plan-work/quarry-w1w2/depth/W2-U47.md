# W2-U47 depth notes (WS9.F, SPA browser session controller)

Format: `- [severity] [kind] what | where | why deferred`. Written during the build, not fixed.

- [medium] [hardening] `setControlMode` takes no `expectedEpoch`; the plan's shape is `setControlMode(mode,{expectedEpoch?})`. The browser client (`setBrowserControlMode`) has no epoch parameter and the SPA carries no epoch yet | `use-browser-session-controller.ts` `setControlMode`, `shared/api/browser-client.ts` | the epoch wire belongs to WS2.C (deployed) and WS9.I; U47 owns no client file
- [medium] [test] The controller test covers open/close, the ZDR profile rule, busy gating, a superseded open, a stale timeline reply, navigation card set and clear, a non-navigation error, approvals through the approval route, and the page-hide keepalive DELETE. Not covered: socket observation, new/select/close tab, control takeover pausing the AI loop, `decideApproval` when no pending approval is found, `dispose` while an open is in flight, and the `startAiRun` stream error branch | `use-browser-session-controller.test.ts` | tests are written to the plan; the extra cases are for the wave-end test phase
- [medium] [risk] Solid 2 (`solid-js` 2.0.0-rc.0, `@solidjs/signals`) applies signal writes on flush: a read straight after a write outside a reactive root returns the old value (observed: `busy()` false right after `setBusy(true)`). The controller gates `busy` on a plain `busyFlag`, but `preview()`, `approvals()` and `error()` reads made in the same tick as a write can lag. Tests flush with `flush` from `solid-js` | `use-browser-session-controller.ts`, its test | a caller that needs same-tick reads must read after an await or inside a component; if a caller needs synchronous state, mirror it in plain variables
- [medium] [decision] `dispose()` closes only a ZDR session (the plan's wording). A non-ZDR session stays open until `close()` or the page hide. The composer's `clearPreview` closes every session. The owner should confirm which rule dispose follows | `use-browser-session-controller.ts` `dispose` | a product rule, not a build detail
- [medium] [risk] The page-hide close sends only `x-verevon-org-id` and `credentials: 'include'`. `requestJson` in `shared/api/http.ts` also applies the dev-auth header (`applyDevAuth`, not exported), so in dev the keepalive close can be refused without notice | `use-browser-session-controller.ts` `onPageHide` | exporting a keepalive helper touches `http.ts` and `browser-client.ts`, which U47 does not own
- [medium] [other-plane] `open` does not run the scrape the composer runs first (`scrapePreview` with `render_page`). A caller that wants the scrape must merge it into the returned preview itself. The composer path is unchanged | `use-browser-session-controller.ts` `open` | the scrape is the composer's Link flow, and the composer is not moved in this slice
- [medium] [kind evidence] No live-browser or end-to-end evidence: the controller is driven by mocked clients only. WS9.G is the first UI entry point, and evidence starts there (stated explicitly per the plan's WS9.F "Evidence: none") | WS9.F plan detail | by design
- [low] [doc] Two implementations of the same lifecycle now exist: `KnowledgeComposer.tsx` 799-1160 and the controller. They drift until the Crawl composer moves onto the controller (unscheduled in the plan) | `KnowledgeComposer.tsx`, `use-browser-session-controller.ts` | the plan leaves the cleanup unscheduled; this slice must not touch the composer
- [low] [other-plane] The older client-side suggest/act loop (`performBrowserSuggestedAction`, `browserRationales`, the `withStepRationale` history) is not mirrored. The controller handles only the durable server-side run | `KnowledgeComposer.tsx` | the composer's own comment marks that loop as replaced by the durable run
- [low] [kind other] Four `solid/reactivity` ESLint warnings: `sessionId` and `entry` are call-time snapshots inside the factory, and the rule reads them as setup captures. The code is intended (the action targets the session that was current when it was called). Rename only if the team's lint policy wants it | `use-browser-session-controller.ts` (the `sessionId` captures in `runAction`, `setControlMode`, `applyTabs`, and `entry` in `decideApproval`) | a warning, not an error; no behaviour change wanted
