# INNH depth findings, lane A (scrape / extract)

One line per finding. Things worth doing later; none is needed to close the item's gap.

INNH-1 | The privacy skip happens after the page fetch (the scrape is still served); a request that is both AI-formatted and credential_or_secret could skip the model lane checks (501s) as ZDR does, but today a deployment without a model still answers 501 before the fetch for such a request. Decide whether the privacy block should behave like ZDR there.
INNH-1 | The ZDR matrix rows for scrape and extract do not name the PRIVACY_POLICY skip (it adds no persistence or new content surface, so the golden was not regenerated); add it to the basis text next time the golden is regenerated.
INNH-1 | /v1/extract reports a privacy-block refusal as a per-source error string starting PRIVACY_POLICY:, like ZDR_UNAVAILABLE:, not as a structured code; a typed code on ExtractItem would be cleaner for the UI.
INNH-7 | max_age is scrape-only: crawl/batch/run_page keep prev_fingerprint. A per-job scrape_options.max_age (INNH-6) would reuse PageCache::result_key and scrape_cache::rehydrate unchanged; needs the orchestrator to carry the option and a decision on billing for hits.
INNH-7 | A hit is not metered as scrape.page (same as the existing page-cache hit). Decide with the Control Plane owner whether a cache hit bills, is free, or bills a smaller unit; the response already says cache_state hit.
INNH-7 | Redirects: the key uses the URL as requested, not the final URL, so a.com and a.com/ that redirect to one page are two entries. Aliasing under the final URL (a second key, same output) would raise the hit rate.
INNH-7 | Browser-served results stay uncached in v1 (also a static request that escalated to the browser). A browser entry would need the render hints and wait options in the options key.
INNH-7 | The write happens for every cacheable success while the flag is on, even for requests that never send max_age, so the first max_age request can hit. If Redis memory matters, switch to write-on-demand (write only when the request carries max_age) and accept a cold first call.
INNH-7 | Option explosion: each distinct option set is its own entry (TTL 3600 s). If a caller varies include_tags per request, memory grows; a per-org entry cap or a shorter TTL for option-bearing keys is the lever.
INNH-7 | stale_while_revalidate_s, min_age and a store=false switch (Firecrawl) are not built; CachePolicy.vary_on is still read nowhere.
INNH-7 | quarry-v2-ci.yml runs cache_policy.rs in the Redis step; scrape_max_age.rs needs the same step (file is outside Quarry-v2; left to the owner or CI session).
INNH-7 | fingerprint() in cache.rs is still dead code (#[allow(dead_code)]); the URL key supersedes it. Delete it or wire it.
INNH-7 | Under QUARRY_CHALLENGE_ENFORCE=log (observe mode) a challenge page is let through the gate and would be written to the URL cache; add a challenge signal check to scrape_cache::is_storable if that mode is ever run with the max_age switch on.
INNH-7 | review | CORRECTION to the line above and to INNH-7-status.md "Not verified": the default is QUARRY_CHALLENGE_ENFORCE=log (challenge.rs EnforceMode default, RUNBOOKS 383), not enforce, so with the shipped defaults a bot-wall page that the classifier flags is let through the pipeline gate and WOULD be written (same for a 200 soft-404: pipeline.rs:1140 only emits an event). Reported to the lead as a blocker; docs (CONTRACTS 9.1 "a bot wall fails the run and is never stored", scrape_cache.rs header) say otherwise until it is fixed.
INNH-7 | review | With the flag off, a request that carries max_age/maxAge changes from 200 + unknown_field warning (lenient) to 400 feature_disabled, so a Firecrawl-style client that always sends maxAge breaks on every stack where the flag is off. It matches captures/actions/AI formats and no sender exists in apps/ today, but "ships dark" is not strictly additive for such a client; consider lenient-ignore-with-warning while off, or tell the Innhenting UI to treat feature_disabled at max_age as "retry without max_age".
INNH-7 | review | cache.max_age_s (u32, up to ~136 years) is used unclamped as the Redis TTL of the new entry (effective_ttl, routes.rs); max_age itself is capped at 30 days. Any caller in any org can pin entries in the shared Redis effectively forever, and with the write-always rule and option-bearing keys that is a cross-tenant memory lever. Clamp the TTL for the result cache to MAX_AGE_CEILING_MS/1000 (or a configured ceiling) and consider a per-org entry cap (owner decision 3). The page cache has the same unclamped TTL (pre-existing).
INNH-7 | review | GDPR erasure does not remove quarry:scrape:{org}:* (nor quarry:page:{org}:*). After an erase the artifacts are gone (a hit becomes a miss) but the entry still holds title, description, excerpt, metadata and branding of the page until its TTL. Hook the org erase flow to SCAN-delete the org prefix before the flag goes on anywhere with real tenants.
INNH-7 | review | CachePolicy cache.max_age_s doc says 0 = default 3600; a reader's max_age larger than the writer's TTL silently behaves as the TTL, but the response does not say so (cache_state miss with no warning). A UI offering "up to 1 day old" will see misses after an hour. Consider a note in effective_options or raising the default TTL when the flag is on.
INNH-7 | review | scrape_cache.rs get_result logs `error = %err` for a stored entry that fails to deserialize; serde_json type errors can echo the offending value ("invalid type: string \"...\", expected ..."), and the entry holds a title/URL. Only reachable after a NormalizedOutput schema change with old entries live, but log a fixed message plus the error category (err.classify()) instead.
INNH-7 | review | ZDR is proven with the body flag only (zdr:true). The token-floor path (org ZDR, body zdr false) goes through the same claims.effective_zdr_mode variable so the code is right, but there is no test like ai_formats_real_token::a_zdr_org_user_gets_every_format_skipped_even_when_the_body_says_zdr_false for max_age, and the matrix row has Log::Unverified (no log-capture canary that a ZDR max_age request logs no URL/key). Add both.
INNH-7 | review | Tests do not cover: html/rawHtml rebuilt equal to the first answer under non-default clean options (include_tags, extractor raw; the run uses cleaned_html there, the rebuild calls to_markdown again), a non-UTF-8 page, an over-cap field on a hit (omitted[]), a planted bot-wall or soft-404 body (the blocker), or a real-token hit by a second user of the same org. The cross-org test plants entries directly, which proves the key, not the Authorization path.
INNH-7 | review | A hit returns the stored output verbatim, including output.privacy (the first caller's purpose_id / lawful_basis) and the first run's run_id/fingerprint. Same org only, so not a tenancy hole, but overwrite output.privacy with the current request's effective privacy so the audit trail of the response matches the caller.
INNH-7 | review | formats `links` and `metadata` are in canonical_options_key although both change nothing (CONTRACTS 9.1), so ["markdown"] and ["markdown","links"] are two entries for identical content. Drop them from the result-cache key (not from the page-cache key, which does not use it).
INNH-7 | review | A hit does not re-run the web-policy gate on output.url.final_url, only on the requested URL; a redirect target that policy later denies is still served until the TTL. Low (TTL-bound), but gate final_url on a hit if policy can tighten at runtime.
INNH-7 | review | openapi.yaml describes effective_options.max_age/cached_at/cache_age_ms in prose only (the property is an untyped object); the Innhenting UI is the first typed consumer, so add the properties and the cache_state enum to the schema.

INNH-3 | review | The `error` field itself carries an operator variable name (`QUARRY_EDGE__MODEL_PLANE_URL is not set on this deployment`, case 1) and the status file tells the UI to show `error` as the reason, while also saying never to tell a person to set a variable. INNH-3 | review | A lane-refused request spends one fetch (and an Auth Core mint attempt) and meters nothing, so any caller can run one unbilled fetch per request on a deployed stack (the body is discarded, so it is a cost lever on Quarry, not a data leak).
