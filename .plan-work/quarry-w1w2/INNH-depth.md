# INNH depth findings (not fixed; one line each)

Format: `item | unit | finding`. Wave first, depth later (user order 2026-10-23): none of these is a fix loop.

- INNH-1 | U1 | The hand-written `ScrapeFormat` JsonSchema (scrape.rs) repeats the AI limits (200..10000, 1..10, 40..1000, 10000, 1000) by hand; `openapi-scrape-parity.test.mjs` checks OpenAPI against the golden but nothing checks the golden against the `ai_spec` constants. A Rust test in `tests/scrape_schema.rs` that reads the consts would close it.
- INNH-1 | U1 | The effective-options golden shares the `ScrapeFormat` schema, whose string enum lists the input names (`rawHtml`), while `wire_name()` writes `raw_html` and now `json`, `question`, `highlights`. The effective golden has described the echo loosely since WS13.4b; a separate `EffectiveFormat` schema would make it exact.
- INNH-1 | U1 | `empty` (blank prompt, question or query) is a code the design table does not list; ERROR_REASONS.md and CONTRACTS.md now do. Confirm with the Innhenting UI copy, or fold it into `missing_field`.
- INNH-1 | U1 | AI object fields are snake_case only (`max_chars`), as the design says, while the capture options and the root options also take camelCase (`fullPage`, `maxInlineBytes`). A Firecrawl-style caller sending `maxChars` gets `unknown_field`. Add aliases only if the UI needs them.
- INNH-1 | U1 | The `scrape` and `scrape_stream` rows of `zdr_matrix.rs` describe the AI refusal in `basis` but list no `enforced_by` test: `tests/zdr_feature_matrix.rs` verifies each reference exists, and the U3 tests do not exist yet. U3 adds `ai_formats::...` to `enforced_by` and regenerates the golden.
- INNH-1 | U1 | Schema `type` may be a list (`["integer","null"]`) and `enum` any array; the validator in `json_schema.rs` supports both but a list with an unknown member is `invalid_value` here while the validator itself would report `InvalidSchema` at run time. Same family as the WS16.S4 validator widening.
- INNH-1 | U1 | `schema_too_complex` counts `properties` entries but not `enum` members or `required` names; the 65,536-byte cap bounds them. A schema of 65 KB made of one huge `enum` is accepted and costs model input tokens.
- INNH-1 | U2 | The gateway fixes `max_tokens` at 4096 and `temperature` at 0.7 on `/v1/ai/chat`, so a per-call output cap cannot be enforced; the engine caps calls, reported tokens (checked before each call, so calls already in flight can pass the cap) and page chars only. Part of OD-2 (WS16.S1).
- INNH-1 | U2 | `/v1/ai/chat` returns no `cost_usd`/`provider_used` yet; `AiChatResponse` decodes both as optional and the report carries tokens only. Add `cost_usd` to `AiUsage` when WS16.S1 ships.
- INNH-1 | U2 | Highlight offsets are char offsets into the page markdown Quarry produced; a client that re-wraps or re-encodes `data.markdown` (UTF-16 JS strings, astral chars) must convert. A UTF-16 offset field would be additive if the Innhenting UI wants one.
- INNH-1 | U2 | `question` and `highlights` replies are parsed from prose-instructed JSON, not from `structured_output_schema`; if the gateway honours the schema string for the alias in use, sending one for them would cut the `bad_reply` rate. Measure on a real dev gateway before changing (E1+ evidence).
- INNH-1 | U2 | A highlight longer than `max_chars_each` is cut at the char limit (still verbatim) and may end mid-word; a sentence-boundary cut would read better. A quote that occurs twice is matched at its first occurrence only, so a repeated sentence anchors at the first one.
- INNH-1 | U2 | The old `ai_formats.rs` runner (used by `/v1/extract` and the answer pipeline) still wraps pages in a fixed `===` delimiter and discards `zdr`; INNH-2/3 should move `/v1/extract` onto `AiScrapeEngine` (or the nonce framing) rather than keep two prompt paths.
- INNH-1 | U2 | `FoldedText` folds whitespace, no-break/Unicode spaces, typographic quotes and three zero-width characters; it does not fold dashes (`-`, en dash, minus), ligatures or Unicode normalisation (NFC/NFD), so a quote that differs from the page only there is dropped. Add if the real-model run shows it.
- INNH-1 | U3 | The 125 s router deadline applies to every `POST /v1/scrape` while the switch is on (design D14), not only to requests with an AI format, so a plain scrape that hangs now holds its connection 125 s instead of 60 s. A body peek in the deadline middleware, or a per-handler deadline, would narrow it.
- INNH-1 | U3 | The AI phase (45 s) runs after the fetch and outside `timeout_ms`; a caller cannot bound it. An `ai_timeout_ms` option, or deriving it from `timeout_ms`, would be additive.
- INNH-1 | U3 | The 501 availability checks are skipped under ZDR, so a ZDR caller on an edge with no Model Plane sees `ZDR_UNAVAILABLE` where a non-ZDR caller would see 501. Right for ZDR, but a client that probes for the feature with `zdr:true` learns nothing about availability.
- INNH-1 | U3 | The chat lane reuses `state.model_plane_token`, the same field the audio route uses; a separate `ai_chat_token` (or the Dynamic provider once OD-1 exists) would keep the audiences apart. The Ingestion compose passes neither token, so the live-style stack cannot reach the lane.
- INNH-1 | U3 | `extract:ai` is not in the Control Plane principal registry (OD-6: users only in v1). The scope check is proven with golden tokens plus the scope added in the test; no registry row or Auth Core contract spec mentions it yet.
- INNH-1 | U3 | The stream refusal looks at the raw `formats` for an object `type` or the string `summary`; bare `json`, `question` and `highlights` strings on the stream are still silently ignored (as every unknown format name is on that route), where `/v1/scrape` answers `missing_field`.
- INNH-1 | U3 | The page-cache test needs a Redis and skips in the plain qtest container; `quarry-v2-ci.yml` runs `cache_policy` with a Redis service and `REQUIRE_CONTRACT=1`, and `ai_formats` should be added to that step so the cache guard is not skipped in CI.
- INNH-2 | /v1/extract still calls `/v1/invoke` through the old `AiFormatRunner` (text alias, no `structured_output_schema`, no repair call), while scrape AI formats use `AiScrapeEngine` on `/v1/ai/chat`; a schema-invalid or prose-wrapped answer is not repaired. Moving extract onto the chat engine removes the second prompt path and gives repair and token usage.
- INNH-2 | Sources are read one after another (up to 25) and the 50 s request budget cuts the tail; a bounded fan-out (3 to 4 in flight) would cut latency. A model call that the budget drops mid-flight is still paid and its result is discarded.
- INNH-2 | The model reads only the first 20,000 bytes of a page (`MARKDOWN_CAP`); `truncated_input` now says so, but a configurable cap or chunked extraction for long pages is not built.
- INNH-2 | No LLM usage or cost on extract: metering stays `quarry.extract.url` per ok or fetched source (a prompt-only model call is billed the same as a plain fetch), and no token usage is returned (WS16.S1).
- INNH-2 | A prompt-only answer has no size cap: `data` is whatever object the model returns, inside a response that has no per-item byte bound.
- INNH-2 | Under ZDR every source still costs a fetch before it answers `ZDR_UNAVAILABLE` (kept so the `structured` harvest returns); a caller who only wants the model result pays a fetch for nothing. A request-level 403 would save it.
- INNH-2 | The legacy `quarry.search.query` event for extract still records `structured: schema.is_some()` and ignores `prompt`.
- INNH-2 | review | The 50 s budget is checked only before the model call, not before `fetch_page`. After it runs out each remaining source is still fetched, then answered with the budget error, so a 25-URL request of slow hosts can still pass the router's 60 s cut the budget was added to avoid. Check `started.elapsed() >= budget` at the top of the loop and answer without a fetch. The markdown-only and ZDR routes have no budget at all.
- INNH-2 | review | A model call that the budget drops mid-flight, or one that fails, is paid upstream and metered as nothing (`quarry.extract.url` counts `ok` and `fetched` only). Also true of an `ok` prompt-only call billed as a plain fetch. Price and meter the model hop (WS16.S1) before the model lane is granted on a deployed stack.
- INNH-2 | review | RUNBOOKS says "log lines carry lengths only" for the prompt, but `extract_routes` logs nothing about it. Either add a length-only line or reword the sentence. `ExtractRequest` still derives `Debug` with `prompt`, so a future `{:?}` of the request would log the prompt; give it a manual `Debug` that prints the length.
- INNH-2 | review | `sdks/python` and `sdks/typescript` were not regenerated: `ExtractItem` lacks `schema_valid`, `schema_issues` and `truncated_input`, and the generated Python model ignores unknown keys, so SDK users cannot see them. No CI step checks SDK drift against `docs/openapi.yaml`.
- INNH-2 | review | A ZDR org that sends `schema` used to reach the model silently; it now gets a per-source `ZDR_UNAVAILABLE` at HTTP 200. The consumer (Verevon gateway / Innhenting UI) must read the per-item `error`, not only the HTTP status. Worth a line in the gateway contract notice.
- INNH-2 | review | The 501 test asserts keys `{code,error,hint}`; the status file planned `next_actions` too. Not a defect, but the enablement text (INNH-3) will change the envelope; pin the key set there.
- INNH-9 | review | `final: true` is not immutable: `final` follows job status, but a late `page_fetched` after the terminal event is still counted (documented in CONTRACTS), so `used` can rise after `final` is true. Reword the `final` description ("status is terminal; used may still rise for a late page") or have the UI not cache it as settled.
- INNH-9 | review | `extract` is in `creditKinds`, but no orchestrator workflow emits `page_fetched` for an extract job (only scrape, crawl, batch run `runPageWith`), so an extract job would show `used: 0.0, final: true`, the misleading zero the design says it avoids. Drop `extract` until it has events, or prove it emits them.
- INNH-9 | review | Credits count fetched pages only. An AI scrape/extract (INNH-1/2) costs model tokens that this figure does not include, so the Innhenting UI would show a page price for a call that is mostly model cost. Needs the model-hop pricing (WS16.S1) before the number is presented as cost; keep it labelled `estimated` and `basis: pages_fetched`.
- INNH-9 | review | "Team and per-job figures agree" holds only for page-priced kinds within the same period: the team SQL sums `page_fetched` over every job of the org (any kind, `ts >= period start`), while the per-job figure is all-time and nil for search/research/agent. If any of those kinds ever emits `page_fetched`, the two diverge. Worth a conformance test with a mixed-kind org.
- INNH-9 | review | `CountsForJobs` (pg) swallows a query or scan error and returns a partial map, so the list shows `used: 0` (and `final: true` for a terminal job) on a DB error instead of omitting `credits`. Pre-existing for `stats`, but now a money-like figure. Omit `credits` when the counts map has no entry for the job and the job is not new.
- INNH-9 | review | Replay dedupe is in better shape than the status says: the orchestrator's event_id is `evt_` + the first 26 hex of sha256(run:url:page_fetched) and `events.event_id` is the primary key (001_init.sql), so a replayed page_fetched is an ErrConflict, not a double count. The same URL fetched twice in one run counts once. The status file's "UNVERIFIED" can be closed by a pg test; the Postgres SQL (`COUNT(*) * $2::numeric` with a float param) is still unrun (TestPostgres_CreditUsage skips without QUARRY_TEST_DSN).
- INNH-9 | review | The status and CONTRACTS say turning the flag on needs a control image rebuild; it is read from the environment per request, so a container recreate with the env set is enough. Reword so the stack session does not rebuild for nothing. GraphQL (`graphql/schema.rs`) was not given a `credits` mirror; additive, but a GraphQL client of the job type cannot see it.
- INNH-1 | review | The AI phase deadline (45 s) is not taken from what is left of the router's 125 s: with actions on, the run may use up to 115 s and the AI phase then runs past 125 s, so the router answers an empty 408 and the paid model calls are lost. Pass `AiScrapeInput.deadline` as the router start plus about 120 s minus a margin.
- INNH-1 | review | `AiScrapeEngine::call` waits for the per-request and the process semaphore before the `timeout_at` that bounds the model call, so a saturated process limit (16) queues tasks past the 45 s phase deadline until the router's 408. Wrap both acquires in `timeout_at(self.deadline, ..)`.
- INNH-1 | review | A `question` answer that is not grounded (`grounded:false`) is still returned in `data.answer`; only the report says it. A client that reads `answer` and ignores `ai.question.grounded` shows an unverified model sentence as fact. Consider withholding it, or a `require_grounded` option, once the UI copy is known.
- INNH-1 | review | `decode_chat` reads the whole body with `resp.bytes()` before checking the 4 MiB cap, so the cap bounds the decode, not the memory. Read in chunks and stop at the cap.
- INNH-1 | review | `chat_for_org` ignores `org_id` on the static dev path (`let _ = org_id`): every org's AI formats are spent on one dev token and attributed to none. Fine while dev only; the Dynamic path must bind the minted token to the verified org before any shared stack.
- INNH-1 | review | The agent guard is label-based (`initiated_by:"agent"`) and only tightens: a Model-relayed scrape on a user token that does not send the label is served and spends model money outside the run budget. The Innhenting/gateway notice must require the label, and OD-6 should say whether the Model Plane's own principal is refused server-side.
- INNH-1 | review | `sdks/python` and `sdks/typescript` (ScrapeRequest) still document `reserved_format` and the old format list; regeneration is blocked by the unparseable spec (W2 U56). Not a regression, but a client built from them will mis-handle the four AI names.
- INNH-1 | review | No edge test sends a page longer than the input cap, and none sends a `privacy` block; both gaps hid the two blockers in the review (truncated_input never set on the scrape route, privacy classification ignored).
