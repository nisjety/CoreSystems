# INNH depth findings, lane C (not fixed; one line each)

Format: `item | unit | finding`. Wave first, depth later (user order 2026-10-23): none of these is a fix loop.

- INNH-6 | 6a | `quarry_transform::sitemap::parse` does not decode XML entities or CDATA and matches `<url>` / `<loc>` case-sensitively without attributes (`<url foo="x">` is missed); the discovery route decodes entities itself (`crawl_sitemap::xml_unescape`). Moving the decode into the parser would also fix `/v1/map`, which still returns `&amp;` raw. A real XML pull parser (quick-xml) would close the attribute and namespace-prefix cases.
- INNH-6 | 6a | `map_routes::fetch_text` still reads sitemaps lossily as text (no gzip, no `Sitemap:` robots lines, no host check on nested sitemaps); `/v1/map` could call `crawl_sitemap::collect` with a `GuardedFetcher` and share the bounds.
- INNH-6 | 6a | The sitemap read is breadth first and sequential, one fetch at a time (30 s budget, 20 files). A large index of many small files is slower than it needs to be; a bounded `join_all` of the children would cut it. The budget is checked between fetches, so one slow file can overrun it by its 15 s timeout.
- INNH-6 | 6a | Sitemap fetches are not metered and not rate limited per host; a crawl of many sites each with a 20-file sitemap costs 20 unmetered fetches per crawl start. Decide whether one `quarry.map` style unit per discovery should be metered (the brief asks).
- INNH-6 | 6a | `lastmod`, `changefreq` and `priority` are parsed and dropped. A "freshest first" or "changed since" seeding order (and `max_pages` taking the highest priority first instead of document order) is additive.
- INNH-6 | 6a | When the robots gate is absent the route fetches `/robots.txt` itself, with no `Crawl-delay` and no cache; with the gate present a robots.txt that is unreachable under `disallow` makes every sitemap URL robots-denied (correct, but the count lands in `robots_disallowed`, not a separate `robots_unreachable`).
- INNH-6 | 6a | Sitemap URLs are queued at depth 1 and the in-memory frontier is capped at 500; the durable frontier has no cap beyond `max_pages` (clamped to 5000), so a 50k-URL sitemap is cut at the page bound, in document order. The `cap` count says how many were dropped but not which.
- INNH-6 | 6a | `sitemap: only` still fetches the seed (it is the scope's anchor and counts as a page). If the Innhenting UI wants "sitemap pages only, seed excluded unless listed", the workflow can skip the seed when the discovery succeeded; that changes `hosts_added` on a depth-0 redirect, which needs a decision.
- INNH-6 | 6b | `formats` inside `scrape_options` is validated and echoed but does nothing: a crawl page always stores markdown and html, and the crawl results route (INNH-12) will decide what a page result returns. If INNH-12 returns per-page inline content, `formats` should shape it.
- INNH-6 | 6b | The page cache bypass is by cleaning options only. `page_hash` is the URL plus the content fingerprint, not the options, so a cleaned artifact and a default one of the same page share it (they differ by run id). Anything that de-duplicates or looks artifacts up by `page_hash` (INNH-12's per-run results, a change monitor) would conflate them; joining an options hash to `page_hash` for non-default cleaning would keep them apart.
- INNH-6 | 6b | `run_page` re-validates `scrape` on every page (a few hundred microseconds of selector-length checks); the check could be cached per run id. Not measured.
- INNH-6 | 6b | Invalid CSS selectors in `include_tags` / `exclude_tags` are not rejected at the handoff: the shared validators check count and length only, and the cleaner skips a selector it cannot parse (`parse_all`). A caller with a typo gets the default cleaning plus (for include_tags) an `include_tags_matched_nothing` warning that the crawl never surfaces. Validating with `scraper::Selector::parse` at the handoff would close it, for `/v1/scrape` too.
- INNH-6 | 6b | `scrape_options` per-page warnings (`clean_warnings`) are dropped by `run_page`; a crawl whose `include_tags` match nothing stores empty markdown with no signal in the job events.
- INNH-6 | both | No Temporal replay test of a history recorded before the markers: the repo has no recorded history fixture. The GetVersion guard is in place and the no-sitemap path never calls it, but a recorded `CrawlJobWF` history from the live orchestrator, replayed with `worker.NewWorkflowReplayer`, would prove it.
- INNH-6 | both | The gateway (`apps/Frontend Plane/verevonv3/apps/gateway`) normalizes the crawl body (`normalize_crawl`) and must forward `sitemap` and `scrapeOptions` unchanged; until it does the Innhenting UI cannot send them. Owned by the Innhenting session.
