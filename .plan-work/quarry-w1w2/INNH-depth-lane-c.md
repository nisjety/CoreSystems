# INNH depth findings, lane C (not fixed; one line each)

Format: `item | unit | finding`. Wave first, depth later (user order 2026-10-23): none of these is a fix loop.

- INNH-6 | 6a | `quarry_transform::sitemap::parse` does not decode XML entities or CDATA and matches `<url>` / `<loc>` case-sensitively without attributes (`<url foo="x">` is missed); the discovery route decodes entities itself (`crawl_sitemap::xml_unescape`). Moving the decode into the parser would also fix `/v1/map`, which still returns `&amp;` raw. A real XML pull parser (quick-xml) would close the attribute and namespace-prefix cases.
- INNH-6 | 6a | `map_routes::fetch_text` still reads sitemaps lossily as text (no gzip, no `Sitemap:` robots lines, no host check on nested sitemaps); `/v1/map` could call `crawl_sitemap::collect` with a `GuardedFetcher` and share the bounds.
- INNH-6 | 6a | The sitemap read is breadth first and sequential, one fetch at a time (30 s budget, 20 files). A large index of many small files is slower than it needs to be; a bounded `join_all` of the children would cut it. The budget is checked between fetches, so one slow file can overrun it by its 15 s timeout.
- INNH-6 | 6a | Sitemap fetches are not metered and not rate limited per host; a crawl of many sites each with a 20-file sitemap costs 20 unmetered fetches per crawl start. Decide whether one `quarry.map` style unit per discovery should be metered (the brief asks).
- INNH-6 | 6a | `lastmod`, `changefreq` and `priority` are parsed and dropped. A "freshest first" or "changed since" seeding order (and `max_pages` taking the highest priority first instead of document order) is additive.
- INNH-6 | 6a | When the robots gate is absent the route fetches `/robots.txt` itself, with no `Crawl-delay` and no cache; with the gate present a robots.txt that is unreachable under `disallow` makes every sitemap URL robots-denied (correct, but the count lands in `robots_disallowed`, not a separate `robots_unreachable`).
- INNH-6 | 6a | Sitemap URLs are queued at depth 1 and the in-memory frontier is capped at 500; the durable frontier has no cap beyond `max_pages` (clamped to 5000), so a 50k-URL sitemap is cut at the page bound, in document order. The `cap` count says how many were dropped but not which.
- INNH-6 | 6a | `sitemap: only` still fetches the seed (it is the scope's anchor and counts as a page). If the Innhenting UI wants "sitemap pages only, seed excluded unless listed", the workflow can skip the seed when the discovery succeeded; that changes `hosts_added` on a depth-0 redirect, which needs a decision.
- INNH-6 | 6b | `formats` inside `scrape_options` is validated and echoed but does nothing: a crawl page always stores markdown and html, and the crawl results route (INNH-12) will decide what a page result returns. If INNH-12 returns per-page inline content, `formats` should shape it.
- INNH-6 | 6b | The page cache bypass is by cleaning options only. `page_hash` is the URL plus the content fingerprint, not the options, so a cleaned artifact and a default one of the same page share it (they differ by run id). Anything that de-duplicates or looks artifacts up by `page_hash` (INNH-12's per-run results, a change monitor) would conflate them; joining an options hash to `page_hash` for non-default cleaning would keep them apart.
- INNH-6 | 6b | `run_page` re-validates `scrape` on every page (a few hundred microseconds of selector-length checks); the check could be cached per run id. Not measured.
- INNH-6 | 6b | Invalid CSS selectors in `include_tags` / `exclude_tags` are not rejected at the handoff: the shared validators check count and length only, and the cleaner skips a selector it cannot parse (`parse_all`). A caller with a typo gets the default cleaning plus (for include_tags) an `include_tags_matched_nothing` warning that the crawl never surfaces. Validating with `scraper::Selector::parse` at the handoff would close it, for `/v1/scrape` too.
- INNH-6 | 6b | `scrape_options` per-page warnings (`clean_warnings`) are dropped by `run_page`; a crawl whose `include_tags` match nothing stores empty markdown with no signal in the job events.
- INNH-6 | both | No Temporal replay test of a history recorded before the markers: the repo has no recorded history fixture. The GetVersion guard is in place and the no-sitemap path never calls it, but a recorded `CrawlJobWF` history from the live orchestrator, replayed with `worker.NewWorkflowReplayer`, would prove it.
- INNH-6 | both | The gateway (`apps/Frontend Plane/verevonv3/apps/gateway`) normalizes the crawl body (`normalize_crawl`) and must forward `sitemap` and `scrapeOptions` unchanged; until it does the Innhenting UI cannot send them. Owned by the Innhenting session.
- INNH-6 | review | BLOCKER-class docs defect (fix before enabling): `docs/RUNBOOKS.md:2015` says "Edge before orchestrator ... nothing is stamped on its jobs". The edge does stamp `sitemap` and `scrape_options` on the job params (routes.rs crawl_handoff) and echoes them in `data.effective`; an old orchestrator reads only the keys it knows (`CrawlInputFromParams`), so it silently crawls links-only with the default cleaning while the ack claims otherwise. The safe order is orchestrator first (it is inert without the params, and an old edge still refuses the options with 400), then the edge flag. The "new orchestrator against an old edge ends the crawl with sitemap_unavailable" sentence also cannot happen for a new job (the old edge refuses at the handoff); only an in-flight crawl can see it. Reverse step 3 and drop the second clause.
- INNH-6 | review | `run_completed.sitemap.error` and the `run_failed` `sitemap` payload carry `err.Error()` of the activity (workflows/crawl_sitemap.go:148). For a transport failure that text includes the orchestrator's internal edge URL (`Post "http://.../v1/internal/crawl/sitemap": dial tcp ...`) and, for a non-2xx, up to 256 bytes of the edge's response body (errs.Error). Page events already do the same (`error: err.Error()`, workflows.go:262), so this is not new, but these events are customer-visible. Replace with a closed code (`edge_unavailable`, `edge_refused`, `edge_unsupported`) from `errs.CategoryOf`.
- INNH-6 | review | Sitemap file fetch follows redirects through the driver, which re-validates each hop (fetch.rs), but the "final host must be on the crawl's hosts" check (crawl_sitemap.rs, GuardedFetcher::fetch after `fetch_conditional`) runs after the body was read. A sitemap URL on the crawl host that redirects to another public host therefore causes one GET to that host whose body is discarded. Not an internal-network hole (every hop is public-address checked), only an unscoped public GET; a `FetchHints` host allow-list on redirects would close it.
- INNH-6 | review | Sitemap URLs are canonicalised (`canonical_url`) and then scope-normalised, but the seed appears to be enqueued as the caller typed it (read from the code, not run), and `FrontierRequestID` hashes the raw string. A sitemap that lists the seed with a trailing slash, fragment or tracking parameter difference gets a second queue entry, so the seed page is fetched and metered twice. Normalise the seed the same way (or put the normalised seed into the dedup set) before the batch.
- INNH-6 | review | Skew with the scrape flag off on the edge: the page is fetched, metered (`meter_crawl_page`) and, with `ingest: true`, ingested with default cleaning before the workflow sees the missing `scrape_applied` and ends the run (workflows.go scrapeAppliedBy). One billed and ingested page per skewed crawl. A preflight (a `scrape` with an empty `capabilities` probe, or checking the flag at the handoff of an in-flight crawl) would avoid it; only matters when the flag is turned off under a running crawl.
- INNH-6 | review | `scrape_options.formats` is echoed in the wire form `raw_html` (crawl_scrape.rs `wire_name`), while the request enum in `openapi.yaml:6945` is `rawHtml` and the parser also accepts `raw_html` (SUPPORTED_FORMATS) that the enum does not list. `effective.scrape_options` is an untyped object so nothing breaks, but the SPA should not compare the echo to what it sent verbatim. Either echo the camelCase name or add `raw_html` to the enum.
- INNH-6 | review | `max_urls` for the durable queue is `max_pages`, so a sitemap can enqueue `max_pages` URLs on top of the seed; the extra entry is never fetched (the loop stops at `max_pages` visited) but it sits in the queue until the run ends. Use `max_pages - 1` (floor 1) or let the loop drain it; harmless today.
- INNH-6 | review | Unverified on the real driver: the 10 MiB compressed cap relies on `FetchHints.max_body_bytes` with `truncate_at_cap: false`, and the gzip-bomb bound relies on `decode_body` (50 MiB decoded). If the HTTP client also negotiates transport `Content-Encoding: gzip`, the cap may apply to the decoded or the encoded stream; the fixture driver ignores the cap, so no test covers it. Add one test against the static driver with a mock server that streams past the cap.
- INNH-6 | review | Test gaps worth adding later: (a) a Redis-backed `cache_policy` case proving a non-default `scrape` neither reads nor writes the page cache (today only the pure `cache_admissible` decision and the code path are covered); (b) a Temporal replay of a recorded pre-marker `CrawlJobWF` history; (c) a `run_page` test with `scrape` and `zdr: true` to pin that the ZDR inline path keeps its markdown-inline default when the cleaning options change; (d) an end-to-end crawl with `sitemap: only` where the seed redirects to a second host, to pin the depth-1 rule.
- INNH-6 | review | Reviewed and held: both flags default off and read once (`on|1|true`), with a flag off the 400 `unsupported_option` is unchanged and `run_page` ignores `scrape` without echo; ZDR holds (handoff refuses with `claims.effective_zdr`, which includes the token floor, before any option is acted on; the sitemap route stores nothing and 400s a body that sets `zdr`; `run_page` keeps `InlineRequest::default_for(zdr)` and only swaps the clean options); the discovery route needs the runtime token, the `x-quarry-run-sig` org binding over org and seed, and fails closed without a secret; org id is only used for the fetch hints and the robots cache; every sitemap file passes web policy, `heur::check`, security preflight, the DNS public-address guard and the crawl's host list; entries are scope-filtered in enforce mode and robots-checked, and are never fetched by the route; no URL, page content or sitemap content is logged (the route logs counts; the run_page warning is static); `GetVersion` is reached only by a crawl whose params carry `sitemap`, so old histories replay unchanged. Go `workflows` and `activities` packages re-run green on the host.
