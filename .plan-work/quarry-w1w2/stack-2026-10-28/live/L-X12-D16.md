## Depth

1. **The X-12 script cannot prove all bounds on the chromium driver as shipped.** Command: `node scripts/x12-budget-stack-proof.mjs` with `enforcement on`, no `ACTION_JSON`. Seen: 6 of 7 bounds FAIL, every step 502 `no_current_page`. Cause: the default action `{"type":"wait","ms":0}` needs an open page on the chromiumoxide driver (`quarry-browser/src/chromiumoxide.rs:1239-1262`, `current_tab_page`), and a fresh run has none; the script never navigates (`x12-budget-stack-proof.mjs`, `action` default line, `startRun`). With `ACTION_JSON` set to a navigate, the `cost` bound cannot pass: a navigate is priced `0.001 + bytes * 1e-7` (`quarry-runtime/src/action_cost.rs:25`), above the bound the script sets (`max_cost_usd 0.00025`, the "two 0.0001 actions" in the script header), so the first step is 402. A fix is either a navigate before the loop in each `prove*` function (not counted in the bound) or a cost bound that fits the navigate price. I proved the cost bound by hand (X12.5e). The script header says "Everything else is the shipped default", but the stack does need a page-independent action or a first navigate.
2. **The runbook's psql path is wrong.** Runbook 3.1 says `state->>'budget_exhausted' = 'steps'`. The stored key is `state->'budget'->>'exhausted'` (`BudgetCheckpoint.exhausted`, serde name `exhausted`, `quarry-runtime/src/step_receipts.rs:121`; the checkpoint has `budget` as a top-level key). The runbook query returns 0 rows although the latch is stored. Same fix in the runbook text.
3. **The user-facing SSE stream never carries `agent.budget_exhausted`.** `is_user_facing_event` (`quarry-edge/src/agent_routes/live.rs:8-21`) allows only AgentStarted, ActionStarted, ActionCompleted, ActionFailed, ObservationReady, AgentCompleted, AgentExpired and AgentFailed, and `event_name` (`live.rs:42-57`) has no `agent.budget_exhausted` name. The event is emitted by `announce_budget_refusal` (`agent_routes/budget.rs:125-150`) and consumes a seq (the gap at seq 12 in my capture), but the stream drops it, and the durable timeline (`quarry_browser_timeline_events`) holds only `lifecycle` rows. So the plan row "SSE shows exactly one `agent.budget_exhausted`" cannot be met today, and the model (or the app) learns of the exhaustion only from the 402 on the step call. Whether the event should be user-facing is the owner's call; the runbook and the plan row say it should be.
4. **Counter semantics differ by mode.** In `shadow` the would-exhaust counter counts once per run (`take_shadow_report`, `budget.rs:~985`). In `on` it counts every refused call (`budget.rs:~976`; `steps 7` after 3 refused calls on the SSE run and one on each of several others). A rate on the `on` counter is therefore "refused calls", not "runs that ran out". The runbook text ("the would-exhaust count") is right for shadow only.
5. **After a hand-back in shadow, an agent run with a small request cap gets the legacy 429.** In X12.3 the run had `constraints.max_steps 2`, one agent step and four exempt person steps; after the hand-back the next steps were 429. The legacy request cap (`legacy_step_cap_applies`) counts every step of the run, takeover steps included, while the new ledger does not. In `on` the script's `takeover` bound passed (402 steps at the right place) because the ledger bound answers first. Low risk, but the two counters disagree about what a "step" is during a takeover.
6. **A resume of an exhausted run starts a browser before it refuses.** X12.6: the resume start answered 200 with a new lease, and only the first step answered 402. Between the two, one browser slot is held. A start-time check of the latched dimension would save the slot. Low.
7. The `ready` page shows `status:"starting"` for the browser slot right after an edge recreate (`generation 0`) and turns `healthy` after the first run; the container health stays green. Not a finding, noted so the next leg does not read it as a fault.
