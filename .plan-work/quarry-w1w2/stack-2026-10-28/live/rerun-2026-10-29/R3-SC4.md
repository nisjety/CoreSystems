## Depth

1. **A wait right after the RS resume answers 502 `DRIVER_FAILED` `no_current_page`** (R3-SC4-rs-wait-after-resume-body.raw, 0.117 s, `retryable:false`), while the following navigate is 200. The checkpoint URL is `""` (`human_browse.rs:218-226` keeps `""` for about:blank; `lifecycle.rs:198-206` clears a stored about:blank), so the resume does no recovery navigation (`lifecycle.rs:571-597` only runs for a non-empty URL) and the chromium session has no tab until the next `goto` (`quarry-browser/src/chromiumoxide.rs:1271`, "no current page; call goto() first"). This is the known behaviour named in 304d6cb22's message ("A resume from a checkpoint with no URL has, on chromium, no tab until its next navigate"), and it is the same for any run resumed before its first committed page. It is the pre-T4b `no_current_page` 502 again, now only after a resume. Option for the lead: on a resume with an empty URL, commit the tab on about:blank the way the first navigate does (FirstNavigation::ByCaller), or answer a typed, retryable "navigate first" error.
2. **Duplicate receipt step key after a resume when a step failed before the checkpoint.** R3-SC4-rs-receipts.txt: step keys `0 navigate failed TIMEOUT`, `1 wait completed` (02:45:09Z), then after the resume `1 wait failed DRIVER_FAILED` (02:45:50Z), `2 navigate completed`, `3 wait completed`: key 1 is used twice in the same run. The resumed run seeds its step keys from `entry.summary.step` (`lifecycle.rs:716`, `run_live.rs:261-264`), which counts successful steps only (`agent_routes/types.rs:101-114`, `LaneSummary::record`), while the keys before it were reserved for every admitted step including failed ones (`step.rs:155`, `run_live.rs:268-270`). Any run with a failed step before an idle expiry gets this; the T4b-1 case makes it likely (its first step always fails). Not new in bd9e7a3f5 (WS8.H code). A replay or reviewer that keys receipts by `(run_id, step)` sees two different actions under one key. Option: persist the reserved-key high-water mark in the checkpoint (or seed from the run's receipt count) instead of `summary.step`.
3. **A redirect to a host outside the run's list costs the full 25 s and answers TIMEOUT, not SECURITY_BLOCKED.** R3-SC4-s1.log: navigate `http://slow.crawl.test/redir` (302 to fixture-b) 504 after 25.195 / 25.039 s, `TIMEOUT`, `effect:"unknown"` (R3-SC4-s1-redirect-body.raw), receipt `failed TIMEOUT`. The browser's Fetch guard aborts the redirect hop (`chromiumoxide.rs:2062-2072`, `domain_grant_blocked`, `ErrorReason::Aborted`), and the egress receipt does reach the next observation (R3-SC4-s1-redirect-next-egress.json: `block domain_grant_blocked` for fixture-b/ext). But the navigation then never finishes from the driver's view, so the caller waits for the deadline. On a first step this also lands in the T4b-1 state (try 1: next wait 200 url about:blank), which now works. Option: map an aborted main-frame navigation whose last hop was `domain_grant_blocked` to a fast `SECURITY_BLOCKED`. Not a regression (no earlier leg tried an off-list redirect).
4. A page can move itself to exactly `about:blank` (not `about:blank#x`) and the next observation passes as "no page yet" (`human_browse.rs:209-212`). It reaches no host, so this matches the design, but a run's checkpoint then holds `""` and a resume starts with no tab (Depth 1). Seen only by reasoning; S1b used `about:blank#off`, which is refused as designed.
5. The off-policy-landing receipt (S1b) carries `cost_micro_usd 100`, `cost_source flat_table`, the same as a completed wait (RS receipts: completed wait 100, navigate 1000). The action ran, so `failed_step_cost` charges what the driver's telemetry gives (`budget.rs:120-131`; the driver reports no provider cost, so the flat value). As 304d6cb22 intends. Info only.
6. chromiumoxide `WS Invalid message` WARN noise: 19 / 2 / 3 per container, unchanged in kind. Chromium's own background requests to `https://www.google.com/` are blocked by the egress guard (`domain_grant_blocked`) and appear in observations' egress receipts (pre-existing, info).
