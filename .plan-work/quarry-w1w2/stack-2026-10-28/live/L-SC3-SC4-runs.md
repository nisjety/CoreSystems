## Depth

1. **Typed TIMEOUT never appears at the shipped navigate deadline (T1).** The edge answers 502 `DRIVER_FAILED` "Request timed out." at 30.01 s, 4 of 4. Likely cause: `Page::goto` calls `Page::execute`, which builds a `CommandFuture` with the library's fixed 30 s timer (`chromiumoxide-0.9.1/src/handler/commandfuture.rs:51`, `REQUEST_TIMEOUT` = 30_000 at `handler/mod.rs:34`). That timer does not read `BrowserConfig::request_timeout`. Our own deadline for navigate is also 30 s (`quarry-browser/src/deadlines.rs:179`), so the two timers race and the library wins. The comment at `quarry-browser/src/chromiumoxide.rs:888-891` says the 40 s `request_timeout` makes the typed timeout win; it does not for per-command timers. The same race applies to every operation with a deadline of 30 s or more in the table (`Pdf`, `WaitFor`, `DownloadComplete`, if they go through `page.*` calls). A deadline below 30 s (for example navigate 25 s) or a check that maps `CdpError::Timeout` to the typed error would remove the race. Not fixed here. Also: this untyped error carries `details.url` (`chromiumoxide.rs:3815`, `json!({"error": ..., "url": url})`), while the typed TIMEOUT never carries a URL. For a ZDR caller that is a URL in an error body.
2. **The first step after a navigate TIMEOUT is slow and fails (T3).** The next step's observation reads the accessibility snapshot, which times out at its own deadline (5 s at scale 0.5) but the response comes after 15 to 21 s (the response time is longer than the deadline, so a retry or several reads add up: not confirmed). The page is still held by the abandoned navigation in Chromium. The second step after the TIMEOUT works. A caller that retries once gets a clean run, but the plan row "the next step works" is not met for the immediate next step. Evidence: L-SC3-SC4-runs-timeout-default.log (the last line is the `ax_snapshot` body). The unit test `agent_step_timeout.rs` uses a driver double, so it cannot show this.
3. The dry-run sweeper logs one `would_expire` warn per run per sweep (every 5 s in this leg, every 15 s by default). A run that nobody closes in dry run gives 4 lines a minute at default. That is fine for a day of dry run but is noise.
4. After the sweeper expires a run the checkpoint stays `active`, as designed (resume works, S3). My runs left 45 checkpoint rows for org_placeholder since 20:15 UTC, 3 of them `active` (the three expired runs). I cannot delete them (SELECT only).
5. The edge metrics carry what is needed to read this leg without logs: `quarry_agent_run_denied_total{reason}`, `quarry_agent_run_starts_total{class,outcome}` (`started`, `denied`, `resumed`), `quarry_agent_run_expired_total{reason}`. There is no counter for slot relaunches; `/ready` `generation` is the only count.
6. A start with no `initiated_by` label from the dev stub person is class `interactive` (the sweeper log shows `class=interactive`), so it counts against the person sub-cap of 6 per org.
7. Process note: while listing flag names with a wide `grep` I printed one env value that holds a token (`QUARRY_EDGE__RUNTIME_AUTH_TOKEN`) into my own tool output. It is not in any file of this leg. It is a dev-stack internal token; the lead may want to rotate it if this transcript is kept.
