## Depth

1. **Enforce-leg counters do not show the robots refusal of a normal crawl.** In the enforce crawl `/private/secret` was removed from the link list by the scope step (denial code `robots_disallowed` in the run events), so no page decision was made for it. `quarry_robots_decisions_total{mode="enforce",outcome="denied"}` stayed 0 and `allowed` equals the 3 pages fetched. `denied` moved only when a page-level decision ran (the 2 direct `run_page` calls in D2-161). For the soak this means: observe `would_deny` counts the pages that observe let through (2 in the observe leg); enforce-mode link denials are visible only in the run events. Not a FAIL. Same as qv2e.
2. **The orchestrator never sends `prev_fingerprint` on a crawl page.** `services/quarry-orchestrator/internal/activities/activities.go` lines 229 to 239 build the `run_page` body with `url`, `org_id`, `user_id`, `ingest`, `zdr`, `kind` and `crawl` only (the `PrevFingerprint` field at line 401 belongs to a different input type that `RunPage` does not read). So a crawl through the orchestrator cannot read the page cache, and the D2-161 path (`crates/quarry-edge/src/routes.rs` lines 1722 to 1731) is reached only by a caller that sends `prev_fingerprint` to `/v1/internal/run_page`. The check above called the internal route directly. The runbook text "crawl once under observe, flip to enforce, crawl again" cannot show a cache hit through `/v1/crawl`. The fix works; today it guards a path the orchestrator does not use.
3. **The job's `effective.robots` says `respect` while the edge robots mode is `off`.** In the legacy leg the `POST /v1/crawl` answer carries `"robots":"respect"`, but there is no gate (`CRAWL_ROBOTS=off`), no `/robots.txt` was fetched and `/private/secret` was fetched. The field states the job's request, not the edge mode. Likely place: the `effective` object in `crates/quarry-edge/src/routes.rs` and `crawl_policy.rs`.
4. **Observe does not report would-deny per job.** The observe job's record has no would-deny count; the only signal is the edge counter (2 here). The user-facing "N pages blocked by robots.txt" can appear only under enforce.
5. **The `mailto:` link is enqueued and fails in legacy and observe.** Both legs show `pages_failed` 1 and `error_classes: {auth: 1}`: the page `mailto:fixture@fixture-a.crawl.test` goes to `run_page`, gets 403 `SECURITY_BLOCKED` ("disallowed scheme"), and the orchestrator files it as category `auth`. Under enforce the scope step drops it (`not_crawlable`). The `auth` label can mislead.
6. **The two robots.txt attempts on an unreachable host run back to back.** The helper log shows two `GET /robots.txt` 503 one millisecond apart (...575.065 and ...575.066). No backoff, so a short upstream blip fails both. Also `/v1/map` on the same host answered 403 and the counter `{enforce,unreachable}` rose by 1 for the crawl, so the map call either reused the cached verdict or is not counted (helper log shows no third request).
7. **Fixture host aliasing.** `docs.fixture-a.crawl.test` is the same container as `fixture-a.crawl.test`, so under observe and legacy the crawl fetches every page twice (8 fixture-a fetches). The script's checks (at least one, or zero) still hold.
8. **The script reads `docker logs --since` windows and does not clear the nginx logs.** I restarted the fixtures before each main leg, so this did not change any count. The unreachable and redirect helper logs hold my own pre-check requests (one 503, one 302) from before the script start; the script's `--since` window excluded them (counts 2 and 1 are the crawl's own).
9. **Edge boot ERROR on live.** After every edge recreation the log has one `async_nats::connector` line "authorization violation" (the Data Plane NATS refuses the edge; the page-image producer is disabled). It is the same finding as P0-live Depth 3 and is not caused by this leg. No other ERROR lines in the final container's log (1 line in all).
10. **Earlier edge logs are gone.** Each recreation replaces the container, so the edge logs of the earlier legs were not read. Not checked.
11. **Possible data left on live by this leg:** 5 crawl jobs and 2 `run_page` runs for `org_placeholder` (all completed), page cache entries for the two fixture pages (TTL 300 s), and robots cache entries in the edge memory (lost at recreation). No row was changed or deleted by hand.
