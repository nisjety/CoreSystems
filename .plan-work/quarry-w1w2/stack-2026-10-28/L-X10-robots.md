## Depth

1. **The enforce-leg counters do not show the robots refusal of a normal crawl.** In the enforce crawl `/private/secret` was removed from the link list by the scope step (denial code `robots_disallowed`, `links_denied` 4, `pages_blocked_robots` 0), so no page decision was made for it. `quarry_robots_decisions_total{mode="enforce",outcome="denied"}` stayed 0 and `allowed` equals the 3 pages fetched. `denied` moved only when a page-level decision ran: the D2-161 direct `run_page` calls (2) and the unreachable and redirect hosts (`unreachable`). For the soak (section 3.3) this means: the observe-mode `would_deny` counts page fetches that observe let through (2 in the observe leg), and the enforce-mode link denials are visible only in the job's crawl report, not in the counter. The soak go criterion reads `would_deny` and `would_unreachable` in observe, which does work. Not a FAIL; worth knowing when reading enforce dashboards.
2. **The orchestrator never sends `prev_fingerprint` on a crawl page.** `services/quarry-orchestrator/internal/activities/activities.go` lines 230 to 239 build the `run_page` body with `url`, `org_id`, `user_id`, `ingest`, `zdr`, `kind` and `crawl` only. So a crawl through the orchestrator cannot read the page cache, and the D2-161 path (`crates/quarry-edge/src/routes.rs` line 1723) is reached only by a caller that sends `prev_fingerprint` to `/v1/internal/run_page`. The D2-161 check above therefore called the internal route directly. The fix is correct and works; today it guards a path the orchestrator does not use. Runbook text "crawl the fixture once under observe (fills the page cache), then crawl again" cannot show a cache hit through `/v1/crawl`.
3. **The job's `effective.robots` says `respect` while the edge robots mode is `off`.** In the legacy leg the `POST /v1/crawl` answer and the control job both carry `"robots":"respect"`, but the edge gate does not exist (`CRAWL_ROBOTS=off`), no `/robots.txt` was fetched and `/private/secret` was fetched. The field states the job's request, not the edge mode. A reader of the job record can think robots was applied. Likely place: the handoff stamp in `crates/quarry-edge/src/routes.rs` (the `effective` object) and `crawl_policy.rs`.
4. **Observe does not report would-deny per job.** The observe job's `run_completed` payload has `pages_blocked_robots` 0 and no would-deny count; the only signal is the edge counter (2 here). The user-facing "N pages blocked by robots.txt" can therefore appear only under enforce.
5. **The `mailto:` link is enqueued and fails in legacy and observe.** Both legs show `pages_failed` 1, `error_classes: {auth: 1}`: the page `mailto:fixture@fixture-a.crawl.test` goes to `run_page` and gets 403 `SECURITY_BLOCKED` "disallowed scheme: mailto", which the orchestrator files as category `auth`. Under enforce the scope step drops it (`not_crawlable`). Observe leaves the link in on purpose, but the failed page and the `auth` label can mislead (it is not an authentication fault).
6. **The two robots.txt attempts on an unreachable host run back to back.** In the unreachable leg the helper log shows two `GET /robots.txt` 503 at msec ...068.796 and ...068.797, one millisecond apart. The check wants exactly 2 and passes. There is no backoff between the attempts, so a short upstream blip fails both. Also, `/v1/map` on the same host answered 403 without a third robots.txt request, and the counter `{enforce,unreachable}` rose by 1 for the crawl, so the map decision either reused the cached verdict or is not counted.
7. **First D2-161 attempt was void.** I ran `d2161.sh` with `MSYS_NO_PATHCONV=1` exported. `qv2e.sh restart-edge` then got an empty `QV2E_REV` and the compose call failed, so the edge stayed in `enforce`; every call in that attempt ran under enforce and `/private/secret` was refused even in the "observe" step. Log kept as `x10/L-X10-robots-d2161-attempt1-no-restart.log`. The two flag edits at 17:05:52Z and 17:06:05Z in `flags-log.md` are file edits only (a note is in that file). I fixed my helper so `restart_edge` fails when the running flags differ from the file, and repeated the check; the valid run is the log without a suffix. No stack harm: only flags and an edge restart.
8. **Fixture host aliasing.** `docs.fixture-a.crawl.test` is the same container as `fixture-a.crawl.test`, so under observe the crawl fetches every page twice (8 fixture-a fetches) and the fixture log cannot tell the two host names apart. The script's counts still hold (they test for at least one or zero).
9. **The script prints `docker logs --since` windows only.** It does not clear the nginx logs. A rerun inside the same second of a previous leg could overlap; I restarted the fixtures before the three main legs, so this did not affect the counts.
10. Edge ERROR lines were not counted: each edge restart replaced the container, so the logs of the earlier legs are gone. Not checked.
