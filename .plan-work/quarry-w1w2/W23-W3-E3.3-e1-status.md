## Gap check

- No element rect type existed in quarry-core. `CssRect` (quarry-browser `sensitive_rects.rs`, `x, y, w, h`) is the browser crate's own shape, and quarry-core does not depend on quarry-browser, so it was not reused. `ClipRect` (quarry-core `capture.rs`) is a request-level input type with `deny_unknown_fields`, so it was not reused for an output field.
- No CDP box-model call exists in Quarry: a search for `getBoxModel` and `box_model` finds nothing. The only geometry call is `DOM.getContentQuads` in `quarry-browser/src/actionability.rs` (`content_quads`, private), used at click time.
- Timing: `ActionStarted` is emitted in `observation.rs` before the driver's verified-target probe (`act_on_verified_target`) runs, so a rect taken from that probe would arrive after the event. A rect needs its own read before the emit.
- The `native_target` (`backend_node_id`) that such a read would key on is already resolved at the emit point, in `verified_target_action`. Nothing else in the path carries geometry.

## Assumed decisions

1. Field names are `x, y, width, height`, as `ClipRect` in quarry-core, so the core contract has one rect shape. The browser crate's internal `x, y, w, h` is not exposed.
2. Coordinates are CSS pixels, viewport-relative as CDP reports them. Off-screen values are kept, not clamped; the client decides what to show.
3. A rotated box gives the axis-aligned bounds of its corners. A malformed quad (not eight finite numbers) or a zero-area box gives `None`: nothing to highlight.
4. `rect` is omitted when absent, so an event without a box has the same JSON as before. A payload written before this field reads back with `rect: None`.
5. ZDR: the emit still goes through `emit_for_zdr`, so ZDR runs stay on the ephemeral route with no new branch. The rect is geometry only: no text, selector, value or URL. `zdr_matrix.rs` has no `action.started` row, so no ZDR rule needed changing.
6. The payload is a typed struct in `event.rs` (the queue names event.rs for the payload), not a new field on the `Event` envelope.
7. For the producer, a highlight should use the `border` quad (what the user sees) rather than `content`. This is a recommendation for ask 1; nothing reads it yet.

## Asks for follow-up units (outside this unit's files)

1. Producer (blocks any rect). In `quarry-browser/src/lib.rs`, add `async fn target_box(&self, session: &BrowserSession, target: &BrowserNativeTarget) -> QuarryResult<Option<ElementRect>>` to `BrowserDriver`, default `Ok(None)`. In `chromiumoxide.rs`, implement it with `DOM.getBoxModel` keyed by `backend_node_id`: read-only, no scroll, no focus. Take the `border` quad and call `ElementRect::from_content_quad`; any error gives `Ok(None)`. Then in `observation.rs`, before the emit, read the box from the `native_target` of `verified_target_action` (an `Option<BrowserNativeTarget>`) and set `rect` in place of the current `rect: None`. Gate it with a flag that defaults off. Lane a owns `chromiumoxide.rs` (sole writer for E3.3-h and E3.3-k), so coordinate the edit or give it a lane-a unit.
2. Frames. For a target owned by a child frame (`frame_id` set), confirm whether `DOM.getBoxModel` quads are relative to the main viewport before shipping. Until that is confirmed, return `None` for frame-owned targets.
3. Docs. `docs/CONTRACTS.md`, `docs/openapi.yaml` and the SDK's AgentApi event list do not yet name an optional `rect` on `action.started`. A docs unit should add it when the producer is on.
4. Presentation consumer (SPA). The gateway's `browser.rs` has no `action.started` field mapping (its only match is a test mock), and `browser-client.ts` types `payload` as `Record<string, unknown>`. The rect will reach the page untyped. The consumer should type it, clamp it to the viewport, and treat it as page-derived geometry: draw a highlight only, never act on it.
5. Queue row. `W23-FINISH-QUEUE.md` E3.3-e1 lists three files, but a rect needs `quarry-browser/src/lib.rs` and `chromiumoxide.rs` as well. Split a producer unit in lane a, or widen this row.
