## Assumed decisions

1. Scope kept to the two named files. No CSS, no barrel, no tests. The variant reuses the generic card's classes. A dedicated origin row style would need a CSS unit (depth row).
2. Approve is withheld, and reject stays, when: the page origin cannot be read; the page is not https (the E3.1-c https precondition); the frame origin is missing or differs from the page origin (the frame-equality precondition); the provider is not one the card names.
3. Fail closed only on an empty approval id (the model is null). Other gaps are shown with their reason, so the person can still reject.
4. Origins are shown as `scheme://host[:port]`. Path, query, fragment and user info are dropped, so a token in a query string never reaches the card.
5. Account label: trimmed, capped at 64 characters, and dropped when it contains `@`, so the card never shows an address.
6. Providers: `google` and `microsoft` (integration-core keys) and the short forms `gmail` and `outlook`, named Gmail and Outlook. Brand names are not translated.
7. "I will type it myself" maps to the chrome's takeover (`onTakeOver`, control mode `human_takeover`), not to an approval decision. The card sends no decision. Whether the pending approval stays open or is rejected on takeover is open (MP ask).
8. Approve covers one fill. The copy says so and the button says "once". Single-use enforcement stays with Quarry and the broker (E3.1-ab, E3.1-h), not with the card.
9. `fill_otp` and `fill_otp_ref` both count as an OTP fill: the sensitive action and the proposal's wire tag, as MP-ASKS W3-E3.1-ab uses them.
10. Norwegian and English copy through `i18n.tr`.
