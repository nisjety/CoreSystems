## 0. Question

How does Quarry (quarry-edge, Ingestion Plane) call integration-corev2 (IC) for one-time-code reads (`mail.otp.read`, executor-only), so that:

- the model never sees the code (no value on the wire to the model, in receipts, logs or artifacts);
- each OTP use is approved by the user for one origin, one frame and one mail connection;
- Quarry has its own identity toward IC, not the shared IC key;
- the call stays inside IC's actions surface (CLAUDE.md: provider actions go through integration-corev2's actions surface).

The memo also records the open ADR-2 sub-split (2a before the IC action ships, 2b before E5 only) and the R-13 registry row the identity choice needs.

## 2. Facts checked at HEAD (for the decision)

Checked by reading the files in this worktree on 2026-10-23.

- **IC has no OTP action yet.** `apps/Ingestion Plane/integration-corev2/internal/actions/` holds `mail_read.go`, `calendar_read.go`, `drive_read.go`, `service.go` and tests. A grep for `otp` in that directory returns nothing. The `mail.otp.read` operation in the epic is new.
- **IC internal routes use one shared key.** `apps/Ingestion Plane/integration-corev2/internal/api/server.go` (about 170-176) builds `internalAuth` from `cfg.Config.InternalAPIKey` (`auth.InternalOnly`). A second per-caller key already exists for one route: `codexSubscriptionModelPlaneAuth` (about 176-179, env `CODEX_SUBSCRIPTION_MODEL_PLANE_API_KEY`). This is the only per-caller key pattern in IC.
- **Bearer-protected routes refuse the shared key outside dev.** `apps/Ingestion Plane/integration-corev2/internal/auth/middleware.go` `InternalOrBearer` (line 167): a matching internal key is refused with 403 `scoped_service_token_required` unless `AllowLegacyTenantKey` is set. That flag (`internal/config/config.go` 280) needs `ALLOW_LEGACY_TENANT_KEY=1`, `ALLOW_INSECURE_DEV_DEFAULTS=1` and `ISOLATED_E2E=1` together. So a Quarry call that uses the shared key to reach an action route would fail in production. The shared key is the wrong credential for the action surface anyway.
- **IC verifies bearer tokens for one audience.** `internal/controlplane/clients.go` `NewAuthClient` (106-111) sets the expected audience from `INGESTION_AUTH_AUDIENCE`, default `ingestion` (`internal/config/config.go` 288). `VerifyToken` checks JWKS signature, issuer and that audience (`parseToken`, 219).
- **`ingestion` is already a known auth-core audience.** `apps/Control Plane/auth-core/src/auth/convex-token.service.ts` lists `'ingestion'` in the audience union (93) and mints it with `audience: INGESTION_AUTH_AUDIENCE || 'ingestion'`, TTL 300 s (about 371-374). `plane-token-scopes.ts` also lists it (23). No new auth-core audience is needed for option C below.
- **There is no `integration-core` audience.** The epic and the audit say "a distinct identity or manifest row toward IC". Neither names an audience. None exists in `plane-service-principals.json`, so the name must be chosen from `ingestion`, as in option C.
- **Quarry's principal row.** `apps/Control Plane/config/plane-service-principals.json` `quarry-edge` (line 380): audiences `browser-broker`, `data-plane`; `retentionByAudience` `browser-broker: zdr`, `data-plane: persistent`; top-level `scopes` equal the union of `scopesByAudience`. Per the A2a design note (section 0), the parser requires that equality, and an audience the Quarry Rust side does not know makes the whole manifest fail to parse.
- **Quarry's Rust audience enum.** `apps/Ingestion Plane/Quarry-v2/crates/quarry-runtime/src/service_tokens.rs` 40-46 has three variants (`DataPlane`, `ModelPlane`, `BrowserBroker`). `from_registry_audience` (68-72) is the only mapping from a registry audience name. A registry or manifest row naming any other audience fails (210-218, 233). So a manifest row for `ingestion` needs a Rust variant in the same commit (the same lesson as A2a section 0).
- **Sensitive-action allow-list.** `apps/Model Plane/go/services/browser-broker/internal/grant/grant.go` lines 101-105: `respond_dialog`, `upload_ref`, `download_ref`. Line numbers in the epic (32-36) are stale. `fill_otp` is not there yet.
- **Quarry agent routes are split.** `apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes/` is now a directory (`admission.rs`, `lifecycle.rs`, `sensitive_approval.rs` with `sensitive_approval_for_action` at line 12, and `used_sensitive_approval_grants` read at `admission.rs:415`). The epic's single-file path `agent_routes.rs` is stale.
- **Lease list excludes Quarry.** `INTEGRATION_TOKEN_LEASE_CONSUMERS` default (`config.go`, about 347) does not contain Quarry. Keep it that way: the lease list hands out raw provider tokens, which the OTP read must never do.

Not verified in this unit: whether IC's action dispatcher checks a token scope for each operation (`Principal.HasScope` exists at middleware.go:61, but the call sites for actions were not read); the exact mint route for audience `ingestion` on auth-core (the generic `:audience/internal-token` controller is assumed, not read); whether `ingestion` tokens minted for quarry-edge would carry `zdr:true` as the registry row says. All three are first-slice checks (E3.1-g).

## 3. Decision 1: how Quarry authenticates to IC

| Option | What it is | Verdict |
|---|---|---|
| A. Shared IC internal key | Quarry holds `InternalAPIKey` and calls an internal route | **Rejected.** One key for every internal route and every caller; no per-caller identity; refused by the bearer-or-key routes outside dev (section 2). The audit calls this out (server.go:170-173). |
| B. Per-caller static key on a dedicated IC route | New `auth.InternalOnly` block with its own key, like `codexSubscriptionModelPlaneAuth`; a compose-held secret; the R-13 static-credentials PR (PR 2) | **Fallback only.** No auth-core change and no Rust variant, and it matches four existing static credentials. But a static key is not org-bound or short-lived, and it puts a provider read on a dedicated route, which conflicts with the rule that provider actions go through the actions surface. |
| C. Plane token for principal `quarry-edge`, audience `ingestion`, narrow scope | auth-core mints a 300 s bearer token for quarry-edge (org-bound, retention `zdr`); IC verifies it with its existing `AuthClient`; a new scope `integration:otp:read` is checked on `mail.otp.read` only | **Recommended.** Matches R-13's rule that per-org manifest-minted tokens are used where the consumer can verify them (WS1, WS16). IC's verifier and auth-core's audience already exist, so no new audience. The change is in the Control Plane registry, the manifest, one Rust variant, and one IC action. |
| D. Relay through Model Plane (model-gateway or a mail bridge) | Model Plane fetches the code and passes it to Quarry | **Rejected on principle.** The model must never receive the code, and CLAUDE.md puts the model in the proposing role. |

**Recommendation: option C.** Scope `integration:otp:read` is new and narrow; it is not `integration:read` (which would let Quarry read every connector) and it is not `org:...`. IC must enforce it on `mail.otp.read` (E3.1-g). If the first IC slice finds that the actions surface cannot check a per-operation scope, the fallback is option B, and this memo must be revisited before the IC action ships.

Consequences of C that the owner must accept:

- Control Plane edits: the quarry-edge registry row (section 6, A), the vendored manifest and auth-core fixture with `.sha256` pins (section 6, B). Rust: one `ServiceTokenAudience` variant for `ingestion`, and its test pins. These are the R-13 PR 1 and the Quarry lane, in one commit as A2a did.
- IC: no change to its verifier. One new operation `mail.otp.read` (E3.1-g) with the scope check.
- Quarry may also use the `ingestion` audience for other future IC calls. Keep the scope list minimal so that the first grant is OTP-only.

## 4. Decision 2: approval for each OTP use

Recommended, and covered by the approved ADR-2 text ("every OTP read approved and shown with origin and connection"):

- One approval per OTP fill. It is a `fill_otp` sensitive action added to `allowedSensitiveActions` (grant.go 101-105) and to `sensitive_approval_for_action` in `quarry-edge/src/agent_routes/sensitive_approval.rs`, with a single-use child grant of the run grant (E3.1-a and E3.1-d).
- The approval names the origin, the frame origin, the mail connection (provider and account label, never the address) and offers "I will type it myself". Approval is bound to those three values; a different origin, frame or connection means a new approval.
- Single use. The used-approval set (`used_sensitive_approval_grants`, admission.rs 415) is process-local. A restart clears it, so a replayed approval after restart is a known gap. The epic accepts this for the first slice; a durable set is a later decision and is recorded as a depth item, not built here.
- No scope above "once" for sensitive actions (plan B7 override, E3.2).
- Preconditions, as the epic lists them: https only; frame origin equal to top origin; exactly one visible required non-password input; no options and no QR; insert through trusted input; afterwards the loader id is marked credential-delivered so AX, DOM and screenshot reads are denied until navigation.
- ZDR: receipts keep a boolean only (`[redacted:otp]`); no value in observations, logs or artifacts. Non-ZDR receipts store typed text today (`step_receipts.rs` 185-200), so WS12 S3 must merge first.

## 5. Decision 3: the 2a/2b split (proposed, not ratified)

- **2a (before the IC action ships).** Option C for the identity (section 3) and the per-use approval rule (section 4). Also the Control Plane registry row (section 6) and the R-13 PR 1 entry for it.
- **2b (before E5 only).** User-secret custody owner: extend IC's at-rest vault (`internal/crypto/vault.go`, AES-GCM for provider tokens) or a Control Plane secret service. Not decided here. E5 (`secret://` references, password fill) is not scheduled.

Why the split: 2a is needed for OTP, which is in scope now. 2b is needed only when passwords or stored secrets are added. Splitting keeps OTP from waiting on the custody decision. The epic recommends it; the plan's ADR-2 row does not name it.

**Not ratified.** The split, the identity option, the scope name, the retention posture and the R-13 row are proposals. The user should ratify 2a explicitly in chat. Until then E3.1-g (the IC action) and E3.1-h do not start, and no Control Plane row is merged.
