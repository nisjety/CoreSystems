## The gap
No issuance path for a non-interactive caller. A design must decide, in order (Quarry's code is the smallest part):
- D1 How an API key becomes a principal Quarry understands. (a) auth-core exchanges a verified API key for a short-lived quarry-aud user-shaped JWT bound to the key's owner user and org (new exchange route; scopes from key metadata, default none); (b) a registered service (the Verevon gateway) presents the key, verifies it with auth-core and mints via the existing token-exchange path (acting_user_id = key owner), so Quarry sees a service principal with browser:execute. (b) reuses an audited mechanism but hits the known gap that a service principal is not bound to the grant's owner (start_run_grants.rs:397); the design must close that gap (bind grant.owner_id to acting_user_id) before any key-driven run.
- D2 What a grant for an API key is. Recommended: an ordinary broker SESSION grant (mode allowlist, never human_browse, never open web) owned by the key's owner user, with a hard host allow-list at issue time, TTL at broker default or shorter, mandatory budget claim (WS6.E: micro-USD, max steps, max runtime), ZDR inherited from org and key, max-active-per-key (not just per owner), revocable by revoking the key.
- D3 Who issues. BrowserBroker is the only issuer. A new door is needed because model-gateway's require_user refuses services and the broker refuses services without browser:write. Either the gateway issues on behalf of the key owner with a delegated browser bearer (needs a minted user-shaped browser-broker token for the key owner, i.e. the D1 exchange), or a dedicated broker method AcquireKeyGrant that records key_id on the grant. The second is cleaner for audit and revocation.
- D4 Key-to-grant binding: key_id on the grant row so revoking a key revokes its live grants, and the ValidateGrant response returns it (Quarry could then reject a grant whose key is revoked on every step, as it already revalidates each step).
- D5 Quarry changes (small, additive, dark): accept a `key_id` / `auth_method` claim in Claims (serde default so existing tokens are unaffected) and log/audit it; require a grant for API-key principals even outside production; reject human_browse grants for API-key principals; apply per-key run caps (run_limits.rs supports per-org classes); enforce initiated_by agent semantics; exact 403 reasons; document in openapi + CONTRACTS.
- D6 Audit: every issue, renew, revoke, deny and run start is an audit event carrying key_id, org, owner, ZDR and host list (hosts omitted under ZDR, as browser_grants.rs already does).
- D7 Owner decisions: (1) D1a vs D1b; (2) may a key hold any browser capability or only scopes it was created with (recommend explicit scope `browser:agent` on the key, default off); (3) is open-web ever allowed for a key (recommend NO); (4) max TTL and absolute cap for key grants; (5) per-key budget ceiling and who sets it; (6) whether ZDR orgs may use keys (recommend yes: grant and runs are ephemeral); (7) org-keys vs user-keys: whose identity owns the run and the profile; (8) rate limit and concurrency per key.

## Risks
SECURITY (highest-risk item of the list):
- A leaked API key must not become an open browser. Worst case today if a key could mint a run on a non-production edge: grants are optional there (grant_boot.rs Noop), so a run starts with caller-supplied allowed_domains. The design must require a grant for key principals in every environment; the broker's host policy (StaticPolicy: internal names, deny suffixes, max domains) is the only host authority.
- SSRF and internal reach: a key-driven browser can be pointed at internal or metadata hosts. Egress broker and web policy apply, but the grant host list must be policy-checked at issue time and the run must stay on the egress-guarded path (browser_egress_boundary tests).
- Credential and session theft: persisted profiles (persist_profile, profile_id) let a run reuse a person's cookies. A key principal must not attach to a user's persistent profile or take over an interactive session; attach/takeover routes and /v1/profiles are user-only (profile_guard.rs); keep them refused for keys.
- Owner binding gap (start_run_grants.rs:397): under D1b a service can start a run under ANY grant in its org. Closing it is a precondition.
- Blast radius of an org-key: references organization, so whose identity owns the run? A per-org key would let any key holder use every grant in the org unless the grant carries key_id.
- Revocation latency: grants live up to the broker TTL. Quarry revalidates every step, so revoking the grant or key stops the run within one step, but only if the broker deletes or marks key grants on key revocation (D4).
- Cost: browser minutes, model tokens and proxy egress. Mandatory budget claim, per-key caps, rate limits, plan cap path (org_plan_cap). Abuse of free-tier keys is a real vector.
- ZDR: a ZDR grant may only back a ZDR run (lifecycle.rs:337); keys in ZDR orgs produce ephemeral runs only, no checkpoint, no resume, no durable receipts beyond metadata tombstones, host list omitted from responses and logs.
- Audit: grant issue/deny/revoke are durable audit events with key id and never log the key, the host list under ZDR, or tokens.
- Cross-tenant: org comes only from the verified token (Quarry and broker both enforce); the exchange must refuse an orgId different from the key's reference.

## Design (2026-10-31)
`INNH-10-design.md` resolves D1-D7 as recommendations: a new auth-core principal type `api_key` (sub `apikey:<key_id>`, `acting_user_id` = key owner, scope `browser:agent`, TTL at most 120 s) minted only through a gateway-only exchange; BrowserBroker stays the only grant issuer (key grant = allow-list session grant stamped with key_id, mandatory budget, 600-900 s, no renew); the Verevon gateway composes exchange, grant and run. Quarry side: U1 principal + route fence, U2 start-run binding, U3 per-step and per-key rules, U4 docs + ZDR matrix row. Asks: CP-1..CP-4 (auth-core), MP-1..MP-3 (broker, model-gateway), GW-1..GW-2 (gateway). Owner decisions: section 13 of the design note.
