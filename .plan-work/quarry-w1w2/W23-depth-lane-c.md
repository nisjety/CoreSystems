# W23 depth findings, lane C (not fixed; one line each)

Format: `unit | finding`. Wave first, depth later.

- W2-U30-33a | `include_answer` on `POST /v1/search` (`search_routes.rs` ~894) calls the ungated `AnswerPipeline::answer`, so its page fetches skip the web policy. `answer_routes::url_gate` (make it `pub(crate)`) plus `answer_gated` closes it; the search route already holds a policy `decision`. Outside this unit's file scope.
- W2-U30-33a | The Data Plane / local-index search tiers return result URLs with chunk text as the snippet. A policy-denied URL from those tiers is skipped like a web one (no snippet fallback), which also hides the chunk; whether a private-corpus hit should be gated by a web-domain rule at all is a product decision.
- W2-U30-33a | `gate_url` counts a denial per URL per request (`record_denial`), so a query whose top-K are mostly denied hosts bumps the denial counter K times; a per-request aggregate (like `gate_urls`' `denied_count`) would be quieter.
- W2-U30-33a | The streaming answer cache key is org + query only (`answer:stream:v1`); it does not include the policy decision, so an answer cached under a permissive policy is replayed after the org tightens its policy. Same shape as the scrape cache's `is_default` rule; either key the entry by a policy fingerprint or skip the cache when the decision is not the default.
- W2-U30-33a | The RunPolicy `policy_fp` is not computed on the answer routes at all; "policy_fp unchanged" holds trivially. If answers should be reproducible per policy, the response could echo a fingerprint.
- W2-U30-33a | security review | FIXED in this lane (not depth): `include_answer` on `POST /v1/search` now passes the same URL gate (`answer_routes::gate_for`), and the stream answer cache plus an include_answer search-cache entry are read/written only when the decision `is_default`; the two earlier rows on these gaps are closed by it.
- W2-U30-33a | security review | `SimpleHttpMarkdownFetcher` uses a default reqwest client: it follows up to 10 redirects and has no private-address/SSRF guard, and the gate checks only the requested URL. An allowed host that redirects to a denied host (or a search result pointing at a link-local/metadata address) is fetched. The scrape family has a final-URL recheck behind an operator flag; the answer fetcher has none. Pre-existing.
- W2-U30-33a | security review | `WebPolicy::check_url` maps an unparsable URL to host "", which passes a deny-only policy (only an autonomous allow list refuses it). Not exploitable through the answer gate (the fetch fails too), but the gate is not fail-closed on a parse failure.
- W2-U30-33a | security review | The dev bypass hands ANY failed-verification bearer the `org_placeholder` stub; the start-up refusal matches only env `prod`/`production`, so a staging deployment with the bypass on is still open (now with no scopes). Pre-existing.
- W2-U30-33a | security review | Results-only `POST /v1/search` (and `include_answer` citations) still list a denied host's URL, title and provider snippet: the gate stops the page fetch and the model hop, not the search listing. Product decision whether a deny rule should also filter the listing.
- W2-U28a | `control-ack` (`POST /v1/internal/jobs/{id}/control-ack`) names no org, so a holder of the control-internal secret can raise `applied_seq` of any org's job. Lower risk than finalize (it only suppresses a pending pause/resume/cancel), but the same `org_id` check would close it; the orchestrator already has `j.OrgID` at both call sites.
- W2-U28a | `claim`, `running` and `pending-control` return every org's jobs by design, so the control-internal secret is an all-orgs credential. It is held by the orchestrator only; a per-route principal (or an mTLS identity) rather than a shared HMAC would be the next step if the orchestrator's blast radius matters.
- W2-U28a | `docs/CROSS_PLANE_AUTH.md` (the secret table), `docs/ARCHITECTURE.md` line 46 and `docs/RUNBOOKS.md` still describe one `QUARRY_INTERNAL_SECRET` for control; they need the two-secret table and the rollout order from the U28a status file.
- W2-U28a | `deploy/compose/docker-compose.yml` (the older Quarry-v2 compose) passes only `QUARRY_INTERNAL_SECRET` to control and the orchestrator; it runs on the fallback. Add `QUARRY_CONTROL_INTERNAL_SECRET` there when the soak ends.
- W2-U28a | Pre-existing node failures at the lane base: `/v1/audit/page` (POST, `routes.rs:262`, `audit_page::capture`) is in neither `openapi.yaml`, `openapi-internal.yaml` nor `scripts/openapi-route-allowlist.json`; and three stale ignored generated SDK files (`sdks/typescript/src/apis/InternalApi.ts`, `models/InternalRunPage.ts`, `models/InternalRunPageResult.ts`) sit on disk and trip the SDK guard.
- W2-U28a | `QUARRY_INTERNAL_HMAC_REQUIRED` is one mode for both groups. The orchestrator-only group could be enforced (require=true) while the edge group stays in rollout mode; today they move together.
- W2-U28a | The orchestrator warns through `controlauth`'s package-level `sync.Once`, so it warns once per process, not per Manager. Fine for the soak; a startup check in `main.go` would be tidier.
