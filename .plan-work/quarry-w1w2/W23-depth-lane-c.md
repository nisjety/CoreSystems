- W2-U30-33a | `include_answer` on `POST /v1/search` (`search_routes.rs` ~894) calls the ungated `AnswerPipeline::answer`, so its page fetches skip the web policy. `answer_routes::url_gate` (make it `pub(crate)`) plus `answer_gated` closes it; the search route already holds a policy `decision`. - W2-U30-33a | The Data Plane / local-index search tiers return result URLs with chunk text as the snippet. Same shape as the scrape cache's `is_default` rule; either key the entry by a policy fingerprint or skip the cache when the decision is not the default.

- W2-U42 | security review | No blocker. The new span carries only `method`, `request_id` (inbound `X-Request-Id` is already filtered to 1-128 bytes of `[A-Za-z0-9._:-]`) and `status_code`; no URL, query, header, body or org id. `MarkZDR` on both call sites reaches the `ZdrSpan` span through the chi group context, and the zdr attribute makes `zdrProcessor.OnEnd` drop it. With `OTEL_EXPORTER_OTLP_ENDPOINT` unset or `QUARRY_TELEMETRY_EXPORT=off` the global provider is the no-op one, so the default state exports nothing (fail closed). `go test ./internal/httpx -run ZdrSpan` re-run: ok.
- W2-U42 | security review | `ZdrSpan` sits outside `SplitHMAC`, so it extracts an inbound `traceparent` (and, under `Init`'s composite propagator, `baggage`) before authentication. An unsigned caller can pick its trace id and the sampled flag: sampled=00 suppresses its own span, and reusing a trace id that another request flagged ZDR drops that caller's spans. Neither leaks data (the span holds no content) and nothing in quarry-control injects baggage outbound today, so it is not a relay. Fix if telemetry integrity matters: adopt the inbound context only after HMAC verification (or only from the orchestrator/edge principals), and drop baggage extraction in this middleware.
- W2-U42 | security review | The span name and the `method` attribute are the raw `r.Method`. Go accepts any token as a method, so a caller can put an arbitrary (token-charset) string of any length into an exported span name, and `redactingExporter` filters attribute keys only, never the span name. Not a ZDR or cross-org leak (the caller supplies it), but it is unbounded cardinality in the collector. Fix: map methods outside the standard set to `OTHER` before naming the span.
- W2-U42 | security review | ZDR is not signalled across processes. The Go registry is per process and the Rust edge's registry is its own; neither puts a zdr mark in `tracestate`. A trace that an upstream flagged ZDR after its span started (so the outgoing traceparent still says sampled=01) gets a quarry-control span exported unless control itself calls `MarkZDR`. The control span is content-free, so this is a trace-linkage gap, not content retention. Today quarry-edge injects no `traceparent` toward control, so it is latent; the first service that forwards one should carry the zdr bit in `tracestate` and have `ZdrSampler` honour it.
- W2-U42 | security review | `TraceRegistry` evicts oldest-first at `QUARRY_TELEMETRY_ZDR_REGISTRY_CAP` (default 100000). An HMAC-authenticated caller that triggers many `MarkZDR` calls (change webhook ZDR bodies are refused cheaply) can evict a still-live ZDR trace id, after which later spans of that trace would export. quarry-control's request spans end in the same request that flags them, so nothing is exposed today; it matters once a long-lived span (a run) relies on the registry. Pre-existing design shared with `otel_zdr.rs`.
- W2-U42 | security review | In `cycle23.go` `MarkZDR` runs after `UpsertByOrgAndURL` has already persisted the source for a `zdr:true` body; the span drop is correct but the persistence decision for a ZDR source registration is outside this unit and was not reviewed here.
