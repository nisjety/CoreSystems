## Flag and default

`QUARRY_EDGE__FILL_OTP`, default **off**. The client is built disabled and refuses every read with `Unsupported` before any validation, mint or request; the executor wiring must call `.with_enabled(fill_otp_enabled())`. `deliver_otp` also refuses while off, and the edge still refuses `fill_otp_ref`. integration-core's own `INTEGRATION_OTP_READ` is off by default too.

## Assumed decisions

- Row name `mail-otp-read`, reason "read one approved one-time code", `granted: true` (R-13 PR 1 grants exactly this audience and scope), `feature_flags: []`: `QUARRY_EDGE__FILL_OTP` is not a `quarry-edge` config field (`fill_otp_enabled` reads the env), and the contract test requires every listed flag to be one.
- The client spends the approval before the read (fail closed) and keeps its own process-local set on top of the edge's E3.1-ab set; a second read on the same grant is `Forbidden` with `details.reason = otp_approval_spent`.
- `found: false` maps to `NotFound` (`otp_not_found`); status 401/403 -> Forbidden, 404 -> NotFound, 408/504 -> Timeout, 429 -> RateLimited, 400/409/422 -> BadRequest, 501 -> Unsupported, others -> DriverFailed.
- The connection id is a path segment, so it is restricted to the opaque-id charset rather than percent-encoded.
- `windowSeconds` is sent only when configured (clamped to 30..=1800); otherwise integration-core's 600 s default applies. `from` and `codeLength` are not sent (no caller has them yet).
- The integration-core base URL is a constructor argument; no edge config field or wiring was added (not in scope; the executor wiring is a later unit).
