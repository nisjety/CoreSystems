- INNH-8 | `/v1/answer` and `/v1/answer/stream` under ZDR still send page text to the Model Plane (the model hop has no ZDR posture, ADR-4). `include_answer` now skips under ZDR, so the two surfaces disagree. - INNH-10 | review | Flag off is not literally byte for byte, only for every token minted today. Differences: (1) a token with `principal_type: api_key` was a 401 (unknown principal), it is now a valid principal refused 403 `api_key_agent_runs_disabled`; (2) a user or service token that carries a `key_id` claim was accepted (unknown claims are ignored), it is now a 401 (`auth.rs` user/service arms); (3) the edge now refuses to boot on an unreadable `QUARRY_EDGE__API_KEY_AGENT_RUNS` or `QUARRY_EDGE__MAX_CONCURRENT_RUNS_PER_KEY=0`. - INNH-10 | review | Quarry does not bound the key token's lifetime. The revocation story (design section 7, RUNBOOKS kill switches "within the token's life, at most two minutes", CONTRACTS `exp` row) rests entirely on Auth Core minting at most 120 s; `Claims` has no `iat` and Quarry checks only `exp`. A CP-1 mistake (for example reusing the ordinary plane-token TTL) silently turns the 2-minute kill into the full TTL, and the event stream follows `exp`. Cheap fail-closed fix for the arm in `validate_and_normalize_principal` or the fence: refuse an `api_key` token whose `exp - now` exceeds 120 s plus the leeway (a named reason, e.g. `api_key_token_ttl_exceeded`), and say so in CONTRACTS. `jti` is not checked either (pure bearer within its life; replay from a gateway log leak works for its lifetime; sender binding is OD-15).
- INNH-10 | review | A key grant backs any number of runs. One grant id can start up to `MAX_CONCURRENT_RUNS_PER_KEY` concurrent runs and an unlimited number of sequential ones within the grant's TTL, and each run snapshots the FULL grant budget (`grant_budget` at `lifecycle.rs` start, applied per run). So the grant budget bounds one run, not the grant; the design's "spend per run" row says this, but its leaked-key paragraph ("each within the key's budget ceiling") reads as if the grant were the spend unit. Since the gateway composes one grant per run (OD-3), make key grants single-run: Quarry records the grant id on start and refuses a second start under the same key grant (`api_key_grant_in_use` or reuse `api_key_grant_kind_refused`), or the broker consumes the grant on first validate for kind session+key_id. Owner decision on whether the ceiling is per run or per grant (OD-10).
- INNH-10 | review | Budget claim "bounds something" means any ONE of `micro_usd`, `max_steps`, `max_runtime_s` (`GrantBudget::is_set`, `grant_validator.rs:112`). Design section 1 makes all three mandatory for a key grant; the U2 text says only "budget claim set". A grant with only `micro_usd` relies on the flat action-cost table to bound steps and time. Fail-closed fix: for key grants require `max_steps > 0` and `max_runtime_s > 0` (and `micro_usd > 0` if the cost table bills browser actions), else `api_key_grant_budget_required`.
- INNH-10 | review | A key run outlives its grant. The lease TTL is the request's `constraints.max_runtime_s` (default 120, `lifecycle.rs:399`), not the grant's remaining life or budget runtime; after the grant expires every step and new tab fails, but the browser lease and the per-key slot stay until the idle sweeper or the backstop. The event stream's viewer guard (`live.rs:294`) keeps the run from idle expiry, so a key that reconnects the stream every token life holds a browser (and one of its two slots) until the agent max-TTL backstop with no grant at all. Bounded (2 runs, backstop), but cheap to close: clamp `ttl_s` for a key run to `min(grant absolute_expires_at, grant max_runtime_s)` and finish the run when per-step revalidation says the grant is inactive.
- INNH-10 | review | A service delegate can attach to a key's run. `attach_run` (`attach.rs:172`) checks only the org, a grant and non-ZDR; it does not refuse a run whose `key_id` is set, so with `QUARRY_EDGE__ATTACH` on a Model Plane service in the same org can attach and drive the key's browser (non-sensitive actions only, because admission refuses sensitive actions for the whole entry, and on the key's hosts).
