# INNH depth findings, lane D (not fixed; one line each)

Format: `item | finding`. Wave first, depth later (user order 2026-10-23): none of these is a fix loop.

- INNH-8 | `/v1/answer` and `/v1/answer/stream` under ZDR still send page text to the Model Plane (the model hop has no ZDR posture, ADR-4). `include_answer` now skips under ZDR, so the two surfaces disagree. The `answer` row of the ZDR matrix still says Honored; it should become a gap with a `gap_rows_currently_violate_*` test, or the routes should refuse under ZDR like the AI formats. Needs the owner's choice with INNH-8b.
- INNH-8 | An `include_answer` search runs the provider twice (the route's search, then the pipeline's own) and reads up to 5 pages; the pipeline could take the route's results instead. Cost, not correctness.
- INNH-8 | The answer fetcher (`SimpleHttpMarkdownFetcher`) fetches result URLs from the edge; confirm it goes through the web policy and egress guard (answer candidate filter WS7.G is not done).
- INNH-8 | Answer routes keep the legacy `{error, code, hint, reason}` body, not the typed envelope with `details.reason`; moving them is a breaking change for clients that parse `error` as a string, so it was left. A typed envelope could be offered under a version or header later.
- INNH-8 | `model_plane_rate_limited` only arises from a rate-limited Auth Core mint: `decode_invoke` maps a gateway 429 to `DriverFailed`, so a gateway rate limit shows as `model_plane_error`. Mapping 429 in `mp_client.rs` would make the reason exact.
- INNH-8 | The stream route classifies its own model errors by hand (`classify(true, code)`) instead of through `AnswerPipeline::answer`; if the gateway ever implements `/v1/invoke/stream`, tag the hop in `query_stream` too.
- INNH-8 | The failed-synthesis cache rule is proven by unit tests of `cacheable` and `usable_hit` and by a Redis integration test that skips without Redis; add `answer_provider_status` to the CI step that runs with a Redis service and `REQUIRE_CONTRACT=1`.
- INNH-8 | Deployments that already set `MODEL_PLANE_URL` and relied on synthesis being implicitly on must now also set `QUARRY_EDGE__ANSWER_SYNTHESIS=1`. The live compose has an empty URL so nothing changes there; a side-by-side stack with the URL set will answer 501 `synthesis_disabled` until it does.

## INNH-8 review (2026-10-31, read-only review of ab65682aa and 2fa5dc787)

Checked: gap closed, dark by default, ZDR, org scoping, logs and error text, openapi and CONTRACTS against the code, test quality. Node docs tests run on the host: 63 tests, 51 pass, 0 fail, 12 todo. Rust not run (as instructed). Findings 1 to 3 are blockers; the rest are depth.

- INNH-8 | review | BLOCKER 1, contract mismatch: `failed()` in `crates/quarry-edge/src/answer_routes.rs:95` builds `code` as `format!("{:?}", e.code).to_uppercase()`, which is `DRIVERFAILED` and `RATELIMITED`. CONTRACTS.md (reason table) and ERROR_REASONS.md promise `DRIVER_FAILED` and `RATE_LIMITED`, and openapi `ErrorBody.code` is the SCREAMING_SNAKE wire name. `a_model_plane_failure_keeps_its_502_and_gains_a_reason` asserts the status and `reason`, not `code`, so it passes. Fix: `code: e.code.wire_name().to_string()` (`ErrorCode::wire_name`, `quarry-core/src/error.rs:79`) and assert `body["code"] == "DRIVER_FAILED"` in that test.
- INNH-8 | review | BLOCKER 2, ZDR claim is false in the machine-checked matrix: the `answer` row (`crates/quarry-core/src/zdr_matrix.rs:181-191`) is `Treatment::Honored` + `Status::Enforced`, while its own `basis` (edited in this commit) says a ZDR `/v1/answer` and `/v1/answer/stream` still send the query and page text to the Model Plane, which carries no ZDR posture. The matrix has a mechanism for exactly this (`Status::Gap`, row `search_suggest`, with a `zdr_gap_rows::gap_rows_currently_violate_*` test), and `docs/openapi.yaml` `/v1/answer` still says "A zero data retention request runs with the ZDR posture" without the gap. A ZDR org that uses `/v1/answer` on a stack where the switch is on and a credential works (the dev bypass path the runbook documents) leaks content to a non-ZDR lane. Minimum fix, no owner decision needed: re-class the row as `Treatment::Degraded { warning }` + `Status::Gap { issue: "INNH-8b: ..." }`, add a `gap_rows_currently_violate_answer` test, regenerate the goldens, and add one sentence to the openapi description. Preferred fix (small, matches `/v1/extract` and the AI formats): in `answer_run` and `answer_stream`, when `claims.effective_zdr(...)` is true, refuse before the pipeline starts (4xx with a ZDR code, tombstone status recorded, no model call) and keep the row Honored with a test that the gateway double sees 0 requests. The choice between the two stays with the owner (INNH-8b), but the row must not read Honored until one lands. Today the exposure is dev-only (deployed stacks get 503 and the switch is 0), which is why this is not worse.
- INNH-8 | review | BLOCKER 3, integration: `main` (and `model-plane`) already carry the QB-T17 gate this branch says does not exist. `main:.../quarry-edge/src/model_plane_gate.rs` decides seven Model Plane features at boot, `main:.../config.rs:155-158` already has `pub answer_synthesis: bool` (`QUARRY_EDGE__ANSWER_SYNTHESIS`), main's answer 501 hint already names it, and the live P0 evidence (`stack-2026-10-28/live/P0-live.md` f1) shows that hint with the flag at 0. This branch (merge base bd61260ee; `d24854ef4`, which added the gate, is not an ancestor) adds a second `answer_synthesis` field (`config.rs:145`), a second boot gate (`main.rs:1457-1520`, `answer_status.rs`) and different semantics: main REFUSES a switch that is on when the manifest row `model-invoke` is not `granted` (boot error, routes answer their unavailable response), this branch lets the switch on and answers 503 `model_plane_auth_refused`. So the status file's "No existing Quarry flag gates answer synthesis" (G7) and the runbook line "a deployed stack that sets the switch would only answer 503" are both false on main, the merge will conflict on a duplicate field or pick one gate silently, and the wire contract the UI reads (`reason`, `answer_status`, `answer_reason`) does not exist on main, whose 501 has no `reason`. Fix before the UI depends on it: rebase lane D onto main, delete the duplicate field and `ENV_ANSWER_SYNTHESIS`, feed `AnswerPipelineStatus` from `ModelPlaneFeatures.answer_synthesis` and `Decision.refusals` (add a closed reason such as `model_path_refused` for the gate's refusal, since the switch can now be on and still refused at boot), and fix the RUNBOOKS, CONTRACTS, openapi and ERROR_REASONS wording to the merged behaviour. If quarryv2-next is never to merge back, say so in the status file; otherwise reconcile before 8b.
- INNH-8 | review | Cache regression while the gate is closed: a request with `include_answer: true` and no answer is never cached (`search_routes.rs:1077 cacheable`), and the cache key includes `include_answer` (`params_signature`), so with the switch off (the default and today's live state) every `include_answer` search misses the cache and repeats the provider call, where before the null result was cached. The Innhenting UI will send `include_answer` on exactly the traffic that now loses its cache. Fix: when the gate is closed or ZDR, compute the cache key with `include_answer=false` and cache the results without an answer (a hit then reports `unavailable` from the live gate, not `no_sources`); skip the write only for a Ready pipeline that failed transiently. The status file's own G3 offered "key the cache on pipeline readiness".
- INNH-8 | review | A model reply that is empty on a call that did happen is classed `no_sources`, not metered, and cached: `AnswerOutcome::from_result` tests `sources_used == 0 || answer.is_empty()`, and `cacheable(.., Some(""))` is true. With sources present and a blank model answer (a transient gateway fault) the provider bill exists, the customer is not metered, and the blank is replayed as `no_sources` for the search TTL. Treat `sources_used > 0 && answer.is_empty()` as `unavailable` / `model_plane_error` and do not cache it; keep `no_sources` for `sources_used == 0` only.
- INNH-8 | review | Billing doc and code disagree on `/v1/answer`: `answer_routes.rs:183` meters `quarry.answer.synth` on every 200, including the `sources_used == 0` result where no model was called. BILLING.md and the RUNBOOKS Billing paragraph now say "never on a `no_sources` answer" and "once per model call". True for `include_answer` and the stream (`!full.is_empty()`), false for `/v1/answer`. Change the code (`if result.sources_used > 0`) and add a test.
- INNH-8 | review | The `SEARCH_QUERY` usage metadata now always carries `"answer_status"`; it is `null` for every plain search (`search_routes.rs:994`, an `Option` serialized into `json!`). Additive, but it changes the metadata of every search event. Insert the key only when set.
