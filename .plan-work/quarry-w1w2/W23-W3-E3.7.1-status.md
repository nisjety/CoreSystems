`QUARRY_EDGE__BATCH_IDEMPOTENCY`, default **off** (read per call from the env, like `QUARRY_EDGE__DOWNLOADS`). Off: the batch handoff is byte-identical to before. Migration 028 is not flagged: it only relaxes a cross-tenant collision (a bug fix; a key stays unique per org).

## Assumed decisions

- The payload hash is computed at the edge and stored in the job's params, and the comparison is done at the edge on control's replay answer (control returns the held job with its params). No control handler change was needed, and the hash is covered by the existing HMAC over the body.
- What is hashed: the caller's URLs as sent, in order, plus `ingest`. Not the validated/clamped URL list, the policy snapshot or the admission stamp, so a retry is not refused because the plan or the policy changed between attempts.
- A held job without a stored hash (created with the flag off, by the crawl path or by another client) re-attaches as before; it cannot be compared.
- The 409 is `CONFLICT` with `details.reason = idempotency_key_reused` and the held `job_id` (control's lookup is per org, so it is always the caller's own org's job).
- Crawl stays as it was (the unit names the batch path); the crawl route still forwards the key without a hash.
