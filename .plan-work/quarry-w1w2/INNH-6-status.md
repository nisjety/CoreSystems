## Risks
- SSRF/abuse (highest): sitemap and robots `Sitemap:` URLs are attacker-controlled; every fetch goes through the guarded driver chain with heur check and web-policy gate, sitemap host stays inside crawl scope hosts, nested fan-out bounded, compressed + decoded size caps (gzip bomb covered by decode_body), fetch time budget; each loc scope-filtered and robots-checked before enqueue AND again per page in run_page.
- Amplification/cost: a 50k-URL sitemap multiplies fetches; cap at the clamped effective max_pages; only normal quarry.crawl.page metering (sitemap fetches unmetered; decide whether to count one map-like call).
- Temporal: seeds must go through FrontierEnqueueBatch, not per-URL activities nor workflow input (history size); needs GetVersion; the in-memory frontier keeps URLs in workflow state.
- Cache poisoning: non-default scrape options MUST bypass the fingerprint-keyed page cache (key quarry:page:{fingerprint}; org segment present since WS4.K per INNH-7 reading, verify) or later default requests receive differently-cleaned markdown.
- Ingest semantics: Data Plane gets cleaned markdown with ingest=true; document it.
- ZDR: crawl refused under ZDR; the new internal route declares zdr:false only and must be classified in the ZDR matrix.
- Options: include_tags/exclude_tags are CSS selectors parsed by the cleaner (cap count/length, reuse scrape validators); timeout_ms must stay under the activity timeout.
- Drift/skew: SDKs and gateway (other session) must not forward unvalidated scrape_options; hot spots workflows.go, store.go, routes.rs (plan E3.7 risks, R-20 merge order). An old edge ignoring `scrape` would crawl with default cleaning silently: gate by the edge flag AND have the edge echo `applied_options` in the run_page response so the workflow can fail the run like edgeScopeUnsupported does for scope. The new edge must tolerate an old orchestrator.

## Deviations from the brief
- Sitemap URLs are queued at depth 1, not depth 0: a depth-0 page may add a redirect host to the crawl scope (`hosts_added`), which an attacker-controlled sitemap URL must not be able to do. The seed itself is still fetched at depth 0, also in `only`.
- `SitemapSeeds` enqueues into the durable queue from inside the activity (the brief's "enqueueChildrenBatch from the workflow" would have passed up to 5000 URLs through the activity result and so the workflow history); the workflow path of `enqueueChildrenBatch` is unchanged. The in-memory frontier gets the URLs back, capped at 500.
- The activity talks to the runtime base URL with the runtime token (as `RunPage`), so sitemap seeding works with or without the edge queue credentials.
- The discovery route returns a plain object (like `run_page`), not an envelope. No new fetch helper `fetch_bytes`: the existing `Driver::fetch_conditional` with `FetchHints.max_body_bytes` already reads capped bytes.
- Error codes inside `scrape_options` are the shared validators' (`empty`, `too_long`, `too_many`, `out_of_range`, ...), not an invented `invalid_selector`: the shared validator checks count and length only, not CSS syntax (depth file).
- `formats` inside `scrape_options` is validated but changes nothing stored (a crawl page stores markdown and html always); it does not defeat the page cache; only the cleaning options do.
- Failure policy: a failed discovery ends a `sitemap: only` crawl (`run_failed` `sitemap_unavailable`) and lets `include` go on with links; chosen so `only` never reports a success it did not earn.
- Sitemap fetches are not metered (the brief left it open).
- SDKs were not regenerated (the generator needs Docker with the openapi-generator image); `sdks/typescript/docs/CrawlRequest.md` is stale for the new `scrape_options` shape (the `sitemap` and `scrapeOptions` rows keep their types).
