# INNH depth findings, lane b

One line per finding, tagged with the item. Things worth doing later; none is needed to close the item's gap.

INNH-4 | Bug fixed on the way: `quarry_transform::chunk::paragraph_chunks` cut long paragraphs by byte index and panicked on a multi-byte character at the cut. `pipeline.rs` calls it with 1000 on every page's markdown, so a page with a paragraph over 1000 bytes and non-ASCII text could hit it. Now cut on a character boundary (3 unit tests). Worth a look at whether the pipeline call is guarded anywhere and whether a live page ever hit it.
INNH-4 | The change fingerprint is still the raw-byte one (`content_fingerprint(&resp.body)`), so ad or timestamp churn is `status: changed` with `real_delta: false`. Switching the monitor to `text_fingerprint(&md)` needs a re-baseline plan for existing monitors (the E3.5 slice).
INNH-4 | `POST /v1/change/check` takes a caller-supplied fingerprint, fetches nothing and stores nothing, so an ad hoc check has no text diff; making it fetch-and-record is its own item. `POST /v1/change/refresh` enqueues `change_refresh` rows that nothing consumes.
INNH-4 | The artifact janitor (`services/quarry-control/internal/janitor/janitor.go`) deletes by age only, dry-run by default. Arming it deletes the text of old baselines (`artifact_gone` on the read route); it needs a baseline-provenance guard first. Org erasure (`org_erasure.rs`) has no baseline handling at all.
INNH-4 | `record_internal` ignores the Idempotency-Key header, so a retried CheckChange activity can write a second baseline and a second diff record for one change. `find_diff` takes the newest, so reads are stable, but the history gets a duplicate row.
INNH-4 | `load_latest` and `load_history` order by `captured_at DESC` only; two baselines saved in the same microsecond tie. The default pair of `GET /v1/change/diff` inherits that. The `prev_baseline_id` chain is the exact order.
INNH-4 | The paragraph diff is set-based (a repeated paragraph counts once; a list or table is one block). A word-level diff inside a changed paragraph would let the UI highlight the edit; ops are capped at 500, so a very large rewrite is truncated and a paged ops read may be wanted.
INNH-4 | Storage grows by one markdown artifact per new or changed baseline plus a small JSON diff. A compaction rule (keep the last N texts per url) is not designed.
INNH-4 | `verify_markdown_artifact` reads the whole artifact to learn its key (`get_with_key`); a key-only lookup on the store trait would make the check cheap.
INNH-4 | The SQL of `load_baseline`, `load_diff` and `find_diff` has Postgres-gated tests that skip without `DATABASE_URL`; none ran here. Run them once on a side-by-side Postgres (`REQUIRE_CONTRACT=1`).
INNH-4 | `quarry_transform::diff::diff_paragraphs` now reports `moved` only for paragraphs that changed place among the shared ones (longest increasing run), and looks paragraphs up in a map instead of a scan per paragraph. Its only callers are the new text diff and the unit tests.

INNH-4 | review: `verify_markdown_artifact` (change_diff.rs) maps EVERY artifact-store error to 400 BAD_REQUEST. The orchestrator classifies a 400 as Client4xx, which is non-retryable (`errs.FromHTTPStatus`), so an S3 or filesystem blip during a changed check ends that tick as run_failed. Nothing is lost (the baseline is not saved, the next tick sees the change again) but RUNBOOKS says "the activity fails and Temporal retries it", which is wrong. Fix: map only NotFound and Forbidden to 400, let other errors surface as 500 (retryable), and correct the runbook line. Note S3Store::get_with_key itself reports any index-read error as NotFound.
INNH-4 | review: `read_markdown` (change_diff.rs) turns every read error into `artifact_gone`, and `store_text_diff` stores that outcome as the diff artifact. `diff_core` then trusts a stored artifact even when `available` is false, so a transient read failure at record time makes that diff permanently "unavailable" while both texts are still there; the webhook's diff_id resolves to it forever. Fix: in `diff_core` recompute when the stored artifact is unavailable with reason `artifact_gone`, and make the record path fail on a non-NotFound read error instead of storing an unavailable diff.
INNH-4 | review: `verify_markdown_artifact` checks `key.contains("markdown")` on the whole key `org=<org>/run=<run>/page=<hash>/<stem>.<ext>`, so an org id or page hash containing the word passes for any kind. Compare the last path segment (`markdown.md` stem) instead. It is only the internal orchestrator that can reach it, so low risk.
INNH-4 | review: ordering in `record_core`: `save_baseline` runs before `store_text_diff` and `create_diff_record`. If the diff artifact write fails the baseline is already saved, the activity retries, `compare_snapshot` then says unchanged, and the change event, webhook and diff are lost. This ordering is pre-existing, but the text path adds an artifact encode and write after the save, so the window is wider. Fix: store the diff artifact before the baseline, or save baseline and diff record in one transaction.
INNH-4 | review: enabling the flag changes event semantics beyond "text diff". Before, `change_detected` events of one URL all had the idempotency key `change_detected:<org>:<url>:` (empty baseline id), so a dedupe on that key kept only the first change per URL. With the flag on every change gets its own key. That is the intended fix, but control and the UI should expect more change events per URL than they saw before, on the same stack, the moment the flag flips.
INNH-4 | review: the ZDR refusal on `GET /v1/change/diff` is not a total barrier. `/v1/artifacts/{id}` and the artifact list are not refused for a ZDR reader (matrix row `artifacts`: reads what exists), and the diff view hands out the markdown artifact ids and the `change_diff` artifact is listable. Text stored before an org turned ZDR (or by a schedule stamped non-ZDR before then, per `zdr_posture_stamp::record_trusts_the_stamp_not_the_current_posture`) stays readable by id. Same posture as stored scrapes; the owner decision on "refuse entirely vs metadata only" should say this out loud.
INNH-4 | review: the read route is not on the service-principal allow-list in `require_service_route_scope`, so a service token gets 403 (as `/v1/change/history` already does). The Innhenting gateway must forward the user's bearer, not a service identity, or add the route and a scope on purpose.
INNH-4 | review: op truncation keeps all `added` ops, then all `removed`, then `moved`. With more than 500 added paragraphs no removed paragraph is listed (counts are complete, `truncated` is true). The docs say "added and removed first"; interleave by index or cap each kind to 250 if the UI shows removals.
INNH-4 | review: a paragraph over 8192 bytes is cut at fixed byte offsets, so an insertion early in a long paragraph shifts every later unit and reports each as added and removed. Rare for markdown, visible on a page that is one huge block.
INNH-4 | review: the org-scoping tests for the read logic run against `MemStore`, which re-implements the org filter, and the SQL tests skip without `DATABASE_URL`. So the real `WHERE org_id = $1` in `load_baseline`, `load_diff` and `find_diff` is unexercised. Read by eye it is right (all three bind org first); run the two Postgres tests once with `REQUIRE_CONTRACT=1`.
INNH-4 | review: `GET /v1/change/diff?diff_id=` returns `diff_id: null` when the stored record is a pre-flag `text` one or its artifact no longer reads back, although the caller passed an id; the UI cannot tell this from "never stored". Echo the requested id or add a field.
