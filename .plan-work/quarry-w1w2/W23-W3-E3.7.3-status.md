## Behaviour

- Flag off (default): the wait keys are ignored and every read is the WS15.L1 read on the same code path as before.
- Flag on, no `wait` or `wait=0`, no `resume`: the plain read.
- Flag on, `wait=N` (N at least 1; above 25 is clamped to 25; a value that is not a whole number, or an empty one, is 400 BAD_REQUEST). A ZDR caller is refused with 403 FORBIDDEN before any control call. Otherwise the read polls control every 2 s until the job is terminal (200, the status document) or N seconds pass (408).
- 408 body: `error.code` TIMEOUT (retryable), `error.details` with `reason` processing_continues, `job_id`, `status`, `phase`, `counts`, `progressed` (null without a token, otherwise true or false against the token), `waited_s`, `retry_after_seconds` (1) and `resume_token`. The HTTP response also carries `Retry-After: 1`.
- `resume` with no `wait`, or with `wait=0`: 400. A token for another job, or a malformed token: 400.
- A foreign or unknown id, or a kind mismatch, is 404 at every poll, the same as the plain read.

## Assumed decisions

1. "non-ZDR only" is read as applying to the wait. Cancel, pause and resume stay open to ZDR callers, as WS15.L2 shipped them and as the ZDR matrix and its test pin them. The owner should confirm; if cancel must be refused under ZDR too, `control_request` and the matrix row and test change together.
2. A ZDR caller who asks for a wait gets a typed 403 (FORBIDDEN), not a silent plain read, the way `errors_for` refuses the error URLs under ZDR.
3. The 408 uses `ErrorCode::Timeout` (wire TIMEOUT) with HTTP status 408 and `details.reason` processing_continues. No new ErrorCode (rule R-10). Elsewhere TIMEOUT is 504, so a client keys on the HTTP 408 and on `details.reason`.
4. The resume token is unsigned and does not expire. It holds a job id and the marker (status, phase, the four counts, the two control seqs), and no URL or content. The job id must match the path. A forged token can misreport only `progressed`.
5. A resumed wait does not return early on progress. It still waits for terminal or the deadline, and `progressed` says whether the job moved since the token. Early progress would need a token in the 200 body, and JobStatusView has none. Progress streaming is the job event follow (WS15.L3).
6. Cap 25 s, below the router's 60 s path deadline and below a typical 30 s proxy timeout. Poll 2 s, matching the orchestrator control loop.
