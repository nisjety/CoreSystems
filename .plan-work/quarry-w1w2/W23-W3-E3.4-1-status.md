## Gap check

Existed: `AgentRunStatus { Active, Closed }`, `close_run_checkpoint`, the 0006 table with an inline `CHECK (status IN ('active','closed'))`, and the edge's resume path (`agent_routes/lifecycle.rs`) that already refuses closed (409) and ZDR (403) checkpoints. Missing: the two statuses, a way to set them, a store-level resume gate, and the migration. Built only that.

## Built

- `src/step_receipts.rs`: `AgentRunStatus` widened to `Active, Suspended, Expired, Closed` (doc: the durable side of the D8-10 machine, not a second enum). `as_str`, `parse` (unknown -> `None`, fail closed), `is_terminal`, `is_resumable`, `can_move_to` (only `Closed` is sticky). `AgentRunCheckpoint::check_resumable()` refuses `Closed` (Conflict) before ZDR (Forbidden); `Active`/`Suspended`/`Expired` pass. New trait method `StepReceiptStore::mark_run_checkpoint(org, run, status)` (default no-op, like `close_run_checkpoint`), implemented in `InMemoryStepReceiptStore` (tenant-keyed, closed stays closed). Tests in a new `checkpoint_status_tests` module: wire values round trip and unknown fails, legacy JSON (no status / `closed`) reads unchanged, the arc and terminal close, the resume gate refuses ZDR for every non-closed status and closed for both ZDR modes, the in-memory mark (arc, other tenant, closed terminal, missing row is fine).
- `src/postgres_step_receipts.rs`: save binds `status.as_str()`. Load selects `state, status` and takes the status from the column (unknown value -> Internal error). Close now also sets `state.status` to `closed` via `jsonb_set`. New `mark_run_checkpoint`: one `UPDATE ... WHERE org_id, run_id AND status <> 'closed'` setting the column and the JSON. Tests (`#[ignore]`, need DATABASE_URL and migrations through 0020): the arc round trip incl. JSON in step and tenant bound; a legacy row closed in the column with stale `active` JSON loads closed; migration 0020 applies twice, accepts the four values, refuses `paused`, leaves one CHECK.
- `migrations/0020_agent_run_checkpoint_status.sql`: drop `quarry_agent_run_checkpoints_status_check` if exists, re-add with the four values. No new column, no backfill. LF like 0018.

**Bug fixed on the way:** Postgres `close_run_checkpoint` updated only the status column, but `load_run_checkpoint` decoded the status from the state JSON, so a closed run loaded as `active` and the edge's closed-run 409 on resume (and `run_is_resumable`) never fired against Postgres. The load now reads the column, and close keeps the JSON in step.

## Flag and default

None (additive, per queue). Nothing writes `suspended` or `expired` yet: the only writer will be E3.4-2-3 (lane b, behind `QUARRY_EDGE__RUN_TTL`, default off). Old binaries keep working on the wider CHECK (they write only `active`/`closed`), but an old binary that loads a checkpoint whose JSON says `suspended`/`expired` fails to decode it: roll the binaries before E3.4-2-3's flag is turned on.

## Assumed decisions

1. Migration number 0020 (queue: W2-U49a takes 0019 in S1). sqlx applies by version, so 0019 landing after 0020 on a database is applied when it arrives; the lead arbitrates at merge.
2. `Closed` is terminal at the store (mark never moves it, in memory or in SQL). A resume of `Suspended`/`Expired` goes back to `Active` through the existing `save_run_checkpoint` or `mark_run_checkpoint(.., Active)`.
3. `check_resumable` checks closed before ZDR (matches the edge's order, 409 before 403).
4. The status column is the authority on load (it is what the CHECK guards and what close always wrote).
5. Trait default for `mark_run_checkpoint` is a no-op `Ok(())`, matching `close_run_checkpoint`, so the edge's test stores (`Flaky`, `NoErasureStore`) need no change.
