## Assumed decisions

1. "Tag column" is one tag per row, a single TEXT column. The scope names a column, and the queue says "the E3.5-6 tag column" (singular). A set would be `TEXT[]` with a GIN index, which is a migration change as well as a store change. Owner question, see D-E356-4.
2. The grammar is my choice: trimmed, lowercased, 1 to 32 characters of `[a-z0-9._-]` starting with a letter or digit. No plan value named one. Refusals use reason `invalid_tag`.
3. Whitespace-only input trims to `''`, so `tag: "  "` clears a tag.
4. `ListByOrgTag(org, "")` lists the org's untagged rows (equality). An empty org, or a tag that does not normalise, matches nothing (fail closed).
5. `UpdateTagByOrg` leaves `schedules.updated_at` alone, as the struct comment defines it (the create or enable/disable stamp). It moves `quarry_sources.updated_at`, as `SoftDeleteByOrg` does.
6. The tag belongs to the row it describes. A monitor created from a source does not inherit the source's tag (both start untagged).
7. A repeat source registration keeps the existing tag (write on insert only).
8. No GIN index. The org-scoped tag list is served by the partial `(org_id, tag, created_at)` index, which is the access path the scope asks for.
9. Migration numbers: 028 stays with E3.7.1 and the E3.5-7 notify-filter persistence takes 029 (see `W23-W3-E3.5-7-status.md`). Unchanged by this unit.
