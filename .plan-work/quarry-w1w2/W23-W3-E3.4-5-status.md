## Built

- quarry-edge `agent_routes/live.rs`: `LIVE_SCOPE_HEADER = x-quarry-live-scope`, `LiveScope { Full, ViewOnly }`, `live_scope_from` (flag off: header ignored, always `Full`; flag on: `full`/absent = Full, `view_only`/`view-only`/`view` = ViewOnly, anything else 400), `view_only_zdr_refusal` (403 `live_view_only_zdr`), `view_only_ws_refusal`, `scoped_live_view_ref` (view-only keeps only `hls` and `frames`; iframe, provider and unknown kinds are dropped), `owner_live_scope` (always after `caller_owns_live_run`, so a non-owner still gets the plain 404).
- quarry-edge `agent_routes/ws.rs`: `live_frame_ws` reads the scope after the owner check; `browser_ws_loop` takes `scope: LiveScope` and answers any client frame the scope does not accept (everything but `ping`) with a `FORBIDDEN` / `live_view_only` error frame without executing it; the socket stays open.
- gateway `domains/browser.rs`: new route `GET /api/v1/browser/sessions/{session_id}/view/frames/ws` (interactive rate class, next to `frames/ws`), 404 unless `BROWSER_LIVE_VIEW_ONLY` is on. Both socket routes share `proxy_live_frames_ws_scoped`; the owner projection check runs first on both. The view-only route sets `x-quarry-live-scope: view_only` on the upstream request (derived from the route, never from the client; the client's own headers are not forwarded on the socket) and drops every client frame except the JSON keep-alive and transport ping/pong/close, answering `browser_live_view_only` to the client. That gateway filter holds even against an edge with its flag off.
- gateway `config.rs`: `AppState.browser_live_view_only`, read once in `build_state` from `BROWSER_LIVE_VIEW_ONLY` (`human_browse_enabled` parser); `false` in the five test/fixture AppState literals (`browser.rs`, `chat/shared.rs`, `orchestration.rs`, `main.rs`, `onboarding/crawl_preview/stream_e2e.rs`).

## Flag and default

- `QUARRY_EDGE__LIVE_VIEW_ONLY` default off, read per call like `QUARRY_EDGE__DOWNLOADS`. Off: the header is not read, every live route behaves as before.
- `BROWSER_LIVE_VIEW_ONLY` (gateway) default off, on AppState (not a handler env read). Off: the view route answers 404; the existing `frames/ws` route is unchanged.
- Neither flag is in compose or RUNBOOKS yet (absence = off).

## Assumed decisions (owner said stop asking)

1. The scope travels as an edge header the gateway sets from its own route (`/view/frames/ws`), never from a client value or a bearer URL; the only non-default value takes authority away, so a client cannot widen it.
2. "Owner-only share" = the view-only socket is served only to the run's owner (same owner checks as the full socket); no cross-user share link is built (that needs a share grant from Control Plane, not in scope).
3. ZDR: a view-only share of a ZDR run is refused with 403 at the edge (scope: "ZDR refused"); the full-authority owner socket is unchanged for ZDR.
4. View-only keeps `ping` and read-only live-view kinds (`hls`, `frames`); an unknown kind counts as interactive.
5. The gateway gets its own flag (two planes, two switches) and filters input itself, so turning the gateway on before the edge cannot open an input path.
6. Only the WebSocket gets a gateway view route: it is the only live transport that accepts input. The SSE routes are read-only; the edge already filters their live-view event by scope when the header is present.
