## Assumed decisions

1. "Per-origin consent defaults" = two org-level defaults over the person's per-origin decisions: may people extend a run to other origins at all (`browser.consent.origin`), and the widest scope such a decision may have (`browser.consent.max_scope`). No per-host org rows: org host rules are `domains.allow`/`deny` already, and an org pre-consent list would loosen, which tighten-only forbids.
2. Both ride in `caps` (task: "claim v1 caps include them"), so no claim version bump and no new top-level field; the edge already ignores and counts unknown cap keys.
3. Key names under `browser.consent.*`; baseline `allowed` / `always` (states nothing, matching user-core E3.2-e3 which allows all three scopes).
4. Not added to Quarry's catalogue (not this unit's files; the catalogue copy is byte-pinned): org-core holds a local table with a guard test that fails when the catalogue gains the keys.
5. auth-core validates the two keys' values (fail closed) instead of passing any string, because a consumer added later must not see an unknown scope word.
6. Golden: one new user case only; service cases would show the same caps (the resolver is principal-agnostic) and the existing web-policy service cases already pin that path.
