## W2-U58 | security review

No blocker. The read-back calls `Storage.getCookies` with the session's own `browser_context_id` (one context per lease, created in `chromiumoxide.rs`), so it never sees another session's or org's jar. Only name, host and path are kept from the response; cookie values are dropped at once, `CookieKey`'s `Debug` prints neither name nor host, and nothing logs the CDP response. The new `failed` paths only move toward fail-closed: `apply_cookies` can set `failed` but never clears it, and the seeding-script failure still sets it after. `load_failure` is a closed `&'static str` label, never the store error text (a test checks this). `KeyDestroyed` not blocking the save is right: `save` wraps a new DEK under the active master, so a fresh profile cannot bring back shredded content.
