## Design

### 3.1 Invariants

1. The Model proposes; the owner executes. A tool call never reaches an effect except through: capability policy, hooks, permission and autonomy rung, Control decision, owner verification. The model supplies argument values only. It never names a thread, Space, actor, org, run, audience, key or digest.
2. One run-action table (cross-audit C6). Control's registry is the single table of run-bound actions; `tickets.create` becomes row 1 with its pinned values unchanged. No Space-only table, no new grant type, no new envelope version for Phase 1 and 3 (`run-action-v1` is reused; Phase 2 needs `v2`, 3.10).
3. Every layer can only narrow: Control entitles, Capability Core intersects with health and its own list, execution-core intersects with its adapters. A response naming an action a layer did not expect makes the whole view invalid (fail closed, not skipped).
4. Authority is the delegating human's, never wider. Phase 1 acts only on the run's own thread, owned by the run owner, and does no more than the owner can do in the UI; it never overrides what a human set.
5. ZDR: none of this runs under ZDR (3.12).
6. Realtime events and logs carry ids and kinds only.

### 3.2 The registry of record

Golden file `apps/Model Plane/api/contracts/space-self-api-registry.json` (+ `.sha256`) in the existing contracts folder; vendored byte-identical copies in Control (`apps/Control Plane/user-core/internal/spaces/registry/`, `go:embed`), Capability Core (`internal/api/registry/`), the Rust crate `mp-contracts` (`include_str!`, used by session-core and execution-core), the SPA (`src/shared/api/contracts/`) and the gateway (embedded). A new script `scripts/tests/space-self-api-registry-sync.test.sh` checks pin and copies (the existing `zdr-contract-sync.test.sh` is M and ZDR-specific; do not edit it). `contract-goldens.yml` gets two path lines.

Row fields: `action_id` (= tool name), `capability_id`, `owner_plane`, `owner_service`, `service_audience`, `decision_type` (`run_action`, or `schedule_create` for Phase 3), `permission`, `min_role`, `risk`, `default_level` (`allow`|`ask`), `approval` (`none`|`owner_approval`), `autonomy_rung`, `reversible`, `max_per_run`, `reservation` (bool), `argument_order`, `parameters_json` (exact bytes models see), `schema_sha256` (sha256 of the `parameters_json` bytes; for the legacy row the existing pinned value), `zdr` (`refuse`), `ui_action_id`, `phase`, plus `digest_vectors` (golden inputs and expected digests for Go and TypeScript parity).

Rules enforced by a registry test: ids match `^space\.[a-z_]+\.[a-z_]+$` or are `tickets.create`; no id or argument name contains `member`, `role`, `delete`, `credential`, `grant`, `policy`, `thread_id`, `space`, `org`, `user`, `actor`; `parameters_json` has `additionalProperties:false`; no argument is a URL or markup field.

Digest (computed only in Rust, by `mp-contracts::space_self_api`, shared by execution-core and Session Core; Control never sees arguments):
`payload_digest = "sha256:" + hex(sha256("space-self-api/v1" 0x00 || F(action_id) || F(run_id) || F(org_id) || F(idempotency_key) || for each argument in argument_order: F(name) || F(value_text)))`, `F(x) = u32_be(len(utf8(x))) || utf8(x)`. Booleans are `true`/`false`, integers decimal, arrays flatten to `fields.len`, `fields.<i>.label`, `fields.<i>.value`. No JSON is hashed (Go's default HTML escaping and Rust differ on `&` and `<`, which free-text titles will contain). Idempotency key: `"{action_id}:" + hex(sha256(action_id 0x00 run_id 0x00 step_id))`, the pattern of `ticket_tools.rs:735-742`.

### 3.3 Data flow

```
Mention turn:  SPA -> BFF (features stripped of client space_self_api; binding.self_api_enabled and not ZDR add
               "agentic","space_self_api") -> model-gateway (RunAgentRequest.tool_profile="space_self_api")
Run start:     execution-core merged_tool_defs: profile -> only server-resolved tools
  view:        execution-core -> Control POST /api/v1/internal/spaces/model-action-view {run_id, org_id, view_version:2}
               Control -> Session Core ResolveRunActionAuthority -> evidence (role, entitlement, ZDR, revisions)
               <- token model-action-view-v2 {actions:[{action_id, schema_hash, level}]}
               execution-core -> Capability Core POST /api/v1/internal/model-actions/run-view {run_id, control_view_token}
               <- {actions:[{name, description, parameters_json, action_schema_hash, requires_approval, level, autonomy_rung}]}
               execution-core compares each to its vendored registry bytes, offers the survivors
Tool call:     capability policy (evaluate_with_evidence) -> hooks -> permission/rung (+ WS10 gate)
               -> Control POST /api/v1/internal/spaces/run-action-decision {run_id, org_id, action_id, action_schema_hash,
                  payload_digest, idempotency_key}  -> run-action-v1 token (2 min)
               -> Session Core RunService.ApplyRunThreadAction (delegated bearer of the run owner + token + typed args)
               <- receipt {receipt_id, outcome, thread_id, message_id?}  -> tool result JSON to the model
```
