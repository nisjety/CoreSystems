| Piece | Owner and why |
|---|---|

### D2 Session Core: persisted thread activity summary (slice S5)

Migration `SC/../migrations/0049_thread_activity_summary.sql` (provisional number; revert file `migrations/revert/0049_thread_activity_summary.down.sql`):

```sql
ALTER TABLE threads
  ADD COLUMN IF NOT EXISTS last_message_seq BIGINT,
  ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS turn_count INTEGER NOT NULL DEFAULT 0,          -- user + assistant rows
  ADD COLUMN IF NOT EXISTS last_role TEXT,
  ADD COLUMN IF NOT EXISTS last_author_subject_id TEXT,                    -- last human author
  ADD COLUMN IF NOT EXISTS recent_author_subject_ids TEXT[] NOT NULL DEFAULT '{}',  -- at most 5, newest first
  ADD COLUMN IF NOT EXISTS activity_max_audience_revision BIGINT;
CREATE OR REPLACE FUNCTION thread_activity_apply() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE threads t SET
    last_message_seq = GREATEST(t.last_message_seq, NEW.sequence),         -- GREATEST ignores NULL
    last_activity_at = GREATEST(t.last_activity_at, NEW.created_at),
    turn_count = t.turn_count + CASE WHEN NEW.role IN ('user','assistant') THEN 1 ELSE 0 END,
    last_role = CASE WHEN NEW.sequence >= COALESCE(t.last_message_seq, 0) THEN NEW.role ELSE t.last_role END,
    last_author_subject_id = CASE WHEN NEW.role = 'user' AND NEW.author_subject_id IS NOT NULL
        AND NEW.sequence >= COALESCE(t.last_message_seq, 0) THEN NEW.author_subject_id ELSE t.last_author_subject_id END,
    recent_author_subject_ids = CASE WHEN NEW.role = 'user' AND NEW.author_subject_id IS NOT NULL
        THEN (SELECT COALESCE(array_agg(x ORDER BY o), '{}') FROM (
                SELECT x, o FROM unnest(array_prepend(NEW.author_subject_id,
                       array_remove(t.recent_author_subject_ids, NEW.author_subject_id))) WITH ORDINALITY u(x, o)
                ORDER BY o LIMIT 5) s)
        ELSE t.recent_author_subject_ids END,
    activity_max_audience_revision = GREATEST(t.activity_max_audience_revision, NEW.recipient_audience_revision)
  WHERE t.id = NEW.thread_id;
  RETURN NULL;
END $$;
CREATE TRIGGER messages_thread_activity AFTER INSERT ON messages
  FOR EACH ROW EXECUTE FUNCTION thread_activity_apply();
CREATE INDEX IF NOT EXISTS idx_threads_space_activity
  ON threads (org_id, space_id, last_message_seq DESC)
  WHERE space_id IS NOT NULL AND archived_at IS NULL AND last_message_seq IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_threads_activity_pending ON threads (id) WHERE last_message_seq IS NULL;
```

Why a trigger and not edits in `append_message_in_tx`: that function is the hotspot of WS01, WS08, WS12; the trigger covers every present and future writer (V7) and runs inside the appender's transaction, on a row the appender already holds `FOR UPDATE`, so it adds no lock wait. WS02's `thread.updated` trigger is column-specific (presentation fields), so this UPDATE emits no realtime event. Rollback of the message insert rolls the summary back.

Backfill: not in the migration (sqlx runs migrations in one transaction at boot; a full-table pass would block startup). A bounded task `thread_activity_backfill` (new `SC/thread_activity.rs`, spawned in `main.rs` after `run_migrations` at :70) updates 500 threads per batch where `last_message_seq IS NULL AND EXISTS (SELECT 1 FROM messages ...)`, ordered by id, sleeping 50 ms between batches; idempotent. The window RPC refuses with `failed_precondition("summary_backfill_pending")` while any such row exists (answer cached 30 s); the BFF then degrades to the legacy listing (D5). `thread_activity_recompute(thread_id)` (SQL function in the same migration) rebuilds one thread's row from `messages`; any future erase or tombstone path (WS12, author erasure) must call it.

Per-reader safety: summaries are aggregates over all messages. A thread is eligible for a reader only when `COALESCE(t.activity_max_audience_revision, t.recipient_audience_revision) <= ceiling`; otherwise it is omitted (fail closed, same direction as today's thread-level rule at `grpc.rs:5584-5586`). The BFF mints a fresh decision with the current audience revision on every page, so this only hides a thread for the length of a revision-bump race.

### D3 Session Core and model-gateway: contracts

`ListSpaceTimeline` (`SC/space_timeline.rs`, N; body called from the `SpaceRoomReadGrpc` impl):
1. Authority in order: `identity(&request)`; `authorize_operation(&caller, "session:read")` (writes nothing, so ZDR credentials pass, as WS07); `org_id` and `space_id` non-empty; `caller.authorize_org`; `verify_thread_read_space_decision(...)` must return `Some` (no owner-bound mode; absent decision is `permission_denied`); ceiling = decision's `recipient_audience_revision`.
2. `limit` 0 means 50, clamp 1..100; query runs `limit + 1`.
3. Backfill guard (D2).

Page query (descending, `before_seq` absent means newest):
```sql
SELECT t.id, t.created_at, COALESCE(t.presentation_title, fu.content) AS title,
       COALESCE(t.presentation_preview, lm.content) AS preview, t.pinned_at, t.last_activity_at AS updated_at,
       t.last_message_seq, t.turn_count, t.last_role, t.last_author_subject_id, t.recent_author_subject_ids,
       t.user_id AS owner_subject_id, t.origin, t.persona_enabled, lr.id, lr.status, lr.updated_at
FROM threads t
LEFT JOIN LATERAL (SELECT content FROM messages WHERE thread_id = t.id AND role='user' ORDER BY sequence LIMIT 1) fu ON TRUE
LEFT JOIN LATERAL (SELECT content FROM messages WHERE thread_id = t.id ORDER BY sequence DESC LIMIT 1) lm ON TRUE
LEFT JOIN LATERAL (SELECT id, status, updated_at FROM runs WHERE thread_id = t.id ORDER BY updated_at DESC, created_at DESC, id DESC LIMIT 1) lr ON TRUE
WHERE t.org_id = $1 AND t.space_id = $2 AND t.archived_at IS NULL AND t.last_message_seq IS NOT NULL
  AND COALESCE(t.activity_max_audience_revision, t.recipient_audience_revision, 0) <= $3
  AND ($4::BIGINT IS NULL OR t.last_message_seq < $4)           -- before_seq
  AND ($5::BIGINT IS NULL OR t.last_message_seq > $5)           -- after_seq (then ORDER BY ASC)
ORDER BY t.last_message_seq DESC LIMIT $6
```
The lateral joins run for at most `limit + 1` rows, because the sort and limit use the persisted key on `idx_threads_space_activity` (a DB test asserts the plan uses it). Also: `pinned` (first page only): same predicates, `pinned_at IS NOT NULL ORDER BY pinned_at DESC LIMIT 10`; `refreshed`: same predicates and `t.id = ANY($7)` for at most 30 caller-supplied ids (so a non-terminal run's status or a failed run with no new message is refreshed without a full list); `total_posts`: `count(*)` over the base predicate, first page only. Orphan threads (no message) never appear, which also fixes the internal-`session_key`-as-title leak WS01 noted.

Cursor: `before_seq`/`after_seq` are message sequences, unique per thread tail, so there are no ties and no timestamp skew. Activity ordering is bump-on-reply (today's order); a post that gains a reply while the reader pages backwards moves to the newer end and cannot cause a skip, only a duplicate the client removes by `thread_id`.

Tail transcript: `list_conversation` (`grpc.rs:5387-5501`, M; WS01 and WS07 also edit this file) gains a branch when `tail_limit > 0`: same authority and same predicate (`m.recipient_audience_revision <= ceiling`), then `ORDER BY m.sequence DESC LIMIT tail_limit + 1` re-sorted ascending; with `include_first` and no `before_sequence` the first visible row is selected separately and `omitted_before` is the count of visible rows strictly between it and the window; with `before_sequence` the rows with `sequence < before_sequence`. `tail_limit` absent keeps today's behaviour exactly. Typed entry (D6) and `sequence` are populated on every row.

model-gateway (`MG/http_routes.rs`, M): `.route("/v1/spaces/:space_id/timeline", get(list_space_timeline))` beside :144 (same pattern as WS07's artifacts route: `Claims` org, `VerifiedModelBearer`, `authenticated_session_request`, errors through `session_thread_error`); `ThreadMessagesQuery` (:8470) gains `tail`, `before_sequence`, `include_first`; `ThreadMessage` (:7726) gains `sequence` and `entry` (typed, serialised as `{kind, version, link_previews:[...]}`, not flattened with the free metadata); `ThreadSummaryResponse` (:7779) gains the new summary fields. The WS07 metadata allowlist (`room_metadata.rs`) must keep `entry` out of the reduced map because `entry` is its own typed field. A new `AppState.space_room_client` is WS07-S9's; reuse it.

Cursor format: opaque `base64url("v1|" + sequence)`; a malformed value is 400 `invalid_cursor`. Cursors carry no authority: every page re-runs lifecycle, membership, the Control read decision and the Session Core ceiling.

Interval stitching for system entries (no merged cursor): page n covers posts with activity time in `[t_lo, t_hi)`, where `t_hi` is the previous page's oldest `updated_at` (infinity for the first page) and `t_lo` is this page's oldest `updated_at` (minus infinity when `has_more` is false). ### D6 Typed entries and link previews

Entry envelope: `MessageEntry{kind, version, link_previews}` is the only typed in-thread payload. Session Core (`append_message_in_tx`, plus a pure `validate_entry(&MessageEntry) -> Result<serde_json::Value, &'static str>` in `SC/space_entry.rs` N) accepts it only when the append is a human post (`post_kind = 'post'`, WS01) and refuses it on every other path with `InvalidArgument`. Rules: `kind` in {`link_previews`}; `version == 1`; at most 3 previews; `url` and `final_url` `http` or `https`, at most 2048 bytes, no userinfo; `host` is recomputed from `final_url` (a client value is ignored); `title` at most 200, `description` at most 400, `site_name` at most 80 characters after trimming and removing control characters; `fetched_at` required and not in the future by more than 5 minutes. It is persisted under `messages.metadata.entry` (existing JSONB column, no migration), so it shares the message's audience columns, erasure and retention, and WS01's client-metadata rule (ignore client `metadata`) is untouched because `entry` is a separate typed field. Reads rebuild the typed message; an unknown future `kind` is returned as `{kind, version}` with no payload so older clients render the fallback card. Posts never enter model context or memory (WS01), so previews cannot be injected into a prompt.

Preview fetch (Ingestion): contract assumed from sibling a, `POST {QUARRY_EDGE_URL}/v1/preview` with scope `preview:read` (added to `auth.rs:514` map), body `{url, zdr:false}`, static fetch only, no browser, 5 s total timeout, 256 KB body cap, redirects at most 3 through `dns_guard`, robots honoured, response `{final_url, title, description, site_name}`. Until it exists (UNVERIFIED that sibling a will build it), the BFF uses today's `/v1/scrape` with render hints removed (the `without_browser_rendering` shape, `quarry.rs:724`) and reads `data.metadata.title/description` only, discarding markdown and artifact ids. No image is fetched or stored in v1: no third-party image load for recipients, no image proxy to build, smaller SSRF and tracking surface. Residual risk: a post author can attach a snapshot text that the site did not serve, because the digest the Control decision binds covers the message content only; mitigated by the BFF cache indirection (the client cannot supply text), the card labelling "Preview captured when sent" with the host taken from the URL, the `safeHref` rules of WS07-S5, and `rel="noopener noreferrer nofollow"`. Binding `entry` into the Control v2 digest is a hardening option, not built.

SPA card registry (`FV/src/features/spaces/lib/entry-registry.ts` N, components in `components/entries/` N): `TimelineEntry = {kind:'post', thread} | {kind:'system', id, at, code, actorId?, subjectId?, fromRole?, toRole?} | {kind:'unknown', id, at, rawKind}` and `TurnEntry = {kind:'link_previews', items} | {kind:'unknown', rawKind}`. Registry maps kind to component; `UnknownEntryCard` is the neutral fallback ("This item is not supported in this version of Verevon"). WS09's run card and WS10's approval panel register here instead of adding branches in the timeline.

System rows: the server sends codes and ids only; the SPA builds the sentence with `i18n.tr` ("Kari added Ola", "Kari changed Ola from viewer to editor", "The room was archived"). Codes: Control `member_added`, `member_joined`, `member_left`, `member_removed`, `role_changed`, `archived`, `unarchived`, `visibility_changed`, `settings_changed`; Application `agent_bound`, `agent_paused`, `agent_resumed`, `agent_revoked`, `room_renamed`, `topic_changed`. Application notices (slice S12): Convex table in `schema.ts` (next to `spaceAgentBindings`): `spaceRoomNotices {noticeId, spaceRef, externalOrgId, kind (union of the six Application codes), actorExternalAuthId?, subjectId?, createdAt}` with indexes `by_space_and_created (spaceRef, createdAt)`; written inside the existing mutations `bindExistingSpaceAgentForGateway` (:529), `createSpaceAgentForGateway` (:412), `setSpaceAgentBindingStateForGateway` (:596) and the room-details mutation (WS04-S2) in the same transaction; read by `spaces:roomNoticesForGateway` (query, args `{externalOrgId, spaceRef, after?, before?, limit}`, service-key gated like the other `*ForGateway` functions); pruned by an existing-style cron after 90 days. ### D8 Authority and ZDR summary

| Hop | Check |
|---|---|
| Browser to BFF | session cookie; `authorized_org_id`; flag; rate limit (preview 20 per minute per user; timeline limit 1..100) |
| BFF to Convex | `space_lifecycle_by_ref` active; notices read with the service key, org and space scoped |
| BFF to Control | membership resolved under the signed delegation; read decision minted per page (fresh, never cached); membership-events read under RES; role editor or above for previews |
| BFF to model-gateway | verified user bearer; decision relayed in the query like the two existing shared reads (do not log URLs) |
| model-gateway to Session Core | `authenticated_session_request`; Session Core verifies the decision (subject equals caller, org, Space, `thread:read` without write permission, expiry) and applies the ceiling; org-scoped SQL |
| Session Core to Postgres | every query is `org_id` and `space_id` scoped; the trigger never crosses threads |
| BFF to Quarry | user-scoped Quarry token (`shared::quarry_token`), SSRF pre-check, Quarry `dns_guard` is the enforcement point |

ZDR: timeline, transcript window, notices and membership rows contain ids, counts and closed words only; no new durable content is written for ZDR callers. Drafts: `isLocalRetentionAllowed()` false means nothing is stored and stored text is removed (existing hook behaviour). Link previews: refused with the typed ZDR code at the BFF (R3) and never fetched, cached or attached; an `entry` on a non-post append is refused by Session Core; posts themselves are already refused for ZDR by WS01. The preview cache entry is never written when `zdr` is active (reuse of `CacheAdmission` logic, `quarry.rs:212-229`). Logs: route handlers log ids, counts and status, never URLs, titles or draft text.
