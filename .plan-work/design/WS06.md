### D2 The Space decision flag (S2)

A gate, not a policy change. `mp-contracts/src/retention.rs` (U) gains `space_zdr_mode(Option<&str>) -> SpaceZdrMode`, exact-match like `process_host_enabled_from` (only `"enforce"` enables). | Mode | Flag true | Metric |
|---|---|---|

### D6 Resource caps (S7, S8)

Layers, cheapest first; none needs `unsafe`.

1. Container (S7, compose only). The execution-core block and the production overlay gain `mem_limit: ${EXECUTION_CORE_MEM_LIMIT:-3g}`, `memswap_limit` equal to it, `cpus: ${EXECUTION_CORE_CPUS:-3.0}`, `pids_limit: ${EXECUTION_CORE_PIDS_LIMIT:-1536}`, `ulimits.nofile: 16384`. Starting values, calibrated in S10: tmpfs `/tmp` (512m in production) counts against `mem_limit`, and the pids budget must cover tokio's blocking pool (up to 512 threads) plus a fork-bomb margin. `RLIMIT_NPROC` is not used per spawn: it counts every thread of uid 10001, execution-core's own included.
2. Bounded output (S7). `spawn_capture` (`executor.rs:270-309`) stops using `output()`: it spawns with piped stdio, reads each stream through `take(EXECUTION_SANDBOX_MAX_OUTPUT_BYTES)` (default 1 MiB), keeps `scrub_and_cap` for the 64 KiB result and kills the child past the cap. `ExecOutcome` gains `limit_hit: Option<LimitHit>`.
3. Spawn concurrency (S7). A process-wide `tokio::sync::Semaphore` (`EXECUTION_SANDBOX_MAX_CONCURRENT`, default 8) taken before every spawn in `executor.rs` and `process_host.rs`, wait bounded by `EXECUTION_SANDBOX_QUEUE_WAIT_MS` (5000); on timeout the step fails with "sandbox is busy, retry later" (transient on purpose).
4. Per-spawn rlimits (S8). `sandbox::wrap_command_with` prefixes the argv with `prlimit` so the limits are inherited by bwrap and everything under it:
```
prlimit --cpu=<s> --as=<bytes> --fsize=<bytes> --nofile=<n> --core=0 -- bwrap <existing argv> -- <program> <args>
```
`LaunchOptions` gains `limits: Option<&ResourceLimits>` (a struct in `policy.rs`; `MpSandboxPolicy` stays the one canonical vocabulary). Defaults, env-tunable, read once: `EXECUTION_SANDBOX_LIMITS=enforce|off` (default `enforce`), CPU seconds = wall timeout x `EXECUTION_SANDBOX_CPU_FACTOR` (2; background processes use their TTL), `EXECUTION_SANDBOX_MAX_ADDRESS_SPACE_MB=4096`, `EXECUTION_SANDBOX_MAX_FILE_MB=64`, `EXECUTION_SANDBOX_MAX_OPEN_FILES=1024`, core dumps 0. `RLIMIT_AS` bounds virtual size, not RSS, and 4096 is a guess for numpy, pandas and matplotlib (S10 measures; too low breaks real work); the RSS backstop is the container limit. `prlimit` comes with util-linux in `debian:bookworm-slim` (UNVERIFIED in the built image: S8 adds a `prlimit --version` build-time assertion to the Dockerfile). A `limits_enforceable()` probe, run once like `is_supported` (`sandbox.rs:250`), makes the host refuse restricted spawns when limits are `enforce` and `prlimit` is missing: fail closed, as for missing bwrap.
5. Classification. On unix `ExitStatusExt::signal()` maps SIGXCPU to `Cpu` and SIGXFSZ to `FileSize`; SIGKILL is `Killed` (OOM or timeout, indistinguishable). `limit_hit` reaches `CodeResult` as one additive object `execution: {sandboxed, limits: "enforced"|"unlimited", limit_hit}` (sibling b F-t3-043 part a wants these badge fields; WS06 supplies the data). Counter `execution_core_sandbox_limit_hits_total{kind}`, `kind` in `cpu, file_size, output, killed, busy`. The capability profile gains `limits: "enforced"|"unlimited"` (`sandbox.rs:279`), which changes `capability_profile_digest` values by design; Control validates only the digest format and sandbox-manager binds the string it is handed, so there is no contract bump (`capability_verifier.go:155-190`).
6. Retry safety (S8). Add `"resource limit exceeded"`, `"requires a sandbox lease"`, `"sandbox egress is not available"` to `NOT_TRANSIENT_MARKERS` (`retry.rs:88`) and extend the collision test at 270. "sandbox is busy" stays transient.

## Open questions for the user

1. Should a Space whose org policy row says zero data retention refuse new posts and agent turns (the `enforce` mode), keep working as today (observe), or also get scratch-only sandboxes?

5. May the Dockerfile gain `socat` and the container gain unix-socket bind mounts for the egress track, or is that track closed until a vendor sandbox backend is chosen?
