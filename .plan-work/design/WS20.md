## Design

### D1 Model and the conflict ruling (C1)

- A **room browser run** is an ordinary Session Core run: owner = the starter, `source = GatewayBrowser`, thread = a room thread carrying the Space audience columns (copied at start, `grpc.rs:3113-3123` per WS09), executed by execution-core, driven through Quarry. Nothing new is stored in Session Core except events, one approval kind and one assistant result turn.
- **Space authority is server-resolved (conflict C1).** The client never sends a Space reference in a body. `space_ref` comes from the route path, is validated through membership and lifecycle, and authority is a Control-signed decision. The Space is then carried three ways that must agree: the thread row (Session Core), the signed browser decision (broker), and `ExecuteStepRequest.space_id` (execution-core). Any mismatch is a hard denial. This satisfies sibling b's rule (`resolve_space_role`, never client-supplied, b:546) and the audit's "decision bound to the room audience hash and revision".
- **Narrowing only.** The Space may only narrow a grant. Broker domains = the requested hostnames, bounded (at most 8, canonical, no IP literals, no wildcards), intersected with any org policy (sibling a F-t2-022; v1 ceiling = request). The profile is forced to ephemeral; `profile_id` is rejected for room runs.
- **Starter-bound control.** Run ownership stays with the starter (Session Core, Quarry `initiator_subject`). Viewers are members who pass a Control read decision. Control of the page (agent or human) is a single lease in Quarry with one holder. v1 holder-eligible: the starter. S9 adds manager/owner.

### D2 Data flow

```
Start    SPA -> BFF POST /api/v1/spaces/{ref}/browser-runs
           -> (new thread? Control thread-decision) + Control thread-append-decision (goal) + Control browser-run-decision
           -> model-gateway POST /v1/browser/runs {thread_id?, goal, space_context, space_append_context, space_browser_authority, ...}
           -> broker AcquireGrant(space_authority)   verifies the Control decision (Ed25519), stores space_ref/audience/view_scope, narrows domains, ephemeral profile
           -> Session Core CreateThread/AppendMessage/StartManagedRun (existing Space path, ThreadSpaceContext)
           -> execution-core ExecuteStep(browser_agent, space_id = run's space)  three-way agreement check
           -> Quarry POST /v1/agent/runs {grant_id, delegation{run_ref, initiator_subject, view_scope}}
Read     SPA poll -> BFF GET .../browser-runs/{run}/timeline -> model-gateway -> Session Core ReadRoomBrowserTimeline (Control read decision, audience ceiling, revocation, projector)
Frames   SPA -> BFF .../frames/(stream|ws) -> model-gateway relay (heartbeat re-auth via Session Core every 15 s) -> Quarry /v1/agent/room-views/{run_ref}/frames/*  (service principal, acting subject)
Handoff  execution-core sees challenge -> approval(kind HUMAN_ASSIST) + event BrowserHandoffRequested -> room card -> starter Take control (Quarry lease) -> I'm done -> approval GRANTED + lease back to agent -> loop resumes
End      model-gateway: terminal -> append one assistant turn (metadata.browser_run, plain-text result) -> broker RevokeGrant
```

### D5 Model Plane

**BrowserBroker (Go, `apps/Model Plane/go/services/browser-broker`)**
- `browser.proto`: `AcquireGrantRequest.space_authority = 10` (`SpaceBrowserAuthority {space_ref, decision_ref, decision_token, claims_json, thread_id}`); `ValidateGrantResponse` gains `space_ref = 10`, `recipient_audience_hash = 11`, `recipient_audience_revision = 12`, `view_scope = 13`, `profile_scope = 14`, `max_runtime_s = 15`. Additive.
- New `internal/authz/space_browser_verifier.go` modelled on the sandbox-manager verifier (same envelope check; new permission and digest). Verifies signature, key id, expiry, org and subject equal the delegated principal, audience, action, schema, and that the digest binds the claims. On success the grant stores the Space fields, canonical domains (decision list, already normalized by `NormalizeAllowedDomains`), `profile_scope="ephemeral"`, TTL `min(max_runtime_s + 60 s, 10 min)` (shorter than the 15 minute default so removal latency is bounded), and refuses a second grant when active grants for (org, space_ref) reach 2 (`ResourceExhausted`).
- `RevokeGrant` is called on terminal and on stop; Quarry validates the grant on every step (V5), so a revoke stops the run at the next action.
- Depends on sibling a F-t2-001 for the durable store and the model-gateway issuance endpoint; the Space fields live in whichever store that item ships.

### D8 Authority at each hop

| Hop | Check |
|---|---|
| Browser to BFF | cookie session only; no decision, run owner id or Space body field on the wire |
| BFF | live org membership, Space lifecycle, ZDR lookup, flag, then Control decisions minted per request and never cached |
| Control | role floor, `browser_run_entitled`, current audience and privacy, `thread_read_entitled` for reads |
| model-gateway | verified bearers; two decisions agree on audience revision; no authority from JSON |
| Broker | verifies the Control decision signature and binding, org and owner from the bearer; stores narrowed policy |
| Session Core | thread Space columns, thread decision, run owner, read decision, audience ceiling, revocation table, posture |
| execution-core | run owner, grant validity, three-way Space agreement, ZDR |
| Quarry | service principal scope, per-step grant validation, lease holder, domain policy, SSRF guards |

Removal latency: a removed viewer loses the stream within the 15 s re-authorization; a removed starter's run ends at the next Quarry step after grant expiry at the latest (10 minutes), or sooner on manager stop. This is the stated bound.

### D9 ZDR

A browser run is a durable feature, so every ZDR surface refuses with an existing typed code (no new catalogue key, so `zdr-refusals.json` does not change): BFF (org lookup) -> model-gateway `browser_run_zdr_blocked` (`browser_run.rs:631`) -> Session Core read RPCs -> execution-core `enforce_persistence_free_execution` -> Control (`zdr_inert`) -> broker (no grant). Room viewers in a ZDR org never see the card. Frames are transient but are not offered under ZDR because no run can exist.

### D10 Explicitly not built

Agent-initiated browsing from a room turn (needs WS10 tool policy and F-t3-008; the seam is that room turns would call the same R1 internals). Teach by demonstration. Persistent or user-private profiles in a room. A shared per-run frame fan-out. Browser steps in the generic run stream or an Application Plane projection. Model-written hand-off instructions. Challenge bypass or proxy escalation of any kind. A second run state machine (the run, approval and events are Session Core's; sibling a F-t2-035 reuses the same). Human free browsing outside the grant's domains (F-t2-011). Member steering of a browser run. Co-browsing in the user's own tab (F-t2-013 phase 2).
