## Design

### D0. Decisions this design assumes (details under "Decisions needed")

| Id | Assumed option | Effect on the design |
|---|---|---|
| D-WS04-1 membership writer | Control writes human membership of named rooms through actor-carrying routes; every row carries a `source`; Application's declarative PUT is kept only for the organization room and for agent (`service`) bindings and may touch only rows whose source is `application_sync` | S4 and S6. Removes the self-join, guest and team clobber the audit lists (9.4 item 4). Application's `spaceMemberGrants` is retired in S12 |
| D-WS04-2 visibility | Rooms are `private` by default; `org_public` needs a per-org opt-in row (absence denies); history is full for open rooms | S8, S11 |
| D-WS04-3 archive | Archive is a Control `registration_state` (access state), orthogonal to Application's lifecycle; amends ADR-0001's "Application owns lifecycle" for this one reversible state | S7 |
| D-WS04-4 owners | Several active `owner` rows may exist (co-owners, assignable only by an owner); `registered_spaces.owner_principal_id` stays the immutable registrar and ownership transfer is not built | S4 role matrix |

### D1. Ownership map

| Piece of state or logic | Owner and service | Why |
|---|---|---|
| role, source, roster mode, visibility, join role, history mode, archive state, directory policy, membership ledger | Control, `apps/Control Plane/user-core` (`internal/spaces`) | Authority state; ADR-0001. Control already holds `space_memberships` and the revisions |
| room name, topic | Application, Convex `spaces` | Display metadata; ADR-0001 says Application owns name and collaboration metadata |
| recipient audience (the product recipient set) | Application derives it from Control's roster and registers it at Control through the existing outbox | ADR-0001: "the owning service supplies the audience, Control verifies each recipient" |
| organization-room roster | Application reads org-core and declares to Control (`application_sync` rows) | Roster is derived from the organization, not edited |
| people search | Control, user-core (`users` joined to `user_org_memberships`) | It owns both tables; org-core's search fans out and truncates (V10) |
| agent directory | Application registry (ADR-0002), composed in the BFF | Presence, not authority |
| composition, rate limits, typed errors, flags | Gateway (BFF) | Holds no durable state; validates and proxies |
| history floor filter | Session Core reads, using a Control-signed claim (S11 only) | Session Core owns messages; Control owns who may see what |

Nothing in WS04 stores messages, reactions, canvases or documents, and nothing is added to Convex that Control owns. WS04 adds no proto, no gRPC method, no Control decision type and no NATS subject; every wire change is HTTP JSON (additive) or an additive field on an existing event or decision.

Data flows (authority is checked at every hop, and the browser never supplies actor, organization, role rank or audience):

1. Add or change a member (flag on): SPA -> gateway (session, org from Control membership, rate limit, flag) -> Control `POST|PATCH .../members` under a signed delegation (body-bound, 30 s) -> Control locks the Space row, re-reads the actor's and the target's rows, applies `roles.go`, writes the row, advances revisions, appends the ledger row, commits, publishes the event -> gateway calls the Convex reconcile action -> Convex reads `audience-candidates` from Control, plans, calls `replaceRecipientAudience` -> the existing outbox registers the new audience snapshot at Control, which re-verifies every recipient -> the member's next shared decision succeeds and `recipient_ready` turns true.
2. Self-join: SPA directory page -> gateway `POST .../join` -> Control checks org policy, `visibility`, room state and the caller's active organization membership, then writes membership only (no `resource_grants`, no effect-policy change) -> same audience reconcile as above.
3. Archive: gateway -> Control `POST .../archive` (manager or owner) flips `registration_state`; every write resolver now fails closed and the five read resolvers keep answering; Application is not told and does not need to be (the UI reads `state` from Control).
4. Organization-room reconcile: org-core member change -> durable consumer -> `requestOrganizationRoomSync` (debounced) or the 10-minute cron -> `syncOrganizationRoom` reads org-core and declares the human roster with `roster_mode:"org_derived"` -> Control's source-scoped replace -> audience reconcile.

#### D2.2 Role rules (pure functions, one file)

New `internal/spaces/roles.go` (no database, no clock): closed role enum with rank `viewer 1 < editor 2 < manager 3 < owner 4`; `elevated(role)` is manager or owner. Functions return a typed `RoleDenial{Code, Details}` or nil. Matrix (golden vectors live in `internal/spaces/testdata/room-role-matrix.v1.json`, consumed by the Go table test and by the SPA mirror):

| Operation | Allowed when | Denial code (HTTP) |
|---|---|---|
| `CanAdd(actor, newRole)` | rank(actor) >= manager, and newRole is not elevated unless actor is owner | `room_role_forbidden` (403) if actor below manager; `room_elevated_role_requires_owner` (403) |
| `CanChangeRole(actor, targetCurrent, newRole, targetIsActor, activeOwners)` | rank(actor) >= manager; neither targetCurrent nor newRole elevated unless actor is owner; a self-demotion is always allowed; never a self-promotion | same two codes; `room_sole_owner` (409) when targetCurrent is owner, newRole is not owner and activeOwners <= 1 |
| `CanRemove(actor, target, targetIsActor, activeOwners)` | leave (targetIsActor) is always allowed; otherwise rank(actor) >= manager and target not elevated unless actor is owner | same codes; `room_sole_owner` (409) when the target is the only active owner, including on leave |
| `CanJoin(joinRole)` | joinRole is viewer or editor (never elevated, enforced again by the CHECK) | `room_not_joinable` (409, only if the CHECK would be violated) |
| `CanArchive`, `CanEditSettings`, `CanEditDetails` | rank(actor) >= manager (history mode: owner only) | `room_role_forbidden` (403) |

`activeOwners` counts rows with `role='owner' AND active AND subject_type='user'` whose user is an active organization member (an owner who left the organization cannot be the last owner of record). All inputs are read inside the transaction, never taken from the gateway.

Control adds `history_floor_revision` (`json:"history_floor_revision,omitempty"`, the same omitempty precedent as `import_source_type`, `decision.go`) to the signed read decision when the room's `history_mode` is `since_join` and `SPACE_HISTORY_WINDOW_CLAIM` is on. The floor is derived from audience snapshots, with no new membership column: the first audience revision after the latest revision that did not contain the subject, computed from `space_recipient_audience_members`. Session Core adds `history_floor_revision: Option<u64>` to `ControlSpaceDecisionClaims` (`grpc.rs:631`) and `history_floor: Option<i64>` to `VerifiedSpaceRead` beside `recipient_audience_revision` (`grpc.rs:1796-1808`; the struct stays `Copy`), and applies `AND (floor IS NULL OR m.recipient_audience_revision IS NULL OR m.recipient_audience_revision >= floor)` wherever the ceiling is applied today: the message read (`grpc.rs:5438-5465`), `list_threads` (`grpc.rs:5503`) and the run reads (`run_service_grpc.rs:708-735`, which reads the thread's revision). Rows with a NULL revision keep the existing thread-level rule. A claim of 0 or an absent claim means full history. A mixed-version fleet (new Control, old Session Core) therefore shows full history, which is today's behaviour: for an opted-in room an old Session Core ignores the claim until it is upgraded (fail-open on a presentation rule, never on authority), and a room that did not opt in is never affected.

## Open questions for the user

1. Should the product show the four role names (viewer, editor, manager, owner) or friendlier labels? The matrix assumes the four names.
2. Do you accept co-owners (D-WS04-4), or exactly one owner per room?
3. May a person a manager removed rejoin an open room by themselves? The design says yes; Slack does, a moderation model (F-t1-043) may not.
4. Is showing colleagues' email addresses in the directory acceptable by default, as `list_members` already does today?
5. May ZDR organizations store a room topic as a label (D-WS04-6)?
6. Who may mark a room `org_public`: any manager of the room (assumed) or only organization admins?
7. Is a hard limit of 512 people per shared room's audience acceptable until the audience contract is widened, or should S5 also raise it in Control and Application?
8. Space memberships and recipient-audience rows of an erased user survive GDPR erasure today (V19). Should WS04 extend the saga to them now, or is that WS05 scope?
9. Where does the production credential registry (`USER_CORE_SERVICE_CREDENTIALS`) live? Only the dev compose is in the repo, so the scope additions for production are unverified.
10. Is a 10-minute reconcile interval acceptable, or should removals reach the organization room faster than the existing member-change event path allows?
