### D1 Direct messages

**D1.1 Model.** A DM is a Control-registered Space of kind `dm` (exactly 2 people) or `group_dm` (3 to `MaxDMParticipants = 9`, creator included), one owner (the creator) and the rest `editor`, humans only. Its content is the ordinary room timeline: each message is a WS01 post thread; there is no second message model, no single "DM thread", and no new append path. A DM with an agent is never a `dm` Space containing a service subject (audit constraint); it is the personal scope plus a personal agent (WS17). Agents cannot be bound: Control refuses service members for DM kinds and the gateway and Convex bind mutations refuse the kind.

**D1.2 Identity.** `participant_hash = "sha256:" + hex(SHA-256("participant-set/v1\0" || for each id in byte-sorted, trimmed, unique subject ids: uint64be(len) || id))`, the exact encoding of `RecipientAudienceHash` (`personal_thread_decision.go:44-71`) with its own domain string. Ids are Better Auth ids, compared as bytes (not `localeCompare`; WS04 V23 shows the existing TS order defect). One shared vector file `apps/Control Plane/user-core/internal/spaces/testdata/participant-set-vectors.v1.json` is consumed by a Go test and a Convex `.cjs` test (WS04 vector-sync pattern). Kind follows from the count (2 gives `dm`, 3 to 9 `group_dm`), so the hash needs no kind. A one-person set (self note) is refused: that is the personal Space.

### D2 Message lifecycle

**D2.1 Model.** `messages` rows are never modified except the single sanctioned purge write below. A revision is a row in `message_revisions` (append-only) keyed by `message_id`; reads fold the latest revision into the message. Differences from the rejected design (V9): per-message not per-exchange, no nesting (a revision names exactly one message and an edit cannot target a deleted one), no supersede, and the fold runs in the SQL that every `ListConversation` consumer shares, so skill learning, memory extraction and model context all see effective content.

**D2.2 Session Core migration** `0048_message_revisions.sql` (reserve 0048; revert file `migrations/revert/0048_message_revisions.down.sql`, 0044 pattern):
```sql
CREATE TABLE IF NOT EXISTS message_revisions (
  revision_id         TEXT PRIMARY KEY,
  org_id              TEXT NOT NULL,
  thread_id           TEXT NOT NULL,
  message_id          TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  revision_no         INTEGER NOT NULL CHECK (revision_no > 0),
  action              TEXT NOT NULL CHECK (action IN ('edited','deleted')),
  actor_subject_id    TEXT NOT NULL,
  actor_class         TEXT NOT NULL CHECK (actor_class IN ('author','agent_owner','moderator')),
  moderation_reason   TEXT NOT NULL DEFAULT '' CHECK (moderation_reason IN ('','policy_violation','spam','harassment','privacy','other')),
  content             TEXT,             -- edited: new text; NULL for deleted or purged
  content_digest      TEXT NOT NULL,    -- sha256 of new text; sha256 of empty for deleted
  prev_content_digest TEXT NOT NULL,
  original_retention  TEXT NOT NULL CHECK (original_retention IN ('retain','purge')),
  idempotency_hash    TEXT NOT NULL,    -- sha256(org, thread, message, actor, key); raw key never stored
  space_id TEXT NOT NULL, recipient_audience_revision BIGINT NOT NULL,
  authority_revision BIGINT NOT NULL, resource_authorization_ref TEXT NOT NULL,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (message_id, revision_no), UNIQUE (message_id, idempotency_hash));
CREATE INDEX IF NOT EXISTS idx_message_revisions_thread ON message_revisions (thread_id, message_id, revision_no DESC);
```
`ON DELETE CASCADE` makes thread delete, GDPR erasure and Space deletion remove revisions with their messages (V10).

## Open questions for the user

1. Is a fixed roster acceptable for group DMs ("add someone" opens a new group with no history, as Buzz does), or is Teams-style add-with-history required now?
2. When an org enables edits and deletes but sets no retention rule, should the original text be purged (assumed) or retained for audit?
3. Do you want reactions stored in the Application plane (audit catalogue, assumed) or in Session Core with the message (cleaner erase, authority and realtime, needs one more Control decision)?
4. May room managers and owners delete other members' posts, and should org admins who are not room members be able to?
5. Should creating a DM require its own org entitlement (assumed) in addition to posting and reading rights?
6. What should happen to a DM when its creator is erased under GDPR (the thread owner's deletion removes the peer's messages today): block, anonymize authored rows, or accept?
7. Is the interim sidebar unread poll (10 DMs, 60 s) acceptable until WS11's aggregate ships?
