## Design

### D1 Model and vocabulary
- A Space **thread** stays the container: one room post, its human replies and its agent turns. A **post** is a `role='user'` message with the new column `messages.post_kind = 'post'`; `post_kind = 'turn'` (default) keeps today's meaning (addressed to the model: feeds context and memory).
- Two caller classes on `AppendMessage`: **owner** (thread owner, today's path, unchanged) and **member** (any other human who holds a verified `thread:append` decision for that Space). The member path accepts only `role='user'` + `post_kind='post'`.
- Posts are excluded from model context and from memory extraction always (not behind a flag, so a rollback cannot leak them). WS08 later adds explicit, attributed, fenced inclusion.

### D2 Data flow
```
New post:  SPA -> BFF POST /api/v1/spaces/{ref}/threads
             -> Control thread-decision (create, key=space-post-{id})
             -> model-gateway POST /v1/threads
             -> Session Core CreateThread (verify create decision; get-or-create by session_key)
             -> Session Core AppendMessage (first message, post_kind=post, client_message_key)
Reply:     SPA -> BFF POST /api/v1/spaces/{ref}/threads/{tid}/messages
             -> Control thread-append-decision (post_kind=post, content_digest, key)
             -> model-gateway POST /v1/threads/{tid}/messages
             -> Session Core AppendMessage (member or owner gate, decision v2)
Read:      unchanged routes (transcript, list); new fields post_kind, reply_count, last_author_subject_id
```
No run is created on either path. The BFF never calls Session Core; model-gateway only maps HTTP to gRPC and holds no durable state.

### D4 Session Core (`apps/Model Plane/rust/services/session-core`)

**D4.1 Migration** (reserve number 0046 for this slice; revert file `migrations/revert/0046_message_post_kind_and_dedupe.down.sql` follows the 0044 pattern):
```sql
ALTER TABLE messages ADD COLUMN IF NOT EXISTS post_kind TEXT NOT NULL DEFAULT 'turn';
ALTER TABLE messages ADD CONSTRAINT messages_post_kind_chk
    CHECK (post_kind IN ('turn','post')) NOT VALID;
ALTER TABLE messages VALIDATE CONSTRAINT messages_post_kind_chk;
CREATE TABLE IF NOT EXISTS message_send_dedupe (
    org_id         TEXT        NOT NULL,
    dedupe_hash    TEXT        NOT NULL,  -- sha256 over len-prefixed org, thread, author, client_message_key
    content_digest TEXT        NOT NULL,  -- sha256 of the content bytes; never content
    message_id     TEXT        NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    sequence       BIGINT      NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (org_id, dedupe_hash)
);
CREATE INDEX IF NOT EXISTS idx_message_send_dedupe_message ON message_send_dedupe (message_id);
```
`ON DELETE CASCADE` makes every existing erase path (thread delete `grpc.rs:490`, GDPR `gdpr.rs:290`, Space deletion) remove dedupe rows with the messages; no sweeper is needed. The column default is metadata-only on PostgreSQL 11+.

**D4.2 Proto** (`apps/Model Plane/proto/model_plane/v1/sessions.proto`, additive, wire compatible):
`AppendMessageRequest`: `string post_kind = 18;` (`""`/`turn`/`post`), `string client_message_key = 19;` (opaque, at most 128 bytes, separate from the authority-bound `idempotency_key` 16 so the first message of a new thread, which carries no decision, can still dedupe). `AppendMessageResponse`: `string message_id = 2; bool deduplicated = 3;`. `SessionMessage`: `string post_kind = 7;`. `ListConversationRequest`: `bool exclude_human_posts = 6;`. `ThreadSummary`: `uint32 reply_count = 15; string last_author_subject_id = 16;`. **D4.3 Authority gate (new `authorize_append`, beside `authorize_thread_owner`, `grpc.rs:294`)**
```rust
enum AppendAs<'a> { Owner, Member { subject: &'a str } }
// handler (grpc.rs:4495): authorize_operation first (unchanged, keeps the ZDR refusal first), then
let appended_as = authorize_append(&self.pool, &caller, &req).await?;
```
Logic: run today's `authorize_thread_owner(..Mutate)`. `Ok` -> `Owner`. Any error other than PermissionDenied (NotFound etc.) returns unchanged. On PermissionDenied evaluate the member gate; if it denies, return the **original** denial. The gate is a pure function over facts so it is table-testable without a database:
```rust
struct MemberFacts<'a> { flag_on: bool, caller_is_human: bool, org_matches: bool,
  role: &'a str, post_kind: &'a str, has_context: bool, schema: &'a str,
  thread_space: Option<&'a str>, req_space: &'a str, owner_is_system: bool,
  author_revoked: bool, content_bytes: usize }
fn member_append_denial(f: &MemberFacts) -> Option<&'static str>  // None = allowed
```
Allowed only when ALL hold: `SPACE_HUMAN_POSTS_CORE` on; human caller (not service); org equal; `role=='user'`; `post_kind=='post'`; complete decision envelope (`validate_append_space_context_shape` true); `action_schema_hash` is the v2 schema; thread has a Space equal to `req.space_id`; owner is not a system owner; no `space_membership_revocations` row for (space, caller); `1 <= content_bytes <= 32768`. Everything else is today's denial. The member path never accepts `assistant`/`system`/`tool`, never `post_kind='turn'` (otherwise an old chat client's prompt would persist as an orphan owner-context message because `start_managed_run` is still owner-gated, `grpc.rs:6307`).

**D4.4 Transaction (`append_message_in_tx`, `grpc.rs:2432`; keep the signature, add `append_message_in_tx_as(tx, req, author, AppendAs)` and make the old function a wrapper with `Owner`, so `terminalization.rs:1606` is untouched)**
1. Dedupe lookup, under the existing `FOR UPDATE` thread lock, when `client_message_key` is non-empty. Order matters: for a decision-bearing append (member or owner) it runs **after** the decision verified, so a replay never reveals a message to an unauthorized caller; for a decision-less owner bootstrap it runs before the `message_count` check. Hash = sha256 over len-prefixed `org`, `thread`, `author`, `key`. Hit with equal content digest: return the stored `message_id`/`sequence` with `deduplicated=true`, write nothing, emit no event. Hit with a different digest: `Status::already_exists` (BFF code `idempotency_key_conflict`). Miss: continue and insert the dedupe row after the message row. The bootstrap ordering (`message_count==0` path, :2457-2471) means a replayed create+post returns the original instead of "fresh decision required".
2. Member path only (extend the thread `SELECT` at :2447 with `recipient_audience_revision`): decision subject for `verify_append_space_decision_with_key` is the caller (`subject`), not `thread.1` (the :2498 fix; the digest at :2063 then binds the caller, matching Control's `evidence.Membership.SubjectID`). Reject with `Status::aborted("space_authority_stale")` when `req.recipient_audience_revision < threads.recipient_audience_revision` (a decision minted before an audience change cannot post). Do **not** run the thread-level `UPDATE threads SET space_decision_ref ...` (:2499-2514): the thread keeps the owner's newer-or-equal authority, and old history keeps its stamps. Stamp the new message from the verified request (`INSERT ... VALUES` with `space_id`, audience ref/revision/hash, `authority_revision`, `resource_authorization_ref`, `post_kind`) instead of `INSERT ... SELECT FROM threads` (:2570-2592). Ignore client `metadata` (it could relabel `source_scope`, :2538-2553); a conversation-only thread stays conversation-only (`conversation_only = stored_isolation`).
3. Owner path keeps the thread UPDATE and the `SELECT` stamp (unchanged), plus: accept `post_kind` (a `post` needs a v2 decision when a decision is present), dedupe, and the response fields.
4. For `post_kind='post'` (either path): skip `extract_memory_candidates`/`persist_candidates` (:2632-2675) and the Letta sync, so no post is learned.
5. Event: `MESSAGE_APPENDED` payload (:2611-2622) gains `post_kind` and `author_subject_id`. Hash and idempotency columns unchanged. Whether the outbox publishes it to NATS is WS02's (UNVERIFIED).

**D4.5 Containment and read changes (always on)**

### D9 Idempotency, end to end

| Layer | What dedupes | Key |
|---|---|---|
| SPA | one `sendId` per user action, reused on retry | `sendId` |
| BFF | passes keys; Control decision digest binds the key | `space-post-{sendId}` |
| model-gateway | in-memory claim (stream) and durable run-start dedupe exist; adds opaque message key | `derive_message_key` |
| Session Core | `message_send_dedupe`: same key + same content digest returns the original `message_id`; different content is `already_exists`; thread create is get-or-create on `session_key` | sha256(org, thread, author, key) |
| Control | stateless; no dedupe | n/a |

### D10 ZDR
Human posts are durable writes, so a ZDR org or credential gets the typed `zdr_durable_mutation_forbidden` (412) at the BFF and at model-gateway, and the free-text Session Core refusal (`auth.rs:277-281`) stays a third, backstop layer (typing it: WS06). The SPA shows the catalogue text and disables the Send-as-post control (Ask follows the existing ZDR chat rules). Dedupe rows and `post_kind` are never written for ZDR. The Space-level `zero_data_retention` decision claim is **not** enforced for posts, following the matrix policy `space_zdr: not_applied_in_v1`; if the owner decides otherwise it is one check in `verify_append_space_decision_with_key` plus the same typed refusal (Decision D-3).

### D11 Explicitly not built
Per-thread agent-engagement record and ambient wake-up (WS08); identity-bound @mentions and notifications (WS08, WS11); member-invoked or member-steered runs (WS09, ADR 5); edit, delete, reactions (WS12); markdown/link rendering of posts (WS07/F-t1-030, WS15); drafts and attachments (WS14, WS15); push/echo frames (WS02); server windows and virtualisation (F-t1-034); a normalized client store; per-room flood control (F-t1-043); author-level erasure of a member's posts (owner thread deletion removes them: Open question 4).
