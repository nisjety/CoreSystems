### S1 [FINISH] LoopGuard helper and the gateway inline loop
**Goal:** detect repeat failure, cycles and no progress; remind, then stop; never replay.
- NEW `MP/rust/crates/mp-contracts/src/loop_guard.rs` (+ `pub mod loop_guard;` in `lib.rs` line 2 neighbourhood) - pure, no I/O: `CallRecord{signature, outcome: Ok|Err|Suppressed}`, `LoopGuard::observe_round(&[CallRecord]) -> Verdict{Continue | Remind{level,text} | Stop{reason: Repeat|Cycle|NoProgress, signature_hash}}`. Rules: same signature failing or suppressed 3 and 5 times gives escalating reminders, 8 stops; cycle = period 2-3 repeated 3 times over the last 12 signatures; no progress = 4 consecutive rounds whose calls all errored or were suppressed. Thresholds are constants with env override clamped in the callers. The guard never executes or retries anything: it only produces text and a verdict (so reminders cannot replay side effects; the retry gate `EC/runtime_loop/retry.rs:149-150` and `MG/tool_retry.rs:16` stay the only retry authority).

- `MG/state.rs` or `tool_loop.rs` - read `LOOP_GUARD_MODE` once.

## 6. Cross-session interfaces

- **(a) Verevon Space session.** Shared: per-tool allow/ask/block with an org floor and a Space ceiling, a strict/standard/open posture, an admin UI. Owner: Model Plane owns the lattice (`agent_mode::resolve` takes `ceilings: &[Ceiling]` so a `space` source tightens without a new code path) and the engine; Space owns its binding fields. Why: capability-core `IsSupportedScope` accepts only org/global (`engine.go:46-54`), so a `space` scope is a small additive extension neither F-t3-003 nor F-t3-032 lists; assumed to land later, tighten-only, keyed by `SpaceRef`. Assumptions: the Space session does not build a second mode vocabulary (adopts `AgentMode` ids), shares the hub components rather than a second admin UI, and Control keeps owning only standing grants and `turn_origin`. Hooks apply to Space runs through the same `org_policy`. The overlap table says "Control decides"; this design records the deviation (D1) for owner ruling.
- **(b) Quarry v2 / browser session.** Shared: lockdown and hooks over `browser_agent`. Model proposes, Quarry executes or rejects is untouched; org hooks may deny `browser_agent` by name and lockdown sets `do_runs=false`. Per-site and web policy stay in org-core/Quarry (F-t2-022, F-t3-055); they register keys into the schema registry later. Assumes Quarry keeps the versioned browser contract.

## 8. Effort and risks

**Total:** about 70-95 engineer-days (XL). Critical path: S0, then S3, S6, S7, S8, S9, S10, S11, S12 (about 45-55 days with two engineers). S1, S2, S4, S5 run in parallel and need no owner decision.

**Top risks**
1. Hot-file collisions in `agent.rs`, `runtime_loop/mod.rs`, `sse.rs`, `permission/mod.rs` (live +207, +18, +425): mitigated by the edit-first order, small additive hunks and rebasing on WS03 `waived`.
2. Fail-closed policy reads breaking Do availability: typed 503 with the D8 stale bounds, no-row means defaults, shadow mode first, kill switch `ORG_AGENT_POLICY_MODE=off`.
3. Untrusted content parked then re-read unscreened (S4/S5): store the screening verdict, prepend the rendered label to every slice, ZDR never parks, dedicated tests.
4. Evaluator semantics change (first-match to strictest-wins, fail-open to fail-closed) surprises existing rules: shadow mode logs `would_have_denied`, ledger entries, order-independent semantics, in-memory rules today are rare (no consumer).
5. Ownership disagreement (D1) after building: single read contract in mp-contracts keeps the producer swappable; decision recorded in S0 before any store code.
