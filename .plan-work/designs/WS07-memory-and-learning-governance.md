### S2 [BUILD] Reset all memory

## 8. Effort and risks

**Total.** S1 L (5-6d), S2 M (2-3), S3 M-L (4-5), S4 L (5-7), S5 S (1-2), S6 S-M optional (2-3), S7 M-L (4-6), S8 M-L (4-5), S9 L (5-6), S10 M (3-4): 36-47 days, about 5-6 calendar weeks with a backend and a frontend engineer in parallel. **Critical path:** WS01 live set -> S1 -> S4 (session-core part) -> S7 -> S8 -> S9 -> S10. S2, S3, S5 and the org-core/UI halves of S4 run beside it.

**Top risks.**
1. A memory writer outside the gate (capability-core SQL, a future path). Mitigation: source-scan test, S5, `MEMORY_CONTROLS_ENABLED` kill switch with ERROR logging, ownership-matrix note.
2. Merge pressure on live-modified session-core, model-gateway and settings files (hundreds of uncommitted lines). Mitigation: land the live set first (WS01), thin edits, new logic in new modules, proto appends.
3. Org policy staleness and outage behaviour (poll interval; fail-open dev vs fail-closed prod). Mitigation: explicit bound, `ORG_POLICY_FAIL_CLOSED`, mirror watermark, metrics on mirror age.
4. Cross-user skill exposure during the cache and index change. Mitigation: unique-index fix before any user-scoped write, fail-closed ownership for learned skills, the four gateway tests plus the live two-user proof.
5. Review cost and injection persistence. Mitigation: disabled owner-scoped proposals, per-user and per-org caps, org opt-in default off, WS26 hook; OD4 stays an owner decision and cannot be enforced until a route kind exists.

**Not determined (do not assume).** Callers of capability-core `/api/v1/memory`; whether `bindJSONRequest` rejects unknown fields (S5); capability-core's Redis wiring (S10); the setter handler for `persona_enabled` (S6); the exact chat message action component for "Husk dette" (S3); whether `execute_recall_memory` needs more than the error mapping.
