### 2.1 F-t2-009: what the scrape pipeline does with a body

- `PageRunner::run_inner` fetches through the driver (`Q/quarry-runtime/src/pipeline.rs:361-364` [C]), caps the body at 16 MiB (`:421-443`, `MAX_HTML_BYTES`), reads Content-Type only for the `PageFetched` event and for charset decode (`:444-448`, `:452-463`, `:473-476`), then runs readability, link extraction and metadata extraction over the lossy-decoded text of every body (`:506-508`). Branding silently yields `None` for non-UTF-8 bodies (`:559-591`). Soft-404 detection also runs on the decoded binary (`:490-504`).
- [DRIFT] audit citations `pipeline.rs:441-506` and `:440-480` are now `:444-508`; `answer.rs:679-753` is `:680-683` (the `PDF_MAGIC_SCAN_BYTES = 1024` constant) plus `:738-754` (`fn is_pdf`, private). The PDF branch of the answer fetcher is `Q/quarry-runtime/src/answer.rs:835-841` [C], the only caller of `quarry_transform::pdf::extract_text`.
- `docx::extract_text` (`Q/quarry-transform/src/docx.rs:18-44` [C]) has no production caller. Confirmed by grep for `docx::` outside quarry-transform. `images.rs` is HTML lazy-image helpers only (`images.rs:27`, `:59`, `:89`, `:121`); there is no image parser and none is planned here.
- [CLAIM-FALSE] "keep ... zip decompression-bomb limits". No such limit exists. `docx.rs:15` caps the compressed input at 25 MiB and `docx.rs:39` then does an unbounded `read_to_string` of `word/document.xml`, so a 25 MiB archive can inflate to gigabytes. For PDF the same hole sits in the dependency: `lopdf` 0.42.0 `decompress_zlib` ends in `read_to_end` with no output cap (`lopdf-0.42.0/src/object.rs:849-865`, read from the cargo registry), and `Document::load_mem` (`Q/quarry-transform/src/pdf.rs:209`) plus `get_and_decode_page_content` (`pdf.rs:73`) decompress object and content streams. The 25 MiB caps (`pdf.rs:40`, `docx.rs:15`) bound input only. There is no parser timeout either: both parsers are synchronous and the pipeline would call them on an async worker.
- [CLAIM-FALSE] "the 25 MB parser cap" as seen from /v1/scrape. The pipeline rejects anything above 16 MiB first (`pipeline.rs:421-443`), and worse, the driver has already buffered the whole body in memory by then: `Q/quarry-runtime/src/fetch.rs:387` `resp.bytes().await` (reqwest decodes gzip, brotli, deflate and zstd transparently, features at `QR/Cargo.toml:42`) and `Q/quarry-tls/src/lib.rs:357-360` `resp.bytes()`. The 16 MiB cap is a post-hoc check, not a read limit. Routing documents makes users point scrape at large files, so the read limit has to land with this item.
- [CLAIM-FALSE] stale docs: `QR/docs/GAP.md:85` says PDF/text/binary routing is implemented in the pipeline; `QR/docs/PARITY_IMPLEMENTATION_PLAN.md:129` says DOCX is SHIPPED. Neither holds (S4 sweep, re-checked).
- The sniff helper to reuse: `is_pdf` (header contains `application/pdf`, or `%PDF-` anywhere in the first 1024 bytes). Its unit tests are `answer.rs:1251-1266` (including "text/html with `%PDF-1.4` body is a PDF" and "marker after 1024 bytes is not"). One weakness for a scrape path: an HTML page whose first KiB contains the literal `%PDF-` (a docs page, an inline script) would be routed to the PDF parser. The shared helper adds a guard (section 4, slice 1).
- Browser driver: `Q/quarry-runtime/src/browser_driver.rs:281-285` [C] always returns a synthesized `text/html; charset=utf-8` DOM snapshot, so documents never reach the sniffer through a browser plan; the default plan is static (`driver_plan.rs:36-50`, `DriverPlan::static_fetch`). A PDF URL fetched by the browser driver yields the viewer DOM [INF, not run]. The card's "reuse the bytes the browser downloaded" is out of scope here (needs F-t2-039 governed downloads).
- Fallback driver: `Q/quarry-runtime/src/fallback_driver.rs:118-155` [C] runs `needs_browser_escalation(&resp.body, ...)` on whatever body static returned. `visible_text_len` (`:486-542`) counts non-whitespace bytes outside tag-shaped spans, so for a random binary roughly half the bytes count as "text" and the `>= 2000` gate (`:403`) returns false for any binary above a few KiB. A browser escalation on a PDF is therefore unlikely, not impossible (binaries of 8 to 20 KB with long `<...>` runs). A defensive guard costs 0.25 day (slice 1).
- `/v1/extract` has the same blind spot: `Q/quarry-edge/src/extract_routes.rs:138-165` [M] does `String::from_utf8_lossy(&resp.body)` then `html_to_readable_markdown` for any 2xx body, with no content-type use. It can adopt the shared module (slice 2, optional step); the file has uncommitted hunks at `:205-228` and `:512+` (F-t2-019 gate work).

## 3. Design decisions

Each decision lists options, the recommendation and why. "ADR-GATED" means it needs an owner decision tied to an audit 9.3 topic; "DECISION" means a smaller choice the user should confirm but that does not block the build.

**D1. Where content-kind detection lives and which signal wins.** Options: (a) a new pure module `quarry-transform::sniff` shared by the pipeline, `/v1/extract` and the answer fetcher; (b) inline code in `pipeline.rs`; (c) put it in the Driver trait. Recommendation (a). Precedence: binary magic bytes beat the Content-Type header (the Norwegian public-sector rationale at `answer.rs:738-744`: PDFs served as `text/html` or `application/octet-stream`); the header only chooses among kinds the bytes cannot distinguish (html vs xml vs text vs json) and for confirming OOXML flavour. Firecrawl checks the header first and magic second; Verevon already has evidence that headers lie, so bytes first. Table: `%PDF-` within the first 1024 bytes, with a guard so an HTML document that merely contains the literal does not match (when the body's first non-whitespace byte is `<` and the header says html/xml/text, require `%PDF-` at offset 0); `PK\x03\x04` zip, confirmed by reading the central directory and a bounded `[Content_Types].xml` entry (the check Firecrawl lacks; plain zips, ODF, EPUB, XLSX and PPTX must not reach the DOCX parser); OLE2 `D0 CF 11 E0 A1 B1 1A E1`; PNG/JPEG/GIF/WEBP; gzip, 7z, rar, tar; MP3/MP4/OGG/WEBM/WAV; `MZ` and ELF; `{\rtf`. `application/octet-stream` with no magic hit and no NUL byte in the first KiB and a valid UTF-8 prefix stays on the text path (a misconfigured server serving HTML), otherwise it is an unknown binary skip. Text-ish kinds (html, xml, xhtml, text, json, csv) keep today's path unchanged. Rationale: smallest behavioural change, one function, easy to table-test.

**D2. How a non-routable body is reported.** Options: (a) new `ErrorCode::UnsupportedMedia` mapped to HTTP 415, not retryable, with `details {reason:"unsupported_media", kind, subtype, content_type, bytes, source, supported}`; (b) reuse `ErrorCode::Unsupported` (501); (c) return 200 with empty markdown and a `skipped` field. Recommendation (a). (b) is wrong because 5xx is retried: the Temporal orchestrator classifies 5xx as retryable (`QR/services/quarry-orchestrator/internal/errs/errs.go:161-187`) and the gateway preview retries 5xx with a static fetch (`GW/domains/knowledge/quarry.rs:144-147`). (c) hides the reason from agents and makes crawl counts lie. A 415 maps to `CategoryClient4xx` (non-retryable) in the orchestrator and counts as `pages_failed` without failing the crawl (`workflows.go:465`, `:571`). The pipeline also emits the existing `PageBlocked` event with `reason:"unsupported_media"` (same vocabulary as `body_too_large` and `soft_404`, `pipeline.rs:423-433`, `:493-503`). Additive per CONTRACTS.md section 10: the Rust enum gains a variant, the Go mirror (`QR/pkg/quarrycontracts/envelope.go:30-70`, which already lags the Rust enum) gets a constant. DECISION for the user: confirm that crawl runs now report image/archive links as failed pages (415) instead of ingesting mojibake (question Q2).

**D3. Where documents are parsed.** Options: (a) in-process in quarry-transform behind `spawn_blocking`, with a timeout and a concurrency semaphore; (b) a re-exec'd child process of quarry-edge with `RLIMIT_AS` and `RLIMIT_CPU`; (c) call imports-core's Python parsers (`apps/Ingestion Plane/imports-core/app/parsers.py`, budgeted office parsers per S4); (d) Model Plane document intelligence. Recommendation: (a) in slice 2 with every limit this design can apply in-process, (b) as slice 3, a hardening gate before `DOC_ROUTING=on` serves untrusted multi-tenant traffic. Reject (c): imports-core `/api/v1/import/extract` is ephemeral and has no `zdr` parameter (S4 F-t2-037 citation `main.py:204-212`) and Ingestion would depend on a sibling service for a core fetch step; reject (d): the model-gateway grant is `granted:false` with no owner (audit 9.4 note 7) and OCR is F-t2-037. Why (b) is needed: the in-process limits cannot stop a flate bomb inside lopdf (2.1); a timeout cannot kill a blocking thread, so the semaphore is held until the thread really finishes. ADR-GATED(10 partial): isolation level of document parsing is a substrate question adjacent to ADR topic 10 (shared pool vs per-session isolation); it needs the owner's call on whether in-process is acceptable (question Q1).

**D4. Byte and time limits.** HTML/text stays at 16 MiB (`pipeline.rs:421`). PDF and DOCX get 25 MiB (existing `MAX_PDF_BYTES`/`MAX_DOCX_BYTES`). The driver hard cap is 26 MiB, enforced while reading (D4a, new): `FetchHints.max_body_bytes`, a `Content-Length` precheck and a streamed read that aborts at the cap (decoded bytes, so gzip bombs count). DOCX adds: `word/document.xml` at most 32 MiB inflated via `Read::take`, at most 4096 zip entries, compression ratio at most 200:1, `[Content_Types].xml` at most 256 KiB. PDF adds: at most 2000 pages and 8 MiB of extracted text (output caps the existing code lacks). Parse deadline 15 s, concurrency 2 per process, all configurable downward only. Rationale: the numbers sit above real documents (a 1000-page DOCX has a roughly 5 to 20 MB `document.xml`) and well below memory exhaustion.

**D5. Fingerprint stays the raw-body hash.** Options: salt the fingerprint with the content kind; keep it. Recommendation: keep it (2.1 table). Salting would flip every existing PDF baseline and every change monitor on rollout for no benefit; the raw bytes already identify the document. The new `metadata.content_kind` carries the kind.

**D6. Response shape: where inline text goes.** Options: (a) nested `content: {markdown, html}`; (b) top-level `markdown`, `html`, `raw_html` on the scrape data object (Firecrawl shape); (c) change `OutputFormats.markdown` to an enum of ref or inline string. Recommendation (b). Three existing consumers already read `data.markdown` (rows 1, 3 and the TS type in 2.2), (a) would leave them broken, and (c) breaks the typed Rust consumers and the generated SDKs. The legacy `formats` object (refs, links) is untouched, so v1 stays additive. Names are snake_case to match `NormalizedOutput` (`final_url`, `prev_fingerprint`); the TS `ScrapeResult.rawHtml` type is corrected in slice 7.

**D7. A wrapper type, not new fields on `NormalizedOutput`.** `ScrapeResponse { #[serde(flatten)] output: NormalizedOutput, scrape_id, effective_options, markdown, html, raw_html, truncated, omitted, warnings }` in quarry-core. `NormalizedOutput` is also the Redis cache value (`cache.rs:38-75`), the `internal_run_page` projection source and the orchestrator contract; inline page text there would be cached under a fingerprint key shared across orgs and would balloon Temporal payloads. The wrapper is only ever built in the scrape handler. The persisted scrape record (D13) stores the `NormalizedOutput` and `effective_options`, never inline text.

**D8. Request names and shape.** Use the names CONTRACTS.md already promises: `formats`, `only_main_content`, `include_tags`, `exclude_tags`, `remove_base64_images`, plus camelCase aliases (`onlyMainContent`, `includeTags`, `excludeTags`, `removeBase64Images`) via `#[serde(alias)]` because the gateway and the Firecrawl ecosystem send camelCase and `formats` is already camelCase-era. New keys flattened onto the request root: `ScrapeRequest { url, prev_fingerprint, cache, zdr, privacy, signals, ingest, org_id, render, prefer_http3, #[serde(flatten)] options: ScrapeOptions }`. Additions beyond the documented schema: `extractor` (`readability` | `clean_full` | `raw`), `timeout_ms`, `max_inline_bytes`. `formats` takes strings now (`markdown`, `html`, `rawHtml`, `links`, `metadata`); typed objects (`{type:"json"...}`, `screenshot`) arrive with F-t2-019 and F-t2-023. `ScrapeFormat` is a `#[non_exhaustive]` enum with a custom deserializer so adding object variants later is additive. `links` and `metadata` are accepted as always-on (links already ride in `formats.links`, metadata in `data.metadata`). Unsupported documented formats (`images`, `summary`, `screenshot`, `attributes`, `query`, `branding`, `audio`, `changeTracking`, `json`) are rejected with a field error, code `unsupported_format`, naming the supported set. Deviation from CONTRACTS.md, stated: the contract says unsupported things return `UNSUPPORTED` (501); this design returns 400 with a field-level code because callers retry 5xx.

**D9. Strict validation with a lenient period.** `#[serde(flatten)]` cannot be combined with `#[serde(deny_unknown_fields)]` (serde limitation), and a typed `Json<ScrapeRequest>` extractor cannot return field paths. So the handler takes `Json<serde_json::Value>`, computes `unknown = keys(body) - (ScrapeRequest::FIELD_NAMES + ScrapeOptions::FIELD_NAMES + aliases)`, then deserializes the typed struct and collects `FieldError {path, code, message}`. A unit test pins `FIELD_NAMES` against the serde output of a fully populated request so the list cannot drift. Modes, latched at startup from `QUARRY_EDGE__SCRAPE_REQUEST_VALIDATION` (`lenient` | `strict`) and `QUARRY_EDGE__SCRAPE_STRICT_AFTER` (RFC 3339): lenient before the date, strict after, strict immediately if the mode is forced. Lenient behaviour for unknown keys: ignore, add `warnings[] {code:"unknown_field", field, message}` to the response and echo them in `effective_options.ignored_fields`; send `Deprecation: true` and, when a date is configured, `Sunset: <date>` headers (CONTRACTS.md section 10 prescribes `Sunset`; its "event" half is not added: the event type list is frozen, CONTRACTS.md `:70`, so the log line carries it: `tracing::warn!(target="quarry.scrape.unknown_field", org_id, principal, fields=?names)`, names only, never values, never the URL). Never lenient: a reserved denylist (`skipTlsVerification`, `skip_tls_verification`, `proxy`, `proxyUrl`, `headers`, `mobile`, `stealth`) is rejected with 400 from day one, because accepting and ignoring a security-sensitive key is the exact Firecrawl footgun the audit warns about. `org_id`, `prefer_http3` and `render` stay accepted. Field-level 400 shape: `QuarryError(BadRequest, "invalid scrape request").with_details({"fields":[{"path":"include_tags[2]","code":"invalid_selector","message":"..."}]})` inside the standard envelope, so a Model that proposed bad options can read `error.details.fields` and correct itself ("Model proposes, Quarry rejects").

**D10. `skipTlsVerification` never enters the contract.** No TLS toggle exists today (2.2). The key is on the reserved denylist (D9); `effective_options` will never carry it. If a future item wants one, it needs an ADR (it is a security-posture switch), defaults false, is rejected for ZDR and for service principals, and must be echoed in `effective_options`.

**D11. Extractor and main-content semantics.** `only_main_content` defaults true and `extractor` defaults `readability`, which is exactly today's `html_to_readable_markdown(&body_text)` call (`pipeline.rs:506`): default requests are byte-identical to before (golden test). `only_main_content:false` selects `clean_full`: strip `script, style, noscript, template, iframe` and `head`, keep nav/header/footer, resolve lazy images (`images.rs:59`), strip base64 images (`images.rs:121`, default on, otherwise giant inline `![](data:...)`), then html2md. `extractor:"raw"` runs html2md over the decoded body with no cleaning. Cross-field rules: `only_main_content:true` with `extractor:"raw"` or `"clean_full"` is a field error on `extractor`. `include_tags` and `exclude_tags` are CSS selector lists (the contract calls them tags but Firecrawl and the gateway treat them as selectors), at most 32 entries of at most 256 chars, parsed with `scraper::Selector` (full CSS, errors become field errors with the entry index; `lol_html`, which attributes.rs and images.rs use, cannot express "keep only these subtrees"). Order: parse once, detach excluded nodes, keep included subtrees (deduplicated when nested), then the extractor. An include list that matches nothing yields empty markdown plus warning `include_tags_matched_nothing`; it never silently falls back to the whole page (that returns content the caller excluded by omission). Firecrawl's 42-selector chrome list is not copied: readability scoring already handles chrome. The Apify-style "readability too thin, fall back to the cleaned full page" quality fallback is out of scope; add it only with eval evidence.

**D12. Inline return and ZDR.** Inline text is returned to the caller that asked, held only in the response; nothing is written. ADR-GATED(4, soft): ADR 4 asks what ZDR means per feature and recommends "do not loosen existing refusals". Inline return loosens nothing: no artifact, no cache, no event content, no record. The design states the scrape row for the ZDR matrix (owned by F-t2-003): `scrape.inline` = inline-only, `scrape.record` = refused, `scrape.page_cache` = bypassed, `scrape.doc_parse` = in-memory only. Inline cap: default 1 MiB per field (`QUARRY_EDGE__SCRAPE_INLINE_MAX_BYTES`, ceiling 8 MiB, `max_inline_bytes` can only lower it). Over the cap without ZDR: the field is omitted, listed in `omitted`, and the existing `formats.*` `FormatRef` is the fallback. Over the cap under ZDR (no ref can exist): the field is truncated at a char boundary and listed in `truncated`. Under ZDR with no `formats` supplied the default is `["markdown"]` inline, because refs cannot exist and returning nothing is the bug being fixed; non-ZDR keeps the legacy shape unless `formats` is sent.

**D13. Scrape-by-id storage.** Options: (a) a small `scrape_record` artifact in the existing tenant-bound artifact store, `scrape_id` = that artifact's id; (b) Redis key `quarry:scrape:{org}:{id}` with TTL; (c) a Postgres table (`QR/crates/quarry-runtime/migrations/0010_*.sql`, next free after `0009_browser_timeline_events.sql`). Recommendation (a). It needs no migration and no new store, works on memory/fs/s3 backends, inherits the tenant check (`ensure_org_owns`, `artifact_store.rs`; a foreign id reads as NotFound, not Forbidden) and the retention behaviour of the html/markdown artifacts, and `zdr::guard(Artifact)` already makes it vanish under ZDR. (b) depends on Redis being configured and loses records on eviction; (c) is durable but only exists with `postgres-queue`. Record content: `NormalizedOutput` plus `effective_options`, never inline text; GET returns refs and metadata, the content stays behind `/v1/artifacts/{id}`. GET is refused for any caller whose token or org is ZDR-floored (`claims.effective_zdr_mode(None)`), even for a record written before the org turned ZDR on (Firecrawl refuses only for forced-ZDR teams too). Cost: one more small artifact per non-ZDR scrape. Kind name `scrape_record`, extension `scrape.json`.

**D14. Caching.** The existing page cache is left alone for default-option requests. For any request whose resolved options differ from the legacy default, both the `prev_fingerprint` read and the write are bypassed (the cache key has no options in it; a hit would return a response shaped for different options). Under ZDR the bypass already exists (`!zdr.is_active()`); this design routes it through `zdr::guard(zdr, WriteKind::Cache)`, which has no production caller today (S6), so the unwired guard is finally used. A URL-plus-options cache with `maxAge` is not built here: it is F-t2-048's item. This design delivers its key so the two cannot diverge: `canonical_options_key(&ResolvedScrapeOptions) -> String` (blake3 of the canonical JSON of the resolved options, excluding `zdr`, `timeout_ms`, `max_inline_bytes`), to be combined as `quarry:scrape:{org_id}:{blake3(canonical_url \x1f options_key)}`, org-keyed, bypassed under ZDR, never read for a different org. ADR-GATED(4): ZDR semantics of the URL cache are a topic-4 item; bypass is the recommended and safest reading.

**D15. OpenAPI from types: schemars or hand-maintained.** Options: (a) keep hand-editing `openapi.yaml` and add only a route-coverage check; (b) add `schemars` 1.x to quarry-core behind an optional `jsonschema` cargo feature, snapshot the JSON Schema of `ScrapeOptions` and `ScrapeResponse` to a golden file, and check that the OpenAPI schema and the snapshot agree, plus the route-coverage check; (c) full generation with `utoipa` or `aide` over all routes. Recommendation (b). It is a new direct dependency decision, but `schemars` 0.9.0 and 1.2.2 are already in `QR/Cargo.lock:5167-5180` through `serde_with`, so no new crate enters the supply chain, and the feature flag keeps it out of the production binary. Audit ADR topic 7 recommends exactly "do the OpenAPI-from-types slice now" and gates MCP exposure; no gate here. Note the OpenAPI is 3.1.0, whose schema dialect is JSON Schema 2020-12, which schemars 1.x emits.

**D16. Consumer switch.** `model-gateway` sends `formats:["markdown"]`, reads top-level `markdown` first, and only falls back to the artifact GET when the edge did not inline (rolling-deploy safe against an older edge that ignores `formats`). `execution-core`'s `web_fetch` keeps calling `/v1/extract` (already one call, inline) until the Model Plane session decides whether to unify the two fetch tools; this is a cross-session item (section 7). ## 6. Plane ownership, ZDR propagation and Model-proposes/Quarry-executes check

**Plane ownership, per rule.**
- Control Plane owns identity, orgs, billing, sessions, audit, quotas, entitlements: not touched. The only identity inputs are the verified `Claims` (`org_id`, scopes `scrape:read` and `scrape:write`, the ZDR floor through `Claims::effective_zdr_mode`, `auth.rs:136`) and the existing scope map. No new claim, no new scope, no quota or entitlement.
- Data Plane v2 owns documents, chunks, embeddings: reached only through the existing ingest contract (`DataPlaneIngest`, `POST /v1/documents`, `ingest_client.rs:140`). Slice 2 sets `raw_ref` for documents; whether `ingest_client.rs` forwards `raw_ref` is [UNVERIFIED], check in slice 2 and drop the field if the mapper ignores it. No database access crosses a plane.
- Ingestion Plane captures evidence: every new behaviour (sniff, parse, options, inline, records) is in Quarry-v2.
- Model Plane owns reasoning, sessions, capabilities, browser grants, cost: only the thin client in `model-gateway/src/quarry.rs` changes. Browser grants (BrowserBroker) are not touched; `DriverSignals::browser()` stays a hint Quarry plans (`driver_plan.rs:36-50`).
- Application Plane: not touched. Frontend Plane: gateway stays a thin request builder and error mapper; it adds no secret, no forged header, and removes a dead key; the SPA gets type and i18n edits only.
- Channel Plane: not built against.
- Support Plane: not involved.

**ZDR propagation, per content-persisting boundary.**

| Boundary | Behaviour under ZDR | Mechanism |
|---|---|---|
| Artifacts (html, markdown, raw, meta, scrape_record) | none written | `zdr::guard(zdr, WriteKind::Artifact)` at `pipeline.rs:601`; handler guard before the record write |
| Page cache (`quarry:page:{fingerprint}`) | not read, not written | `!zdr.is_active()` at `routes.rs:432`, `:480`, now via `WriteKind::Cache`; non-default options bypass it for everyone |
| Future URL+options cache | bypassed, org-keyed, never cross-org | D14, owned by F-t2-048 |
| Inline content | returned in the response only; truncated at the cap with `truncated[]`; never logged, never in events beyond the existing ephemeral `page_extracted` excerpt | D12 |
| Scrape record and `GET /v1/scrape/:id` | no record; readers with a ZDR floor refused (403) | D13 |
| Events | `emit_page_event` routes through `emit_for_zdr` (`pipeline.rs:259-269`); new `content_kind` label is content-free; `PageBlocked` carries kind and bytes only | existing |
| Local Tantivy index and Data Plane ingest | skipped | `LocalIndexWriteback.decide` and the `zdr::guard` at `pipeline.rs:856` |
| Logs and tracing | new log lines carry field names, kinds and byte counts only; never URL, selectors or content | D9, slice 1 and 2 review checklist |
| Document parsing | in memory only; the sandbox child (slice 3) gets bytes on stdin and writes nothing to disk | slice 3 |
| Billing meter | still carries URL and fingerprint under ZDR | pre-existing, F-t2-046 (`routes.rs:498-507`); not widened here |

**Model proposes, Quarry executes or rejects.** The Model (through model-gateway tool arguments) can propose `formats`, `only_main_content`, `include_tags`, `exclude_tags`, `extractor`, `timeout_ms`, `max_inline_bytes`. Quarry resolves and clamps them and rejects with field-level 400s; none is executable (selectors are declarative DOM filters, no script, no `evaluate`, no actions); `timeout_ms` and `max_inline_bytes` can only lower server limits; `zdr:false` cannot lower the token floor (`routes.rs:416`); `doc_routing` and parser limits are server configuration, not request fields; `skipTlsVerification`, `headers`, `proxy` are reserved and rejected. Quarry, not the client, decides the document route from bytes. Nothing here lets a Model reach a browser action; `signals.actions` stays a string list that Quarry's planner reads, and typed actions arrive only with F-t2-023 under its own grant design.

**Rules at risk.** (1) ZDR semantics: inline-only for scrape is a new ZDR behaviour; it loosens nothing but belongs in the matrix (ADR 4, D12). (2) Cross-org cache: the existing fingerprint-keyed cache is not org-scoped (`cache.rs:31-32`); this design does not widen it and keeps inline text out of it (D7), but the underlying hole is F-t2-048's. (3) Observation, not verified exploitable: `GET /v1/artifacts/{id}` serves a scraped `html` artifact as `text/html` with `nosniff` (`resource_routes.rs` `artifact_content_type`, `content_type_for_key`), i.e. attacker-controlled HTML under the API origin; documents are stored as `raw` (octet-stream) so slice 2 adds no exposure; the HTML case goes to F-t2-039 and the security review. (4) Resource exhaustion by large documents: addressed by D4 and slices 1 to 3, with the flate-bomb residual open until slice 3.

## 7. Cross-session interfaces

**(a) Verevon Space (shared workspaces, agent PC and browser in Spaces, ZDR-safe telemetry).**
- Shared piece: the inline ZDR path and the typed 415. A Space chat that fetches a page for a ZDR member goes through model-gateway `fetch_url`; slice 7 makes that return text with one call. Proposed owner: Quarry contract (this design), Space consumes through model-gateway.
- Shared piece: ZDR-safe telemetry (F-t2-004). This design adds log lines that carry names and counts only and a content-free `content_kind` label; the Space session should reuse that rule for any fetch telemetry it adds, and must not log `data.markdown`.
- Not shared on purpose: `scrape_id` is org-bound, not Space-bound. Sharing a fetch result with Space members needs the resource-taxonomy decision (ADR 8); do not widen `GET /v1/scrape/:id`.
- User must reconcile: the Space UI copy for `unsupported_media` and `document_has_no_text_layer` (i18n keys in `SPA/shared/i18n/errors.ts`, which is [M] with unrelated edits).

**(b) Model Plane and chat/agents (BrowserBroker grants, agent browser path, delegated bearer forwarding, approvals).**
- Shared piece: the fetch tool. Today two implementations exist: model-gateway `fetch_url` and grounding (`scrape_readable`, two calls, broken under ZDR) and execution-core `web_fetch` (`web_tools.rs:149`, `/v1/extract`, one call, no PDF routing, no options). Proposed owner: the Model Plane session owns the tool surface; Quarry owns the contract. Decision to make: unify both on `/v1/scrape` inline (recommended, gives PDFs and options to both) or keep two. This design only changes the model-gateway client.
- Shared piece: tool-argument schema. The slice 8 golden `QR/docs/schemas/scrape-options.schema.json` is the machine-readable options contract; propose the Model Plane vendors it with a digest pin (the repo already pins cross-plane goldens with `scripts/tests/zdr-contract-sync.test.sh` [M]; a separate pin is simpler than editing that script's GOLDENS list, which is mid-change). Field errors arrive as `error.details.fields[]` so the tool result can tell the Model what to fix.
- Shared piece: service-principal scopes. `GET /v1/scrape/:id` accepts `scrape:read` or `scrape:write`, the scopes model-gateway already requests (`SCRAPE_SCOPES`); no new grant. Delegated bearer forwarding (F-t2-001) is unaffected: scrape is not a browser-grant route.
- Shared piece: gRPC mapping. `UNSUPPORTED_MEDIA` needs a mapping in `grpc.rs quarry_err_to_status` (slice 7, small).
- Shared piece: `gateway.proto FetchRequest` (`:380-401`, fields 1 to 6) would need options fields to let the Model choose formats or selectors over gRPC; deferred, because the `buf breaking` gate is inert today (`apps/Model Plane/proto/baseline.binpb` is 0 bytes, S9 H5) and the proto change belongs to the Model Plane session.

## 9. Open questions for the user (real blockers only)

1. **Q1, document parser isolation.** Is the in-process parser (slice 2: input caps, output caps, 15 s deadline, 2 concurrent parses, container memory limit) acceptable for production multi-tenant traffic, or must slice 3 (child process with `RLIMIT_AS` and `RLIMIT_CPU`) land before `QUARRY_EDGE__DOC_ROUTING=on` is the production default? Evidence: `lopdf` 0.42.0 `decompress_zlib` has no output cap (`object.rs:849-865`). Blocks the production flag, not the build.
2. **Q2, how a skipped media type is reported.** Confirm HTTP 415 `UNSUPPORTED_MEDIA` (non-retryable, counted in `pages_failed` for crawls) instead of a 200 with an empty body. It changes crawl dashboards: image and archive links start showing as failed pages.
3. **Q3, strict-validation date.** When should unknown scrape keys start returning 400, and who contacts the gateway and SPA owners? Until a date is set the edge stays lenient and warns.
4. **Q4, scrape-record retention.** Records live as long as html and markdown artifacts, which is forever unless `QUARRY_RETENTION_DAYS` is armed (off by default, and the janitor is not yet a safe tombstone base, S6). Acceptable, or should the first slice add a TTL concept to the artifact store?
