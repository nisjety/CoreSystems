## 2. Verified current state

### 2.1 What the code does today (path:line, all read in the live tree)

**Capture.** `capture_snapshot(page: &Page)` is `QB/chromiumoxide.rs` [C] 1771-1832. It calls `Page::get_cookies()` (1772). In chromiumoxide 0.9.1 that is `execute(GetCookiesParams::default())` on the Network domain, documented "all cookies that match the tab's current URL" (`chromiumoxide-0.9.1/src/page.rs` 900-907) [CONFIRMED]. It then maps each cookie to `Cookie { .. expires: None }` (1781-1789), reads `localStorage`/`sessionStorage` of the current document only through one `page.evaluate` (1792-1811), hard-codes `indexed_db: vec![]` (1817), leaves `viewport` to the caller (`persist_current_page` 693) and captures UA, locale, timezone from page JS (1797-1799). Capture runs only in `release` (1944-1949 via `persist_current_page` 675-697, 5 s timeout at 685) and only for the active tab. Nothing is saved while a run is live.

**Restore.** `open_tab_page` (371-557) calls `self.load_snapshot(&lease)` on EVERY tab creation (472; `load_snapshot` 661-673 swallows load errors and starts fresh). Cookies are hydrated after the initial `goto` through `hydrate_cookies` (925-942, `Page::set_cookies`, which needs a real http(s) page URL), storage through `hydrate_storage` (944-967, `window.localStorage.setItem` on the current page only), then the page is reloaded (528-538). UA, locale, timezone and the saved viewport are never re-applied.

A second, unused capture/hydrate pair exists in `session.rs` 625-676 (`BrowserSession` behind feature `chromiumoxide`; no caller found by grep) that also writes `expires: None`.

### 2.3 New findings (not in the audit)

1. **Second tab re-hydrates stale cookies over the live jar.** `load_snapshot` runs per tab (472) and hydration applies whenever the tab has an initial URL and the profile has cookies (512-526). Opening a second tab of a persistent session overwrites the session's fresher cookies with the saved ones. The existing test `second_tab_on_same_session_shares_that_sessions_cookies` (`chromiumoxide.rs` 3515) uses a lease with no profile, so it cannot catch this. Fixed in C2.
2. **Restore sends the first request unauthenticated.** Cookies are applied after the first `goto` and a reload repairs it (the origin sees one anonymous hit, which also trips login-redirect side effects). `Storage.setCookies` on the browser context needs no page URL, so restore can precede navigation. Fixed in C2.
3. **A failed restore can destroy the profile.** `load_snapshot` turns every load error into "start fresh" (669-671); the release then saves the fresh (possibly empty) snapshot over the real row. With encryption this becomes dangerous (key service down = every profile overwritten). `Kernel` has the same shape (`.unwrap_or(None)`). Fixed by D16-14.
4. **Two unrelated "profile" stores share the path name.** quarry-control mounts `mountSimple[store.BrowserProfile](r, "/v1/profiles", ..)` (`QC/internal/resources/resources.go` [C] 42; `BrowserProfile{ID, Name, SnapshotURI, CreatedAt}` in `QC/internal/store/store.go` [C] 326-331) with no org column (the purge doc calls it global). It is not the edge's profile data and is not changed here; flagged because an erasure or ACL review that greps `/v1/profiles` will find both.
5. **Gateway profile picker is silently empty.** `GW/domains/ingestions/profiles.rs` [C] 51-61 keeps only list entries that are JSON strings (`v.as_str()`), but Quarry's list returns objects `{profile_id, name, scope}` since the Phase 3 continuation (`profile_routes.rs` 36-57). `/api/ingestions/profiles` (used by `VerevonIngestionsPage.tsx` tests) returns `profiles: []` for a real stack. One-line gateway fix, owner: the browser-UI workstream (D9); listed in section 7.
6. **`persist_current_page` can save a worse snapshot than it loaded** (no active tab returns early, but a tab on `about:blank` or an error page saves an empty cookie list). No "never replace a non-empty profile with an empty capture" rule exists. Addressed in C1 (empty-capture guard).
7. **`restorable` in the probe ignores expiry** (410-411 counts items only). Once expiry is captured, an all-expired profile still reports `restorable: true` unless the probe is changed (P0/C1).
8. **Doc drift.** `docs/RUNBOOKS.md` [M] 117-128 tells operators to `curl /v1/profiles/<id>` and check `expires_at` (no such field exists). `docs/CONTRACTS.md` [C] 150-201 specifies an S3 artifact snapshot (`state.bin.enc`, `scheme`, `key_source: env:QUARRY_PROFILE_KEY | kms:<id>`), which differs from the Postgres reality and from this design's envelope. The OpenAPI file `docs/openapi.yaml` [M] documents no `/v1/profiles` path (only run-body fields at 2394-2436).
9. **Org-core migration runner has a ledger now.** `OC/internal/database/migrate.go` [C] 14-76 applies `*.up.sql` in lexicographic order with a `schema_migrations` ledger; the header of `008_rls_tenant_isolation.up.sql` ("no ledger, re-applies every boot") is stale. New org-core migrations should still be written idempotently (`IF NOT EXISTS`), as the existing ones are.

## 3. Design decisions

Tags: "ADR-GATED topic N" names an audit section 9.3 topic. Three decisions have no 9.3 topic; they are tagged "ADR-GATED (new, proposed 9.3 item 11)".

### D16-1. Layering: encrypt below the cache, so Redis holds ciphertext

- Problem: `ProfileStore` is typed on `SessionSnapshot`, and `CachedProfileStore` serializes the snapshot itself (`cached_profile_store.rs` 91, 126). An encrypting `ProfileStore` wrapper placed under it still lets the cache see plaintext; placed above it, the cache layer never sees ciphertext either way unless the cache moves down.
- Options: (a) encrypt in `PostgresProfileStore` only and bypass the cache for snapshots (loses the restore-latency benefit the cache exists for); (b) keep `ProfileStore` and add a decorator above the cache (cache holds plaintext, rejected by the card); (c) split the stack into a byte-level `ProfileBlobStore` and a snapshot-level `EnvelopeProfileStore` on top, with the cache between them.
- **Recommendation (c).** New stack: `EnvelopeProfileStore` (implements `ProfileStore`, owns codec + key provider) over `CachedBlobStore` (Redis, stores opaque envelope bytes) over `PostgresProfileBlobStore` (sqlx). `InMemoryProfileStore` stays as the dev/test store and is never durable. Metadata (name, scope, owner) stays plaintext columns and passes through the blob layer.
- Cache semantics change from write-through to **cache-aside with invalidate-on-write**: after a store call returns `Stored`, `DEL` the key; populate on read. Reason: with monotonic saves (D16-6) a save can be ignored; the current unconditional `set_ex` after `inner.save` (cached_profile_store.rs 90-103) would then cache the ignored, older payload for an hour. New key prefix `quarry:profile:v2:{org}:{profile}` so rolling-deploy pods running the old code never read an envelope as JSON and old plaintext keys age out (TTL 3600); the one-off backfill also `UNLINK`s the old `quarry:profile:{org}:*` keys (plaintext cookies sit in Redis up to an hour after deploy otherwise).
- Rationale: smallest change that satisfies "cache holds ciphertext"; the trait split also gives the S3 store (if ever wired) one place to be encrypted.

### D16-2. Cipher, nonce handling, key granularity

- Options: AES-256-GCM via `ring` (already in `Cargo.lock` 0.17.14 through rustls, no new crate), AES-256-GCM via the RustCrypto `aes-gcm` crate (new dependency; only `aes` 0.8.4 is present), XChaCha20-Poly1305 via `chacha20poly1305` (new dependency, 192-bit nonce, listed first in CONTRACTS.md 190-195).
- **Recommendation:** `ring::aead::AES_256_GCM` (`LessSafeKey::seal_in_place_append_tag`), one 96-bit nonce per seal from `ring::rand::SystemRandom` (never derived from a counter or the profile id), **one data key (DEK) per profile, rotated every 256th save (`rev % 256 == 0`) and whenever none exists**. At most 256 messages per key makes the random-nonce collision bound (about 2^-81) irrelevant, which answers the audit's "AES-GCM nonce handling review" risk by construction instead of by argument. Compress (gzip via `flate2`, already in the tree) before sealing when the plaintext exceeds 4 KiB; set a hard plaintext cap (D16-11).
- Envelope (compact JSON bytes, stored identically in Postgres `envelope BYTEA` and Redis): `{"enc_v":1,"alg":"A256GCM","key_id":"oc:3","wrapped_dek":"<b64>","snapshot_id":"snap_<ulid>","z":"gzip|none","nonce":"<b64 12B>","ct":"<b64>"}`. The AAD is NOT stored; it is rebuilt from the row context: `"quarry-profile\0v1\0" || len32(org_id) || org_id || len32(profile_id) || profile_id || len32(snapshot_id) || snapshot_id || enc_v`. Length-prefixing removes separator ambiguity (the card's `org|profile|snapshot` string form is a logical description). This binds a ciphertext to its org and profile: moving an envelope between rows or orgs fails authentication. `key_id` and `wrapped_dek` are deliberately outside the AAD so a KEK rotation can rewrap the header without re-encrypting (D16-3). A database writer can still roll a row back to an older valid envelope (stale restore); the monotonic `saved_at`/`rev` in D16-6 protects against races, not against a DB admin.
- DEK memory: `zeroize::Zeroizing<[u8;32]>`, never logged, never in error details. Add direct deps `ring = "0.17"`, `zeroize = "1"`, `flate2` (workspace) to quarry-runtime. `cargo audit --deny warnings` (quarry-v2-ci.yml 231-237) must stay green; `Cargo.lock` is not tracked in git [?] (provenance), so pin by the lockfile used in CI/Docker builds.

### D16-3. Key hierarchy, owner service and API shape (ADR-GATED, new, proposed 9.3 item 11)

- Constraint: keys come from a Control Plane API; Quarry never reads Control Plane tables; erasure is crypto-shredding driven by a Control Plane event; environment master key first, KMS later.
- Owner options: (a) **org-core** (Go): owns the organization lifecycle, the hard-delete stored procedure `gdpr_hard_delete_organization`, the erasure fan-out (`internal/org/gdpr_erasure_fanout.go` [C]), RLS tenant isolation, a service-credential scheme with per-principal scopes (`internal/http/service_auth.go` [C] 25-50, `ORG_CORE_SERVICE_CREDENTIALS` in `apps/Control Plane/docker-compose.yml` [C] 539), and the `/internal/orgs/:orgId/...` machine routes (server.go 158-181). A key table with `org_id ... REFERENCES organizations(id) ON DELETE CASCADE` is destroyed atomically by the existing hard delete with no procedure change (the pattern used by `018_org_deletion_ledger.up.sql`). (b) auth-core (TypeScript, token issuer): wrong blast radius (identity plus keys in one compromise) and no erasure ledger. (c) a new `key-core` service: cleanest separation, but a new service (compose, CI, ports, credentials) turns this into XL; defer.
- **Recommendation (a), behind an interface** (`internal/orgkeys` with `MasterKeyProvider` and `Store`), so extracting a `key-core` later is mechanical. The Control Plane ownership docs (`apps/master-ownership-matrix.md` [C], `apps/Control Plane/CONTROL_PLANE_OWNERSHIP.md` [C]) list no key responsibility today; they must be updated in E2, which makes this a user-ratified ownership decision.
- Hierarchy (KMS-style, so a real KMS drops in later): `master key (env now, KMS later) -> per-org KEK (wrapped at rest in org-core) -> per-profile DEK (wrapped by the KEK, stored in the Quarry row/envelope)`. Quarry never holds a KEK. Alternatives rejected: returning one long-lived plaintext org key to Quarry (makes crypto-shredding depend on every Quarry process forgetting it, and every Quarry pod holds an org-wide secret); local HKDF per-org derivation inside Quarry from an env key (kept only as the interim `env` provider, D16-4: it cannot shred an org because the derived key is recomputable).
- API (org-core, machine-to-machine, typed envelopes `{data}` / `{error:{code,message,details}}`, `Cache-Control: no-store`, bodies never logged):
  - `POST /internal/orgs/:orgId/keys/data-keys`, scope `org:keys:wrap:any`. Request `{"purpose":"quarry.profile","context":{"profile_id":"prof_..."}}`. Response 201 `{"data":{"key_id":"oc:3","kek_version":3,"alg":"A256GCM","dek_b64":"...","wrapped_dek_b64":"..."}}`. `wrapped_dek` = `nonce(12) || AES-256-GCM(KEK, DEK, aad = "quarry.profile|org=<org>|profile=<id>")`; the AAD omits the KEK version so rewrap is possible.
  - `POST /internal/orgs/:orgId/keys/data-keys/unwrap`, scope `org:keys:unwrap:any`. Request `{purpose, context, key_id, wrapped_dek_b64}`, response `{"data":{"dek_b64":"...","current_kek_version":3}}`.
  - `POST /internal/orgs/:orgId/keys/data-keys/rewrap`, scope `org:keys:wrap:any`. Same request, response `{"data":{"key_id":"oc:3","wrapped_dek_b64":"..."}}` (the DEK never leaves org-core).
  - `POST /internal/orgs/:orgId/keys/rotate` and `GET /internal/orgs/:orgId/keys` (metadata only: versions, states, timestamps), scope `org:keys:admin:any` (operators, not Quarry).
  - `DELETE /internal/orgs/:orgId/keys` (crypto-shred: state `destroyed`, `wrapped_kek` zeroed), scope `org:keys:destroy:any` (operators and the erasure saga, not Quarry).
  - Errors: 404 `org_not_found`; 403 scope; 410 `key_destroyed` (the org was shredded); 422 `invalid_context`; 503 `keys_unavailable` (master key missing or failing its canary).
- Quarry authenticates with a static credential row `{"principal":"quarry-edge","audience":"org-core","token":"${QUARRY_ORG_CORE_SERVICE_TOKEN}","scopes":["org:keys:wrap:any","org:keys:unwrap:any"]}` in `ORG_CORE_SERVICE_CREDENTIALS` (Control Plane compose [C] 539, validated by `retention_posture_contract_test.go`-style contract test). This is the org-core precedent (auth-core holds `org:retention:read:any` the same way); it does not go through the Auth Core mint manifest `cross-plane-token-requests.json`. The token's owner file is the Control Plane's `.env.generated-secrets`; the Ingestion mirror must hold the same value (the drift class recorded in the integration-core-env-drift note). `QUARRY_ORG_CORE_SERVICE_TOKEN` is minted once and never rotated by a re-run (run-control-plane.sh behaviour).
- Org-core data model: `org_key_encryption_keys(org_id TEXT NOT NULL REFERENCES organizations(id) ON DELETE CASCADE, kek_version INT NOT NULL, wrapped_kek BYTEA NOT NULL, master_key_id TEXT NOT NULL, state TEXT NOT NULL CHECK (state IN ('active','retired','destroyed')), created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), retired_at TIMESTAMPTZ, destroyed_at TIMESTAMPTZ, PRIMARY KEY (org_id, kek_version))` plus a partial unique index allowing one `active` row per org, RLS like migration 008. The KEK is created lazily on the first `data-keys` call for the org.
- Audit: key creation, rotation, destruction and denied unwraps are written through the existing audit outbox (`gdpr_audit_outbox.go` pattern); successful unwraps are a counter metric only (volume).

### D16-4. Master key: environment first, KMS later; custody and loss (ADR-GATED, new, proposed 9.3 item 11)

- org-core reads `ORG_CORE_KEY_MASTER_KEYS` (JSON `{"v1":"<b64 32 bytes>"}`) and `ORG_CORE_KEY_MASTER_ACTIVE` (default the highest id), asserted at boot like the existing `internalkey` package (length, placeholder detection) and refused in release mode when `ORG_CORE_KEYS_ENABLED=1` and absent. A boot canary (a stored known-plaintext row wrapped under each configured master id) detects a wrong or missing master key before the route serves; a failed canary answers 503 `keys_unavailable`, never "decrypt error".
- KMS later = another `MasterKeyProvider` (`Wrap(kekBytes) / Unwrap`), switched by rewrapping the (small) KEK rows; no Quarry change and no profile re-encryption.
- Interim in Quarry: `QUARRY_EDGE__PROFILE_KEY_PROVIDER=env` (D16-E1) wraps DEKs with a local master (`QUARRY_PROFILE_MASTER_KEYS`, same JSON shape; `key_id` prefix `env:`). It gives encryption against a database or Redis read, but no crypto-shredding. Production may run it only as an explicit, logged interim until E2 ships.
- **Master-key loss destroys every profile of every org** (and every wrapped KEK). Mitigations that are part of the slices, not afterthoughts: (1) the key is generated once by the bootstrap and stored in the secrets ledger (`.env.generated-secrets`, which the bootstrap guard refuses to regenerate); (2) an offline escrow procedure (two-person split) documented in `docs/RUNBOOKS.md` before E2 goes to production; (3) the canary above; (4) a restore drill (restore the org-core database and Quarry database from backup into a scratch stack, unwrap and decrypt one profile) listed in the E2 evidence. Honest limits: a point-in-time restore of org-core older than an org's KEK creation orphans that org's profiles; crypto-shredding is only as strong as backup retention of the org-core database (a backup holds the wrapped KEK and the master key lives outside it, so shredding is effective once backups age out; state this to counsel as the "beyond use" position).

### D16-5. Erasure: crypto-shred in org-core, row purge in Quarry through the existing consumer (ADR-GATED topic 4 for what ZDR/erasure covers; mechanics not gated)

- Mechanism 1 (authoritative): org hard delete (`gdpr_hard_delete_organization`, `OC/migrations/003_gdpr_hard_delete.up.sql`) deletes `organizations`, and the FK cascade deletes `org_key_encryption_keys`. From that commit every wrapped DEK in `quarry_profiles` and every Redis envelope is undecryptable. Soft delete (30-day grace, restorable) does NOT shred.
- Mechanism 2 (hygiene, defence in depth): delete the rows. Where to consume `verevon.gdpr.erasure.requested`? Options: (A) extend quarry-control's existing durable consumer to call a new quarry-edge internal route `DELETE /v1/internal/orgs/:org/profiles`; (B) a second consumer inside quarry-edge on `control-shared-nats` (needs a new broker identity and a new durable consumer provisioned by audit-core's provisioner: a Control Plane change, and the identity `quarry-control-gdpr` is granted no consumer-create authority); (C) quarry-control deletes from `quarry_edge` directly (cross-database, rejected).
- **Recommendation (A).** `QC/internal/gdpr/erasure.go` `HandleErasure` gains an `EdgePurger` (HTTP client with the `QUARRY_EDGE_INTERNAL_TOKEN` bearer pattern used by `change_routes.rs` 453-468 for internal routes); `OrgPurger` stays as is; failures nak and JetStream redelivers (existing ack/nak split, `subscriber.go` handleDelivery). The edge route is idempotent, org-scoped by path, authenticated by constant-time compare (`ct_eq`), deletes `quarry_profiles` rows and tombstones for the org, then `SCAN`+`UNLINK` `quarry:profile:v2:{org}:*`, and drops its in-process DEK cache entries for the org. The route is an `OrgErasable` list (profiles first); other `quarry_edge` tables the same gap affects (checkpoints, receipts, timeline events, baselines, request queue) are named in the E3 risks and left to their owners.
- User erasure (`subject_type: "user"`) is not handled by quarry-control today and is out of scope; once P2 adds `owner_user_id`, deleting a user's profiles is one more `OrgErasable` method (open question Q6, low priority).

### D16-6. Ordering, tombstones, stale saves

- Reference: Firecrawl ignores a save unless `savedAt` is newer than a deletion tombstone, keeps `saved_at = GREATEST(...)`, and deletes rows saved at or before the tombstone; the tombstone is a key-value entry, not a column.
- **Recommendation:** (1) `saved_at TIMESTAMPTZ` = capture time taken by the edge when the snapshot was captured (UTC; clamped to `NOW() + 5 s` in SQL so a skewed pod cannot pin a profile in the future) and `rev BIGINT` incremented per stored save. (2) Conditional upsert: the row is replaced only when `saved_at IS NULL OR saved_at < EXCLUDED.saved_at` (stricter than Firecrawl, which can still replace content with an older save while keeping the max timestamp). (3) A `quarry_profile_tombstones(org_id, profile_id, deleted_at, expires_at, PRIMARY KEY(org_id, profile_id))` table written in the same transaction as the delete; a save with `saved_at <= deleted_at` inserts nothing and returns `IgnoredByTombstone`. Tombstone TTL 7 days (`expires_at`; a sweep deletes expired rows) so a session leased up to the maximum run length cannot resurrect a deleted profile. Tombstones hold only ids and a timestamp, are deleted with the org (E3), and cannot exist for ZDR callers (profiles are refused). (4) `SaveOutcome { Stored{rev}, IgnoredStale, IgnoredByTombstone }` is returned through `ProfileStore::save`; the driver logs and emits a content-free timeline event on the ignored outcomes.
- Honest limit: monotonic `saved_at` prevents out-of-order and zombie writes, not lost updates between two concurrent sessions on one profile (last capture wins, no merge). Concurrent sessions on a shared (`org_shared`) profile are a product question; optional slice S7 adds a single-writer Redis lease so the second session restores read-only. Not recommended before real usage data.

### D16-7. Owner and access model (ADR-GATED, new, proposed 9.3 item 11; legacy-row policy is user question Q2)

- Add `owner_user_id TEXT NULL` set only on INSERT (never updated); value `Claims::actor_id()` (user id, or the signed `service:<id>` for service principals, `auth.rs` 144-146). Created by `create_profile`, by the run that creates a new profile id at first save, and by an import.
- Access rules (one function `profile_guard::authorize(claims, meta, op)` in quarry-edge): org mismatch is impossible (primary key); `user_private`: only the owner may list, attach, probe, rename, rescope or delete; `org_shared`: any org member may list, attach and probe; only the owner may rename, rescope or delete; `run_scoped`: owner only (garbage collection of run-scoped profiles is not implemented today and stays out of scope). Non-owners get 404 (list filtered), not 403, to avoid an existence oracle. Service principals never use `/v1/profiles*` (D16-8). A Space must never widen this ACL: a future Space-shared profile is an explicit Quarry-side ACL row written by the owner through the gateway, never a header or a Space-service call (section 7).
- Legacy rows (owner NULL): by precedent `0008_step_receipt_actor_scope.sql` ("existing evidence must not be guessed or backfilled ... keeps a tenant membership from becoming authority over another user's browser history"), `user_private` legacy rows fail closed (hidden, not deleted) and `org_shared` legacy rows stay org-visible. Rescue is an operator SQL runbook (`UPDATE quarry_profiles SET owner_user_id = ..`). Rollout is observe-first (`QUARRY_EDGE__PROFILE_OWNER_ENFORCE=off|observe|enforce`, default `observe`: log `profile.owner.would_deny{reason}` counts, enforce nothing).
- Attach at run start (`agent_routes.rs` 1415-1432): when `body.profile_id` is supplied, call the guard with op `Attach`; an unknown id is allowed (the run creates it and becomes owner at first save); a known id owned by someone else is 404. This is the "Model proposes, Quarry rejects" point for profiles: a Model-driven run that names another user's profile id is refused inside Quarry.

### D16-8. `GET /v1/profiles/:id` and raw cookie values (answers audit open question 13)

- Options: (a) keep raw values for any org token (today); (b) owner-only raw read with an audit event; (c) never return values: replace the body with a redacted summary and give operators a summary route; (d) (b) plus step-up approval (needs F-t2-033, not built).
- **Recommendation (c).** `GET /v1/profiles/:id` returns `{profile_id, name, scope, saved_at, rev, snapshot_version, cookies:[{name, domain, path, secure, http_only, same_site, session, expires, value_len, value:null}], origins:[{origin, local_keys, session_keys, idb_databases}], locale, timezone, has_user_agent, has_viewport, truncated}`: structure without any secret value or storage value. `restore_probe` keeps its counts and gains `earliest_expiry`, `cookies_expired`, `origins_count`, `saved_at`. There is no raw read route at all. Rationale: no caller needs raw values (the gateway never proxies the read; the runbook workflow only needs presence and expiry); a "show me my cookies" feature is a DSAR/export concern for counsel, to be built as a separate audited export later. The same refusal applies to every service principal (`claims.is_service()` gets 403 on all `/v1/profiles*`): the Model Plane, execution-core and every other service never read or write profile contents, which is how "the Model Plane must never see cookie values" is enforced at the API.
- Adjacent invariants that keep the statement true: snapshots never enter observations, receipts or events (`quarry-core` contracts carry no cookie fields; grep confirms the only "cookie" hit in `observation.rs` is the consent-banner text list at 193); `AgentAction::Evaluate` (contracts.rs 821) can read `document.cookie` and localStorage tokens and is gated by F-t2-002 (W1); AX-tree password values are D12's. ### D16-9. ZDR on `/v1/profiles*` (ADR-GATED topic 4)

### D16-11. Snapshot schema v2 and size limits

- Additive, `#[serde(default, skip_serializing_if = ..)]`: `SessionSnapshot.snapshot_version: u8` (2 for new captures), `origins: Vec<OriginState { origin, local_storage: Vec<(String,String)>, session_storage: Vec<(String,String)>, indexed_db: Vec<IdbDatabase>, truncated: bool }>`; `Cookie` gains `same_site: Option<SameSite>`, `session: bool`, `priority: Option<String>`, `partition_key: Option<PartitionKey { top_level_site, has_cross_site_ancestor }>`, `source_scheme: Option<String>` and `#[derive(Default)]` (existing struct-literal tests in `session.rs`, `kernel.rs`, `chromiumoxide.rs` 3420, `profile_roundtrip.rs` and the Postgres tests must add `..Default::default()`). Legacy flat `local_storage`/`session_storage`/`indexed_db` stay readable: a snapshot with empty `origins` and non-empty flat fields restores the flat entries into the initial URL's origin exactly as today. `IdbDatabase { name, version, stores: Vec<IdbStore { name, key_path, auto_increment, indexes, records: Vec<IdbRecord { key, value }> }> }` with values encoded by a tagged JSON serializer (Date, ArrayBuffer/TypedArray as base64, Map, Set, BigInt, Blob as base64; non-cloneable values dropped and counted).
- Caps (env-tunable in the browser crate): plaintext snapshot 16 MiB (`QUARRY_BROWSER_PROFILE_MAX_BYTES`), per origin 4 MiB, 64 origins, 50 000 IDB records. Over a cap, drop the largest IDB stores first, set `truncated`, never drop cookies. An oversized import or save is rejected with 413, not truncated silently.

### D16-12. Capture strategy (spike-gated, D16-S0)

- Cookies: `Storage.getCookies { browserContextId }` through `Browser::execute` for the session's own context; whole jar, all origins, with expiry (`expires > 0` becomes a timestamp, `session` true otherwise), SameSite, partition key. This replaces `Page::get_cookies` and works even if no tab is open.
- Web storage per visited origin is the hard part. CDP `DOMStorage.getDOMStorageItems { storageId }` resolves the storage area through a live frame of that origin in the same target ("Frame not found for the given storage id" otherwise) [UNVERIFIED: believed from the Blink inspector implementation; the spike must confirm on the pinned Chromium 149]. `IndexedDB.requestDatabaseNames/requestDatabase/requestData` are browser-process calls keyed by `securityOrigin`/`storageKey` and probably work without a frame [UNVERIFIED], but return `RemoteObject`s that need a second serialization step.
- **Recommendation:** an origin journal. (1) Track visited origins per session in `SessionPages` (`visited_origins: BTreeSet<String>`, cap 64; updated from the existing lifecycle listener and `update_tab_metadata`). (2) At capture (release, plus an optional checkpoint), for every LIVE tab run the in-page serializer for that tab's origin (localStorage, sessionStorage, IndexedDB through `indexedDB.databases()` + `getAll`/`getAllKeys` with the tagged serializer). (3) For origins no longer live, use records flushed while the origin's frame was alive: `Page.addScriptToEvaluateOnNewDocument` installs a `pagehide` handler that calls a `Runtime.addBinding` function (`__quarryProfileFlush`) with a capped JSON payload; the Rust listener (`EventBindingCalled`) stores it in the journal. (4) If the spike shows the IndexedDB domain works frame-less, use it for journaled origins instead of the flush. The snapshot schema is identical either way, so the choice is internal to quarry-browser. Cookies are captured first, so an IndexedDB timeout never loses authentication; capture budget 10 s (cookies 2 s, storage 4 s, IndexedDB 4 s), partial results flagged `truncated`.
- Empty-capture guard: if the new capture has no cookies and no origins and the loaded snapshot had some, do not save (`profile_capture_empty_skipped` event). A deliberate "log out" saves via the cookie jar changes (cookies removed while other state remains).

### D16-13. Restore strategy

- Order inside `open_tab_page` for the FIRST tab of a context only (`SessionPages.profile_restored: bool`, fixes finding 2.3-1): after `install_network_guard` and before the initial `goto`: (1) `Storage.setCookies { cookies, browserContextId }` with no page URL; skip cookies whose `expires` is in the past; skip session cookies when the snapshot is older than `QUARRY_BROWSER_PROFILE_SESSION_COOKIE_MAX_AGE_S` (default 604800, 7 days; a stale session cookie replayed on a changed site looks like a hijack); host-only cookies (captured domain without a leading dot) are restored with `url: https://<domain>/` instead of `domain` so `__Host-` and host-only semantics survive (a `domain` parameter would turn them into domain cookies and Chrome rejects `__Host-` ones); `SameSite`, partition key, priority carried. (2) `Page.addScriptToEvaluateOnNewDocument` with an origin-keyed seeding script: at document start, if `location.origin` is in the embedded map and the sentinel key `__quarry_profile_seeded_v1` is absent from that origin's localStorage, set the entries (localStorage, then recreate IndexedDB databases/stores/records, then sentinel). The sentinel lives in the origin's own storage, so it is per-origin and per-context, and it stops a later navigation from clobbering fresher live state with the snapshot. Capture strips the sentinel. This is the approach Playwright's storageState uses (init script keyed by origin), needs no egress to unvisited origins and works without a frame. (3) With cookies and storage in place before navigation, the reload at 528-538 is deleted.
- Emulation (hooks from D3 S2 `apply_page_hygiene`, which runs right after `browser.new_page` and before the Fetch guard): add `Emulation.setLocaleOverride` and `Emulation.setTimezoneOverride` from the snapshot. **User agent is not overridden.** Replaying a stored UA after a Chromium upgrade would contradict the real client hints and is the evasion-adjacent behaviour the audit's honest-identity posture (ADR topic 5, recommendation: honest posture) rules out; the restore report records `ua_changed: true` instead.
- Restore report (content-free, counts only): `{cookies_total, cookies_applied, skipped_expired, skipped_session_stale, origins_seeded, idb_databases, ua_changed, snapshot_age_s, truncated}` returned from `open_tab_page`, attached to the session's telemetry and appended as a `profile_restore` typed timeline event (`quarry_browser_timeline_events`, migration 0009: payload must contain no storage values; counts only). This ends "restores fail silently".

### D16-14. Failure semantics (key unavailable is not "start fresh")

- `ProfileStore::load` returns a typed result: `Ok(None)` (no profile), `Ok(Some(_))`, `Err(ProfileLoadError::KeyUnavailable)` (org-core down, 503: retryable), `Err(KeyDestroyed)` (org shredded: treat as no profile, the next save writes a new KEK), `Err(Corrupt)` (authentication failed or undecodable: start fresh AND mark the lease `restore_failed` so release does not overwrite until an operator or the user deletes the profile, plus a metric). Implemented with `QuarryError` using existing codes: `ErrorCode::RuntimeNotReady` (503, `details.reason = "profile_key_unavailable"`, `retryable` forced true) and `ErrorCode::NotFound`/`Conflict`; no new `ErrorCode` (avoids the D2 mirror checklist).
- Run start: `KeyUnavailable` fails lease acquisition with 503 (the caller retries); it must not start a fresh jar and later overwrite. Save at release: key failure leaves the row untouched and emits `profile_save_failed` (content-free). The Kernel driver gets the same handling (`kernel.rs` 239-250).

## 6. Plane ownership, ZDR propagation, Model-proposes/Quarry-executes check

- **Control Plane owns identity, users, orgs, billing, sessions, audit, quotas, entitlements.** Profile data stays in the Ingestion Plane; the only Control Plane addition is key management, a new responsibility that needs the ownership docs updated and user ratification (D16-3, Q1). Quarry never reads a Control Plane table: it calls org-core's HTTP API with a registered credential. Audit events for key operations are Control Plane's. No direct database crossing: quarry-control reaches `quarry_edge` data only through an edge internal route (D16-5), not through SQL.
- **Data Plane v2 owns documents and chunks.** Not involved. Profile snapshots are never ingested; cookie and storage values never flow to the Data Plane.
- **Ingestion Plane captures evidence and persists durable knowledge through Data Plane contracts only.** A browser profile is not knowledge; it is Quarry-owned operational state under Quarry's own database. Compliant.
- **Model Plane owns reasoning, sessions/runs, capabilities, browser grants, cost.** The Model Plane never sees cookie or storage values: service principals are refused on all `/v1/profiles*` routes, the read route returns structure only, snapshots do not appear in observations, receipts or events, and the key API is called only by quarry-edge. The residual path is `AgentAction::Evaluate` reading `document.cookie`; F-t2-002 (W1) gates it and P0 adds the canary test that a seeded value never appears in any `/v1/*` response or log.
- **Application Plane / Frontend Plane.** No Application Plane change. The gateway stays a normalizing BFF: it forwards the user's token, gains no profile logic beyond a list-shape fix; owner enforcement is inside Quarry, so a Space or the SPA cannot widen an ACL by header or body.
- **Model proposes, Quarry executes or rejects.** A Model-driven run may propose a `profile_id`; Quarry's attach check (P2) rejects another user's profile inside Quarry, and Quarry alone decides what is captured and restored. Restore applies stored state to the session's own isolated context only, never navigates to origins on its own and never widens the egress policy (cookies and seeding do not trigger network requests).
- **ZDR propagation, per boundary.** Run start: refused (existing, `agent_routes.rs` 1470-1476). `/v1/profiles*`: refused for ZDR callers except list and delete (P0, staged, shared with D4 S-8, ADR topic 4). Redis cache: holds ciphertext only, v2 prefix, invalidate-on-write. Postgres: sealed rows; ZDR callers cannot create rows, so no ZDR plaintext can exist. Tombstones: ids and a timestamp only, deleted with the org, cannot be created for ZDR. Key API: carries org id, purpose and profile id, never content; DEK material never in logs or error details. Logs and events: counts only (restore report, capture report, `would_deny` counters); no cookie names, domains or origins at INFO. Spans: no new spans; D10's sampler rules apply. Rules at risk: (1) ZDR on `/v1/profiles*` is observe-only until the flag is on; (2) the interim `env` provider cannot crypto-shred; (3) other `quarry_edge` tables are not erased on org erasure (named in E3, owned elsewhere).

## 7. Cross-session interfaces

**(a) Verevon Space.**
- Shared piece: profile ownership and sharing. Proposed owner: Quarry (`quarry_profiles.owner_user_id` plus `scope`), enforced in `profile_guard`. A Space must never widen a profile's owner ACL: a Space-shared profile, if wanted, is an explicit ACL row (`principal_kind`, `principal_id`) written by the owner through a gateway action, read by Quarry; Space services never pass a `space_id` that Quarry trusts.
- Shared piece: agent browser inside a Space (D8 shared jar attach) uses the session's context, not the profile; restore stays first-tab-of-context only and saves happen at release by the run owner.
- ZDR-safe telemetry: the restore and capture reports are counts only, safe to project into Space activity feeds; origins and cookie names are not.
- User must reconcile: whether Space members may use an `org_shared` profile today (yes by D16-7) or need Space-scoped sharing first (a new scope kind).

**(b) Model Plane and chat/agents.**
- Shared piece: the identity at run start. The owner check needs the user's identity: D1's delegated bearer must carry `user_id` to Quarry for Model-driven runs; an autonomous service run without a user owns its profile as `service:<id>` and should use `run_scoped`.
- BrowserBroker grants (F-t2-001) are unaffected: profiles are not grant material. execution-core and model-gateway must not call `/v1/profiles*` (now refused) and must not forward `profile_id` they did not receive from the user's request.
- Shared piece: ZDR vocabulary. D16 uses D4's refusal codes; new feature key `browser_profile` is a D4 S-9 follow-up in the Model Plane catalogue (owner: that initiative).
- User must reconcile: who adds the `profile_restore` summary to the chat browser UI (D9) and whether the planner should be told "profile restored (N cookies)" (content-free, safe).

**Frontend gateway** (not a sibling session but touched): fix `ingestions/profiles.rs` list shape (P0); `browser.rs` profile proxies need no change.

## 9. Open questions for the user (real blockers only)

1. **Q1 (blocks E2): is org-core the owner of key management** (new Control Plane responsibility, update ownership docs), or should a separate `key-core` service be built (XL)? Recommendation: org-core behind an interface.
2. **Q2 (blocks P2 enforce): what happens to existing profiles with no recorded owner?** Recommendation: `user_private` rows are hidden from everyone until an operator assigns an owner (precedent migration 0008), `org_shared` rows stay org-visible. Cost: users of existing persistent profiles must re-login or be rescued by an operator.
3. **Q3 (blocks E2 production): who holds and backs up the master key**, and is an environment master key acceptable for the first production release (KMS later)? Loss destroys every profile.
4. **Q4 (confirm default): `GET /v1/profiles/:id` never returns cookie values** (open question 13). Recommendation: yes, never; a future "export my cookies" is a separate audited DSAR feature. Confirm no operator workflow needs raw values.
5. **Q5 (confirm default): profile restore does not override the user agent** (locale and timezone only), per the honest-identity posture (ADR topic 5).
6. **Q6 (low priority, can wait): should user erasure delete that user's profiles** (needs `subject_type: "user"` handling and counsel input)?
