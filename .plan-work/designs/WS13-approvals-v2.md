## 6. Cross-session interfaces

**(a) Verevon Space session (F-t1-010).** Shared piece: the decide path, scope vocabulary and rule identity. Owner: Model Plane owns the approval record, `ApprovalScope`, cause, provenance and THREAD/RUN grants (reason: approvals SoR is session-core, capability matrix:55; Model proposes, owner executes); Control owns only the signed Space standing rule and a closed `turn_origin` claim (no code uses `turn_origin` today). Assumptions from the Space session: (1) it adopts `ApprovalScope {ONCE, THREAD, RUN}` with "conversation" = THREAD and treats "always" as a rule, not a scope (D2); (2) it supplies a rule record (`rule_id`, `rule_source=control`) and `turn_origin` for the decision body, which this stream stores but does not interpret; (3) addressee/collaborator routing and the "which approvals actually resume" honesty on the card are Space-side (WS13 shows `continuation_delivery` per kind once WS03 provides it); (4) any new `ApprovalKind` for quarantined tool output takes the next enum value (HEAD 6) through one coordinated proto change; (5) until it confirms owner-only semantics, THREAD/RUN grants are refused in Space threads (D9) and a Space deny keeps cancelling the run. The Space session must not widen the resumable kinds in the cold worker (WS03 D4); loop-level resume is WS03's.

**(b) Quarry v2 / browser session.** Shared piece: browser risk causes. Model Plane computes the gate on Model-proposed actions (`browser_agent.rs:908-948`); Quarry executes or rejects. This stream carries `cause.code=browser_action_risk` and the typed `risk_category` unchanged (no recompute). Assumptions: Quarry keeps the versioned browser contract; a Quarry-side rejection cause (ChallengeSignal, domain policy) is mapped to a cause code by WS21 using the same enum, never invented here; browser approvals stay once-only, denial still aborts the run, per-site consent and durable grants are WS21/broker work.

## 8. Effort and risks

**Total:** S0 1-2 d, S1 4-6 d, S2 4-5 d, S3 4-6 d, S4 3-5 d, S5 7-10 d, S6 8-12 d, S7 3-5 d, S8 3 d = **37-54 engineer-days** (about 8-11 weeks for one engineer; S1-S4 are about 3-4 weeks and independently shippable).

**Critical path:** WS01 S0 (land ZDR) -> S1 -> S3 -> (WS05 S1 + WS03 S3) -> S6 -> S7. S2, S4, S5 branch off S1/S3. S5 is the long pole only if Control capacity is scarce.

**Top risks**
1. **Hot-file contention** (`orchestration_grpc.rs`, `orchestration_store.rs`, `agent.rs`, `mod.rs`, `ChatMessages.tsx`) with WS02/03/05/12/14/24: mitigated by the edit-first rules, by keeping S1 to the three return sites, and by landing the live-only changes first.
2. **A standing grant is wider than a click.** Mitigations: closed eligibility table (D4: no provider writes, destructive, owner effects, browser), tool+operation key, TTL, per-use audit, revoke list, flag default off, Space refusal (D9); never reusing the rung carrier.
3. **Step-up depends on Control Plane.** Mitigation: S5 isolated behind D5 and a `shadow` mode; the other slices deliver value without it; password-less accounts need a method fallback.
4. **Silent provenance regressions**: legacy callers that omit `decision_source`, or a client forging it. Mitigation: gateway hard-codes USER, session-core stores `unattributed` and counts it; auto-posture is labelled; D6 hands the underlying product question to WS24.
5. **Audit/run-log consumers rejecting a new event** (audit-core dead-letter, capability-core session review on unknown `event_type`): mitigation: wire fixture in audit-core, flag `APPROVAL_AUDIT_EVENTS_ENABLED` default off until the proof stack accepts it, D10 verification before the run-log row.

**Not determined (flagged for the implementer):** whether session-core can read verified token claims (would allow step-up enforcement below the HTTP edge); `model-gateway/src/auth.rs` claims struct shape; the settings surface for S7 (WS25/WS23); whether `ListApprovals` payload size justifies a dedicated denied-digest RPC; whether capability-core's `requires_approval` flag reaches the execution gate beyond `Ask` (sweep item 8b); live tree compiles.
