## 3. Design decisions

Gate tags: **ADR-GATED** needs a user or architecture decision before the slice that depends on it; the audit ADR topic number from section 9.3 is named (topics 1 to 10). Untagged decisions are recommendations that can be built now.

### Lifecycle (F-t2-017)

**D1. How cancel, pause and resume reach Temporal.**
- Options: (a) a Temporal client inside quarry-control; (b) the edge calls an HTTP endpoint on the orchestrator; (c) the reconciler pattern: the edge writes a desired state to the control job record, the orchestrator polls and signals.
- Recommendation: (c). Control has no SDK dependency and its `NoopClient` returns `nil` where its own doc promises `ErrNotConfigured` (`temporal/client.go` 84-109), so wiring it would make trigger "succeed" silently. The orchestrator is a worker-only process with no HTTP listener (compose healthcheck is `pgrep`); (b) would add an inbound surface to it. The orchestrator already holds the client, the deterministic workflow id `quarry-job-<jobID>` and the 2 s control poll loop (`dispatcher.go` 128-203).
- Mechanism. New job columns: `desired_state` (`''|'pause'|'resume'|'cancel'`), `desired_seq` and `applied_seq` (BIGINT, each control write increments `desired_seq`), `workflow_id`. The edge calls the org-scoped control route `POST /v1/jobs/{id}/control {action}`; control validates the transition against the stored status, writes `desired_state` and `desired_seq+1`, appends a `control_requested` audit event (actor, action) and returns the job with a derived `phase` (`pausing`, `cancelling`). The orchestrator's new control loop (`QO:internal/jobs/control.go` [NEW]) reads `GET /v1/internal/jobs/pending-control` (rows where `desired_seq > applied_seq` and status is non-terminal; this is a new query, not the unscoped `GET /v1/jobs/?limit=50`, which silently ignores any job outside the newest 50 rows [INF, S5 section 6]), sends `SignalWorkflow(workflow_id, "", signal)`, then acks `POST /v1/internal/jobs/{id}/control-ack {applied_seq}` (compare-and-set: only raises `applied_seq`). Signals are idempotent in the workflow (pause on paused, cancel on cancelled are no-ops), so two orchestrator replicas acting on the same row are safe without a claim lease.
- Edge cases decided: cancel of an `accepted` job (not yet dispatched) sets status `cancelled` directly in control in the same transaction as the desired state, and `markRunning` becomes compare-and-set (`PUT /v1/jobs/{id}` gains `if_status`, 409 on mismatch) so a dispatch that raced the cancel cannot overwrite `cancelled` with `running`; the dispatcher then terminates the workflow it just started. Cancel of a terminal job answers 409 `Conflict` with the terminal status (Firecrawl answers 409 for a completed crawl). Pause of a non-running job and resume of a non-paused job answer 409. `ErrNotFound` from Temporal on signal (workflow already closed) is treated as applied, and the finalize sweep (D5) writes the true terminal state.
- Grace and force (Apify-style): if a `cancel` stays unapplied by the workflow (no `run_cancelled` event) for `QUARRY_CANCEL_GRACE_S` (default 120; a page activity may run up to its 5 minute StartToClose), the loop calls `TerminateWorkflow` and finalizes the job as `cancelled` with `forced: true` in the event. An in-flight `/v1/internal/run_page` call finishes at the edge (its Data Plane ingest is per page and atomic there), so the only residue is that the page result is not recorded; the durable-frontier queue rows for the run stay (the edge queue has no purge route, `QE:queue_routes.rs` [C] 200-202: listed as a follow-up in Risks, S-L2).

**D2. Status vocabulary.** Stored `jobs.status` values: `accepted`, `running`, `paused`, `completed`, `failed`, `cancelled`, `timed_out`, `skipped` (terminal set: `completed failed cancelled timed_out skipped`). `paused` and `running` flip from the `run_paused`/`run_resumed` events (added to `jobStatusForEvent`); a transition never leaves a terminal state (guard added to `markJobTerminalIfNeeded` and `updateJob`). Derived, not stored: `phase` (`queued`, `running`, `pausing`, `paused`, `resuming`, `cancelling`, then the terminal name) from status plus pending desired state. `JobSummary.status` is a free string on the Rust side (`quarry-core/src/resources.rs` [C] 156-180, not `deny_unknown_fields`), so no Rust enum change is needed; the SPA `isTerminalCrawlStatus` (`FE:shared/api/knowledge-client.ts` [C] 802-804) must learn `timed_out`, `skipped` (L5).

**D3. Batch and scrape control.** Options for `BatchJobWF` (`workflows.go` 359-383): add the signal handlers, or document it non-cancellable. Recommendation: add them. It is a sequential loop over at most 200 URLs (`GW:domains/knowledge/quarry.rs` 424), the helper already exists, and a batch the user cannot stop is the same product defect as a crawl. Implementation: `installControlHandlers` plus a shared `controlGate(ctx, a, ids, ctrl, counters)` used at the top of each URL iteration (emits `run_paused`/`run_resumed`/`run_cancelled`, blocks while paused), behind `workflow.GetVersion(ctx, "batch-control-v1", workflow.DefaultVersion, 1)` so in-flight batches replay. F-t2-040 will parallelise this loop: it must call `controlGate` between waves (interface noted in Section 7). `ScrapeJobWF` is one activity and stays non-controllable: control answers 409 `not_controllable` for any verb except cancel-while-`accepted`. Two workflow fixes ride along (both behind `GetVersion`, id `lifecycle-v1`): (1) `emitEvent` idempotency parts for `run_paused`/`run_resumed` currently are `(runID, type)` (`workflows.go` 437-449, 542-552), so the second pause of one run produces the same event id and control drops it as a replay (`resources.go` 261-268); add a monotonically increasing `pauseSeq` to the parts. (2) `waitWhilePaused` polls with `workflow.Sleep(5s)`; replace by `workflow.Await(ctx, func() bool { return c.state != statePaused })`, which costs no timers and no history growth.

**D4. Run origin.** Record `origin_type` (closed set `user`, `agent`, `schedule`, `webhook`, `api`), `origin_actor` (verified `user_id`, service id or schedule id), `origin_ref` (agent run id, Space id or schedule id) on the job. The edge stamps it from verified claims in `crawl_handoff`/`batch_handoff` (`routes.rs` 590-725), never from the body: a user token yields `user`; a service token yields `agent` when its service id is a Model Plane principal and `api` otherwise (the closed `surface` mapping that D6 defines for metering is reused rather than reinvented; `[UNVERIFIED]` the service id list is read from `CP:config/plane-service-principals.json` [C] at implementation); `schedule` is stamped by the orchestrator wrapper; `webhook` is reserved for F-t2-031 and not emitted yet. `origin_ref` carries the agent run id when the caller sends `x-verevon-run-id` on a service token only (same trust rule as D6's surface header). Stored as three columns plus `created_by` (the user id or service id), because the cancel authority rule (D10) and the notification recipient (S4) read them.

**D5. Typed timeout and per-kind deadlines.**
- Options: (a) detect from outside: an orchestrator sweep calls `DescribeWorkflowExecution` for running jobs and finalizes any whose workflow is closed; (b) make the workflow time itself out with a timer and emit the event (needs a bigger Temporal timeout as the backstop); (c) only raise the constant.
- Recommendation: (a) for every workflow death (timeout, terminate, crash), plus (c) per kind so the typed state is the exception, not the norm. New leaf package `QO:internal/timeouts/timeouts.go` [NEW] (a leaf because `jobs` imports `workflows`, which imports `activities`; the reconciler and activities must be able to import it without a cycle): `ExecutionTimeoutFor(kind, params)` with env `QUARRY_JOB_TIMEOUT_SCRAPE_S` (300), `QUARRY_JOB_TIMEOUT_BATCH_S` (default `min(7200, 20*urls)`), `QUARRY_JOB_TIMEOUT_CRAWL_S` (default `min(21600, 10*max_pages)`; 1800 when `max_pages` is unknown), shared by the dispatcher (`dispatcher.go:254`) and the schedule wrapper (S2). The dispatcher writes `deadline_at` (`started + timeout`) with `markRunning`. The sweep (`GET /v1/internal/jobs/running`, `DescribeWorkflowExecution` per row, `POST /v1/internal/jobs/{id}/finalize {status, reason, close_time}`) maps `TIMED_OUT` to `timed_out` plus event `run_timed_out {timeout_type:"execution", limit_s}`, `FAILED` to `failed`, `TERMINATED` to `cancelled` with `forced`, `CANCELED` to `cancelled`, and writes the event with a deterministic event id so a repeated sweep is a no-op. Pausing counts against the deadline: the status response shows `deadline_at` and a `warnings[]` entry `paused_counts_toward_deadline` while paused. Raising the timeout needs a one-line user confirmation (Section 9, Q5) because it changes how long a stuck run can hold an edge page budget; the default per-kind table above is the recommendation. Not ADR-gated.

**D6. Where `completed`/`total` come from.** Options: query the workflow (`QueryProgress`, in-memory, only the orchestrator can read it, gone after close); a checkpoint row (written every 50 pages only); aggregate the event log. Recommendation: aggregate the event log in control with one grouped query (`SELECT type, COUNT(*), MAX(seq), MIN(ts), MAX(ts) FROM events WHERE job_id=$1 GROUP BY type`, served by the existing `events_job_id_idx`, `001_init.sql`): `completed` = `page_fetched`, `failed` = final `page_failed`/`page_retried`+`final`, `blocked` = `page_blocked`, `retried` = non-final retries. `total` is `len(urls)` for a batch and the effective `max_pages` for a crawl (it is a ceiling, labelled `total_kind: "budget"`; D6 S0 stores the effective value in `params.max_pages`); never a prediction. The same aggregate fills `JobSummary.stats` in `jobWire` so the Ingestions page progress works (it already reads `stats.completed/total`, `GW:domains/ingestions/runs.rs` [C] `to_run_item`). Warnings are derived: `max_pages_clamped` (from params), `failures_present`, `paused_counts_toward_deadline`. `expires_at` = job `created_at` + control retention (`QUARRY_RETENTION_DAYS`, `janitor.OptionsFromEnv`), `null` when retention is off.

**D7. `/errors` shape.** `GET /v1/crawl/:id/errors` returns `{errors:[{id, ts, url, code, category, message, retryable, status}], blocked:[{url, ts, reason}], robots_blocked:[...]}` built from `page_failed`, `page_blocked` and final `page_retried` events, newest first, cursor = event seq. `robots_blocked` is the subset of `blocked` whose `payload.reason == "robots_disallowed"`: empty until F-t2-016 (the crawl has no robots check today, S5 F-t2-016 section 3) emits that reason, so the field exists and is honest. `code` is the Quarry error code mapped from `payload.category` (`blocklist`, `client_4xx`, ...). Payload additions (`final`, `code`) are made in `runPage` (`workflows.go` 191-201) and are not command-sequence changes, so no `GetVersion`.

**D8. Live tail.** Decision: implement in the edge handler by polling control, as the card says, with these properties. `GET /v1/jobs/:id/events?follow=true` (and the `/v1/crawl/:id/events` alias). Without `follow` the legacy drain-once behaviour is kept byte-for-byte (the SPA reads `data: done` as completion; the gateway and `streamCrawlRunEvents` stay valid) except that paging is fixed to loop until caught up instead of stopping at 500. With `follow=true`: first frame `event: snapshot` with `id: <last_seq>` carrying `{status, phase, counts, last_seq, deadline_at, origin, control}`; then events with `id: <seq>`; then the stream stays open, polling control `after_seq` every 500 ms while events flow, backing off to 2 s idle and 5 s after 60 s idle, and re-reading the job record every 5 s so a terminal state with no event (timeout, force-termination) still ends the stream; on a terminal status it sends the legacy `data: done` frame and closes. `Last-Event-ID` (header) wins over `after_seq` and over a snapshot-only resume; `replay=none|all` (default `all`, so existing semantics hold) lets a client that took the snapshot skip the replay. Keep-alive comment every 15 s (axum `KeepAlive`), `retry: 3000` and a graceful `event: reconnect` close after 30 minutes. Limits: per-org concurrent streams `QUARRY_EDGE__JOB_STREAM_MAX_PER_ORG` (default 20) and global `..._MAX` (500), over limit answers 429 `RATE_LIMITED` with `retry_after_seconds` in the envelope; the limiter is a process-global `LazyLock<Mutex<HashMap<String, usize>>>` with an RAII permit in new `QE:job_stream.rs` [NEW] (no `AppState` field, so no conflict with the uncommitted `state.rs` hunk and no harness literal to update). The cap is per edge instance; with N replicas the effective cap is N times higher (documented, not solved). Control load: at the cap 500 streams at 0.2 to 2 requests/s each; accepted because control is one indexed query per poll, and revisited by F-t2-029 metrics. No new bus. The NATS subject `quarry.run.<run>.<type>` (`quarry-runtime/src/nats_event_bus.rs`) carries only runtime-sink events, not the orchestrator's control events, so it cannot replace polling.

**D9. Result pagination data source (ADR-GATED, new topic, not in audit 9.3; adjacent to F-t2-052 "per-run result sets", W4).** Crawl output is not stored per job: events carry a 300-character excerpt (`page_extracted`, `workflows.go` 248-266), pages go to artifacts through `PageRunner` and to the Data Plane only when `ingest=true`.
| Option | What `GET /v1/crawl/:id/results` returns | Cost | Problem |
|---|---|---|---|
| A. Events as a page index | `page_extracted` rows: url, title, status, excerpt, word count, fingerprint, `artifact_id` when known | S, no new store | Excerpts, not documents; capped at 100 items or 10 MiB with `next` = last seq returned (Firecrawl's rule) |
| B. Artifact store | `FormatRef`s for each page via `ArtifactStore` keyed org/run/page/kind | M | `/v1/artifacts` has no run filter; whether every non-ingest crawl page writes an artifact is `[UNVERIFIED]` (check `PageRunner` artifact write path) |
| C. Data Plane retrieval | Documents for `ingest=true` runs through Data Plane contracts only | M, cross-plane | Only for ingest runs; needs the user token; Data Plane owns the contract |
| D. New per-run result set | Own table or object, export, TTL | L | This is F-t2-052 |
- Recommendation: ship A as phase 1 (slice L4, flag off by default, documented as a page index with `kind: "page_index"`), with `artifact_id` filled when B is confirmed, then replace by D when F-t2-052 lands. Decision needed from the user because A is a product statement ("results are an index, not content"). Everything else in F-t2-017 is independent of it.

**D10. Route shape, authority and ZDR.** Routes (all behind `require_auth`, org from the verified claim, never from the body): `GET /v1/jobs/:id` (kind-agnostic status), `GET|DELETE /v1/crawl/:id`, `POST /v1/crawl/:id/pause|resume`, `GET /v1/crawl/:id/errors`, `GET /v1/crawl/:id/events`, `GET /v1/crawl/:id/results` (L4), `GET /v1/crawl/ongoing`, and the same under `/v1/batch`. Static routes `/v1/crawl/jobs`, `/v1/batch/jobs`, `/v1/crawl/ongoing`, `/v1/batch/ongoing` are registered explicitly (collision, Section 2.2). The kind in the path must equal the job's kind, else 404. `DELETE` maps to cancel and answers 200 with the job and `phase: "cancelling"` (202-style semantics in a 200 envelope, consistent with the other edge routes); 409 on terminal. Authority: any member of the same org may read and control (matches `/v1/sources` delete and artifact reads); the control audit event records the actor. Whether control should be limited to the creator or an org role is Q4 (non-blocking; the rule lives in one function `authorize_control(claims, job)`). Service principals: `require_service_route_scope` is default-deny (`QE:auth.rs` [C] 504-545: only scrape, search, extract, artifacts, `/v1/agent/*`), so a Model Plane service token gets 403 on every lifecycle route; "Model proposes" therefore reaches Quarry only through the gateway registry actions executed under the user's session (D20). ZDR: crawl and batch are refused for ZDR callers (`routes.rs` 563-588), so a ZDR org has no new jobs; for jobs created before the org turned ZDR on, the control verbs and status counts stay available (wind-down), while content-bearing reads (`events`, `errors` URLs, `results`) are refused with the existing 403 ZDR wording, the conservative reading pending D4's catalogue code (ADR topic 4, rows for durable jobs).

### Schedules (F-t2-018)

**D11. Persistence model.** Extend `store.Schedule` and the `schedules` table with `name`, `config` (JSONB: `url`, `urls`, `max_pages`, `max_depth`, `ingest`, `schema`), `overlap_policy` (`skip|allow|cancel`, default `skip`), `timezone` (IANA, default `UTC`), `catchup_window_s`, `pause_on_failure`, `jitter_s`, `last_run_at`, `next_run_at`, `skipped_overlap_count` (the last three written by the orchestrator, D13), `updated_at`. `target_ref` keeps its meaning (the URL for scrape/crawl, the first URL or a `urls:<n>` label for batch; Validate requires it, and the edge fills it from `config`). The edge maps `kind` to `target_kind` (`scrape|crawl|batch` only; `extract`, `search`, `research`, `agent` answer 400 `unsupported_schedule_kind`), `config` to `config` plus `target_ref`, and stamps `org_id` and `created_by` from the verified claim (the preset path already does, `schedule_routes.rs` 286-294). Control's create handler reads `org_id` from the signed `?org_id` query and ignores any body value (`resources.go` 113-130 never read it), which fixes the 400. `schedule_at` (one-shot) is refused in v1 with 400 `unsupported_schedule_at` (control has no field for it; a one-shot is `Calendars` plus `RemainingActions: 1` in Temporal and is an optional S-size follow-up); the cron stays the strict 5-field grammar and the edge check is tightened from "at least 5" to exactly 5. A minimum cadence guard (default 15 minutes for crawl and batch, 5 for scrape, env-tunable) is added to control validation by evaluating two consecutive fire times: recurring crawls multiply cost and Firecrawl enforces a 5 minute minimum on monitors (card).

**D12. Fire path (how a Temporal fire becomes a tracked job).**
| Option | Shape | Verdict |
|---|---|---|
| A. Schedule action starts `CrawlJobWF`/`BatchJobWF`/`ScrapeJobWF` directly with fixed args | Needs `RunID` derivation inside three hot workflows; no control job record unless each workflow registers one; no place for preflight, skip reasons, notification | Touches three workflows that D2, D5, D6, F-t2-016 and F-t2-040 are editing |
| B. New wrapper workflow `ScheduledJobWF` as the schedule action: preflight activity, register-run activity, child workflow `quarry-job-<jobID>`, outcome events | One new workflow; the three job workflows only need to accept `RunID`/`JobID` they already take; the control job record exists so every lifecycle verb (D1) and `GET /v1/schedules/{id}/runs` work for scheduled runs for free | Chosen |
| C. Schedule action creates a control job row and lets the dispatcher run it | A tick workflow that returns immediately breaks overlap `skip` (the schedule thinks nothing is running) | Rejected |
- B in detail. Input `ScheduledJobInput{ScheduleID, OrgID, CreatedBy, Kind, Params, OverlapPolicy, ExecutionTimeoutS}` built by control's `workflowFor` (so config edits propagate through the reconciler). `ScheduledJobWF`: (1) `runID := "run_" + strings.ReplaceAll(workflow.GetInfo(ctx).WorkflowExecution.RunID, "-", "")` exactly as `ChangeMonitorWF` (305-313): replay-safe and unique per fire, so deterministic event idempotency keys (`emitEvent` hashes `runID+...`) never collapse two fires; (2) activity `PreflightFire` (D16) returns `{allow, reason}`; (3) activity `RegisterScheduledRun` posts to control `POST /v1/internal/schedules/{id}/runs {run_key, run_id, status, reason, workflow_id}`; control derives `org_id`, `kind`, `params` and `origin=schedule` from the schedule row (the orchestrator supplies none of them), uses `Idempotency-Key = sched:<id>:<execRunID>` against the existing `jobs.idempotency_key` unique index (`007_jobs_idempotency_key.sql`) so an activity retry returns the same job, and creates the row as `running` (so the dispatcher, which only starts `accepted`, never double-runs it) or as terminal `skipped` with the reason; (4) child workflow with `WorkflowID: "quarry-job-"+jobID`, `ParentClosePolicy: REQUEST_CANCEL`, `WorkflowExecutionTimeout: time.Duration(in.ExecutionTimeoutS) * time.Second` (a workflow must not read the environment, so the reconciler fills `ExecutionTimeoutS` from `timeouts.ExecutionTimeoutFor` when it builds the Temporal schedule args, and the same value is the `ScheduleWorkflowAction` timeout plus 60 s) and the input built from `Params` by a pure helper `CrawlInputFromParams`/`BatchInputFromParams`/`ScrapeInputFromParams` in `QO:internal/workflows/inputs.go` [NEW] (the dispatcher's `crawlInputFromJob`, `dispatcher.go` 432-469, is switched to the same helpers so ad-hoc and scheduled runs cannot drift; F-t2-016 and D6 add their fields there once) with `RunID: runID`, `JobID: jobID`, `UserID: CreatedBy`, `OrgID`; the job id comes from the activity result, which Temporal replays from history, so no non-determinism; (5) on child error the wrapper emits `run_failed` or, for `*temporal.TimeoutError`, `run_timed_out` with `schedule_id`, `created_by`, `org_id`, `reason` (no URL in the payload); (6) on wrapper cancellation (overlap `cancel` uses Temporal `CANCEL_OTHER`) it signals the child `cancel` through a disconnected context and waits up to 2 minutes.
- Reconciler changes (`schedules.go`): `ScheduleSpec` gains `Kind`, `Overlap`, `TimeZone`, `Jitter`, `CatchupWindow`, `PauseOnFailure`, `ExecutionTimeoutS`; `create`/`update` set `ScheduleOptions.Overlap`, `Spec.TimeZoneName`, `Spec.Jitter`, `CatchupWindow`, `PauseOnFailure`, and `ScheduleWorkflowAction.WorkflowExecutionTimeout`; `update` is skipped when the memo `spec_hash` is unchanged (today every 30 s pass calls `Update` plus `Pause`/`Unpause` for every schedule, `schedules.go` 328-361, and the unconditional `Unpause` overrides any pause made on the Temporal side); a spec whose `Workflow` is empty but whose Temporal schedule exists is paused, not skipped (otherwise setting the kill switch off would leave live Temporal schedules firing: today `reconcileWith` 160-163 only skips). Control stops serving a `Workflow` for the three kinds unless `QUARRY_SCHEDULED_JOBS_ENABLED=1` (default 0 until F-t2-016 lands, Section 5); `change_monitor` is unaffected.

**D13. Explicit enable.** All new scrape, crawl and batch schedules are created with `enabled=false` and the response says `needs_activation: true`; activation is the existing unpause/enable verb. The edge accepts `activate: true` on create only for a user token (a service token's `activate` is ignored), so a Model-proposed schedule always waits for a human. The migration `UPDATE schedules SET enabled=false WHERE target_kind IN ('scrape','crawl','batch')` runs once, so any row that predates the fix cannot start firing. `change_monitor` rows are untouched (they are created enabled and already run). Runtime state flows back: the reconciler reads `ScheduleInfo` (`NextActionTimes`, `RecentActions`, `NumActionsSkippedOverlap`) and `PUT /v1/internal/schedules/{id}/runtime {next_run_at, last_run_at, skipped_overlap}`, which fills the `nextRunAt`/`lastRunAt` fields the SPA already renders and today always gets `null`.

**D14. Trigger and backfill transport (ADR-GATED; new ADR, adjacent to audit topic 9 "automation owner"; the card asks for the choice to be recorded).**
| Option | Shape | For | Against |
|---|---|---|---|
| 1. SDK client in quarry-control | Add `go.temporal.io/sdk` to control, implement `temporal.Client` (`client.go` 75-82) | Synchronous result; smallest handler change | Second Temporal client and dependency; control becomes a Temporal caller (it is the plane's CRUD tier); today's `NoopClient` returns nil, the failure mode is silent success |
| 2. Pull-model request rows | Control table `schedule_requests`; the edge route inserts a row (202 + id); the orchestrator claims rows every 2 s and calls the existing `Manager.Trigger`/`Backfill`, then writes the result | Same direction as the jobs and schedules reconcilers; durable across restarts; org-scoped and auditable; no inbound port; reuses the unused `Manager` methods | Up to a 2 s delay; a new table and claim query |
| 3. Orchestrator HTTP endpoint | Add a listener to the orchestrator; control or edge POSTs `trigger` | Synchronous | New inbound surface on a worker, auth to design, hard runtime coupling control to orchestrator, reverses the poll direction |
- Recommendation: 2. Claim query uses `FOR UPDATE SKIP LOCKED` with a lease (a Verevon choice; the reference's claim SQL is not observable, audit F-t2-018 reference section). `trigger` is subject to the same fire-time preflight (D16) because a manual run spends the same budget; `backfill` is refused for crawl and batch (a backfill of N missed windows would start N crawls): allowed only for scrape and change-monitor schedules, and capped at 24 windows. The route returns 202 with `request_id` and `GET /v1/schedules/{id}/requests/{rid}` returns `pending|claimed|done|failed` plus the Temporal workflow id.

**D15. ZDR for schedules (ADR-GATED, topic 4).** (a) Refuse creation for ZDR callers with the existing helper `refuse_durable_job_under_zdr` made `pub(crate)` (`routes.rs` 563-588): this is the "refuse" option of D4's matrix rows 6 and 7 and the audit text assumes it is already true; D4 slice S-8 adds the catalogue code `zdr_durable_mutation_forbidden` and a staged flag in the same function, so the two slices share one call site and whichever lands second rebases. (b) Re-check at fire time (the pre-existing-schedule hole D4 left open, its open question 3): `PreflightFire` asks the edge, which reads the org's posture from org-core `GET /internal/orgs/:orgId/retention-posture` (`CP:org-core/internal/http/retention_posture_handler.go` [C], returns `{zdrIntent, entitled}`; effective ZDR is `zdrIntent && entitled`, `CP:auth-core/src/auth/interactive-retention-policy.ts` [C] 212-214). That scope (`org:retention:read:any`) is held only by auth-core today (`CP:docker-compose.yml` [C] 531-540) by design; granting it to a `quarry-edge` principal is a Control Plane change. Posture unknown (timeout, 5xx, no credentials) fails closed as `skipped_posture_unknown` and is retried by the next cron fire; posture ZDR records `skipped_zdr` and pauses the schedule. Rollout flag `QUARRY_EDGE__SCHEDULE_POSTURE=enforce|observe|off` (default `observe` for one week, as D4 stages S-8). (c) The same preflight is added to `ChangeMonitorWF` behind `GetVersion` so existing monitors of an org that later turns ZDR on stop (resolves D4 question 3; gated on the same flag).

**D16. Entitlement at fire time.** Reuse the one Control Plane client the edge is gaining in D6 S3 (`LimitsResolver` reading billing-core with a `quarry-edge` service principal): the edge route `POST /v1/internal/schedules/preflight {org_id, schedule_id, kind, units}` (authenticated like `/v1/internal/run_page`: runtime token plus the existing run-binding HMAC over `org_id\nschedule:<id>`, `verify_run_binding`, `QE:internal_auth.rs` [C] 194-209) returns `{allow, reason, zdr, clamped_units}`.
