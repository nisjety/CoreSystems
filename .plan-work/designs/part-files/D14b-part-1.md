Total about 46 engineer-days in two parallel streams (Section 4 and Section 5). Nothing here is XL, but two parts cannot be finished by Ingestion Plane alone: the failure notice (Application Plane must register Quarry as a notification caller) and the fire-time ZDR re-check (Control Plane must grant one narrow read scope). Both are named as blockers in Sections 8 and 9; both slices still ship their Quarry-side half behind flags.

Statement of the product outcome: a user or agent can see what a crawl or batch is doing, stop it, pause it and resume it from the product, with a typed terminal state for every way a run can end (completed, failed, cancelled, timed out, skipped); and a schedule created in the UI for scrape, crawl or batch is stored in full, is created disabled, becomes a real Temporal schedule only after an explicit enable, fires through a wrapper that re-checks ZDR posture and entitlement at fire time, shows its runs, and can be triggered or backfilled.

### 2.2 Audit claims that are wrong or drifted

| Tag | Claim | What the code does |
|---|---|---|
| [DRIFT] | Card F-t2-017: reuse "control `GET`/`PUT /v1/jobs/{id}` (resources.go:24-31, 486-530)" as the desired-state carrier. | `PUT` has no org check and no desired-state field (`resources.go:513-549`). The signed `?org_id` makes an org-scoped route safe (control HMAC canonical string includes path and query: `QCT:internal/httpx/hmac.go` [C] 168-186), so this design adds a dedicated org-scoped `POST /v1/jobs/{id}/control` and leaves `PUT` for orchestrator status transitions only (made compare-and-set). |
| [CLAIM-FALSE] | Card F-t2-018 and audit ADR topic 4: "Durable jobs, crawl, batch and schedules are refused under ZDR (`routes.rs:563-588`)". | `refuse_durable_job_under_zdr` is called only from `crawl_handoff` (596) and `batch_handoff` (687). `create_schedule` (`QE:schedule_routes.rs` [C] 239-340) has no ZDR reference. Confirmed by D4 section 2.3. A ZDR org can create schedules and change monitors today. |
| [CLAIM-FALSE] | `Q:docs/SCHEDULES.md` [C]: "`GET /v1/schedules` paginated, org-scoped" and "`DELETE` soft-delete (row kept for audit)". | Control `listSchedulesHandler` (`resources.go:63-76`) reads only `limit` and `cursor`: it lists every org's schedules (the orchestrator needs that). The edge `list_schedules` (`QE:resource_routes.rs` [C] 795-817) forwards `org_id` but control ignores it, so any authenticated tenant receives all tenants' schedule rows, including each `target_ref` URL, through `GET /v1/schedules`; the gateway monitoring list filters only on `target_kind` (`GW:domains/monitoring.rs` [C] 353). `deleteScheduleHandler` is a hard `DELETE FROM schedules` (`QCT:store/pg/resources.go` 796-805). Control `get`, `delete`, `enable`, `disable`, `pause`, `unpause` take only an id: no org check, so a foreign schedule id can be paused or deleted by any tenant that learns it [INF]. `scheduleTrigger`/`scheduleBackfill` fetch by id and use `sched.OrgID` without comparing to the caller. **New finding, fixed first in S1.** |
| [CLAIM-FALSE] | "Failure notices go through Application Plane notification-core by API" (card F-t2-018) as a wiring task. | notification-core rejects the legacy `x-internal-api-key` (README.md [C] 17-19; `AP:internal/http/server_test.go` asserts it) and requires HMAC v2 delegation (`AP:internal/delegation/verifier.go` [C] 80-165). `CreateNotificationRequest` accepts only service ids `verevon-gateway`, `support-worker`, `capability-core` and a closed type allow-list (`AP:internal/http/handlers.go` [C] 154-173, 199-217). Failure notices need Application Plane code (new principal, allow-listed types, `_default` channel rows) plus a Quarry-side HMAC v2 signer. |
| [DRIFT] | Card F-t2-017: "build `/errors` from existing `page_failed` and `page_blocked` events". | A page that fails with a retryable category after the activity retries are exhausted is recorded as `page_retried` (the only event the branch emits for network, timeout, 5xx) while the crawl counts `pagesFailed++` (`workflows.go:464-469`). `page_failed` plus `page_blocked` would omit the commonest real failures. Fix: mark the terminal-branch payload `final: true` and `code`, and build `/errors` from `page_failed`, `page_blocked` and `page_retried` rows that carry `final: true`. |
| [DRIFT] | Card: "Surface the 30-minute `WorkflowExecutionTimeout` (dispatcher.go:254) as a typed terminal state". | A workflow killed by Temporal's timeout runs no code, so no event is emitted and the control job stays `running` forever. Also `waitWhilePaused` sleeps in 5 s timer steps (`signals.go:30, 140-146`): pausing consumes the 30 minutes and about 2 history events per 5 s [INF], and a 5000-page crawl at one page per second needs about 83 minutes, so the timeout ends large crawls today (D6 S0 flags the same). The terminal state must be detected from outside the workflow (Section 3, decision D5). |
| [DRIFT] | Sweep S5: `crawl_handoff` ack at routes.rs 590-667 forwards to control with "HMAC". | `QE:handoff.rs` [C] 57-69 sends `POST {control}/v1/jobs?org_id=` with no HMAC triple, while the standalone compose sets `QUARRY_INTERNAL_HMAC_REQUIRED: "1"` on control (`Q:deploy/compose/docker-compose.yml` [C] 155) and control's verifier returns "missing HMAC headers" for unsigned requests when required (`QCT:internal/httpx/hmac.go` 107-113).
