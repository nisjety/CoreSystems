**Eval corpus v0 (Tier A, runs in CI, deterministic).** `stale_ref_recovers_after_auto_reobserve`; `timeout_never_replays_the_action`; `one_driver_error_is_retried_once`; `policy_denied_is_terminal_with_fixed_text`; `challenge_detected_ends_blocked`; `forbidden_off_domain_is_terminal`; `rate_limited_waits_once_then_backpressure`; `three_consecutive_failures_stop_the_run`; `same_action_three_times_without_change_stops_no_progress`; `done_answer_is_returned_in_the_summary`; `done_blocked_ends_failed_with_prefix`; `planner_auth_expiry_is_terminal_not_an_observe_loop`; `malformed_reply_retried_once_then_tolerant_parse`; `first_step_is_deterministic_goto_without_a_planner_call`; `legacy_procedure_prompt_is_byte_identical`; `prompt_goldens_match`.

**API / data model.** None (no proto, no SQL). Run output format additions are text only.

**Flags and rollout.** `QUARRY_BROWSER_AGENT_PROCEDURE` (`browse/1` default, `legacy/0` rollback), `QUARRY_BROWSER_AGENT_MAX_CONSECUTIVE_FAILURES`, `..._MAX_TOTAL_FAILURES`. The loop changes apply only when a planner is selected, except the typed error mapping, which is also correct for the deterministic path. Rollback: `legacy/0` plus raising the failure limits restores today's prompt and near-today's leniency; a full revert restores the rest.

**Tests.** Unit: `cargo test -p execution-core --lib -- browser_agent quarry_agent llm_planner procedure failure`: every `classify_quarry_error` row, `no_progress_detector_*`, `failure_budget_*`, `procedure_text_is_under_the_word_budget`, `done_payload_is_parsed_from_strict_and_plain_schema`. Hermetic: `cargo test -p execution-core --test browser_planner_hermetic` (the corpus above). Existing live probe `planner_on_terra_returns_valid_action_json` stays `#[ignore]` and gains the `answer` field case.

**Definition of done.** The Tier A corpus is green in CI; on a dev stack a task that hits a stale ref completes; `legacy/0` reproduces the old prompt byte for byte; a `done` answer reaches the chat as the tool result.

**Deployment evidence.** Rebuild execution-core; dev stack, mode `allowlist`, real bearer. Flow 1 (recovery): a fixture page whose button re-renders on first click (the page replaces the DOM once): the run completes with `failed_actions:1` in the usage line, and Quarry's receipts (`GET /v1/agent/runs/<qid>/receipts`) show the failed step followed by an observe and a successful click; baseline before the slice: the run ends `failed` at the first stale ref. Flow 2 (answer): "read the price on this page" ends `completed` with the price in `summary`. Flow 3 (stop rules): a page that never changes after the click ends `failed` with the `no_progress` prefix after exactly 3 repeats. Flow 4 (rollback): `QUARRY_BROWSER_AGENT_PROCEDURE=legacy/0` restart, the prompt golden for `legacy/0` is the one in use (log line `procedure:legacy/0`).

**Effort.** L, 5 engineer-days (failure classification and loop 2, procedure and view 1, answer and planner errors 1, fake Quarry state and corpus 1). **Risks.** The loop function is a hotspot for [D8] (attach mode), [D3] (challenge) and [D6]; land S1 and S3 first and tell their owners (section 5); a stricter loop can end runs the old loop would have "completed" by observing; prompt wording is only provable with the live Tier C probe, so S3 ships the mechanism and the corpus, not a success-rate claim.
