
## 3. Design decisions

Format: decision; options; recommendation; rationale. "ADR-GATED" marks a decision that needs a user or ADR answer, with the audit 9.3 topic number.

**D-1. Where free omnibox text goes.** Options: (A) render Verevon search results inside the browser frame area and let the user click a result to navigate; (B) hand off to the Home "Nett" tab (`?tab=web`, no query parameter exists, `DashboardHome.tsx` L60-64); (C) send it to chat only. Recommendation: A as the default Enter behaviour, plus an explicit "Ask Verevon" row (C) and an explicit "Search the web" row in the dropdown; B is not built. Rationale: A keeps the user in the dock, reuses `runWebSearch` (`search-client.ts:85`) and the gateway search route, and never sends a person to a third-party engine (the demo guard already encodes that policy). A result click is a normal `navigate`, so it is governed by Quarry exactly like a typed URL; until WS8 lands a cross-host click returns 403 and the UI says so (D-6).

**D-2. A new feature slice `FE/src/features/browser/`, not more code in BrowserChrome.** Options: keep adding to the 2172-line `BrowserChrome.tsx` (seven items touch it per sweep S7 hotspot 1), or put new components, stores and the extracted controller in a new folder and keep BrowserChrome hunks to wiring lines. Recommendation: new folder `browser/{omnibox,evidence,dock,session}`; BrowserChrome gets one-line mounts and prop additions. Rationale: CLAUDE.md asks for feature-sliced folders and "prefer existing plane patterns"; it also minimises merge conflicts with F-t2-028, 033 and 038, which all edit BrowserChrome.

**D-3. ZDR rule for omnibox history and suggestions: none.** No local history read or write, no suggestion fetch (local or remote), no search-home card recording, whenever the org retention verdict is "deny" (`isLocalRetentionAllowed()`, `chat-retention.ts`), the active chat thread is temporary, or the browser session is ZDR (`session().zdr`). The gateway also refuses server-side: `search_suggestions` returns the empty list when `request_zdr(&headers, None)` or `org_zdr_enabled(&state, &user)` is true. Options considered: allow remote suggestions under ZDR but not local history (rejected: the typed prefix is user content that would reach autocomplete-core), refuse the whole omnibox search (rejected: search is not retention, and `search_routes.rs` already skips `SearchIssued` when `zdr`). Free-text search itself stays available under ZDR and carries no `includeAnswer` by default. ADR-GATED, audit topic 4 (ZDR per feature): the recommendation matches the D4 default ("do not loosen refusals").

**D-4. Org-scoped autocomplete in the omnibox.** Options: (A) include `scope=queries` from autocomplete-core like the dashboard dropdown; (B) local history plus related queries only; (C) hosts only. Recommendation: A behind the same behaviour as the dashboard dropdown, flagged as an open question. Rationale: surfacing a colleague's query terms in a private browser bar is a product-privacy choice, not a technical one; today's dashboard already does it, so B or C would be inconsistent unless the user decides the omnibox is stricter. Listed in section 9 (question 2).

**D-5. What the local history stores.** Entries `{ url, title, lastVisitedAt, visits }`, max 200, key `verevon.browser-omnibox.v1:{org}:{user}` produced next to `webHistoryStorageKey` in `home-local-content.ts`, purged by `clearHomeLocalContent()` (so a ZDR verdict flip and sign-out-style purges reach it). URL scrub before storing: http(s) only, userinfo removed (`cleanWebHistoryUrl`), fragment dropped, query kept only when at most 256 characters and no key matches `token|key|secret|password|auth|session|code|sig|jwt` (case-insensitive), otherwise the query is dropped. Never stored: page text, screenshots, form values. Rationale: copy the proven shape of `web-history.ts` (zod, tidy, per-identity key) instead of inventing one.

**D-6. Navigation outside the session's scope.** Until WS8, a cross-host navigation returns Quarry 403 "outside the run's allowed domains". Recommendation: the gateway maps that exact Quarry message to a typed error `browser_navigation_outside_scope` in `forward_quarry_failure` (string match, marked interim; WS8 should emit a typed Quarry code and delete the match), and `errors.ts` gets `no`/`en` copy; the omnibox shows an inline row "This session is limited to {host}" with "Open in a new session" disabled until the capability `human_browsing` appears in the session's `capabilities`. Rationale: the SPA must not guess; capabilities are the existing server-driven switch (D-17).

**D-7. Hard reload is a new Quarry action; error-page retry is SPA-level.** Options for hard reload: (A) new `AgentAction::Reload { ignore_cache }` executed with CDP `Page.reload{ignoreCache}`; (B) emulate with `navigate` to the same URL (cannot bypass cache, and a `navigate` to the failed URL is the soft path already). Recommendation: A, small, Quarry-owned, human-only by construction (the Model-facing action list in `quarry_agent.rs` and `tool_bridge/mod.rs` never gains it). Caveat recorded: `Page.reload` on a page that was the result of a POST re-submits it; the SPA labels the menu item "Reload ignoring cache" and soft reload stays a GET `navigate`. Error-page retry: BrowserChrome gains `navigationError?: { url, code, message } | null`; when set, the reload button retries `navigationError.url` (Codex semantics) and an in-frame card shows the typed message with a Retry button; cleared on the next successful action. The detection helper `navigationFailureFromError(action, error)` is a pure function shared by the old and new controllers.

**D-8. Dock state: client-side, per org and user, layout only.** Record `{ position: 'right'|'bottom'|'maximised'|'hidden', size: 0.25..0.7, chatPerTab: 'keep'|'new', composerHidden: boolean }` under `verevon.chat.browser-dock.v1:{org}:{user}` using `readClientJson`/`writeClientJson` and a zod schema that rejects any extra field. No URL, title, session id or run id is ever written. Not synced server-side, ever (ZDR rule: nothing server-side that a ZDR workspace could not also do; and there is no gateway store for it). Not purged by ZDR because it holds no content; asserted by a unit test that the serialised record contains only the four fields. Migration: if `verevon.chat.runPanel.collapsed.v1` is `'1'` and no dock record exists, start at `hidden` (which keeps today's rail). Pattern copied from `home-layout-state.ts` [C] (key shape, forgiving read, strict write).

**D-9. One `BrowserDock` hosts two bodies.** Options: (A) a second, parallel panel for interactive sessions beside `ChatLiveRunPanel`; (B) one dock host with positions, hosting either the existing run-watch body or an interactive session body; (C) rewrite `ChatLiveRunPanel`. Recommendation: B. `ChatLiveRunPanel` keeps its run-stream logic and its `ChatWideResearchPanel` slot; the dock owns placement, size, maximise and hidden. Rationale: the audit says the live-run panel "becomes a compact mode of the same component"; B gets there without a rewrite and keeps its 20 existing tests (`ChatLiveRunPanel.test.tsx`) intact.

**D-10. Extract the session controller, do not migrate KnowledgeComposer in the same PRs.** `useBrowserSessionController` is written as a new module that mirrors KnowledgeComposer L799-1160; KnowledgeComposer is not touched (except the 15-line error hook in Slice 2). A later cleanup slice (not scheduled) moves the Crawl composer onto it. Rationale: KnowledgeComposer is [M], 1999 lines, CRLF, and owns scrape preview state; a risky refactor of a shared monolith inside a feature PR is how regressions ship. Duplicating about 350 lines for a quarter is cheaper than a broken Crawl composer.

**D-11. "New chat per tab or keep the chat".** Default `keep` (one thread continues across tabs), user toggle in the dock header `new` (a new thread starts when the user asks about a different tab). Aside defaults to new-session; Verevon threads are durable and billed, so surprise-creating threads is the worse default. The tab-to-thread map is an in-memory `Map` only (lost on reload, never in storage), so it also needs no ZDR handling. Question 3 asks the user to confirm the default.

**D-12. Floating composer: focus first, own send second.** A floating textarea that really submits needs the composer's current model, tone, privacy tier and ZDR snapshot (`DashboardComposerSubmitPayload`, `DashboardComposer.tsx:319-360`); bypassing them could send a turn below the user's minimum privacy tier. Recommendation: first cut is an "Ask about this page" affordance that focuses and prefills the main composer (the `focus-composer` shortcut path already exists). `composer-settings-client.ts` is only a catalogue loader; the snapshot lives inside `DashboardComposer` state. A 0.5-day spike at the start of Slice 4c decides whether to lift that snapshot into a small shared store; only then add the floating send. No page content is attached in either cut (F-t2-028 owns governed page context).

**D-13. How the dock binds to the agent's browser. ADR-GATED, audit topic 3 (shared human and agent sessions).** Options: (A) attach: the Model Plane run acts in the user's own Quarry session (F-t2-013 phase 2), so every existing gateway session route (frames, control, tabs, timeline, receipts) works unchanged because the run actor is the user; needs a delegation design and `attach_session_id`. (B) observed relay: execution-core records the Quarry run and lease it leased, model-gateway exposes a read relay (frames, devtools, receipts, egress) behind session-core's owner check, the gateway proxies it; read-only, pause/resume/stop stay as today. (C) keep per-step artifact screenshots (today). Recommendation: B (Slice 6a) as the no-ADR step that makes the panel live and unlocks the evidence panels for chat runs, A as the target (Slice 6b) once the ADR is decided. Rationale: B needs no new authority (the same service token that already drives the run reads its own session) and no change to `caller_owns_live_run`; A is the only way a user can take over or steer, but widening ownership is exactly what D1, D2 and the audit warn about. Do not implement the "viewer" variant that teaches Quarry to admit org members to service-owned runs.

**D-14. Evidence proxies: a new gateway module with allowlisted queries and compact projections.** New `GW/domains/browser_evidence.rs`, merged in `main.rs` next to `browser::router`. Rules: (1) path segment validation with the existing `is_valid_path_segment`; (2) org from the verified session (`resolve_browser_run_owner`), never from `x-verevon-org-id`; (3) query strings rebuilt from an allowlist (`afterSequence`, `limit` 1..512, `levels` subset of {debug, info, log, warn, warning, error, verbose} max 5 items, `filter` at most 200 characters without control characters, `category` in {console, network, lifecycle}, `tabId` charset `[A-Za-z0-9_-]{1,64}`), never `query_suffix`; (4) responses are projections, not pass-through: receipts drop `observation` and `action.text`, procedures replace typed text by `{ redacted: true, length }` before they leave the gateway, egress receipts are renamed to camelCase; (5) typed errors for the 409 compile failure (`browser_procedure_not_compilable`) and the ZDR no-receipt case (`browser_receipts_unavailable_zdr`). The existing `get_devtools_events` is switched to the same allowlisted builder. Rationale: the fabrication guard in `verevonv3-ci.yml` forbids domain reads of org headers, and receipts are the one place typed secrets live until F-t2-021.

**D-15. Procedure panel is read-only and server-composed.** One gateway call compiles the procedure from the caller's receipts and, server-side, runs Quarry's quality check on the raw procedure, returning `{ procedure (redacted), quality }`. No replay and no impact-check surface in this slice (they are for the owning release workflow). Rationale: the compile route only succeeds when every step is completed and verified; showing the reason a session is not compilable is itself useful, and the raw action JSON never reaches the browser.

**D-16. `browser.console` is a read-only Model Plane tool with a fixed output shape, and the untrusted-content classification is fixed with it.** Input `{ grant_id, quarry_run_id, lease_id, levels?, filter?, limit<=100, since_sequence? }` with `deny_unknown_fields`, validated like `browser.observe` against the broker-validated grant; output `{ entries: [{ sequence, tab_id, level, text }], next_sequence, truncated }`, never `payload` (raw CDP objects with remote object ids), each text capped at 500 characters and the whole result at 16 KB, passed through the existing scrubber. Classification: add `browser.console`, `browser.observe` and `browser.act` to `BrowserScraped` in both copies of `TrustClass::classify` (they say "keep in sync by hand"). Owner: sibling (b) implements it in `execution-core` (its files are in flight); this design specifies it. No ADR (audit topic 6 does not apply: nothing is executed in the page).

**D-17. Feature gating.** The SPA has no runtime feature-flag system (`import.meta.env.VITE_*` only), and the capability builder in the gateway is a free function (`browser_response_from_owner_projection(projection, observation)`, `browser.rs` L2589) with seven or more call sites in the hottest file of the plane, so threading `AppState` flags through it would collide with D1, D2 and WS8. Recommendation: (1) the existing server-driven `capabilities` array (static lists at `browser.rs:2578` and `:2700`) for features whose availability is a backend fact (`hard_reload`, `evidence`, later `human_browsing`, `attach`), added only after the backing service is deployed; (2) Vite build flags for staged rollout and rollback: `VITE_BROWSER_OMNIBOX_SEARCH` and `VITE_CHAT_BROWSER_DOCK`. Rollback is unsetting a Vite flag (frontend container restart, memory recipe) or removing a capability string (gateway image swap).

**D-18. Action contracts first.** New registry ids: `browser_omnibox.search` (ownerPlane `ingestion`, risk low, no approval, reversible, input `{ query, limit? }`), `browser_omnibox.suggest` (ownerPlane `ingestion`, risk low, input `{ query }`), `browser_evidence.compile_procedure` (ownerPlane `ingestion`, risk low, input `{ sessionId, procedureId? }`). Updated: `browser_action.run` description and a doc note listing `reload`; `browserSetControlModeInput` gains `expectedEpoch` (after D2). Each id gets a dispatcher arm in `handlers.rs` and a function in a new `GW/domains/actions/browser_omnibox.rs` (declared in `actions.rs`), otherwise `action-surface-contract.test.mjs` fails. They are not model-eligible and stay out of `model-eligibility.ts`; the exact-set tests in `action-registry.test.ts` and `catalog-manifest.test.ts` must still pass unchanged. Reads that are not operations (receipts list, egress list, devtools) get typed client functions in `browser-client.ts`, like the existing timeline and devtools reads. The existing browser UI calls clients directly, not the registry, and this design keeps that practice; the contract is the catalog and agent surface. The existing browser ids use `ownerPlane: 'model'` although Quarry executes them; new Quarry-owned ones use `ingestion` to be honest about the owner (noted deviation, no behaviour effect).

**D-19. Where "agent-flagged tab" comes from.** Options: infer from the timeline `initiatedBy` on `Tab` events (D2 adds it) or have Quarry store the opener per tab and return `openedBy: 'user' | 'agent'` on the tab list. Recommendation: Quarry returns `openedBy` (small per-run map in `RunEntry`, written in `new_tab` from the derived initiator, first tab is `user`), the gateway passes `tabs` through unchanged (it already does), the SPA reads `tab.openedBy`. Rationale: inference from a paginated timeline races the tab list; the flag is cheap and authoritative. Owned by the WS8 and D2 Quarry work; Slice 5 reads it when present and degrades to no marker when absent.

**D-20. Control hand-off UI is compare-and-set.** Take over and Give back send `expectedEpoch` from the last projection (`controlEpoch`, D2 `expected_epoch`); a stale epoch returns 409 `CONFLICT`, the strip refetches the projection and re-renders instead of silently undoing a newer takeover. `USER_TOOK_OVER` reaches the SPA through the gateway's existing `browser_human_takeover_active` code and is shown as a state ("paused because you took over"), never as an error toast.
