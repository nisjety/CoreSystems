### 2.2 Per-token costs the audit does not list (opened; magnitude NOT measured, S1 measures)

1. **Local snapshot rewritten on every flush.** Effect `use-chat-controller.ts:1742-1767` subscribes to `deep(state.turns)` and `deep(state.taskSteps)` and calls `writeThreadSnapshot` (`:557`). That function deep-clones the transcript (`snapshot`), runs `turnsToTranscript`, `readChatThreadHistory()`, `upsertChatThreadHistory` and `upsertChatThreadTranscript`. The latter reads and parses the whole `verevon.chat.threadTranscripts.v1` key and re-stringifies it (`FP/src/features/chat/lib/chat-thread-history.ts:417`, caps 40 threads x 120 turns x 32,000 chars, lines 18-24; `FP/src/shared/session/client-storage.ts:56-63`), and `writeClientValue` writes to **both** localStorage and sessionStorage. So per-flush work is proportional to all locally cached transcripts, synchronous on the main thread. Only the server snapshot is debounced (500 ms, `:455-461`).
2. **Per-delta task-step rewrite.** `onMessage` (`:2609-2616`, resume `:1619-1644`) calls `upsertTaskStep(createTurnStep(...'answer'...))` on every delta; `createTurnStep` stamps `createdAt: new Date().toISOString()` (`chat-normalizers.ts:1260-1277`) and `upsertTaskStep` (`:3809-3818`) replaces the whole `taskSteps` array with spread copies of every step. Reasoning deltas do the same (`:3109-3114`).
3. **One Trace row per token.** Every chunk frame also goes through `onUiEvent` -> `appendUiEvent` (`:272-275`: `[...current, event].slice(-5000)`); `toVerevonUiEvent` maps `chunk` to `message.delta` (`FP/src/shared/chat/verevon-ui-events.ts:311`); `TracePanel` (`ChatPanels.tsx:1410`) lists every event with `uiEventLabel` (`verevon-ui-events.ts:387-391`). A 5,000-token answer evicts all earlier lifecycle events from the live Trace and trips the truncation notice. Whether the Steps panel filters `message.delta` (`ChatPage.tsx:651`) is not determined.
4. **Cold open is a sequential waterfall of full reads.** `loadThread` (`:1004`): `listChatThreads()` (`:1051`), then `getChatThreadTranscript` (`:1055`), then `getThreadMessages` (`:1075`), then plan/effect-class/trace hydrators. It does **not** paint the local snapshot first. `/transcript` (BFF `history.rs:196` `get_thread_transcript`) lists all durable threads (`read_durable_threads`) and then `read_canonical_transcript` (`:595-640`) calls MG `GET /v1/threads/{id}/messages`; `/messages` (`json_handlers.rs:239`) calls the **same** MG route. `canonical_messages_to_transcript` (`history.rs:642`) always sets `task_steps: None` and an empty `updated_at` that the handler overwrites from the thread listing. So the open path performs two identical unpaged session-core reads plus two thread listings. `readSavedAnswer` (`:1241-1254`) does a third full read after an interrupted stream.
5. **Event-name facts for batching.** SSE `chunk` -> `onMessage` in `FP/src/shared/api/chat-client.ts` `dispatchEvent` (WT `:1437`, `case 'chunk'` `:1466` [LV 1497]); `readSseStream` (`FP/src/shared/api/sse.ts:25-130`) dispatches every complete frame synchronously inside one `reader.read()` loop, so Solid's microtask batching already coalesces all frames of one network read into one reactive flush. rAF batching therefore only helps when reads arrive faster than frames; S1 decides.

## 8. Effort and risks

**Total.** Committed core (S1, S2, S3, S5): about 12-17 days. Conditional (S4, S6, S7): 3-6 days. Paging (S8, S9): 11-16 days. Virtualisation (S10): 8-12 days. Worst case ~35-50 days; expected, if S2/S3/S7 clear the D5 triggers, ~15-23 days. The audit's "M" covers only the committed core, and only if S3's extra findings are accepted into scope.

**Critical path.** S1 -> (S2 || S3 || S5) -> D5 decision on S1 numbers -> S7 / S4 / S6 -> (only if triggers still fire) S8 -> S9 -> S10. S5 is independent and can ship first.

**Top risks and mitigations.**
1. **Solid 2.0 rc `<For>` behaviour is read, not run.** Mitigation: the S1 counter pins it before S2 builds; reference-keyed fallback and `VITE_CHAT_RENDER_LEGACY` rollback.
2. **Incremental parse diverges from the full parse in an edge case** (HTML-comment tail rewrite, tables, lists with blank lines). Mitigation: restartable-block flags, `FROZEN_TAIL_BLOCKS = 2`, differential property test at every prefix over a corpus plus random chunkings, full-parse fallback on any non-prefix change.
3. **Hot-file merge pressure on live-modified files** (`ChatMessages.tsx`, `use-chat-controller.ts`, `chat-client.ts`, `index.tsx`, `sessions.proto`, `grpc.rs`). Mitigation: small disjoint hunks, WS01 S0 first, the edit-order rules in section 5, add-only proto, never reset the live tree.
4. **Wrong target.** The biggest per-token cost may be elsewhere than I5 assumed (local snapshot, step rewrite, Trace rows, section 2.2). Mitigation: S1 measures before S2-S4 and attributes cost per source (the spec records `setItem` bytes, mutations, long tasks separately); D5 triggers are numbers, not opinions.
5. **Paging changes what the UI can see** (evidence panels, `savedAnswerForTrailingTurn`, cached-metadata merge, pins) and a global-identity cursor would leak. Mitigation: message-id cursor resolved inside the thread, conditional on measurement, explicit "load all", partial-aware merge and saved-answer logic with tests, default-off flag.
