## 2. Verified current state

**The chain, as built.** The Do loop offers `browser.observe` and `browser.act` unconditionally (`EC/runtime_loop/agent.rs:4196-4205`, inside `offered_tool_defs`, fn at 4109). Each call goes `agent.rs:1919` -> `runtime_loop::execute_step_with_subagent` (`runtime_loop/mod.rs:400-452`), which passes `None` for `browser_grant` (447; the doc at 390-394 says "deliberately carries no browser grant") -> `execute_step_inner` arm `mod.rs:589-594` -> `tool_bridge::execute_quarry_browser_mcp` (`tool_bridge/mod.rs:237-249`) returns "browser MCP requires a broker-validated grant". Only the unary `ExecuteStep` gRPC builds a `ValidatedBrowserGrant` (`EC/grpc.rs:184-215`, call 886-948), from a model-supplied `grant_id` re-validated with the caller's `x-browser-authorization` bearer (`EC/auth.rs:449-465`).

**Findings beyond the audit text (code wins):**
1. Even with a grant, nothing creates a Quarry run for the Do loop. `execute_quarry_browser_mcp` explicitly "does not create a browser run" (`tool_bridge/mod.rs:229-232`); the tool schema makes the MODEL supply `grant_id`, `quarry_run_id`, `lease_id` (`agent.rs:4199`; parse `tool_bridge/mod.rs:429-458`, `deny_unknown_fields`). No production code mints either id for it. `QuarryAgentClient::start_run` (`EC/quarry_agent.rs:574-609`) is used only by the `browser_agent` loop (`browser_agent.rs:674`).
2. `RunAgent` accepts no browser bearer (`EC/grpc.rs:1203-1271`: data-plane, inference, sandbox only). model-gateway's auth middleware already verifies and injects `VerifiedBrowserBearer` when the header is present (`MG/auth.rs:1078, 1212, 1271-1273`), but the agentic stream never forwards it (builder `MG/sse.rs:8296-8346` carries sandbox only). The BFF never mints it for chat: `GW/domains/chat/shared.rs:630-692` has no browser header; `GW/audience_tokens.rs:27,42,247` only declares the audience.
3. Capability gate: `browser.observe`/`browser.act`/`browser_agent` all map to `cap.browser.open` (`EC/capability_policy.rs:793`), seeded `high` (`MP/go/services/capability-core/migrations/0008_execution_dispatch_capabilities.up.sql:12`, floor `internal/models/capability.go:85-94`). So even a working `browser.observe` asks for approval on every call under `ask`. No reporter attests it (`agent.rs:3954`, `UNATTESTED_BASELINE`; `capability-core/internal/api/availability.go:78-90` says it "must be attested by its own owner"). `browser.act` is also in the risky-name list (`EC/permission/mod.rs:266-271`) and therefore never retried (`runtime_loop/retry.rs:149-151`); a new `browser.open` would NOT be (not in RISKY).
4. Browser workspace "AI run" is dead in prod: `GW/domains/browser.rs:1235` sends `grant_id: "session:{id}"`, the call at 1349-1362 forwards no browser bearer, while `MG/browser_run.rs:304` requires `VerifiedBrowserBearer` and `resolve_browser_grant` (138-202) validates with the broker. Exact status code not run.
5. Broker: in-memory store (`BB/internal/grant/grant.go:62-70`), TTL 15 min (`BB/internal/server/server.go:22`), no renewal, owner = verified actor (`server.go:78-79`). `AcquireGrant` takes domains from the caller (`server.go:61`); there is no policy source behind it, so "the broker owns the domain fence" is true only in the sense that Quarry takes the broker's list verbatim (`IQ/crates/quarry-edge/src/agent_routes.rs:1397-1412`, with `require_browser_grants`). **Top risks**
