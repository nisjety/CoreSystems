## 2. Verified current state

**Run state is a free string and the persisted truth is thinner than the audit assumes.**
- `runs.status` is `TEXT DEFAULT 'queued'` (SC/migrations/0001_init.sql:33). The only writers are terminalization.rs:999 (`completed|failed|cancelled|...` outcome), grpc.rs:12360 and run_service_grpc.rs:814 (`cancelled`). No `UPDATE runs` anywhere sets `awaiting_approval`; a paused run stays `running` in Postgres. The audit's seed `execution-core::RunStatus` (execution-core/src/state.rs:15-40, Running/Paused/AwaitingApproval/...) is an in-memory per-replica enum, not the persisted state. Derivation must therefore read `approvals` (status `requested`, SC/migrations/0003_orchestration_tables.sql:135-161) and `plans` (status `proposed`, :29-44), not `runs.status`.
- `ThreadSummary.latest_run_status` is the raw string (sessions.proto:995, [L] 1006); ThreadSummary ends at `persona_enabled = 14` (sessions.proto ~1017), so the next free field is 15 in both trees. The list SQL joins the latest run per thread (grpc.rs:5405-5411, [L] ~5576). model-gateway relays it in `ThreadSummaryResponse` (MG/src/http_routes.rs:7680, mapper 7907, route `/v1/threads` :144); the BFF mirrors it (GW/domains/chat/history.rs:64, 146-147, 407); the SPA normalises it (FE/src/shared/api/chat-client.ts:733 [L 750], normalizer 2295-2315 [L 2348]; chat-thread-history.ts:53, 81).
- The FE vocabulary is duplicated: `chatRunStatusChip` (FE/src/features/core/components/CoreSidebar.tsx:867-897, [L] +2 for `ChatWorkLinks`) and `activeStatuses/attentionStatuses` (FE/src/features/chat/lib/chat-organization.ts:47-48, filter 55). The only rail sections are the organizer's project/date groups; "Waiting for you / Unseen results / Settled" do not exist; "Needs attention" is only a chip label (CoreSidebar.tsx:891).

**Typed events: emitted in-process only; the orchestrator publisher does not exist in production.**
- session-core emits `ApprovalStateChanged` and `RunPausedForApproval` from `create_approval` (SC/src/orchestration_grpc.rs:2461, emit 2555-2585 [L 2509/2626]) via `broadcast_event` (:1726) into an in-process broadcast + per-run replay buffer. No NATS publish, no outbox row. The cross-replica NATS bridge only consumes `mp.v1.orchestration.>` into the same broadcast (orchestration_nats.rs:1-52).
- orchestrator-core's typed publisher (`orchestration.New`, `Service.Publish`, `NewRunPausedForApproval`) has no production caller: `cmd/main.go:305` discards the Service (sweep, re-confirmed in code map). So the postmortem 0002:272 / publishers_registry_test.go:70-73 "grant drop" is not the cause of an empty `MP_ORCHESTRATION_EVENTS`; fixing nats.conf alone yields no typed events. **Audit text is wrong here.** The orchestrator's real publishes go to `mp.v1.run.<id>.event` (activities.go:412) and are allowed (nats.conf:105).
- The session-core outbox is the right home and is wider than the audit implies: `session_audit_outbox` accepts `mp.v1.run.%.event` (SC/migrations/0016_...sql:26-34); `classify_outbox_subject`/`check_outbox_authority` need only `producer=session-core`, `event_id` match, `resource_ref=run:<id>`, non-empty `event_type` and `org_id` (audit_publisher.rs:69-123); session-core already holds the publish grant (nats.conf:44); capability-core already holds subscribe + the durable deliver subject (nats.conf:88-96); stream `MODEL_PLANE_RUN_EVENTS` captures it (nats-provisioner/main.go:44-50). The only enqueuer today is `RUN_COMPLETED` for skill learning (learning_events.rs:185-293), inside a SAVEPOINT, and it is **withheld for ZDR runs** (learning_events.rs:263). Consequence: a ZDR run produces no run-watch notification at all today; "content-free on all threads" is currently "silent on ZDR threads".
- Unknown `event_type`s are ignored by every consumer I opened: Convex mirror (AP/convex-core/convex/nats.ts:1007-1010), insight-core allow-list (AP/insight-core/internal/consumers/agent_subscriber.go:126), taskexec (CC/internal/taskexec/completion_consumer.go:95), sessionreview (CC/internal/sessionreview/trigger.go:56), runwatch (consumer.go:202-205). Consumers not enumerated: generated TS under FE/../verevon (no runtime consumer seen).

**Notification path (run-watch) and its gaps.**
- Consumer binds the JetStream durable `capability-core-run-watch-notify` on `mp.v1.run.*.event` (consumer.go:64-76, 163-174), maps only `RUN_COMPLETED/RUN_FAILED` (:80-97), looks up pending watcher rows, posts to notification-core (:194-247). Idempotency key = `run-watch:{org}:{run}:{user}:{event_type}` (:253): independent of the publisher, so the two RUN_COMPLETED publishers (session-core outbox, orchestrator-core) dedupe at notification-core and via `MarkNotified` (resolves sweep NOT DETERMINED #2). It sets no `retention_mode` and never reads the envelope `zdr` (the Go envelope has `Zdr *bool`, `IsZDR()`, `DeclaredZDR()` at go/pkg/envelope/envelope.go:66-96; the comment in learning_events.rs:29-30 that Go lacks the field is stale).
- Allowlist: `isNotificationTypeAuthorized` (NC/internal/http/handlers.go:199-218; capability-core = `modelplane.run_completed|run_failed` :211-214). Channel rows: NC/migrations/013_register_run_watch_notifications.up.sql:1-16 (latest migration is 014).
- **Per-channel matrix is not per-channel.** `Service.IsNotificationEnabled` returns false if ANY preference row for the event type is disabled, regardless of channel (NC/internal/preferences/preferences.go:144-155), and `Accept` gates the whole request on it (NC/internal/notification/service.go:324-335, 446-460). Turning email off suppresses in-app. The channel-aware `IsEnabled(org,user,type,channel,fallback)` exists (:127) but is unused by Accept.
- **Default stack cannot deliver.** `NOTIFICATION_DELIVERY_MODE` is `novu|disabled`, default `disabled` (NC/internal/config/config.go:62, 84-105; AP/docker-compose.yml:914). In disabled mode `dispatchAndFinalize` marks the request failed (service.go:469-477) and the in-app feed mirror runs only after a successful dispatch (:522). Whether the running stack uses Novu is not determined; the audit's "the watcher runs end to end" needs that fact recorded.
- ZDR: async ZDR refused (service.go:296-301), ZDR persists no payload (:337-339), feed skips ZDR (:522), delivery worker marks ZDR failed (delivery_worker.go:91-94). README:62-67 says the full payload still reaches Novu. Web Push: Novu channel vocabulary only (NC/internal/runtime/client.go:201-219); no native sender, no subscription table.
- `AccountSettingsPage.tsx:102` already stores a coarse `pushNotifications` preference with no sender behind it.

**Shell polling.** The "REST refetch" is the navbar resource (FE/src/features/core/components/CoreShell.tsx:35) with a 60 s/180 s timer plus visibilitychange refetch (:59-84); it carries notification unread counts (GW/domains/navbar.rs:150-195). The rail's thread list is refreshed by the chat controller, not this timer. No per-user stream exists.

**PWA.** index.html has only favicon + fonts (:3-9); public/ has no manifest or service worker. nginx gives every `*.js` a one-year immutable header (FE/nginx.conf:103-115), so `sw.js` would be cached for a year unless an exact-match location is added; CSP (:70) has no `worker-src`/`manifest-src` (both fall back to `default-src 'self'`, workable but should be explicit).

**Live-only items touching this stream (land first, WS01 S0):** SC grpc.rs (+861), terminalization.rs (+123), orchestration_grpc.rs (+249), learning_events.rs (+77), sessions.proto (+42, `SessionRetentionService`), migrations 0044/0045 + `migrations/revert/`, `retention_receipt.rs`; MG sse.rs (+883), http_routes.rs (+237); FE CoreSidebar.tsx (+2), ChatSidebarOrganizer.tsx (+2), use-chat-controller.ts (+4), chat-client.ts (+53), notifications-client.ts (snake_case drift: `cta_href`, `event_type`), untracked `ChatWorkLinks.tsx`. **Corrections to the audit (code wins).** (a) orchestrator publishers are unwired, not "dropped". (b) approval/pause events are emitted, in-process. (c) `runs.status` never holds the pause.
