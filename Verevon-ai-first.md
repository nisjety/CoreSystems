## 0. TL;DR — Start Here

**Verevon is a broad platform, not only a support assistant.** The SolidJS SPA reaches every backend plane _only_ through the Rust BFF (`verevon-gateway-rs`); there are **zero mock modules** under `src`; ~40 typed gateway clients back the feature slices. The engine includes durable knowledge, Norwegian contextual lookups, search, agent runs, tools, inbox/tickets, social, monitoring, and governance surfaces. **Reality score: ~72% production-real (backend planes ~85%)** is a dated audit estimate, not a release certificate. The remaining high-leverage work is mostly **wiring, deployment proof, security, and scope discipline**, not inventing the product category.

**But the differentiator is also the attack surface.** A trust/residency-positioned product currently ships with (a) a **critical cross-tenant data-leak (IDOR)** and (b) **fabricated "Configured/Verified" trust UI**. Both must be fixed _before_ any second tenant or pilot.

### Product capability loop

The platform should be evaluated as a loop rather than as a list of vertical products:

1. **Connect and capture** — ingest company systems, files, websites, web evidence, and bounded Norwegian public sources.
2. **Build context** — store durable knowledge in Data Plane, retrieve with source traces and GraphRAG, and enrich with live contextual lookups.
3. **Reason and plan** — use chat, search, research, agents, model selection, and policy-aware tool catalogs.
4. **Act under control** — call approved integrations, browsers, MCP tools, plugins, inbox/ticket/social actions, or future external channels.
5. **Review and learn** — require approval where appropriate, retain audit/cost/evidence trails, monitor changes, and feed accepted outcomes back into the workspace.

The support inbox is one complete vertical slice through this loop. Other slices include Norwegian market and regulatory research, knowledge maintenance, logistics/property context, social operations, and future meeting intelligence.

### 1.1 Cross-plane architecture synthesis — what the new improvement work changes

The new Model Plane and Quarry reviews do **not** justify replacing Verevon's planes or importing another framework as an authority. They sharpen the platform around five first-party systems:

1. **Verified Outcome Foundation** — shared proof-bundle, runtime-evidence, typed receipt, postcondition, and false-success contracts across tools, browser actions, provider effects, memory promotion, and human approval.
2. **Agent Quality OS** — production traces, corrections, incidents, procedures, simulations, shadow replay, canaries, promotion, and rollback become one measurable loop. The key metrics are verified completion rate, false-success rate, cost and time per verified outcome, evidence support, intervention, and unnecessary approvals.
3. **Procedure/Skill layer instead of a speculative canvas** — human-readable SOPs compile to capabilities, retrieval requirements, approval boundaries, verification, and simulations. Existing linear execution should be hardened before the greenfield GraphPlan/DAG bet.
4. **Adaptive web execution in Quarry** — wire the already-written durable frontier, close the confirmed headless SSRF/DNS gap, then add adaptive target fingerprints, challenge intelligence, compiled browser procedures, change impact analysis, and Quarry Quality/Proof systems.
5. **Data Plane Memory Intelligence** — async typed memory candidates, multi-signal retrieval, entity/temporal indexing, provenance, validity, contradiction and supersession. Mem0 is useful for algorithms and benchmarks; Verevon must exceed its ADD-only and caller-scoped limitations.

These are platform-enabling systems, not five new products or microservices. Start as contracts, libraries, Temporal workflows, eval datasets, and projections inside the existing owners.

## 8. Top Risks

1. **Security/sales blocker:** the IDOR fails any enterprise security review — fix before selling multi-tenant. The safe pattern already exists in-repo (contained fix).
2. **Tenancy depth:** data-layer isolation is a single gateway perimeter (RLS inert, dead code; shared internal key; documents-api auth unimplemented). No defense-in-depth for the multi-tenant claim.
3. **Trust misrepresentation:** fabricated "live" SSO/SCIM/social/run-id state on a product whose entire differentiation is observability/trust — existential with EU buyers.
4. **Compliance procurement gap:** GDPR/DSAR unreachable + SSO is a mockup — table-stakes for Norwegian/EU deals (the transparency story behind it is genuinely strong).
5. **Strategic focus:** leverage is in _wiring + hardening_, not chasing greenfield media/builder categories. Lead GTM with the real wedge.
6. **Operational fragility:** no root build/test orchestration; partial CI (most planes ungated); Quarry coverage CI calls non-existent Make targets; DB_PASSWORD drift breaks clean recreate.
7. **False-success risk:** plans, browser actions, mutations, memory extraction, and provider effects still need one shared distinction between verified success, verified failure, partial/unknown, and extraction/verification failure.
8. **Memory-truth risk:** append-only observations are valuable, but stale or contradictory claims must not remain equally active and rely on vector ranking to guess the current truth.
9. **Browser-maintenance risk:** selector repair and page adaptation must be semantic, risk-aware, tested against dangerous near matches, and prohibited from auto-repairing consequential actions from similarity alone.
