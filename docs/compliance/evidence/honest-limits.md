# Honest limits: what Verevon enforces, what it only declares, and what it does not offer

> **Draft for counsel. Engineering evidence, not legal advice.** The text in sections 2 to 9 is written in the tone a customer would read, so that counsel can edit it into the form counsel wants. It is based on reading the code and the developer stack on 2026-10-01 (task J13 of the chat gap-closure plan) and refreshed where it matters on 2026-10-03 (L13, L32 and the open items) and on 2026-10-06 (L12, L33, L34 and L35, and L17 to L19, L36 and the open items on the ChatGPT-account route), not production, and it has not been reviewed by counsel or approved by the owner. Do not publish it, send it to a customer or quote it as a compliance statement until both have happened. Public content is changed by the owner only; this draft changes nothing. Each statement carries an id (L1, L2, and so on) that section 10 ties to a row of `claims-vs-code.md` and to the code lines behind it.

## 1. For counsel: how to use this draft

- **What it is for.** It replaces broad claims (EU by default, zero retention, zero external traffic, a human says yes before anything happens) with statements that the code supports, and it states plainly what is missing. It follows the pack's own honesty rule: nothing is described as in place unless engineering can confirm it.
- **What it does not do.** It does not say where production runs, which vendors have signed what, or that any region or retention promise holds at a vendor. The repository holds no deployment record and no vendor contract. Those sentences are marked `[owner to confirm]` and left out.
- **Wording that needs a legal view** is marked `[counsel]`. The most important ones: whether the label list the code treats as "EU" (it includes Switzerland North) may be called EU/EEA; whether "zero data retention" may be used for a provider whose attestation is a record we wrote ourselves; and whether the draft transfer assessment needs to name OpenAI as well as Microsoft.
- **The Norwegian public copy** was proposed in `trust-page-edits.diff` and applied, hunk by hunk and with adaptations, to the website sources on 2026-10-03 (`claims-vs-code.md` section 7.1). It still needs the owner's and counsel's review. The sentences that depend on unbuilt work are listed in `trust-claims-pending-reverification.md`.
- **Open items for the owner** (not for customers) are in section 11.

## 2. What the platform enforces on every request

These statements describe checks that run before any content leaves, and that refuse the request instead of weakening it.

- **L1. A requested privacy floor is honoured, or the request fails.** When a request names a minimum privacy tier, a model provider below that tier is skipped before any data is sent. If no provider is left, the request ends with an error that names the tier. It is never answered by a weaker provider.
- **L2. A zero-retention request is sent only to a provider that has an attestation, or it is refused.** When zero data retention applies (the organisation's signed settings say so, or the request does), a provider without a valid attestation is skipped. If none is left the request is refused.
- **L3. A zero-retention request leaves no conversation content behind in the platform's own response cache, and a zero-retention agent run stores no conversation content.** The response cache neither reads nor writes for such a request. The run is recorded with a redacted agent name and an empty goal on a metadata-only thread; a metadata row still exists.
- **L4. Paid web search is never used for a zero-retention request, and never by an agent run.** Paid providers need a per-request permission that is off unless the plan grants it, and agent runs never ask for it.
- **L5. The Azure OpenAI text-to-speech override is ignored unless an operator explicitly allows a non-EU resource.** A non-EU endpoint set for that override is not used, and speech falls back to the EU endpoint. This is the only speech check: the Azure Speech endpoint and region and the speech-to-text endpoint are plain configuration with no such check, so the speech region is a label like the others (L7).
- **L6. A deployed agent stops for human approval before a risky action.** Deployed agents run under the stricter approval posture: sending, publishing, paying, deleting, shell and external tool calls pause for Approve or Reject, and reads do not. Two tools always pause, whatever the posture.

## 3. What is declared but not independently verified

- **L7. Every region in the platform is a label we set.** Azure OpenAI is labelled Sweden Central. Our own start-up check warns that it cannot prove the EU boundary because the deployment type (regional, data-zone or global) is not set. We have not independently measured where any request is processed, and a run record stores the configured region, not the region that served the call. `[counsel]` The code's list of regions it treats as EU includes Switzerland North.
- **L8. The zero-retention attestation is a record we write.** A provider counts as zero-retention only when we have recorded the resource, the approval reference, the effective and review-by dates and a reviewer, with a digest that ties those fields together. The digest does not tie them to the endpoint that receives traffic, and whether the vendor honours the arrangement is a contract matter that the code cannot show. On the environment we read, no provider has an attestation, so every zero-retention request is refused rather than served. `[owner to confirm]` the production state.
- **L9. The tier shown in the model picker follows from those declarations.** The labels "EU" and "ZDR" in the model picker are derived from a declared region and an attestation. They are not a measurement and they are not a legal opinion about jurisdiction. Their hover text says so since 2026-10-03.
- **L32. The "Used by AI?" trail is built but was not verified end to end.** The model plane queues an event for each tool action, and the Trust Center in the product reads them from the audit service. On the developer stack on 2026-10-03 none of the 4,992 queued events had reached the audit service: each ran out of attempts with the error "no stream found for given subject", and the audit service held events from the control and ingestion planes only. The cause was read on 2026-10-06 (the receiving stream was never created on the model-plane broker) and the broker side is fixed, but the stuck events are not replayed and delivery is not yet proven on the stack. Until it is, the "Used by AI?" column can show nothing from the model plane, and the page says the trail is not verified end to end. `[owner to confirm]` whether production delivers them.

## 4. Where the platform applies no floor today

- **L10. The default modes carry no minimum tier.** Budget, Balance and Genius choose the model for you and send no minimum. Some of those turns (complex Balance turns, moderate and complex Genius turns, and tool-heavy turns) are served by Claude models through Azure AI Foundry, a resource that declares no region. If you need an EU floor, choose a model that carries an EU tier explicitly.
- **L11. Helper calls do not carry the floor of the model you picked.** Conversation titles, follow-up suggestions and summaries are separate calls with their own settings. On a turn that uses a ChatGPT account they inherit that route.
- **L12. Document and query embeddings go to a different Azure resource than chat.** The knowledge base embeds documents, page images and queries with a Cohere model hosted on Azure AI Foundry, called directly and not through the gates above. Zero-retention content is refused there when the document is classified restricted or the request itself says zero retention; the organisation's own zero-retention setting is not read on this path (L33). A query that must stay within a sovereign boundary is kept off it; indexing has no region check, and the region of that resource is not declared in our configuration.
- **L13. Web search sends the query to external search engines.** The free search chain goes through our own metasearch service, which forwards the query to external engines (Google, Bing and others). This applies to zero-retention requests too. Only the paid providers are switched off for them. An operator switch exists that turns off the paid providers; a switch that stops all external search traffic does not. Agent runs have used the same chain since the owner's Quarry grant of 2026-10-02.
- **L14. A Space's privacy settings are checked for completeness but do not yet choose the model provider in chat.** The signed settings must carry purpose, lawful basis, privacy class, retention class, residency and deletion scope, and the third-party-processing and zero-retention flags are read; in the chat path they are not applied to the choice of provider. Zero retention is applied elsewhere (scheduled runs refuse it; the Data Plane refuses to embed marked content off-host).
- **L15. In interactive chat a risky action does not stop for approval.** The chat profile runs under an automatic posture. Approval gates apply to deployed agents (L6). `[owner to confirm]` how Do runs on a non-subscription route are meant to behave; Do runs on the ChatGPT route had effects switched off in the test.
- **L33. Background AI work on your documents does not follow your organisation's zero-retention setting.** When a document is indexed, one background job asks a model to write a short summary that places each chunk in its document (contextual retrieval: gpt-4o-mini on Azure OpenAI, called through the same model router as chat, but not through the chat gateway), and another extracts entities from organisation-visible chunks. Both skip a document that is classified restricted, and the entity job honours the zero-retention flag of the signed event that announced the document. Neither reads the organisation's own zero-retention setting: their service tokens carry a fixed "persistent" posture, and the summary job sends "not zero retention" on every call. No provider on the stack read has a zero-retention attestation, so an organisation that turned the setting on would still have document text sent by these jobs. The same holds for the Cohere models that embed documents and page images at indexing time and that embed and rerank queries: they are guarded per document and per request, not per organisation. On the stack read none of the three organisations has the setting on, so nothing has been sent on that basis. A change that makes these jobs follow the setting is designed and not built (the decision ledger of the Model Plane, entries of 2026-10-03); whether the same must apply to embedding and rerank in the same release is an open decision for the owner. `[owner to confirm]` whether to build the embedding and rerank part first or to state the gap on the trust page.
- **L34. The platform's own background AI calls are not in the cost ledger the product reads.** The summaries and entity extraction of L33, and the summaries of groups of related entities, are paid model calls whose usage is recorded nowhere: the cost ledger holds rows from the chat gateway only, and the Data Plane's own table holds rerank and embedding events (embedding token counts are an estimate) and nothing for these jobs. This is not the usage of the ChatGPT-account route (L19), which is a separate gap. A change that records them under the organisation, with exact usage, is designed and not built.

## 5. The ChatGPT-account route

- **L16. A user can connect their own ChatGPT account and choose a ChatGPT model.** The route is off for a user until they connect an account and pick such a model. It is chosen by the user, not by the platform, and it serves only its own models.
- **L17. That route is global and non-ZDR.** It declares no residency commitment and no zero-retention commitment, and it refuses a zero-retention request. The model picker shows the tier "Global" for these models. If your organisation has zero retention on, a person who chooses a ChatGPT model in chat is refused today by the server (its error text says the route supports non-ZDR chat only). The chat composer does not read the organisation's setting, there is no prompt, and there is no way to continue. A way to continue is designed and not built (L36).
- **L18. It runs under the user's own OpenAI account and terms.** The whole prompt is sent to OpenAI on each round: the system and persona text, the conversation history, the memory block, any retrieved knowledge snippets and tool results, and the tools list (about 10,200 input tokens per round in the 2026-10-01 test). The platform keeps the connection's sign-in in a file on its own server volume, not in a database, and its start-up code configures the local Codex process to keep no history and no analytics. What OpenAI keeps is under OpenAI's terms for that account. Disconnecting removes the login; the connection's local state directory is deliberately kept. This is also what a chat run under the designed waiver (L36) would hand to OpenAI.
- **L19. Usage on that route is not in the platform's cost ledger.** In the 2026-10-01 test the cost ledger had no rows for these runs. A chat run under the designed waiver (L36) would be an ordinary saved chat on this same route, so it would start in the same state.
- **L36. If your organisation has zero retention on, a person who uses their own ChatGPT account will be able to continue, and their chats on it will not be zero-retention. This is designed and not built.** Nothing of it exists: today such a chat is refused (L17). The design: the person is told when they add the connection and at first use whether it can provide zero retention, with a stronger warning when their organisation has it on, and may continue. Zero retention is then off only for the chats they run on that connection, never for the organisation, other people, other connections or other models, and the organisation's setting is never changed. Those chats go to OpenAI under the person's own account and terms (L18), and OpenAI may keep them. The platform saves them like ordinary chats. Organisation knowledge retrieved for them goes to OpenAI too (documents classified restricted are left out). Memory indexing, dreaming extraction and learning review do not run on them. The person's confirmation is recorded with the wording shown and the time, can be withdrawn (chats already saved stay saved), and does not cover explicit Temporary chat, scheduled or unattended runs, background jobs or any other provider. An administrator can see the record and cannot prevent the choice, because the owner decided on 2026-10-03 that people are not stopped. `[counsel]` whether a person may override the organisation's instruction to its processor in this way, and the wording of the confirmation, which must be checked against the providers' current terms. Do not describe this as available.
- An organisation administrator cannot switch the ChatGPT-account route off for the people in the organisation. No such control exists: none was found in the gateway's subscription routes or its organisation settings routes. The owner decided on 2026-10-03 that a person who connects their own account is not stopped, so none is built. An organisation setting "members may use own connections without zero retention" (default on) is proposed in the design for before the first regulated customer organisation; the owner has not ruled on it.

## 6. Forwarded email, if mail-to-task is switched on

- **L20. If mail-to-task is enabled, forwarded email passes through Postmark.** The sender, subject, text and HTML body, attachments and authentication headers reach our webhook through Postmark as the inbound processor. Postmark's region, data-processing agreement and transfer basis are not confirmed. The receiver is off on the environment we read. It must not be enabled for customer organisations before Postmark is on the sub-processor list, the transfer assessment covers it and the public trust page names it.

## 7. Deletion and retention

- **L21. Erasing a user's account does not delete that user's conversations.** It removes identity, membership and account records in the Control Plane. A per-user erasure does not reach a person's threads, messages, runs, events, plans or memory in the Model Plane, nor retrieval traces, cost rows or feedback. A person can delete a conversation, clear their history or delete a memory while signed in, and an organisation erasure removes the organisation's copies. The in-product confirmation text used to say model- and data-plane data is removed through a separate process, which for a single user is not what happens; on 2026-10-03 it was changed to say that conversations, memory and documents are not deleted and to tell the person to delete what they want removed before erasing the account. The user-core export notice was narrowed to match, and takes effect when user-core is rebuilt.
- **L22. Organisation erasure is wider but not complete or guaranteed.** It reaches most databases and vector stores. It is published without an acknowledgement, a failure on one table can stop the Model Plane purge, and keyword search indexes and the graph read model are not purged by the path we found.
- **L23. Conversations and run history are kept until someone deletes them.** Nothing deletes them by age. The only age-based deletion we found is audit events (365 days), soft-deleted organisations (30 days), a seven-day clean-up of published audit outbox rows, and some caches.
- **L24. Zero retention does not mean the platform stores nothing.** It limits what the model vendor may keep. The platform keeps run metadata, audit events and, for non-ZDR work, conversations and run history under its own schedule.
- **L25. Disconnecting a Microsoft connector stops our use of it but does not revoke the grant at Microsoft.** We delete our stored tokens and mark the connection deleted. To remove the grant itself, remove the app in the Microsoft account or the Entra admin centre. Whether synced content is purged on disconnect is not established here.
- **L26. A data-access export covers Control Plane data only.** Profile, memberships and API-key metadata. Conversations, memory and documents in other planes are not assembled into it yet.
- **L35. A situating summary is derived personal data, and it is copied into three places.** The summary of L33 is stored in the chunk's database row, in the keyword index as a separate field, and it shapes the chunk's stored vector (the vector is computed from the summary and the chunk together). It is deleted with its chunk when the document or the organisation is erased, and the keyword indexes are not purged by that path (L22). There is no way today to remove summaries without removing documents: switching the feature off for an organisation or for the platform stops new summaries and leaves the existing ones where they are.

## 8. What Verevon does not have

- **L27. No third-party certification.** There is no SOC 2 Type II report, ISO/IEC 27001 certificate, ISO/IEC 42001 certificate or EU AI Act conformity assessment. They are planned.
- **L28. No published independent penetration test.**
- **L29. No customer-managed keys and no self-hosted offer.** Both are roadmap items in the plane roadmaps.
- **L30. No audited sovereignty claim.** No provider is classed as Norwegian-sovereign today; a Norwegian Azure region is classed as EU, not as Norway.

## 9. EU residency is not sovereignty

- **L31. A provider headquartered in the US can be compelled to produce data wherever it is stored.** This applies to Microsoft, which hosts our Azure services, and to OpenAI on the ChatGPT-account route. We record the US CLOUD Act exposure as a residual risk in the draft transfer assessment and do not claim immunity. `[counsel]` the draft transfer assessment names Microsoft only.

**Rule for anyone who describes Verevon (sales, partners, the website):**

- Do not claim parity with Microsoft Enterprise Data Protection or with the EU Data Boundary. Those are Microsoft's own programmes with Microsoft's own commitments. Verevon's controls are request-level routing checks over labels that Verevon sets; they are not that programme and are not independently audited.
- Do not claim that data stays in the EU, that prompts are never stored, that search has zero external traffic or that a human approves everything, without the qualification in this document.

3. **Production text-to-speech region.** The pack says East US 2; the developer stack says Sweden Central.

Their contents were not read. Deleting them is permanent and is the owner's decision; an agent never does it.
5. **Answered on 2026-10-03: no admin lock.** An organisation cannot switch the ChatGPT-account route off for its people, and none is built: the owner ruled that a person who connects their own account is not stopped. Proposed in the design, not decided by the owner, and for counsel (item 11): an optional organisation setting "members may use own connections without zero retention", default on, before the first regulated customer organisation.
6. **The Quarry grant** that lets agents use web search (A6 note) was deployed on 2026-10-02, so L13 applies to agent search today. Quarry's own retrieval and rerank calls are refused (403) on the stack, which leaves agent and chat web search lexical-only and in search-engine order until the rerank path (build item b) works.
7. **The Norwegian wording** of the proposed edits.
8. **Counsel's review** of every `[counsel]` point above, and whether this page is published at all.
9. **Scope of the organisation's zero-retention setting over indexing** (L33). Whether embedding documents, embedding page images and reranking must follow the setting in the same release as the summaries and entity extraction, or whether the setting covers interactive content only and the trust page says so. 10. **Whether an organisation can be switched off from contextual summaries, or held to a spending stop, on customer organisations.** The control exists for evaluation organisations and incidents only until the owner rules (L35 is affected: existing summaries stay when it is used).
11. **Counsel's review of the designed per-connection waiver (L36) before it is built or described.** Whether a person may override their organisation's zero-retention instruction to its processor for their own chats; the wording of the confirmation (the drafts in the design are placeholders), which must be checked against the providers' current terms and must say that retrieved organisation knowledge and tool results go to the provider; and whether the optional organisation setting of item 5 is needed before the first regulated customer organisation.
