# Retention and erasure from code: what is deleted, by whom, per thread, per user or per organisation

> **Engineering evidence, not legal advice.** Compiled by reading code on 2026-10-01 (task J12 of the chat gap-closure plan), plus read-only reads of the developer stack that are kept in `live-reads-retention-2026-10-01.txt` (cited as BLOCK n). It is not reviewed by counsel and must not be quoted to a customer, a regulator or on the public trust page as a compliance claim. No service code was changed, no erasure was fired, nothing was deleted or restarted and no model was called. A row says a path deletes something only when it carries a basis (section 0); a row that cannot says UNVERIFIED. LIVE means the developer stack on this machine, never production.

## 0. How to read this

**Basis** (every status below ends with at least one):

- `read`: the cited lines were opened and the claim is what they do. Nothing was executed.
- `test: <name>`: an existing test covers the behaviour. The test is named and so is the variable that gates it. **None of these tests was run for this document.** A test that returns early when its variable is unset reports success without running anything, so a green run of the default suite proves nothing about these paths.
- `run 2026-10-01`: a read-only live read of the developer stack, cited as BLOCK n in `live-reads-retention-2026-10-01.txt`. These reads count rows, read schema and read logs. No erasure was fired.
- `search Nn`: a `git grep` from the repository root, listed in section 2 as written. A search that finds nothing proves only that this search found nothing, so an absence rests on the search and is marked as such.

**Status words:** `deletes` (the path removes the rows named), `partial`, `blocks` (the path exists but a foreign key it does not clear makes it fail), `not reached` (no path from that trigger reaches the store), `hides only` (archive), `retained` (kept; the code or the pack states no period), `retained by design` (a documented keep), `expiry` (a time limit removes it), `none exists` (the store is not there) and `UNVERIFIED`.

**Triggers:** *Thread* is one conversation deleted by its owner. *User* is a per-user erasure: the user-core saga, which publishes `subject_type` `user` or `user_anonymize`. *Org* is an organisation erasure: org-core's explicit hard delete or its 30-day cron, which publishes `subject_type` `organization`.

Four limits apply to every row:

1. The local stack is not production. Production hosting, backups and production compose overrides were not read.
2. A vendor's own retention is a contract fact, not a code fact. Rows that depend on one say UNVERIFIED.
3. Line numbers are as of 2026-10-01 and several cited files are being edited by other work. The checker's anchors catch a line that moved; run it before relying on any row.
4. Several comments in the code base are stale. Section 6 lists the ones found. Do not quote a comment as evidence.

## 1. The answer, in short

1. **A per-user erasure does not remove that user's session-core threads, messages, events, runs, plans or memory.** The user-core saga publishes one `user` (or `user_anonymize`) event per active organisation. Session Core receives it, decides it is not an organisation event and acknowledges it without deleting anything. No other session-core code reacts to that subject. Section 2 shows the chain and the searches that found no other path. This is by reading and was not run; section 9 is the probe that would run it.
2. **The cross-plane erasure is organisation-scoped.** Fifteen consumers exist on the erasure subject and fourteen have a client attached (BLOCK 4). Thirteen act only on `organization` events and acknowledge `user` events as a no-op. One (documents-api) acts only on `user` events and only re-owns documents to a system account, without deleting their content. One (the gateway) acts on both and only drops cached keys. No consumer deletes a person's chat content, retrieval traces, cost rows or feedback on a person's erasure.
3. **What a person can do themselves** is delete a thread, delete all their threads, or delete one memory, while signed in. Those paths are owner-bound and real (section 3, M1, M4). The account-erasure flow neither calls them nor asks the person to, and its confirmation text says model- and data-plane data is removed by a separate fan-out (finding F2).
4. **The session-core organisation purge cannot complete for an organisation that has ever claimed a scheduled step.** `scheduled_step_receipts` has NO ACTION foreign keys to `runs` and `threads` and the purge never deletes it. The same table also blocks deleting a thread that carries a receipt (M2, F1). The table is empty on the developer stack, so nothing has hit this yet.
5. **The organisation fan-out from org-core is a plain publish with no acknowledgement and no retry**, unlike user-core's, which is outboxed and acknowledged (F3). The stream keeps messages for 7 days (F4). On the developer stack no erasure consumer has ever been delivered an event, and the cost-core consumer is not bound at all (F5).
6. **Archive is not erasure.** Archiving hides a thread and keeps everything (M6). Deleting a thread removes its rows and the semantic twins of its memories, after the commit and without retry (M1, M4, M5).
7. **Time-based retention that the code enforces** is narrow: audit events at 365 days, soft-deleted organisations at 30 days, published audit-outbox rows at 7 days, a few caches and drafts (section 4). **Nothing deletes conversations, messages, runs, events or memory by age.** The pack's proposed 365 days for conversations and run history has no sweep behind it.
8. **What the code does well**, so the findings are read fairly: the organisation purge is one transaction with parameterised statements and a redelivery is a no-op; the semantic-twin step is counted and logged instead of silently dropped; a zero-retention run persists no content; the user-core saga is resumable and its ledger is durable; the auth GDPR routines are real-Postgres tested (gated).
