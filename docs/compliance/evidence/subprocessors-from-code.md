# Sub-processors and recipients derived from code

> **Engineering evidence, not legal advice.** Compiled on 2026-10-01 (task J11 of the chat gap-closure plan) by running `tools/scan-egress.mjs` over the working tree of this repository and then reading the code the scan points to. It is not reviewed by counsel, it is not a compliance claim, and it must not be quoted to a customer, a regulator or on the public trust page. The only things run against the developer stack were read-only: `docker ps` and one `docker inspect` per container, cut down to variable names and set-or-empty before anything was written (kept in `live-reads-subprocessors-2026-10-01.txt`; no value was read into this document, and nothing was read from production). Rows say UNVERIFIED where the code cannot answer. This document proposes changes to the compliance pack and the trust page; it edits neither.

## 0. How to read this

The scan finds every outbound host the code can address and every variable that switches a vendor on, and sorts them into a catalogue of vendors. The catalogue is the engineer's reading. Class, role and disposition are for counsel to confirm or overturn. Region and DPA status are **never** filled in by the tool or by this document: they stay TBC until a contract or a deployment record says otherwise.

**Class** says how the vendor relates to customer content:

| Class | Meaning |
|---|---|
| `subprocessor` | Verevon sends it customer content or personal data under Verevon's own account or contract. A candidate for the Art. 28 list. |
| `user-authorised` | The customer or user connects their own account (a Microsoft or Google sign-in, a Slack workspace, a ChatGPT subscription). Data moves at their instruction under their terms. |
| `infrastructure` | Fonts, scripts, security checks, object storage: no customer file by design, but a recipient of connection metadata such as an IP address. |
| `public-source` | A public data feed or API Verevon reads. The request leaves (a query term, a place name) and the platform's egress address; no customer file. This class is added to the plan's three because public data APIs are neither infrastructure nor a sub-processor. |

**Role** is the engineer's reading of the legal relationship: `processor`, `independent-recipient` (the vendor decides its own purposes, as a search engine or a carrier does), `customer-directed`, `no-content`, `unknown`.

**Disposition** is the proposal for the Art. 28 sub-processor list: `LISTED` means the vendor should be on it (the register says whether it is active or dormant here); `EXCLUDED: reason` means deliberately not proposed for that list, with the reason. An excluded vendor can still belong in a disclosure of recipient classes; that is counsel's call. The checker `scan-egress.mjs --verify-doc` fails when a vendor the scan found has no row, or an EXCLUDED row has no reason.

**Evidence status** in the scan: `code` (a host literal in non-comment source), `config-file` (a host only in a compose or env file), `env-only` (the code reads the gating variable; no literal host), `compose-only`, `sdk-only` (a declared dependency hides the host), `signal-only`, `comment-only` (a host only in comments: it documents a vendor and proves no egress).

**Wiring in this repository** says whether anything here switches the vendor on: `compose` (a plane compose file names a gating variable), `env-example-only` (only an example env file names one, and a compose `env_file:` could still pass it), `legacy-compose-only` (only the root `docker-compose.yml`, whose own header calls it the legacy stack), `none` (gated, and no compose or env file names any gating variable), `ungated` (no gating variable: reachable whenever the feature runs), `config-flag` (a flag in a service config file), `per-user-connection` (the user supplies the connection), `mixed` (some of the vendor's endpoints are gated and some are not; the register says which), `n/a`. A variable that only redirects a host (a base URL, an OAuth endpoint override) is not counted as a switch.

**Dev stack (LIVE)** is the read of the containers running on this machine on 2026-10-01. `set` means the variable has a non-empty value in the container environment; it does not say the value is valid or is not a test credential. One machine, one day, never production.

### What was scanned

The scan lists the files of the repository (git: tracked plus untracked-and-not-ignored) and keeps runtime source and configuration. This run: 7445 files listed, 2869 scanned. Excluded, by reason: doc 1164, generated 153, lockfile 63, manifest-noise 14, not-source 1031, oversize 1, skipped-directory 419, test 1439, tooling 292. A second class of exclusion is by host: first-party-domain 11, in-cluster-name 102, loopback-or-private 4, reserved-placeholder 15, schema-or-namespace 9 (loopback and private addresses, in-cluster service names, reserved placeholders, schema URLs, the operator's own domains). SQL migrations are not scanned, because their only URL literals are documentation links in the capability-core seed rows. Rust blocks under a column-0 `#[cfg(test)]` are skipped. 32 URL literals have a host built at run time and cannot be listed.

### Limits

1. A URL literal shows the code can address a host. It does not show the host is called in production, or with customer content.
2. A vendor's retention, regions and sub-processors are contract facts. Nothing here says what any vendor does.
3. The dev stack is one machine on one day. Production hosting, production compose overrides and production secrets were not read.
4. A variable that reaches a container through an `env_file:` is invisible to the wiring column; the LIVE column is what catches it (Vipps, Twilio and Stripe are set on the dev stack although no compose file here names them).
5. Several code comments are stale; section 9 lists the ones this work found. No comment is used as evidence of behaviour.
6. The scan leaves out operator scripts, CI configuration, Dockerfiles and tool directories (`tooling` in the exclusion counts): an operator runs them or the build does, the running services do not. Some fetch public data feeds, for example `apps/Control Plane/scripts/sync-nvd-feeds.py:17 @"nvd.nist.gov"`, `apps/Control Plane/scripts/sync-disposable-email-domains.py:13 @"raw.githubusercontent.com"` and `apps/Data Plane v2/scripts/write-open-data-manifest.py:23 @"dumps.wikimedia.org"`; they were read by their URL literals only. A host reached only by a script is not in the register.

## 1. What the scan found, in short

1. The scan finds **58 vendors** with evidence in the code: 23 `subprocessor`, 20 `user-authorised`, 7 `infrastructure`, 8 `public-source`. No host is left unclassified and no credential-like variable is left unmapped (115 are reviewed as the platform's own plumbing, each with its reason in the tool).
2. The proposal lists **24 vendors** for the Art. 28 list. The pack has 7 rows, two of them generic (browser, proxy and unblocker vendors; additional model vendors) and one an exception (text to speech in the US), and 16 of the 24 are named by no row (section 4).
3. The trust page names four rows. 19 of the 24 listed vendors are not on it, and two of its rows say something the code does not support: search "with zero external traffic" if keys are omitted, and Anthropic as a mere fallback (section 5).
4. Two entries in the pack have no support in the code: Azure hosting (no deployment record or hosting reference in code) and Text-to-Speech in East US 2 (on the dev stack the Speech path is wired to Sweden Central and the non-EU override cannot take effect).
5. The code switches freight carriers on: Bring, DHL, UPS and FedEx credentials are set in the dev stack's shipping container, the real adapters replace the mocks when they are present, and neither the pack nor the trust page mentions carriers. FedEx defaults to its sandbox host, the dev stack's DHL base URL is DHL's test path and Bring bookings carry a test indicator, so those three are most likely test accounts; that is UNVERIFIED. UPS is the exception: the dev stack's UPS base URL is UPS's production host, not its test host, so rate quotes and tracking calls go to UPS's production API with consignee data whenever the shipping service uses them; UPS booking is blocked on a non-test host unless live booking is set (`docs/compliance/evidence/live-reads-subprocessors-2026-10-01.txt:459 @"UPS_API_BASE_URL"`, `apps/Ingestion Plane/shipping-core/internal/carrier/ups/booking.go:101 @"wwwcie"`).
6. The self-hosted SearXNG forwards the query to external engines whatever the ZDR flags say. This is a recipient class the pack does not name and the trust page denies.
7. Postmark is in the code and wired by no compose file. Novu is in the code with delivery off. Neither may be enabled for customer organisations before the pack, the transfer assessment and the trust page include them.
8. Several recipients receive only a visitor's IP address, such as Google Fonts, which the web app's `index.html` loads, and Google's favicon service, which the app asks for the hostname of each search result. Self-hosting the font would remove the first.
9. Corrections to the plan's seed findings are in section 8: the Novu EU host is a comment and not a setting, one `api.openai.com` hit is a JWT claim name, and the Data Plane's Cohere calls are separate from `AZURE_COHERE_*`.

## 11. How this was made and how to re-check

- The register's code columns come from `tools/scan-egress.mjs`; the prose columns, the Azure services table and sections 4 to 9 were written by reading the cited lines. The vendor catalogue, with its class, role and gating variables, is the `VENDORS` array in the tool.
- Re-run the scan: `node docs/compliance/evidence/tools/scan-egress.mjs` prints the full report with file and line evidence; `--json` is the machine-readable form for a trust-page drift test; `--summary` is the form to diff.
- Detect a new vendor: `node docs/compliance/evidence/tools/scan-egress.mjs --strict` exits 1 when a host is unclassified, a catalogue vendor has no evidence, a curated variable exists nowhere, or a credential-like variable is claimed by no vendor.
- Keep the register complete: `node docs/compliance/evidence/tools/scan-egress.mjs --verify-doc docs/compliance/evidence/subprocessors-from-code.md`.
- Diff against today's baseline: `node docs/compliance/evidence/tools/scan-egress.mjs --summary | diff docs/compliance/evidence/egress-scan-summary-2026-10-01.txt -`.
- Check the citations: `node docs/compliance/evidence/tools/check-citations.mjs docs/compliance/evidence/subprocessors-from-code.md` (add `--show` for the second-reader pass).
- Refresh the live read: the command is at the top of `live-reads-subprocessors-2026-10-01.txt`.
- Tests of the tool: `node --test docs/compliance/evidence/tools/*.test.mjs`.
