## 0. How to read this

Every row is one claim that a customer, a prospect or a regulator could read, with where it is made. The verdict is about **the claim as worded**, against **the code and the developer stack as read on 2026-10-01**. It is never a statement about production.

| Verdict | Meaning |
|---|---|
| `supported` | The code shows what the claim says. The row cites the lines. A supported row can still carry a caveat in its text; it never rests on a comment. |
| `narrow it` | Part of the claim holds, or it holds only on some routes or only on the stack read, or it reads as proof where the code has a label. The diff proposes a narrower sentence. |
| `contradicted` | The code shows the opposite, or a statement that the code overrides. |
| `unverified` | The code cannot answer: it needs production, a vendor contract, a deployment record or a run that was not made. Nothing is assumed in either direction. |

A verdict cell may carry a suffix that records what happened on 2026-10-03, after the leading verdict word:

| Suffix | Meaning |
|---|---|
| `applied 2026-10-03` | The edit named in section 7.1 is in the source and the public wording now says what the code shows, no more. The leading word is the verdict of the old wording. |
| `claim removed from the page 2026-10-03` | The sentence could not be backed, so the page no longer makes it. |
| `unchanged` | The sentence stays as it was because the code supports it. |
| `narrowed 2026-10-03` | Counted with `applied`: the row was `supported`, and the page's wording was still made narrower (T7, T12). |
| `pending re-verification (a, b or c)` | The wording is true of the code and the stack as read on 2026-10-03, but unbuilt work will change it: (a) the contextual retrieval rework, (b) the Data Plane rerank capability for Quarry, (c) the per-connection zero-retention (ZDR) consent flow. Each such sentence is listed in `trust-claims-pending-reverification.md` and in the machine-readable list `trust-claims.ts`. A final pass re-checks it when the item lands. |
| `not applied` | Nothing was edited, with the reason. |

**Basis.** `read`: the cited lines were opened by the author of this document. `live`: a read-only read of the developer stack, cited as BLOCK n of a live-reads file. `A6`: the live proof of Do mode on the ChatGPT Terra route of 2026-10-01 to 2026-10-02. `live 2026-10-03`: the same kind of read, kept in `live-reads-trust-claims-2026-10-03.txt` and cited as BLOCK n there. No test was run for the 2026-10-01 rows; the tests run since are named in section 7.1. No model was called.

**How a row's evidence works.** The checker re-opens every citation and every anchor (`tools/check-citations.mjs`). A green run proves the lines exist and contain the anchor, not that they say what the row says. The second-reader pass is `--show`.

Four limits apply to every row:

1. The developer stack is not production. Production hosting, production compose overrides and production secrets were not read.
2. A vendor's retention, regions and sub-processors are contract facts. A row that depends on one is `unverified`.
3. Line numbers are as of 2026-10-01. Several cited files are being edited by other work (`chat-client.ts` moved 15 lines during this pass). The anchors catch a moved line; run the checker before relying on any row.
4. Public copy is Norwegian. The Norwegian is quoted here only as far as needed to identify the claim.

## 1. The answer, in short

1. **The page and the pack overstate three things the code contradicts.** Search is not "null ekstern trafikk": the free chain goes through our SearXNG, which forwards the query to external engines, ZDR queries included (T9a, T13f, V3). Document and query embeddings do not run on Azure OpenAI: the Data Plane default is Cohere Embed v4 on an Azure AI Foundry host, called directly, outside every residency gate (T1b, A2). The in-product erase text and the pack say model- and data-plane data is removed through the fan-out, and for a per-user erasure it is not (P5, A11).
2. **ZDR is a gate, not a guarantee the code can show.** The gate is real and fails closed. A provider supports ZDR only with an operator-written attestation, and on the stack read both attestations are empty, so every ZDR-flagged chat request is refused. The sentences "Promptene lagres ikke hos modellen", "Kun Azure OpenAI Sweden Central-stien støtter ZDR + EØS i dag" and the pack's "Not retained by the model provider" rest on a contract the repository does not hold (T2c, C7, H2, A5). `VEREVON.md` says ZDR is "enforced by default", which the trust page itself and the code contradict (V1).
3. **Residency is a per-request floor the caller chooses, and the default path carries none.** The Budget, Balance and Genius modes send no tier floor, so Balance complex turns and Genius moderate and complex turns go to Foundry Claude, which declares no region. A model picked explicitly sends its own tier. The Azure OpenAI region is a label and its deployment type is unset, with a boot warning that says the boundary cannot be proven (T1a, T13c).
4. **The ChatGPT subscription route is named on neither the page nor the pack.** It is user-selected, global, non-ZDR, runs under the user's own OpenAI account, and carries the prompt, history, memory block, retrieval snippets and tool results to OpenAI (T13e, section 3). The in-product model picker does show the tier chip "Global" (P4), so the omission is on the public page and the pack, not in the product.
5. **"Mennesket sier ja før noe utføres" is true for deployed agents, not for interactive chat.** The chat profile runs under an `auto` posture that gates nothing; only a deployed agent runs under `ask`. Two tools wait for approval whatever the posture (T3).
6. **Several statements are stale in a direction that hides a real finding.** `VEREVON.md` says there is no public Trust Center; the page exists in the code (V4, V5). The pack says TTS runs in East US 2; on the stack read the override cannot take effect (K4, A3). The Trust Center's sub-processor table has four rows, which cover 5 of the 24 vendors the code scan proposes for the list; 19 are not on it (T13g).
7. **Everything about where the stores are hosted is unverified.** The code names no hosting vendor or region for any store (T1d, C3, A4, A13).
8. **The honest-limits page** (`honest-limits.md`) is the customer-tone text that follows from these rows.
9. **Applied on 2026-10-03.** The narrowing is in the sources of the Trust Center, its metadata, the footer, the homepage band, the scroll copy, the technology statistics, the demo card, the tier tooltips, the erase and disconnect copy of the product, and `VEREVON.md` (section 7.1). The sub-processor table now covers all 24 vendors the register proposes to list, plus the ChatGPT-account route, and a drift test (`trust-data.test.ts`) keeps it so. The ChatGPT (Terra) route is disclosed where the page lists how answers are processed: global, no EU or ZDR guarantee, chosen by the user's own connection (T13e).
10. **New on 2026-10-03: the "Used by AI?" trail did not reach audit-core on the stack read.** Session Core queued 4,992 `tool_action` events for audit-core; none was published, every one ran out of attempts with the error "no stream found for given subject", and audit-core holds no `tool_action` event at all (section 3.1). T4 moves from `unverified` to `contradicted` on the stack read, and the page now says the trail is built but not verified end to end. On 2026-10-06 the cause was read (the model-plane broker had no stream for the subject) and the broker side was fixed; the stuck rows are not replayed yet, so the verdict stands (M3).
11. **Twelve rows wait for unbuilt work** and carry `pending re-verification` (section 0): the ZDR gate, its plan gate and the ChatGPT route (c), the Foundry Cohere, search and classification sentences (b), and the contextual retrieval sentence (a). They are five claims in `trust-claims.ts` and are listed, sentence by sentence, in `trust-claims-pending-reverification.md`.

Verdict counts are in section 4.
