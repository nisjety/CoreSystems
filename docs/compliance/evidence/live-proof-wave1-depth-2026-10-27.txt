WHAT WAS DEPLOYED, AND HOW
  The stack ran images from 2026-10-01 (audit-core), 2026-10-06 (org-core) and 2026-10-21/22 (Model Plane).
  A read-only research workflow (four topics, each checked by a skeptic agent) first established the coupling
  and the migration risks; the pre-checks then confirmed: all 49 applied session-core migrations' sqlx checksums
  equal the worktree files' bytes (no CRLF trap), no idle-in-transaction session on session_core (0055 is a
  CREATE INDEX CONCURRENTLY), org-core's credential registry carries org:retention:read:any and none of the
  scopes HEAD restricts.
  - session-core, model-gateway: built with compose.sh from the worktree and recreated with
    recreate-with-live-env.sh (the live env files read-only, NATS passwords carried from the running NATS server).
    Both healthy at d67c5a43f. session-core applied migrations 0049 0050 0051 0052 0055 0056 0057 0058 0064 0067 0068
    at boot ("migrations applied").
  - org-core and audit-core: built with docker build from the worktree and swapped onto their running containers
    with a replay of each container's own resolved config (read-only root, tmpfs, cap_drop ALL,
    no-new-privileges, memory/CPU limits, networks and aliases, env); the swap reported no config difference and
    no missing env name. The Control Plane runner was not used: the worktree has none of its per-service .env
    files, and running the live checkout's runner could write its secrets ledger.
  - BFF gateway (verevon-gateway-rs): built from the worktree (it carries WS09-S8) and swapped the same way.
  - capability-core: NOT replaced. capability-core HEAD mints its session-core token with the scope
    session:memory-controls:read in one request, and auth-core's live principal registry does not hold that
    scope (it occurs 0 times), so the new service could not call session-core at all (learning review, skill
    upserts, schedule-prepare for scheduled runs). Its HEAD migrations were applied instead by a one-off
    container from the HEAD image that runs only the image's own migration loop (docker-entrypoint.sh, command
    `true`) against the live database: exit 0. The running capability-core stayed healthy on its old image.
  - inference-core and execution-core stay on their running images (built, not deployed): the proofs do not
    need them, and model-gateway HEAD against the older inference-core only logs a WARN.
