### F-t2-017 · Public async job lifecycle: status, paginated results, per-URL errors, cancel/pause/resume, origin and live tail
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-edge, quarry-control, quarry-orchestrator) + Frontend gateway | W2 | High |

**What to build.** Add authenticated, org-checked routes on the Quarry edge for crawl and batch jobs: `GET /v1/crawl/:id` (status, completed/total, warnings, expiry), `GET /v1/crawl/:id/errors` (per-URL failures including robots-blocked URLs), `GET /v1/crawl/ongoing`, `DELETE /v1/crawl/:id` and `POST /v1/crawl/:id/pause|resume`, with `/v1/batch` aliases. Turn `GET /v1/jobs/:id/events` into a live tail that sends a catch-up snapshot first and honours `Last-Event-ID`. Record a run origin (user, agent, schedule, webhook, api) on the job record and surface the controls in the crawl UI and as proposable Model Plane actions. Treat cursor-paged result data as a separate sub-item.

**Why it matters.** A user or agent who starts a crawl of up to 5000 pages has no way to stop, pause or inspect it from the product. Agents need one poll call and a cancel to honour budgets, and the audit model needs to know who started a run. Status and cancel are also the dependency for webhooks, waiters and monitors.

**What the references do.** Job status and cancel exist in 2 of 4 references (Firecrawl, Apify); a live stream with catch-up exists in 1 of 4 (Firecrawl). Firecrawl's `GET /crawl/:jobId` returns status, counts, credits, `expiresAt` and a page of documents that ends at 100 documents or 10 MiB, with a `next` cursor that advances by what was actually returned; `/errors` returns `[{id, timestamp, url, code, error, requiresAction}]` plus `robotsBlocked[]`; `DELETE` marks the crawl cancelled, cancels the queue group and answers 409 when already complete; results expire by a per-team TTL (time to live), 24 h by default [SRC]. Its WebSocket sends a `catchup` status message, then each finished document, then `done`, but it has no resume cursor, polls once a second server-side and there is no SSE (server-sent events) route in the source [SRC]. Apify runs have a persisted status, a graceful abort with a 30 s grace period, resurrection of a finished run with the same storage ids and a recorded `meta.origin`, but no pause [DOC]. Pause and resume are not a reference capability: Firecrawl has them only for monitors, not crawls, so they come from Quarry's own Temporal signals [SRC]. `Last-Event-ID` resume over an event history is a Verevon recommendation, not a reference mechanism [INF]. The step timeline idea comes from Firecrawl's legacy multi-page extract, not from crawl jobs [SRC, medium confidence].

**Verevon today.** The edge exposes only `POST /v1/crawl` and `/v1/batch` (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/routes.rs:133-134), a generic jobs list and an events route that drains once and ends with a done frame (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/resource_routes.rs:1057-1127). Pause, resume, cancel and state queries exist only in `CrawlJobWF` (apps/Ingestion Plane/Quarry-v2/services/quarry-orchestrator/internal/workflows/signals.go:87-146); `BatchJobWF` has no handlers (workflows.go:359-383), and nothing sends the signals: quarry-control's Temporal client is a `NoopClient` (apps/Ingestion Plane/Quarry-v2/services/quarry-control/internal/temporal/client.go:91-130) and only the orchestrator dials Temporal (cmd/orchestrator/main.go:66), starting workflows as `quarry-job-<jobID>` (internal/jobs/dispatcher.go:246). The gateway proxies start, discover, list and events only (apps/Frontend Plane/verevonv3/apps/gateway/src/domains/knowledge.rs:179-196). Reuse the control `GET`/`PUT /v1/jobs/{id}` record (resources.go:24-31, 486-530), the `page_failed`/`page_blocked` events (workflows.go:174-202), the gateway `crawl_run_events` proxy that already forwards `Last-Event-ID` (knowledge/quarry.rs:1098-1120) and the `ingestions.*` action registry (src/shared/actions/action-registry.ts:1320, 2563-2590).

**How to build it in Verevon.** Do not wire a Temporal client into quarry-control. Follow the repo's reconciler pattern: the edge writes a desired state (cancel, pause, resume) to the control job record via the existing `PUT`, and the orchestrator `jobs.Manager`, which already holds the client and the deterministic workflow id, sends the signal. Add control-signal handlers to `BatchJobWF` or document batch as non-cancellable. Build `/errors` from existing `page_failed` and `page_blocked` events, and implement the live tail in the edge handler by polling control with `after_seq`, with a per-org cap on open streams. Every route needs an org check from verified claims; the Model may propose cancel or pause as registry actions but Quarry executes. Crawl and batch are refused under Zero-Data-Retention (ZDR) today, so no ZDR content handling is needed now; any future ZDR crawl must be status-only. Surface the fixed 30-minute `WorkflowExecutionTimeout` (dispatcher.go:254) as a typed terminal state. Result pagination needs a data-source decision first: crawl output is not stored per job today (events carry excerpts; pages go to artifacts or the Data Plane when ingest is on). Cancel must be idempotent against finished workflows and must not leave a half-written ingest. Shares the signal path with [F-t2-018](#F-t2-018).

**Why it matters.** Scheduled re-crawls keep tracked sources fresh, and the UI already lets users create such schedules. Apify schedules are timezone-aware cron with per-run input overrides, a 10 s minimum and a default email when a scheduled run fails to start through misconfiguration, not on every failure [DOC]. Timezone-aware cron exists in both references [SRC; DOC]. Firecrawl monitoring is recent and partly behind a billing rollout, and requires the DB-backed deployment [SRC].

**Verevon today.** `workflowFor` maps only `change_monitor` (apps/Ingestion Plane/Quarry-v2/services/quarry-control/internal/resources/schedule_wire.go:39-51); the orchestrator skips workflowless schedules (apps/Ingestion Plane/Quarry-v2/services/quarry-orchestrator/internal/schedules/schedules.go:158-163); `MountScheduleAliases` receives a nil Temporal client so trigger and backfill return 501 (quarry-control/cmd/control/main.go:177-192). `CrawlJobWF`, `BatchJobWF` and `ScrapeJobWF` are registered (quarry-orchestrator/cmd/orchestrator/main.go:94-116) and `Manager.Trigger`/`Backfill` exist unused (schedules.go:365-398). Reuse the `ChangeMonitorWF` replay-safe `run_id` derivation (workflows.go:296-320), the orchestrator reconcile loop as the single writer of Temporal schedules, native Temporal `ScheduleSpec` overlap, jitter and `TimeZone`, and the preset create path in schedule_routes.rs that stamps org and `created_by` from the claim.

**How to build it in Verevon.** Persistence first: extend `store.Schedule` and the control schema, map kind to `target_kind` and config to `target_ref`/args in the edge, and require the org from the signed query in the control create handler. Then extend `workflowFor` for the three workflows, derive `run_id` from the workflow execution as `ChangeMonitorWF` does, and set overlap policy and `TimeZone` in schedules.go create/update. For trigger and backfill, prefer reaching the orchestrator's existing `Manager.Trigger`/`Backfill` through a pull-model request row or an internal orchestrator endpoint over a second Temporal client in quarry-control; record the choice in an ADR (architecture decision record) because the control-side interface was designed for an SDK client. The Ingestion Plane owns schedules end to end; failure notices go through Application Plane notification-core by API, and entitlement is re-checked at fire time against the Control Plane with no cross-plane DB reads ([F-t2-008](#F-t2-008)). Durable jobs are refused under ZDR (quarry-edge/src/routes.rs:563-588), so refuse schedule creation for ZDR orgs and re-check posture at fire time. Existing rows must not all start firing after the fix: require an explicit enable step. Sequence after crawl scoping so recurring crawls do not repeat off-site walks.

### F-t2-020 · Harden persistent browser profiles: complete snapshots, per-org envelope encryption at rest, ordered saves, ZDR enforced inside Quarry
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-browser, quarry-runtime, quarry-edge) + Control Plane (key API) | W2 | High |

**What to build.** Two independent slices. Snapshot completeness: capture all cookies of the browser context with expiry and SameSite, local and session storage for every visited origin, and an IndexedDB export, and re-apply them on restore. Encryption and ordering: envelope-encrypt the snapshot row and the cached payload with a per-org data key obtained through a Control Plane key API (environment master key first, KMS later), add a monotonic `saved_at` upsert and deletion tombstones, extend the purge consumer to profiles, and apply the ZDR and owner checks to the `/v1/profiles` routes.

**Why it matters.** Persistent profiles hold live session cookies for users' signed-in sites. Today snapshots miss most of the state and are stored as plaintext, so restores fail silently and a database read exposes credentials [SRC]. Encryption is specified in Quarry's own contract (apps/Ingestion Plane/Quarry-v2/docs/CONTRACTS.md:185-199) but not implemented [DOC].

**What the references do.** Some form of persistent browser state exists in 3 of 4 references (Firecrawl through Hangar, Codex, and Aside [INF]), with only a weak analogue in Apify, but no reference encrypts browser profiles per org: Firecrawl keeps only a profile listing while the profile contents live in the closed, hosted Hangar service, and no encryption code exists in its repo [SRC]; Codex keeps browser storage in persistent `persist:codex-browser-*` partitions with a storage id and a profile importer [SRC]; Aside is a full Chromium browser with profiles [INF]; Apify's SessionPool pins cookies to a proxy session, which is only a weak analogue of a named profile [DOC]. The reusable mechanism is Firecrawl's save ordering: a save is ignored unless its `savedAt` is newer than a deletion tombstone, `saved_at` is set to the greater of the stored and new values, and delete removes rows saved at or before the tombstone; the tombstone is a key-value entry keyed by team hash and name, not a column [SRC]. Firecrawl rejects profiles under lockdown and ZDR and answers 409 while a session is still saving [SRC]. Firecrawl seeds caller cookies through Playwright `context.addCookies` with a "last two host labels" domain heuristic, which is wrong for `co.uk`-style suffixes; do not copy it [SRC]. The envelope-encryption pattern (random AES-256-GCM data key wrapped by a per-(user, tool) RSA key, ciphertext only in logs) is Apify's secret Actor input mechanism, not profile encryption, so it is borrowed as a security baseline, not parity [DOC]. The full snapshot specification is Verevon's own intent from CONTRACTS.md [DOC].

**Verevon today.** `capture_snapshot` (apps/Ingestion Plane/Quarry-v2/crates/quarry-browser/src/chromiumoxide.rs:1771-1832) calls `Page::get_cookies`, which in chromiumoxide 0.9.1 returns only cookies matching the tab's current URL, sets `expires` to `None`, reads storage for the current origin only and hard-codes `indexed_db` to empty. Snapshots are plaintext JSON through a last-write-wins upsert with no ordering (quarry-runtime/src/postgres_profile_store.rs:30-92), cached unencrypted in Redis (quarry-edge/src/main.rs:597-600), and `S3ProfileStore` is never constructed (quarry-runtime/src/lib.rs:166). The purge consumer handles page images only (quarry-runtime/src/page_image.rs:43-61). ZDR refusal is already enforced inside Quarry at run creation (quarry-edge/src/agent_routes.rs:527-533, 1466-1476), but the `/v1/profiles` routes check org id only, with no ZDR or owner check, and `GET` returns raw cookie values (quarry-edge/src/profile_routes.rs:102-125, 268-296). Reuse the `ProfileStore` trait as the single serialization boundary, `zdr_forbids_persistent_profile` and `Claims::zdr_floor`, the restore probe and `ProfileScope`, and the migrations directory.

**How to build it in Verevon.** In quarry-browser, use `Storage.getCookies` or `Network.getAllCookies` for the whole context, iterate visited origins for DOMStorage, add IndexedDB through the CDP (Chrome DevTools Protocol) domain, and restore emulation overrides with the hooks from [F-t2-007](#F-t2-007). In quarry-runtime, add the encryption layer below the Redis cache so the cache holds ciphertext, with envelope `{enc_v, key_id, nonce, aad = org|profile|snapshot, ciphertext}`, lazy re-encryption on next save plus a one-off backfill. Keys come from a Control Plane key API; Quarry never reads Control Plane tables, and erasure is crypto-shredding driven by a Control Plane erasure event. Skip the S3 store in the first slice since production already requires Postgres. The store has no owner column, so owner and Space isolation stay enforced above it and a Space must never widen a profile's owner ACL; do not widen the routes' audience before an owner check exists. Decide whether `GET /v1/profiles/:id` should ever return raw cookie values. The Model Plane must never see cookie values. Main risks: master-key loss destroys all profiles; nonce handling in a new Rust AES-GCM implementation needs review; stale restores can look like hijacks to the origin. Profile pinning for scrape is [F-t2-058](#F-t2-058).

Signed claims are Verevon's own design; Firecrawl reads flags from a cached account record [SRC; INF].

**Verevon today.** org-core's `RetentionPosture` (apps/Control Plane/org-core/internal/org/types.go:255-315) feeds an auth-core claim that `Claims::zdr_floor` raises over request flags (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/auth.rs:56-140), but only for user tokens. The edge hard-wires `RunPolicy::default()` (quarry-edge/src/routes.rs:461; main.rs:1485-1493), two unrelated `RunPolicy` types exist (quarry-core/src/policy.rs:1-17; quarry-runtime/src/policy.rs:55-80), control's presets (`fast` = RobotsIgnore) are never consumed (quarry-control/internal/resources/presets.go:45-80), and `/v1/blocklists` entries have no org column and are not read by the edge. The Model Plane gate is one coarse capability, `cap.browser.open` (apps/Model Plane/rust/services/execution-core/src/capability_policy.rs:793-794), plus capability-core org-scope grants (apps/Model Plane/go/services/capability-core/internal/policy/engine.go:158-215) and a sensitive-action allowlist in the broker (browser-broker/internal/grant/grant.go:30-36). Reuse the retention-posture delivery pattern, `effective_zdr`/`zdr_floor` merge semantics, broker `allowed_domains` and `BrowserEgressPolicy` deny-all defaults.

**How to build it in Verevon.** Run the ADR first: org-core claims versus capability-core grants, because capability-core already holds tenant-bound org-scope grants and is a competing policy of record. The claim channel reaches only user-token callers: execution-core and model-gateway call Quarry with service tokens whose ZDR claim is ignored by design, so for Model-Plane-driven runs the resolved policy must ride in the BrowserBroker grant or the start-run body. Ship a Quarry-only thin slice before any org-core storage or admin UI: one `ResolvedPolicy` replacing the `RunPolicy::default()` sites, tighten-only merge with the existing ZDR floor, typed denials for evaluate, upload and download (ties to [F-t2-002](#F-t2-002)), and reconcile or delete the second `RunPolicy` type, the unused presets and `/v1/blocklists` instead of adding a third shape. The remaining work is org-core storage, auth-core claim minting and broker action classes. Depends on robots enforcement [F-t2-016](#F-t2-016), the proxy-tier cap [F-t2-058](#F-t2-058) and production grants [F-t2-001](#F-t2-001); per-origin consent builds on top in [F-t2-032](#F-t2-032). Risks: policy resolved in two places can drift, so test both paths; claim staleness mid-run, mitigated by the short grant TTL and per-action revalidation; strict defaults can break login-based research, so keep escalation through approvals and never block the human user's own manual browsing.

### F-t2-023 · Scrape-time page actions plus screenshot and PDF formats, under one bounded, grant-gated action policy
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Ingestion Plane (quarry-core, quarry-runtime, quarry-browser, quarry-edge); Frontend renders outputs | W2 | High |

**What to build.** Two deliverables. Formats: make `screenshot{fullPage, clip, quality, viewport}` and `pdf` first-class scrape formats captured on the scrape session, stored as artifacts under the claim's org, inline-only under ZDR, with tile-and-stitch only past the single-capture height limit. Actions: carry a validated, capped `Vec<Action>` on the scrape request and run it on the same page before extraction, returning per-action outputs in order, with Firecrawl-style caps (about 50 actions, 60 s total wait). Evaluate inside actions follows the [F-t2-002](#F-t2-002) policy.

**Why it matters.** Declarative actions and screenshot or PDF output are table-stakes for scrape APIs, and the runtime pieces already exist in Quarry on the agent path, but scrape cannot reach them: the screenshot and pdf formats are always `None` [SRC]. Agents and users need a page after consent dismissal, a scroll or a click, and a visual artifact for review.

**What the references do.** Scrape-time actions are in 2 of 4 references (Firecrawl, Apify); screenshot capture is in 3 of 4 (Firecrawl, Codex, Aside), and Apify likely offers it too [INF, not re-checked]. Firecrawl's request schema allows nine action types (wait, click, write, press, scroll, screenshot, scrape, executeJavascript, pdf) with `MAX_ACTIONS=50`, a 60 s total wait, screenshot quality 1-100 and a 7680x4320 viewport cap; outputs are grouped into per-type arrays (`screenshots`, `scrapes`, `javascriptReturns`, `pdfs`), not one ordered list, so an ordered per-action result is a Verevon improvement [SRC; INF]. Execution happens only in the closed hosted fire-engine; the open-source Playwright engine declares `actions:false`, so self-hosted Firecrawl cannot run actions [SRC]. The scrape `executeJavascript` action has no script-size cap; the 100,000-byte and 1-300 s limits belong to the separate hosted-browser `/execute` endpoint [SRC]. Codex captures JPEG at quality 80 with `captureBeyondViewport` plus clip and uses a screencast timestamp to guarantee a fresh frame for hidden pages [SRC]. Aside always scroll-stitches: it plans vertical tiles with CSS-pixel overlap, scrolls to each, waits 150 ms plus two animation frames, captures PNG with `captureBeyondViewport:false` and composes the tiles; element shots use the box model as clip and default to webp; PDF goes through `Page.printToPDF` [SRC, scratch copy of the daemon blob]. Apify's page actions are DOC-only, declarative per-Actor options rather than a general action DSL [DOC]. Firecrawl's OpenAPI spec lists eight types without pdf, so the spec has drifted [SRC].

**Verevon today.** `ScrapeRequest` has only `render.waitFor*` hints (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/routes.rs:346-373); the pipeline hard-codes `screenshot: None` and `pdf: None` (quarry-runtime/src/pipeline.rs:702-703); `signals.actions`, `screenshot` and `pdf` are planning hints only (quarry-runtime/src/driver_plan.rs:13-20). Screenshot via `capture_beyond_viewport` and PDF via `PrintToPdfParams::default()` exist on the agent path (quarry-browser/src/chromiumoxide.rs:2392-2445). `ActionRuntime` (quarry-runtime/src/action_runtime.rs:62-110) has no production caller and acquires its own session instead of the scrape session used by `BrowserDriverAdapter::do_fetch` (quarry-runtime/src/browser_driver.rs:128-240). docs/OSS_PARITY_BACKLOG.md:21-23 marks both as parity, which is overstated. Reuse `do_fetch`, the `Action` enum and `ActionScript` with `on_error` (quarry-browser/src/actions.rs:1-80; it includes Navigate and Evaluate, so both need explicit policy), `driver.screenshot`/`driver.pdf`, `put_artifact_if_allowed` (observation.rs:525-545), the unpopulated `OutputFormats.screenshot/pdf` fields (quarry-core/src/output.rs:140-147) and the tenant-bound artifact read (quarry-edge/src/resource_routes.rs:157).

**How to build it in Verevon.** Formats (M): capture inside `do_fetch` after goto and wait_for, return the bytes through the fetch response so the pipeline fills `OutputFormats.screenshot/pdf` as artifacts, with ZDR no-store, cache bypass and the clip, quality, viewport and fullPage options. The vision sidecar's tiles (quarry-runtime/src/vision.rs) are OCR preprocessing, not capture, so do not reuse them. Actions (M): carry the capped list on `RenderHints`/`FetchHints`, extend `ActionRuntime` to take an existing session, and run it in `do_fetch` on the same page so the scrape's host-pinned egress policy and cookie context are kept; a second `ActionRuntime` page would lose both. The Model proposes scrape actions and Quarry validates, caps and executes them; selectors and scripts from model output are untrusted. Evaluate stays denied until the [F-t2-002](#F-t2-002) gate exists. Cache admission must exclude requests with actions, headers or screenshot options ([F-t2-003](#F-t2-003)); the format registry is [F-t2-005](#F-t2-005). Frontend: render the artifacts in the timeline through the owner-gated gateway route and correct the stale tenant-scoping comment in browser.rs. Risks: memory on very tall pages, stitched seams on sticky or lazy content, and screenshots of authenticated pages, which must stay behind the owner gate and never persist under ZDR.

### F-t2-024 · Credential handoff where the model never sees secrets: executor-side fill_secret and email OTP via integration-corev2
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Absent | L | Ingestion Plane (Quarry executor + integration-corev2) + Model Plane (approval) | W3 | Medium |

**What to build.** OTP (one-time password) first: a `fill_otp` sensitive action beside `upload_ref` and `download_ref`, issued as a single-use child of the run grant bound to one origin and frame after user approval, plus an executor-only integration-corev2 (IC) `mail.otp.read` action that returns only the code. Quarry re-checks origin and field type, fills the value in the page, masks the field in observations and stores only a boolean in receipts. Password and vault-secret references (`secret://` handles) follow later, behind a secret-custody ADR.

**Why it matters.** Aside and the hosted Codex Cloud Browser (not the shipped desktop in-app browser) keep secrets out of the model. Verevon's only fallback today is human takeover into a scoped profile, which works for attended runs but blocks unattended agents and routines. Keeping the model blind to the value is what makes autonomous sign-in acceptable under prompt-injection risk.

**What the references do.** Secret handoff is in 2 of 4 references (Aside, Codex) and is a differentiator; Codex's variant is cloud-only. Codex's `browserAuth` flow lets the model request a handoff on a tab; the runtime proceeds only when the origin is https, the frame origin equals the top origin, exactly one required non-password input is present, there are no options or QR, the credential-observation gate is on and the conversation id is bound, otherwise it answers `unavailable` [SRC]. It then raises an elicitation of kind `browser_email_otp` that a guardian cannot auto-approve, stating the model cannot see the code and the user may type it instead; on approval the value is delivered natively and the model receives only a status, and AX, DOM and screenshot reads of that document are denied until navigation [SRC]. That the host fetches the code from a mail connector is inferred from the elicitation text, not observed [INF]. This flow is wired only to the hosted Codex Cloud Browser through a broker socket; the shipped desktop in-app browser does not advertise the capability, and the socket env is forwarded only in Dev builds [SRC]. Aside fills passwords from opaque password-manager references without a UI form, returning generated-password plaintext only to its trusted agent-manager extension, never to the model [SRC]. Firecrawl and Apify have no equivalent in this record set.

**Verevon today.** `AgentAction` (apps/Ingestion Plane/Quarry-v2/crates/quarry-core/src/contracts.rs:636-700) has only plaintext `Type`, `TypeRef`, `FrameTypeRef` and `TypeSemantic`; typed text is persisted verbatim for non-ZDR runs (quarry-runtime/src/step_receipts.rs:185-200; quarry-edge/src/agent_routes.rs:2346-2362). No secret store with opaque references is reachable from Quarry: IC's vault is AES-GCM at-rest encryption for provider tokens (apps/Ingestion Plane/integration-corev2/internal/crypto/vault.go:1-40), `/internal/connectors/token` leases raw provider tokens to an allow-list that excludes quarry (internal/api/server.go:1315-1345; internal/config/config.go:335-350), IC has mail read operations but no OTP action (internal/actions/mail_read.go:100-175), and BrowserBroker sensitive approvals cover only `respond_dialog`, `upload_ref` and `download_ref` (apps/Model Plane/go/services/browser-broker/internal/grant/grant.go:20-130). Reuse Quarry's sensitive-approval machinery (agent_routes.rs:196-312), `CreateScopedSensitiveApproval` (grant.go:96-130), the `RiskCategory::Login` HITL (human-in-the-loop) gate (execution-core/src/browser_agent/browser_risk.rs:25-45), the orchestration approvals surface (gateway/src/domains/browser.rs:1190-1210) and IC's Gmail and Microsoft mail read capabilities (internal/providers/catalog.go:254, 431). The fill_secret plan exists only in a document (QUARRY_V2_BROWSER_AUTOMATION_IMPROVEMENTS_2026_OWNERSHIP_RECONCILED.md:1106-1127) [DOC].

**How to build it in Verevon.** Add the `fill_otp` variant to the existing sensitive-approval path and reuse the Login risk gate and orchestration approvals for the approval card, naming origin and connection and offering "I will type it myself", instead of a new elicitation channel. Add the IC `mail.otp.read` action with sender, age and pattern filters, audited through the existing outbox, kept off every Model-callable tool surface; give Quarry a distinct identity or manifest row toward IC, since IC internal auth is one shared API key (server.go:170-173), and do not add quarry to `INTEGRATION_TOKEN_LEASE_CONSUMERS`. The Ingestion Plane owns execution and secret resolution; the Model only sees opaque references and proposes, Quarry executes. Secrets are scoped to user or org and never widened by Space access. ZDR forbids persisting values or frames that show credentials, and non-ZDR receipts store typed text today, so [F-t2-021](#F-t2-021) redaction must land first; trusted input is [F-t2-015](#F-t2-015), takeover is [F-t2-013](#F-t2-013), and production grant issuance is [F-t2-001](#F-t2-001). Defer password references until the custody ADR and those items are in place; the full scope would be XL. Main risks: exfiltration through a phishing page or injected iframe, an OTP requested by a page the agent was lured to, and accidental logging; mitigate with https-only, top-origin equality, single-use approval that shows the origin, and receipts that carry a boolean only.
