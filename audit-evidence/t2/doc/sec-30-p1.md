## 4. Priority recommendations

Priority items are the changes that unblock production use of the in-app browser and the Quarry acquisition API, or that close a breach of a Verevon architecture rule (Zero-Data-Retention, ZDR, must propagate; no tenant may read another tenant's data; the Model proposes and Quarry executes or rejects). They are listed in recommended build order within the tier, so an item generally assumes the ones above it. Every card shows the verified status of Verevon at commit afb83928 (2026-10-10): status, gap, effort and approach come from the code-verification pass and supersede the original comparison notes. Where verification corrected a claim about a reference product, the corrected claim is the one stated here. Effort is S, M, L or XL for the verified scope on the card.

### F-t2-001 · Production BrowserBroker grants and delegated bearer forwarding (unblocks every browser path)
| Tier | Verevon today | Effort | Plane | Wave | Confidence |
|---|---|---|---|---|---|
| Priority | Partial | L | Model Plane (BrowserBroker) + Frontend Plane gateway; Quarry validates only | W1 | High |

**What to build.** Give the Model Plane BrowserBroker a durable (Postgres) grant store and an issuance path the Frontend gateway can reach. The gateway obtains a user-session grant when it creates a browser session, sends `grant_id` on `POST /v1/agent/runs`, forwards `x-browser-authorization`, and derives a narrower run grant for AI runs instead of the interim `session:{id}` string. Add one prod-mode contract test across gateway, model-gateway, execution-core and quarry-edge that fails on 401 or 403.

**Why it matters.** Prod-mode Quarry requires a broker grant on every run and step and refuses to boot without a validator, yet nothing in production issues a grant and the broker store is in memory [SRC]. Until this lands, the in-app browser, the AI step loop, co-browsing, the credential bridge, grant-carried budgets and per-origin consent cannot work in production [INF from the code paths below; not runtime-tested]. It is the highest-leverage item in the audit.

**What the references do.** No reference implements a durable, org-scoped grant issuer; it is a Verevon design requirement, not a parity feature [INF]. The closest mechanisms are single-user, local-device trust checks. Aside's browser-control endpoint refuses unauthenticated clients: a client fetches a challenge, signs it with an installation key and receives a short-lived session token, and commands travel over a bridge routed per account, profile and mode that rejects stale connections [SRC, from a scratch copy of the daemon blob]. Codex runs a signed, nonce-bound per-turn browser-access check tied to a "Work settings" toggle [SRC; enterprise gating INF from an error string]. Codex also hardens every guest attach in its Electron main process, forcing partition, session and preload and deleting dangerous flags; that is 1 of 4 references (Codex) and Electron-specific, so it says nothing about Aside [SRC]. Firecrawl's hosted sessions take `ttl` and `activityTtl`, enforced by the external, closed Hangar service; Firecrawl's own 15 s reconciler settles billing and is not a reaper [SRC; enforcement INF].

**Verevon today.** The broker implements AcquireGrant, ValidateGrant and RevokeGrant with org and owner scoping, a host list of at most 32, a 15-minute TTL and sensitive child grants, but the store is in memory (apps/Model Plane/go/services/browser-broker/internal/grant/grant.go:61-71) and no production code calls AcquireGrant. create_session posts to Quarry with no grant_id (apps/Frontend Plane/verevonv3/apps/gateway/src/domains/browser.rs:483-506), which prod Quarry rejects with 403 (apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/agent_routes.rs:1377-1412), and start_ai_run sends `session:{id}` (browser.rs:1235) without the browser bearer that model-gateway's VerifiedBrowserBearer extractor requires (apps/Model Plane/rust/services/model-gateway/src/auth.rs:427-437). Reuse the grant package, browser.proto, resolve_browser_grant, the declared BrowserBroker audience (audience_tokens.rs:27-42) and Quarry's GrpcGrantValidator.

**How to build it in Verevon.** Slice it: issuance, gateway wiring and the contract test on the in-memory store first, then Postgres. Prefer a model-gateway HTTP endpoint wrapping AcquireGrant over teaching the gateway gRPC. Only `x-browser-authorization` is missing from the bearer set; add it to proxy_model_json_with_delegations (chat/shared.rs:629-690). Both create_session and start_ai_run need the grant; deriving a run grant from a session grant is a new broker API. The Model Plane owns issuance and the gateway must never mint authority; domains come from the broker, never the client; ZDR grants are never persisted; a Space must never widen a grant. The 15-minute TTL caps session length until [F-t2-011](#F-t2-011) adds renewal. Risks: scope creep, restart semantics for in-flight sessions, and user-session issuance bypassing the cross-domain approval gate.

**What to build.** Slice 1 (S): add a spend accumulator and start time to RunEntry, add the per-step cost already computed for receipts, and replace enforce_step_budget with an enforce_budget covering steps, cost and wall clock that returns a typed budget-exhausted error. Apply it only to agent-initiated runs or steps, or stop the gateway passing 12 steps and 120 s for manual sessions and use an idle TTL instead. Slice 2 (M): emit a browser-second UsageEvent on close_run, clamp crawl and batch page limits and request rate to the remaining entitlement and return the clamped value, and have cost-core carry the remaining budget in the BrowserBroker grant and reconcile once per run id.

**Why it matters.** Agents with live browsers and paid providers can run up unbounded cost. docs/WEB_AGENT_ROADMAP_EXECUTION.md:50-53 says max_cost_usd is enforced; the HTTP step path does not enforce it [SRC]. Both crawl platforms enforce in the executor, which is where Quarry must do it.

**What the references do.** Executor-side budget enforcement is 2 of 4 references (Firecrawl, Apify). Firecrawl's browser-session create runs a credit check for the full TTL (402 if short) and reserves only a concurrency slot (429); a debit-ahead exists only for keyless use. On stop it locks the session row with SELECT ... FOR UPDATE, settles the actual duration exactly once, and a periodic sweep settles sessions whose stop was missed [SRC]. Rates are plain browser versus a session that used a prompt, plus a ZDR surcharge. Its CostTracking class can throw on a limit, but no open-source caller sets one, so it is dormant [SRC; hosted enforcement INF]. At crawl submit, limit becomes min(requested, remaining credits) and only the clamped value is stored; maxConcurrency is capped to the team limit; results expire after `crawlTtlHours` (default 24) [SRC]. Apify lets an Actor call charge(event, count) within a caller-set maximum total charge and aborts the run automatically when reached; "finish the step and persist partial results" is a Verevon proposal [DOC; proposal INF]. Caveats: the Apify half is documentation only; Firecrawl sessions need the hosted Hangar service.

Cost and runtime logic exists in the library AgentLoop (quarry-runtime/src/agent_loop.rs:154-163), which has no HTTP caller. Per-step cost_usd is computed for receipts (agent_routes.rs:2346-2362) but never accumulated; usage.rs has no browser metric. Crawls are bounded only by max_pages, where absent means unlimited (quarry-orchestrator/internal/workflows/workflows.go:456), plus a 30-minute Temporal timeout (jobs/dispatcher.go:254). execution-core enforces steps and runtime on its own clock but never checks max_cost_usd (browser_agent.rs:320-330, 666). Reuse the receipt cost functions, AgentLoop over_budget, UsageEvent and UsageMeter, and the quarry-control credit-usage read model.

**How to build it in Verevon.** Enforcement belongs in the Quarry step admission path; cost-core owns model spend only; Control Plane owns entitlements, which quarry-control does not model as a ceiling today. The gateway creates every manual session with max_steps 12 and max_runtime_s 120 and human actions share `/step` (gateway/src/domains/browser.rs:481-488, 663-732), so naive enforcement would cap human browsing [INF]. Resolve caps as min(request, grant claim, org default) and fail closed. Under ZDR, receipts are skipped, so accumulate in memory and keep usage events content-free.
