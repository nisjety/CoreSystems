# Audit 3 final: Model Plane and Verevon chat and agent pages

Task T3, global calibration of the 13 category consolidations (159 recommendations, R-t3-*) into 98 final items (F-t3-*): **23 priority, 45 recommended, 30 nice-to-have, 2 dropped**. 52 final items keep needsVerification = true. The machine-readable result is `items.json` in this folder; every R item appears in exactly one final item's sourceItems or in dropped (checked with node).

**Provenance.** REA = reverse engineering of shipped app bundles (Claude desktop, Cursor, Antigravity, T3 Code, Manus desktop, Codex), SRC = source read (Hermes Agent, DeepSeek harness, Verevon/CoresSystem code), DOC = public or internal documentation, INF = inference. The four web products (claude.ai, ChatGPT, Perplexity, Manus web) rest on **public documentation only**; where a final item's best practice comes only from them it is called out. Verevon status rests on the code-verified baselines (SRC) plus re-reads by the consolidators; docs in the repo are partly stale, so code was treated as ground truth. Tiering, merging, ranking and sequencing in this file are my judgement (INF) on top of those inputs.

## 1. How the calibration changed the picture

The consolidators proposed 61 priority, 76 recommended and 22 nice-to-have items. Seen together, the same few defects surfaced in several categories, so the main move was merging, not cutting:

- **Do runs ignore their context** (agent runtime, extensibility and memory all found it) became one item, F-t3-001.
- **Durable resume after a pause** (runtime and platform) became F-t3-002; **plan-continue, ask_user and docked trays** (chat, runtime, UI) became F-t3-011.
- **Message tree, search, recall and paging** (chat, memory, platform) became F-t3-012; **render performance** (chat, UI) became F-t3-021.
- **Agent-browser reachability and governance** (computer control, safety, research) became F-t3-008; **the per-thread sandbox computer** (computer control, platform) became F-t3-009.
- **Audit delivery** (transparency, safety) became F-t3-004; **approval scopes and cause codes** (safety, transparency) became F-t3-006; **tool risk classes and MCP enablement** (extensibility, safety) became F-t3-003.
- **Office files and SKILL.md bundles** (creation, extensibility) became F-t3-014; **learning-loop governance, proof and ledger** (memory, transparency) became F-t3-007.

Items were demoted when they depend on a priority foundation (computer use F-t3-024 needs F-t3-009; deep research v2 F-t3-027 improves an already shipped, honest one-pass feature; decks F-t3-038 need F-t3-014), when they are polish for a non-IDE product (changed-files review F-t3-076, best-of-N), or when the evidence is documentation-only and the benefit modest. Two items were dropped: the parked local execution host (R-t3-13-12) and Cursor-style best-of-N workspaces (R-t3-07-10), which conflicts with a standing decision-ledger ruling.

## 6. Architecture decisions that need an ADR first

These items touch existing Verevon rules (plane ownership, ZDR propagation, Space authority, 'the Model proposes and Quarry executes', no LLM on the permission path). Each needs an ADR or an owner ruling before implementation starts:
1. **Sandbox computer backend and thread-scoped workspace (microVM per thread, snapshot retention and destruction, cost metering)** (F-t3-009, F-t3-024, F-t3-035, F-t3-043, F-t3-084, F-t3-085). Moves execution from hermetic per-call bwrap processes to long-lived machines and introduces durable state outside Spaces; must show ZDR snapshot destruction, that a thread workspace never bypasses Space ACLs, supply-chain ownership of guest images, and VM-second billing.
2. **Computer-use scope: desktop control only inside Verevon's sandbox VM; user-desktop control stays parked** (F-t3-024, F-t3-026). The owner parked OS-level desktop control; the Endpoint Plane can capture and inject input on real machines. An ADR should fix the boundary (sandbox only, consent tiers if ever unparked) and keep the 'Model proposes, executor executes' rule for desktop actions.
3. **Spaces as the chat project container, instruction precedence and multi-author authority (OD19)** (F-t3-013, F-t3-001, F-t3-060, F-t3-061, F-t3-012). Projects must not become a second container beside Spaces; precedence between org, Space, project and persona instructions, and whose delegated token runs a collaborator-triggered agent turn, need a ruling so Space access never widens an owner-plane ACL.
4. **Agent-browser domain policy ownership and model-blind credentials (OD13)** (F-t3-008, F-t3-026, F-t3-050, F-t3-081). Decides whether broker, Control or Quarry owns the domain fence and per-site read/act consent, and how vault secrets are substituted by Quarry so the Model never sees them, preserving 'the Model proposes browser actions and Quarry executes or rejects them'.
5. **Unattended authority: scheduled, goal and trigger runs, stored consent with expiry, renewable delegated credentials (owner ruling 2026-09-28, OD8, D10)** (F-t3-018, F-t3-037, F-t3-047, F-t3-002, F-t3-019). Today scheduled runs are draft-only by owner ruling and the delegated bearer lives 300 s. Tool-using unattended runs need a signed, expiring consent contract, a non-delegable set and a renewal path through Control, not a service-principal shortcut.
6. **Share model, public links and artifact hosting origin under ZDR and residency** (F-t3-046, F-t3-045, F-t3-080, F-t3-031). Public snapshots, published artifacts and a dedicated user-content origin create new egress and retention paths; connectors called from a shared artifact must run with the viewer's credentials. Must state which content types (ZDR threads, private connector content) can never be shared.
7. **Learned and distributed behaviour: three-tier skill library (vendor, org, user), promotion gate and plugin supply chain** (F-t3-007, F-t3-058, F-t3-059, F-t3-014). The promotion gate is deliberately unbuilt pending a product decision while the loop already writes org-matchable skills; executable skill and plugin bundles add code supply-chain risk. One ADR should define scopes, approval, pinning and kill lists.
8. **Model entitlements and provider credentials ownership (allowed_models has no owner; BYO keys custody)** (F-t3-023, F-t3-065, F-t3-042). model-gateway refuses the OrgPolicy allowed_models field because no service owns it. Control Plane should decide and Model Plane enforce; bring-your-own provider keys must stay in Integration Core custody with ZDR and residency attestation per connection.
9. **LLM reviewers on the permission path (revisit HAP WS-3 and ownership-matrix rule 12 for tighten-only monitors)** (F-t3-097). Codex-style guardian reviewers conflict with the standing 'no LLM on the permission hot path' decision; only a tighten-only (deny or escalate, never grant) design could be compatible and needs an explicit ruling.
10. **Connector content in shared Spaces and ZDR propagation for connector and web reads** (F-t3-010, F-t3-056, F-t3-027, F-t3-055). Personal mailbox and drive content read by an agent in a Space thread must not become visible to other members, and ZDR must propagate to connector reads, citations and research ledgers.

## 7. Cross-cutting themes

1. **The agent loop is the product.** Plain chat is close to parity, but Do runs start without context, cannot resume after a pause, cannot ask a question and cannot run on a schedule with tools: F-t3-001, F-t3-002, F-t3-011, F-t3-016, F-t3-018, F-t3-037. Fixing these unlocks most other items.
2. **Built, but dark.** A striking share of the gaps are finished or nearly finished code that is not deployed, not wired or not proven: the audit outbox fix (F-t3-004), ZDR (F-t3-005), connector reads (F-t3-010), MCP calls refused by the gate (F-t3-003), placeholder browser grants (F-t3-008), the OpenAI cache order (F-t3-022), the Redis stream buffer (F-t3-016), promote-on-use (F-t3-093), and a fleet console without a route (F-t3-019). Finishing beats building.
3. **Governed autonomy as the differentiator.** Verevon's signed gate, autonomy ladder, durable approvals and credential isolation are stronger than any reference. What is missing is the declarative layer users and admins see: declared risk classes (F-t3-003), scoped approvals with causes (F-t3-006), modes and an org registry (F-t3-032), stored consent for unattended runs (F-t3-018), and browser site policy (F-t3-008).
4. **From chat to computer, in steps.** The path to Manus-style 'acts like a PC' runs through a governed browser (F-t3-008, F-t3-026, F-t3-050), then a per-thread sandbox computer (F-t3-009, F-t3-035), then computer use inside it (F-t3-024). User-desktop control stays parked.
5. **Learning the organisation controls.** Verevon learns already (Dreaming, skill review, feedback signals) but without review, scope or undo. Governance first (F-t3-007, F-t3-020, F-t3-033), then tailoring (F-t3-061, F-t3-060, F-t3-058).
6. **Transparency that shows cause, cost and context.** Verevon is honest by contract; the next step is making it visible: approval causes (F-t3-006), live cost (F-t3-028), typed lifecycle events (F-t3-049), readable long runs (F-t3-048), the trajectory ledger (F-t3-034) and effective-policy provenance (F-t3-068).
7. **Deliverables, not only answers.** Verified Office files (F-t3-014), decks (F-t3-038), an editable canvas (F-t3-031), research reports cited to passages (F-t3-027, F-t3-053) and inline widgets (F-t3-044).
8. **Open standards for extensibility.** SKILL.md bundles (F-t3-014, F-t3-058), MCP that executes (F-t3-003), MCP Apps (F-t3-045), plugins with supply-chain pins (F-t3-059) and an outward MCP endpoint (F-t3-089) keep Verevon compatible with the ecosystem the references share.

## 8. Main architecture risks

- **Plane-boundary erosion.** A thread-scoped sandbox workspace (F-t3-009), staged attachments (F-t3-017) and connector content in Spaces (F-t3-010) all tempt shortcuts across planes. Bytes must flow through Data Plane APIs, and Space access must never widen an owner-plane ACL.
- **ZDR propagation into new stores.** Loop checkpoints, the search index, artifact versions, recordings, push payloads, provider-side caches and research ledgers are all new places content could persist. Every item that adds a store carries a ZDR clause; the ZDR resolver's golden matrix should gain cases for each.
- **Authority creep.** Scoped approvals, stored consent for unattended runs, takeover carry-over grants, persistent named agents and viewer-bound artifact connectors each widen who or what can act. They should be tighten-by-default, expiring and audited (F-t3-004).
- **A larger prompt-injection surface.** Browser pages, mail bodies, recall snippets, MCP tools, widgets and imported memory all feed untrusted text into the loop. F-t3-033 should land before or with F-t3-008, F-t3-010 and F-t3-003.
- **Cost growth without measurement.** More context per Do run, two-pass research, wide fan-out and VMs raise cost while cache hits are unmeasured. F-t3-022 and F-t3-028 come first.
- **Concentrated dependencies.** Many items hang on F-t3-002, F-t3-003 and F-t3-009; a slip there delays a third of the roadmap. The renewable delegated credential (OD8) is a hidden prerequisite for F-t3-002, F-t3-018 and F-t3-037.
- **Evidence quality.** 52 of 98 final items need verification (status unknown, or a consolidator doubted the baseline), several reference practices are DOC-only (web products), and repo docs are partly stale (the connector-read baseline was corrected by a re-read on 2026-10-14). Verify Verevon status before committing effort, especially for F-t3-010, F-t3-045, F-t3-041, F-t3-051 and F-t3-062.
- **Operational maturity.** The audit trail went undelivered with a fix built but not deployed; no signed release candidate or rehearsed rollback exists yet (F-t3-039). Shipping many runtime changes without that discipline is itself a risk.
