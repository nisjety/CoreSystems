# Application Plane production-readiness audit — 2026-07-13

Audit window: 2026-07-13 09:30–19:13 CEST. Scope: all default Application Plane workloads, the opt-in support worker, Verevon v3 callers, Ingestion notification and provider-action callers, Control membership authority/events, and the Model traffic formatter. This document supersedes the current-state conclusions in `plane-audit-2026-07-11.md`; the older audit remains useful historical evidence.

## Executive decision

The Application Plane is **not yet a production-ready secure MVP** and is not enterprise-ready. Important source fixes and regression tests are complete, but they are not deployed. The release-blocking gaps are deploying/live-testing canonical membership across protected gateway domains, provisioning/deploying the implemented conversation→integration bearer and durable Ed25519 approval proof, incomplete plane-wide ZDR propagation, stale/ambiguous outbound reconciliation and provider callbacks, issuer-unverifiable cross-plane membership fan-out, notification projection availability/outbox/callback recovery, and remaining coverage gaps.

The running stack was not rebuilt or replaced. Root filesystem free space fell to 3.6 GiB during the audit, recovered without action from this audit, and measured 32 GiB on root/Data plus 63 GiB on the workspace volume at 19:13 CEST; Docker retained 35.67 GB of images and 4.17 GB of build cache. Capacity is no longer the immediate blocker, but each build needs a fresh margin calculation, and immutable rollback artifacts, unapplied migrations/functions, unprovisioned credentials, approval/ZDR controls, and live gates still make replacement unsafe. No prune, daemon restart, database mutation, production reconciliation, customer message, social publication, or paid provider action was performed.

## Source remediation completed in this pass

### Canonical membership authority and gateway delegation

- Added Auth Core `POST /api/v1/internal/membership/decision` as an exact Better Auth `(userId,orgId)` decision. It uses a dedicated 32+ character non-placeholder credential, rejects credential reuse, compares digests in constant time, accepts only strict request keys/types, and returns only the v1 member/role decision.
- The authority queries at most two rows and returns 503 on ambiguity. Migration `016_unique_organization_membership.sql` aborts when duplicates exist before creating the unique `(organization_id,user_id)` index; it never guesses which role wins.
- User Core requires an explicit active organization, calls only the canonical endpoint, refuses redirects, strictly decodes a bounded response, denies missing membership, and returns 503 on authority failure. Canonical grants backfill the local projection. A canonical denial now marks the exact trimmed `(user_id, org_id)` projection removed; authority outages never mutate it, and a projection-write failure returns an explicit 500 instead of emitting a partially reconciled session context.
- Verevon gateway's protected routers now share a live exact membership decision. Missing active membership or an authoritative denial becomes sanitized 403; authority non-2xx, redirect, malformed/extra/trailing data, or user/org/role mismatch becomes sanitized 503. `authorized_org_id` reads only that verified decision, canonical tenant role replaces session/platform role downstream, Inbox reuses the middleware result, and conversation signs the canonical user, organization, and role into an HMAC-v2 delegation. Conversation-core verifies service/audience/method/URI/body/user/org/role/timestamp/nonce and enforces reader/agent/admin route roles.

Limitations: Auth Core/User Core/gateway source and migration 016 are not deployed. The shared gateway remediation covers 117 authorization references across 33 domain files, but live no-auth/wrong-tenant/removal/authority-outage negatives have not run. A post-fix review found and TDD-closed two route bypasses: organization path IDs now exact-match the verified tenant, and the blanket onboarding exemption is replaced by an explicit pre-organization allowlist; tenant-bearing graph/connector routes compare scope before any upstream. Process-local nonce caches do not provide HA replay protection. The unique migration has not run against the real database, so duplicate preflight state is unknown.

### Convex projection and public authorization

- Implemented `onOrganizationMemberRemoved` as an idempotent tombstone/soft-delete projection. It revokes all duplicate active membership rows, deletes matching Control Session mirrors, blocks stale add resurrection, and records an audit entry.
- Aligned the subscriber with canonical `aqencia.controlplane.org.*` subjects and snake-case envelopes. Control events now use durable JetStream consumers with explicit ack/nak, bounded redelivery, and a redacted DLQ. Missing organization prerequisites now throw for redelivery instead of being acknowledged as success.
- Removed the predictable NATS token fallback. Required Convex and NATS credentials fail closed.
- Implemented the real `imports.recordCompleted` projection. Removed dead legacy jobs HTTP handlers rather than creating no-op jobs functions.
- Added static API contract tests so called-but-undefined source references fail the test gate.
- Added membership authorization to previously public cross-tenant queries/mutations in `controlSessions`, `plannerDocuments`, `knowledgeQnA`, `projects`, and `agentRuns`. Service-only Control writes are internal mutations.
- Redacted member email logs and genericized projection HTTP errors.
- Added removal-only/demotion-only reconciliation. Apply cannot create grants or widen roles. The operator endpoint uses a dedicated `CONVEX_RECONCILIATION_KEY`, HMAC-SHA256 over method/path/org/timestamp/nonce/body, five-minute skew, server-side nonce claims, and exact org confirmation. The generic NATS webhook can no longer invoke reconciliation.
- Reconciliation is dry-run by default and reports missing memberships and unsafe promotions without applying them.

Limitations: the running Convex bundle is still old; no production drift was changed. Control events still lack authoritative event IDs/revisions and signed issuer identity. The publisher remains fire-and-forget, and a workload with shared NATS publish authority can forge payload `_source`. These are MVP blockers.

### Notification authority, ZDR, and support callers

- The canonical request now requires `organization_id`, a typed `{kind:"user",id}`, organization-scoped idempotency, verified caller source, and `standard|zdr` retention mode. A canonical JSON SHA-256 fingerprint detects same-key contract conflicts.
- Feed, preference, channel, membership, and provider-subscriber mappings are organization scoped. Removed or unknown users fail closed; the earlier gateway-session self-membership bypass was removed.
- Gateway and support-worker use a service-specific HMAC v2 delegation contract bound to audience, method, URI, tenant, user, role, timestamp, nonce, and body digest. Legacy key-only requests, public placeholder token families, wrong origins, and nonce replays are rejected in source.
- Caller workflow allowlists prevent the gateway/support worker from invoking arbitrary notification types. Support requests must be ZDR.
- ZDR dispatch persists only control metadata and the request fingerprint: it does not persist payload content or create a feed projection, and lifecycle events redact the recipient. The current request payload is used transiently for provider submission.
- Notification source has explicit `novu` or `disabled` modes. Missing provider configuration defaults to disabled, never fabricates a provider ID, and reports `/ready` 503. Provider acceptance is recorded as `submitted`, never inferred as delivered.
- Support-worker posts the canonical route, supplies typed Control user/organization identifiers, uses ZDR, applies a 10-second timeout, requires an explicit submitted/suppressed response, and propagates failure. Its default mode is disabled. Existing workflows do not provide the authoritative mapping, so `user_resolved` mode cannot currently succeed.
- The invalid insight-core notification caller was removed; daily-brief notification delivery is explicitly disabled until an authoritative subscription/user mapping exists. The navbar support action now returns an honest 503 rather than generating a fake self-notification.
- Unsigned shared-bus membership/session/social consumers are disabled in notification-core source because those payloads cannot be treated as authorization.

Limitations: source is not deployed. The running old service has no provider key and can claim synthetic submission. There is no production Control-authority writer/backfill for `notification_subscriber_memberships`, so the secure source intentionally denies legitimate feed/intake until that projection is supplied. Provider submission still precedes a best-effort feed write, and no durable feed outbox, provider callback/reconciliation, durable preference sync, multi-replica nonce store, or deep dependency readiness exists. Standard-retention payloads still persist by design, and plane-wide ZDR is incomplete. Support automation and brief delivery must remain intentionally disabled.

### Conversation delivery and HITL containment

- External human replies now require a configured sender, channel thread reference, and supported provider before any message row can be persisted. Attempted provider failures remain HTTP 502; unavailable delivery paths are HTTP 503. Explicit internal notes remain the only store-only path.
- The public `/messages` route rejects caller-selected `internal:true` and always takes external-delivery semantics; `/notes` is the sole store-only route. Caller-provided actor profile fields are not trusted.
- AI-action review is now a compare-and-set from `suggested`. Reapproval of a rejected, approved, or executed action returns conflict, inserts no second review, and publishes no reviewed event.
- Integration 2xx responses must prove success: malformed/`success:false` envelopes and messaging responses without provider IDs fail without persistence. Only the documented empty 202 mail-submission shape remains accepted. Provider response text is reduced to bounded codes in errors/events, and the integration client does not follow redirects with shared authority headers.
- External replies require a stable caller idempotency key. `conversation_outbound_intents` is claimed by `(org_id,idempotency_key)` before transmission and stores only routing, fingerprint, provider ID, and outcome metadata—not a second plaintext message body. Same-key/same-request submission replays the stored message; same-key/different-request conflicts; `sending`/`unknown` never retransmit blindly.
- Integration-corev2 independently claims a tenant-scoped provider-action receipt before the provider call. Completed receipts replay, conflicts reject, and ambiguous outcomes stay unknown. Message, audit, AI executed state, provider ID, and submitted intent are finalized in one Application DB transaction.
- AI draft sends use the action ID as the stable approval/idempotency identity. Terminal provider rejection becomes `failed`; timeout/5xx/ambiguous response becomes `unknown` and is acknowledged for reconciliation rather than redelivered into another provider call.
- Inbox sends `idempotency_key`, retains one UUID/key across an ambiguous retry, and uses the honest success copy `Reply submitted.`. Focused tests confirm no production `Reply sent.` copy remains.
- Conversation now obtains an Auth Core `aud=ingestion`, tenant-bound service JWT per organization, caches it only until a refresh window, and uses Bearer-only action/connection tenant APIs. It never forwards the legacy integration key or caller scoping headers on those paths, refuses redirects, bounds token/action responses, and treats malformed/empty/oversized post-provider 2xx results as unknown except for the documented empty 202 mail submission shape.
- Migration 005 binds each conversation outbound intent to a content-free authorization kind, durable actor, approval/action identifiers, normalized operation, and canonical payload SHA-256. Conversation issues a 30-second Ed25519 compact JWS only after that claim. Manual sends use the verified delegated actor and no approval field; AI sends require a durable `approved` action and `reviewed_by`, ignore the event actor, and bind approval/action IDs. Nil/misconfigured signers and legacy empty-binding rows fail before downstream HTTP.
- Integration requires both the tenant-bound `integration:write` service bearer and top-level `writeAttestation`. It verifies exact EdDSA/type/key/issuer/audience/presenter/time and tenant/connection/provider/operation/actor/payload/idempotency claims before OAuth. Migration 0008 stores only authorization IDs/hashes and enforces one `(issuer,org,authorization)` receipt. Forward-only migration 0009 preserves 0008's recorded baseline, locks writes, aggregate-count audits any weaker human/AI identifier relationships, fails without rewriting them, then installs and validates the stronger constraint. Receipts remain `pending` through OAuth, atomically become `executing` immediately before provider execution, then `completed` or `unknown`; legacy and unknown-operation writes fail closed.
- Provably pre-Integration Auth failures now mark the same conversation intent `retryable` and exact-CAS it back to `sending`; AI NAKs for redelivery. Conversation token refresh is single-flight per organization rather than one network-held global lock. Post-action ambiguity is still `unknown` and is never automatically retried.

Limitations: migrations 004/005 and 0007/0008/0009 were not applied to real Postgres; receipt SQL, the applied-0008 upgrade path, and advisory-lock ordering are pgxmock/migration-contract tested only. Real-Postgres concurrent startup remains a live rollout gate. `sending`/`executing`/`unknown` rows have no lease, sweeper, dry-run reconciliation API, or compensation workflow. Provider acceptance is still published as “sent” in one lifecycle subject, while message records lack callback-driven submitted/sent/delivered/failed timestamps. AI review publication is not transactional, and outcome event publication is best-effort. The Auth Core principal, Ed25519 private/public keys, and workloads are unprovisioned/undeployed. Integration trusts only `conversation-core`, so other Model/provider-write callers now fail closed until their own durable authority can issue the identical contract; that is intentional containment, not feature completeness.

### Information honesty

- Removed deterministic traffic volume/speed generation. Metrics are nullable observation objects with provider/source, measured/estimated/synthetic/unavailable type, timestamps, units, confidence/quality, freshness, and unavailable reason.
- Atlas station metadata now returns `metadata_only`; missing measurements are explicit `null`/`unavailable`.
- Locally inferred county and road fields are marked estimated/low-quality, and unsupported inference returns empty/unavailable rather than plausible fallback facts.
- Atlas HTTP and GraphQL errors fail honestly and are not cached as empty success. Coordinate/radius/search inputs are bounded and reject NaN/infinity/out-of-range values.
- Verevon v3 visibly labels unavailable, estimated, synthetic, stale, and measured values and labels derived road/county metadata as estimated.
- Model Plane preserves provenance and labels any legacy numeric fallback `unverified_legacy`.

Limitations: information-core and Model runtime are not deployed. The focused production frontend is Verevon v3; legacy Verevon v2 still expects numeric fields and must be retired or migrated before it can be treated as an active caller.
