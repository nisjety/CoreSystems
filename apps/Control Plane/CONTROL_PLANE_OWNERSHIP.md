# Control Plane Data Ownership Architecture

## Overview

This document defines the **clear data boundaries** between the Control Plane (source of truth) and Convex (derived/real-time layer). The Control Plane owns all critical organizational and user data, while Convex provides real-time features for conversations and AI interactions.

Companion privacy contract: [`../GDPR_SUMMARY.md`](../GDPR_SUMMARY.md). This ownership map defines authority; the GDPR summary defines the cross-plane retention, deletion, anonymization, processor, and ZDR obligations that follow authority decisions.

---

## 🏛️ Control Plane Ownership (Source of Truth)

The Control Plane services (auth-core, user-core, org-core) are the **single source of truth** for:

### 1. Organization Core Data
**Owned by**: `org-core` service  
**Database**: PostgreSQL `org_core` database

- ✅ **Organization ID** (`org_id`) - Primary key, generated by auth-core
- ✅ **Plan** (`plan`) - Subscription tier: free, pro, enterprise
- ✅ **Status** (`status`) - active, suspended, deleted
- ✅ **Quotas** (`org_quotas` table) - Resource limits per plan
  - `api_calls`, `users`, `storage_mb`
  - Per-plan quota limits
  - Usage tracking and reset periods
- ✅ **Capabilities** (`org_entitlements` table) - Feature flags
  - `feature.chat`, `feature.api_keys`, `feature.audit_logs`, `feature.sso`
  - Enabled/disabled per organization
- ✅ **Role Mappings** (`org_role_mappings` table) - Granular permissions
  - Default roles: owner, admin, member, viewer
  - Custom roles with permissions arrays
  - Example permissions: `org:delete`, `members:invite`, `billing:manage`
- ✅ **Billing Flags** (`org_billing` table)
  - Payment method, subscription ID, subscription status
  - Trial period tracking
  - Auto-renewal settings
  - Billing address and tax information
- ✅ **Compliance Settings** (`org_compliance` table)
  - Data residency (us, eu, asia)
  - Compliance flags: GDPR, HIPAA, SOC2
  - MFA requirements, IP allowlists
  - Audit log retention policies
  - Encryption settings
- ✅ **Hard Deletes** (GDPR purge) - PostgreSQL functions
  - `gdpr_hard_delete_organization(org_id)` - Complete data removal
  - `soft_delete_organization(org_id)` - Mark as deleted
  - `purge_old_deleted_organizations(days)` - Cleanup after retention period

### 2. User Authentication & Identity
**Owned by**: `auth-core` service  
**Database**: PostgreSQL `auth_service` database

- ✅ **User ID** (`user.id`) - Primary key
- ✅ **Authentication** - All auth methods
  - Email/password
  - OAuth providers (Google, GitHub, etc.)
  - SSO (SAML, OIDC)
  - Passkeys/WebAuthn
  - Two-factor authentication
- ✅ **User Profile**
  - Email, name, phone number
  - Email/phone verification status
  - Profile image
  - Role (global admin, user)
- ✅ **Sessions** - All session management
  - Session tokens, expiration
  - Device tracking
  - IP address logging
- ✅ **Security Settings**
  - 2FA enabled status
  - Banned users and ban reasons
  - Rate limiting
- ✅ **Hard Deletes** (GDPR purge)
  - `gdpr_hard_delete_user(user_id)` - Complete data removal
  - `gdpr_anonymize_user(user_id)` - Anonymize instead of delete

### 3. Organization Membership
**Owned by**: `auth-core` service  
**Database**: PostgreSQL `auth_service` database

- ✅ **Member Relationships** (`member` table)
  - User-to-organization mappings
  - Organization-specific roles
- ✅ **Invitations** (`invitation` table)
  - Pending invites
  - Invitation expiration
- ✅ **Teams** (optional)
  - Team structure within organizations
  - Team memberships

## 📡 Event-Driven Projection Architecture

The Control Plane publishes events via **NATS JetStream** for all state changes. Convex subscribes to these events and maintains a **read-only projection** of org/user data.

### Events Emitted by Control Plane

#### Organization Events (auth-core + org-core)

```typescript
// Published by: auth-core (on initial creation)
{
  type: "organization.created",
  organization_id: "org_abc123",
  name: "Acme Corp",
  slug: "acme-corp",
  plan: "free",
  creator_id: "user_xyz789",
  timestamp: "2026-02-19T10:30:00Z"
}

// Published by: org-core (on metadata/settings changes)
{
  type: "organization.updated",
  organization_id: "org_abc123",
  changes: {
    name: "Acme Corporation",
    slug: "acme-corporation"
  },
  updated_by: "user_xyz789",
  timestamp: "2026-02-19T11:00:00Z"
}

// Published by: org-core (on plan upgrades/downgrades)
{
  type: "organization.plan.changed",
  organization_id: "org_abc123",
  organization_name: "Acme Corp",
  previous_plan: "free",
  new_plan: "pro",
  changed_by: "user_xyz789",
  change_reason: "Upgraded to unlock SSO",
  timestamp: "2026-02-19T12:00:00Z"
}

// Published by: org-core (on soft delete or purge request)
{
  type: "organization.deleted",
  organization_id: "org_abc123",
  name: "Acme Corp",
  timestamp: "2026-02-20T09:00:00Z"
}
```

#### User Events (auth-core)

```typescript
// Published by: auth-core (on user registration)
{
  type: "user.created",
  user_id: "user_xyz789",
  email: "john@acme.com",
  name: "John Doe",
  role: "user",
  verified: true,
  timestamp: "2026-02-19T10:00:00Z"
}

// Published by: auth-core (on profile updates)
{
  type: "user.updated",
  user_id: "user_xyz789",
  email: "john@acme.com",
  changes: {
    name: "John D. Doe",
    phone_number: "+1234567890"
  },
  timestamp: "2026-02-19T14:00:00Z"
}
```

#### Organization Membership Events (auth-core)

```typescript
// Published by: auth-core (when user added to org)
{
  type: "organization.member.added",
  organization_id: "org_abc123",
  organization_name: "Acme Corp",
  user_id: "user_xyz789",
  user_email: "john@acme.com",
  role: "member",
  invited_by: "user_owner123",
  timestamp: "2026-02-19T10:30:00Z"
}

// Published by: auth-core (when user removed from org)
{
  type: "organization.member.removed",
  organization_id: "org_abc123",
  organization_name: "Acme Corp",
  user_id: "user_xyz789",
  user_email: "john@acme.com",
  removed_by: "user_owner123",
  timestamp: "2026-02-20T08:00:00Z"
}
```

### NATS Streams Configuration

```yaml
USER_EVENTS:
  subjects: ["user.>", "session.>"]
  retention: 7 days
  storage: File
  
ORGANIZATION_EVENTS:
  subjects: ["organization.>"]
  retention: 7 days
  storage: File
```

## 🔄 Convex: Read-Only Projection Layer

Convex **subscribes** to Control Plane events and maintains a **derived copy** of org/user data for:
1. Multi-tenant scoping of conversations
2. Fast user lookups for real-time features
3. Organization context for AI sessions

### Convex Schema (Read-Only Fields)

```typescript
organizations: defineTable({
  externalOrgId: v.string(),  // ← Control Plane org ID (READ-ONLY)
  name: v.string(),            // ← Synced from Control Plane
  slug: v.string(),            // ← Synced from Control Plane
  
  // Convex-specific settings (WRITABLE)
  settings: v.optional(v.object({
    maxTokens: v.optional(v.number()),
    defaultModel: v.optional(v.string()),
  })),
  
  // Sync metadata
  syncStatus: v.union(v.literal("syncing"), v.literal("synced"), v.literal("deleted")),
  lastSyncedAt: v.number(),
})

users: defineTable({
  externalAuthId: v.string(),  // ← Control Plane user ID (READ-ONLY)
  email: v.string(),            // ← Synced from Control Plane
  name: v.optional(v.string()), // ← Synced from Control Plane
  orgId: v.id("organizations"), // ← Synced from Control Plane
  role: v.union(...),           // ← Synced from Control Plane
  
  // Sync metadata
  syncStatus: v.union(v.literal("syncing"), v.literal("synced"), v.literal("deleted")),
  lastSyncedAt: v.number(),
})
```

### What Convex Can Do

✅ **Read** organization and user data (from synced projection)  
✅ **Subscribe** to NATS events and update its local copy  
✅ **Write** conversation and message data (Convex owns this)  
✅ **Query** multi-tenant data scoped to organization  

### What Convex CANNOT Do

❌ **Create** organizations (must go through auth-core)  
❌ **Update** organization plan, quotas, or billing (must go through org-core)  
❌ **Modify** user email, authentication, or roles (must go through auth-core)  
❌ **Delete** users (GDPR deletion must go through control plane)  
❌ **Change** role mappings or permissions (must go through org-core)

## 🔒 GDPR & Hard Delete Flow

### User Deletion (GDPR Right to be Forgotten)

```
1. Request received → auth-core API endpoint
2. auth-core validates request (admin permission, user consent)
3. auth-core calls PostgreSQL function: gdpr_hard_delete_user(user_id)
4. PostgreSQL function:
   - Deletes all sessions
   - Deletes all OAuth accounts
   - Deletes 2FA secrets
   - Removes from all organization memberships
   - Deletes API keys, bearer tokens
   - Finally deletes user record
5. auth-core publishes NATS event: user.deleted
6. Convex receives event → soft-deletes user projection:
   - Sets syncStatus = "deleted"
   - Sets deletedAt timestamp
   - Applies the deletion action from the privacy event to conversations, messages, and jobs
   - Hard delete is required when content is in scope
   - Pseudonymization is allowed only when a documented retention exception applies
```

### Organization Deletion (Full Data Purge)

```
1. Request received → org-core API endpoint
2. org-core validates request (owner permission, confirmation)
3. org-core calls PostgreSQL function: gdpr_hard_delete_organization(org_id)
4. PostgreSQL function:
   - Deletes quotas, billing, compliance settings
   - Deletes role mappings
   - Deletes plan history
   - Finally deletes organization record
5. org-core publishes NATS event: organization.deleted
6. Convex receives event → soft-deletes org projection:
   - Sets syncStatus = "deleted"
   - Applies the deletion action to conversations, messages, and jobs
   - Hard delete is the default after retention expires
   - Archival or pseudonymized retention requires a documented legal, billing, security, or audit exception
7. auth-core receives event → removes org-related data:
   - Deletes all member relationships
   - Deletes pending invitations
```

## 📊 Data Boundary Summary

| **Data Type**              | **Owner**          | **Convex Access** | **Modification** |
|----------------------------|--------------------|-------------------|------------------|
| Organization ID            | auth-core          | Read-only         | Control Plane    |
| Organization Name/Slug     | auth-core/org-core | Read-only         | Control Plane    |
| Plan & Quotas              | org-core           | Read-only         | Control Plane    |
| Billing & Compliance       | org-core           | Not synced        | Control Plane    |
| Role Mappings              | org-core           | Not synced        | Control Plane    |
| User ID & Email            | auth-core          | Read-only         | Control Plane    |
| User Authentication        | auth-core          | Not synced        | Control Plane    |
| User Sessions              | auth-core          | Not synced        | Control Plane    |
| Organization Membership    | auth-core          | Read-only         | Control Plane    |
| **Conversations**          | **Convex**         | **Read-write**    | **Convex**       |
| **Messages**               | **Convex**         | **Read-write**    | **Convex**       |
| **Jobs (RAG, etc.)**       | **Convex**         | **Read-write**    | **Convex**       |

## 📝 Developer Guidelines

### When to use Control Plane APIs
- Creating/updating organizations
- Changing subscription plans
- Managing quotas or billing
- Updating user profiles or authentication
- Adding/removing organization members
- Configuring compliance settings
- GDPR deletion requests

### When to use Convex APIs
- Creating conversations
- Sending/receiving messages
- Starting RAG indexing jobs
- Streaming AI responses
- Real-time chat features

### Migration from Old to New Events

The Control Plane supports **dual-publish mode** during migration:
- Old events: `auth.user.registered`, `auth.organization.created`
- New events: `user.created`, `organization.created`

Both are published simultaneously. Consumers should gradually migrate to new simplified event names.

## 🔒 GDPR Erasure + DSAR

GDPR right-to-erasure (Art. 17) and data-subject access (Art. 15) are wired by
invoking the GDPR stored procedures that already ship in the migrations.

### Endpoints

| Operation | Service | Endpoint | Proc called (DB) | Gating |
|-----------|---------|----------|------------------|--------|
| User hard erase (irreversible) | user-core | `DELETE /api/v1/users/:id/gdpr/erase` (body `{ "confirm": true }`) | `gdpr_hard_delete_user($1)` (auth_service) + local `users`/memberships delete | admin **or** self |
| User anonymize (softer) | user-core | `POST /api/v1/users/:id/gdpr/anonymize` | `gdpr_anonymize_user($1)` (auth_service) | admin **or** self |
| User DSAR export (Art. 15) | user-core | `GET /api/v1/users/:id/gdpr/export` | — (assembles profile + memberships + API-key metadata) | admin **or** self |
| Org hard erase (irreversible) | org-core | `DELETE /orgs/:id/gdpr/erase` (body `{ "confirm": true }`) | `gdpr_hard_delete_organization($1)` (org_core) | org **owner** or platform admin |
| Org soft delete (reversible) | org-core | `DELETE /orgs/:id/gdpr/soft-delete` | `soft_delete_organization($1)` (org_core) | org **owner** or platform admin |
| Org purge (retention cron) | org-core | daily goroutine (`ORG_PURGE_DAYS`, default 30) | `purge_old_deleted_organizations($1)` (org_core) | n/a (background) |

All proc calls bind the id as `$1` — never string-interpolated. Irreversible
operations require an explicit `confirm: true` body flag. `gdpr_hard_delete_user`
/ `gdpr_anonymize_user` live in the **auth_service** DB, so user-core opens a
second pool via `AUTH_DATABASE_URL` (disabled with a clear error when unset).

### Audit (durable, via the shared bus → audit-core)

Every erasure/DSAR op emits a `velion.audit.v1.control.*` event (mirrors
auth-core's `publishVelionAudit` shape: `occurred_at, org_id, user_id,
actor_role, plane:"control", event, subject, resource_id, outcome, details`):

- `velion.audit.v1.control.erasure` — user/org hard erase + anonymize + org soft-delete
- `velion.audit.v1.control.dsar_export` — DSAR export (read)

### Cross-plane erasure fan-out (emit-only MVP)

On an irreversible user/org erasure, the originating core publishes:

```
subject: velion.gdpr.erasure.requested
payload: { subject_type, subject_id, org_id, requested_by, ts }
          subject_type ∈ { "user", "organization" }
```

so downstream planes can purge their own copy of the subject's data.
**Subscribers are a documented follow-up (not yet built):**

- **Model Plane** — purge run history / sessions / conversations for the subject.
- **Data Plane v2** — purge documents/chunks/embeddings/source-traces owned by the subject/org.

Until those subscribers exist, the event is emitted but not consumed; the
Control Plane-side erasure (auth + user + org rows) is already complete.
