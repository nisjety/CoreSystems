The owner approved the decisions P1 to P3 on 2026-10-10 (see [Decisions](#decisions)); the decisions marked *open* need the owner's confirmation before the build goes past the raw store. The raw store and the day-window sync are built (see [Raw store and day-window sync](#raw-store-and-day-window-sync)); on 2026-10-10 their database tests passed for the first time, against PostgreSQL 16.14 (see [Verification status](#verification-status)). ## Purpose

Catch public tenders, make them clean, validated and traceable to their source, and let the Model Plane assess and act on them. The benchmark for the product is Cobrief's workflow: find, assess (go/no-go with every claim cited to the tender text), write, manage the pipeline, market insight. Its edge is not the notice feed but reading the full tender documents with per-claim citations; the feed is the easy part.

## Pipeline

Each stage has a gate. Nothing reaches the next stage, and nothing reaches Verevon, without passing the previous one.

| # | Stage | Package | What it does | Gate |
|---|---|---|---|---|
| 1 | Capture | `sources/*` | Fetch from Doffin Public API, Doffin CSV, TED; store the **raw** notice immutably with its SHA-256 | Raw bytes and hash stored before anything else touches them |
| 2 | Parse | `eforms` | eForms XML to the canonical model. SDK-version-aware; unknown version fails closed | Parses without guessing |
| 3 | Normalise | `normalize` | CPV, NUTS, currency, dates and time zones, organisation numbers (Brønnøysund), text clean-up. Records provenance of every change | Every correction is explainable |
| 4 | Validate (deterministic) | `validate` | Code lists, cross-source reconciliation (XML vs Doffin search record vs TED), lifecycle consistency. Produces a machine-readable Report | Report has no blocking finding |
| 5 | Validate (AI) | Model Plane | Second opinion on semantics. Consumes the Report as evidence; never rewrites canonical fields | Verdict carries evidence spans |
| 6 | Publish | `lifecycle` + Data Plane | Group into procedures, version, emit to Data Plane and events | Only validated notices are visible |
| 7 | Act | `match`, `actions` | Tenant matching, alerts, typed operations for the Model Plane | Outward effects need human approval |

There is no LLM call inside this service. Stage 5 is a work item sent to the Model Plane and a verdict ingested back, as in finspo-core.

## Identity and lifecycle

The model is **procedure -> notice (+ versions) -> lot**, following DFØ's identifier rules (see [SOURCES.md](SOURCES.md#identifier-model-dfø-notice-identifiers-v01-2026-02-17)). Group by `procedure-identifier`; identify a notice version by (`notice-identifier`, `notice-version`); the Doffin id and the TED publication number are lookup aliases, never identity. The existing Quarry `procurement` package keys on a notice id only, which is fine for a raw snapshot but wrong as the domain model.

## What the first live run changed

Measured on 2026-10-09 (details and numbers in [SOURCES.md](SOURCES.md)). Each point is a design consequence, not just a fact.

- **The identity model holds across sources.** 19 of 22 Doffin notices were found in TED on the same `notice-identifier`, all 19 with the same version and 18 of 18 with the same `procedure-identifier`. De-duplication on (`notice-identifier`, `notice-version`) works; no publication number is ever identity.
- **Never trust the content type.** Doffin labels every download `application/octet-stream`. The format is decided by looking at the body (`eforms.Sniff`), and a body that is not eForms is refused rather than guessed at.
- **One format family, several shapes.** Three document roots (`ContractNotice`, `ContractAwardNotice`, `PriorInformationNotice`), three flavours (`eu`, `national-e` seen, `national` not yet seen) and SDK versions 1.7 to 1.14, including the converted 2017 history. The parser is a set of field maps selected by (root, SDK version, flavour), not one parser.
- **The search window is 1000 hits.** `numHitsAccessible` is capped at 1000 against 159 833 in total, so every crawl slices by date window. A one-day window always fits.
- **The API summary is not the notice.** It lacks per-lot deadlines, the question deadline, tender-opening time, award criteria and weights, and the parties. The XML is the source of truth; the summary is a cross-check, and the reconciliation rules in SOURCES.md become validation findings.
- **Real data is dirty.** A company *name* sat in an organisation-number field; organisation numbers arrive with spaces; `deadline` means something else on result notices. Such cases are findings the validation gate reports, never exceptions that stop the pipeline.
- **Notices carry personal data.** Contact persons' names, e-mail addresses and telephone numbers are in clear text.
- **Tenders are bid for elsewhere.** Documents and submission live on Mercell (12 of 22), EU-Supply, Ivalua, Artifik, Achilles or the buyer's own site. Doffin only registers the notice.

## Tenancy and retention

Public notices are **shared** data: ingested once into one corpus. A single Doffin subscription is one global budget (search 30/min, download 10/min), so tenants never trigger live Doffin calls; they read the corpus. Everything tenant-specific (company profile, go/no-go criteria, shortlists, drafts, uploaded documents) is tenant-scoped, carries the organisation id, and carries the tenant's retention posture (ZDR) through every content-persisting boundary. ZDR does not apply to the shared corpus itself (P2 in [Decisions](#decisions)).

**Personal data in public notices.** The contact fields are personal data even though the notice is public. They are classified as such when parsed, are left out of AI inputs by default (validation does not need them), and are shown only to a user with a reason to contact the buyer. The retention and erasure rules that apply to tenant data apply to a copy of these fields held for a tenant. The lawful basis, retention and erasure for the corpus's own copy are open (O1 under [Open owner decisions](#open-owner-decisions)).

## Rate budget

Token bucket per operation (burst 1, so calls are evenly spaced), `Retry-After` honoured, and a back-off gate shared by every caller after a 429. Defaults keep 20% headroom (24 search, 8 download per minute).

Measured volume is about 45 notices per calendar day on average and about 100 on a busy recent day, so steady state is cheap: one day-window search plus about 100 downloads, roughly 13 minutes of the download budget. History is the expensive part. (The window count below is one search pass per day. The sync pages a full day twice, which roughly doubles its search cost; see [Completeness of a day](#completeness-of-a-day).) Searching every day since 2017 is about 3 600 windows (2 to 7 hours), but downloading all 159 833 notices at 8 per minute would take about two weeks, so history comes from search metadata and the year CSV, and XML is fetched for recent, active or matched notices only.

## Raw store and day-window sync

Status (2026-10-10): built. The pure tests pass, and the database tests passed against PostgreSQL 16.14. The code is `internal/doffinsync` (the engine), `internal/rawstore` (the Postgres store and the budget lock), `internal/db` (the pool, the migrations and the DSN TLS rule, `db.CheckTLS`), `internal/config` (`LoadSyncFrom`) and `cmd/doffin-sync` (the CLI), with migrations `0002_raw_store.sql` to `0006_redaction.sql`. It is a host-side command: it serves no HTTP, runs no scheduler, and the design gives it no compose service. The Dockerfile builds `cmd/api` only. [Verification status](#verification-status) says exactly what has run.

The sync keeps what Doffin returns, byte for byte, before anything parses it. It walks the public search index one UTC day at a time, keeps every search response it reads, and downloads each notice once. It does not parse eForms, normalise, reconcile with TED or read contact fields. The raw layer is evidence and lives in this plane's own database; the parsed, validated tender is knowledge and goes to Data Plane v2 through its contracts (P1). How to run it: [REQUIREMENTS.md, section 9](REQUIREMENTS.md#9-raw-store-sync).

**Migrations and triggers.** Migrations 0002 to 0006 give six tables and thirteen triggers: the six append-only guards (0002), the run provenance guard (0003), the three evidence run guards (0005), and for 0006 the two append-only guards of the tombstone table and the guard against a row that arrives redacted. 0001 is an empty baseline. 0004 adds `sync_days.rejected` and replaces the `sync_days` constraints `sync_days_done_adds_up` and `sync_days_capped_is_saturated` under their old names. 0006 adds `raw_documents.redacted_at`, replaces the two column checks that forbid an erased body under their old names, adds the tombstone table, the redaction function and a view of the bodies still held (`raw_documents_live`), and re-points the existing `raw_documents` UPDATE and DELETE trigger at a new guard function under the same trigger name. Migrations are forward-only: an earlier file is never edited. `TestMigration0002Shape`, `TestMigration0004Shape`, `TestMigration0005Shape` and the tests of `redaction_*_test.go` check these shapes against a live server. The two relaxed checks of 0006 and its new one are added `NOT VALID`: they hold for every row written from then on, and the migration does not scan the existing bodies, which would hash every one of them under an exclusive lock on `raw_documents`, for minutes on a full corpus, and could find nothing, because every existing row already satisfied the stronger checks of 0002. `ALTER TABLE raw_documents VALIDATE CONSTRAINT <name>` marks them validated later, under a lock that does not block the sync (`TestMigration0006UpgradesADatabaseThatAlreadyHoldsNotices` runs it against old rows). The migration still takes a short exclusive lock to add the column.

A failed search leaves no row of its own. Its body is kept if one arrived intact, and the failure is recorded only as the day's state in `sync_days`.

**Append-only.** On each evidence table, a row trigger refuses `UPDATE` and `DELETE`, and a statement trigger refuses `TRUNCATE`. Each raises SQLSTATE 23001 (`restrict_violation`). The one exception is `TRUNCATE` of `raw_documents`: PostgreSQL refuses it first, with SQLSTATE 0A000, because `download_attempts` references the table, and the rows survive either way. The database test accepts either code, so the live run (PostgreSQL 16.14, 2026-10-10) verified the refusal and the surviving rows, not which code came back. `INSERT ... ON CONFLICT DO NOTHING` never runs an `UPDATE`, so deduplication does not trip the append-only trigger. The one exception to the refusal of an `UPDATE` is a redaction of `raw_documents` made by `anbud_redact_raw_document()` (0006, [PERSONAL-DATA.md](PERSONAL-DATA.md)): the trigger admits exactly that transformation while the function's transaction-local door names the row and its tombstone is written, and refuses every other change. A static test scans the store's SQL strings: none that names an evidence table may contain UPDATE, DELETE, TRUNCATE, ALTER or DROP.

The triggers stop application code and accidents. They are a security boundary only when the sync runs as the application role of the role model (`anbud_app`, [ROLES.md](ROLES.md), decision H6), which owns nothing and so cannot drop or disable them. With one DSN whose role owns the tables or is a superuser, which is what a development database still does, they stop application code and accidents and no more.

**Write gating.** Writes from a run that is no longer running are refused with `ErrStaleWrite`. The ledger writes (starting a day, finishing a day, finishing a run) are refused by the store's SQL when they change no row. The evidence writes (search pages, bodies, attempts) are refused by the database. Migration 0005 puts `evidence_run_guard()` on each evidence table as a `BEFORE INSERT` row trigger. It refuses a row unless its `run_id` names a run in state `running`, with SQLSTATE 55000 (`object_not_in_prerequisite_state`); a run id that names no run is refused too. It reads the run row with `FOR SHARE`, so ending a run and inserting evidence serialise: a run cannot end while an insert is in flight under it, and an insert that waits for a run that is ending is refused once the run has ended. The message names the table and the run id and never row data. The store maps the refusal to an error that wraps `ErrStaleWrite` and keeps the database error. The trigger fires before `ON CONFLICT` looks for a conflict, so a duplicate row under a run that has ended is refused too, not skipped. How the engine reacts is under [Known gaps](#known-gaps).

**Run binding.** `FinishDay` writes a day only while the day is `running`, its `last_run_id` is the run the caller names, and that run is still `running`. A day that recovery interrupted, a run that has ended, or a day that another run began is refused with `ErrStaleWrite`, and its row keeps its state. `FinishRun` is tried up to three times. A stale write after an earlier failed try is treated as success, because that earlier try committed before it returned its error. A stale write on the first try is returned as an error and is not retried. Still open: `FinishDay` is not retried.

### Window and closed days

- A window is an inclusive range of UTC calendar days. Each day `D` is one search with `issueDateFrom = issueDateTo = D`, sent from a UTC midnight, so the label is the UTC date. Europe/Oslo is not used anywhere in the algorithm. The two parameters filter by each notice's `publicationDate`, a plain date, not by its `issueDate` timestamp (smoke test, 2026-10-10; see [SOURCES.md](SOURCES.md)), so a day is a publication day.
- A window is refused when a bound is not a UTC midnight, when the start is before 2017-01-02 (the first day of the public corpus), when the start is after the end, or when the end is later than UTC yesterday. Only closed days are synced. A day still in progress grows while it is paged, which would break the completeness rule below. UTC yesterday is closed in every zone at or ahead of UTC. A zone behind UTC would need more margin (open question 7 in [SOURCES.md](SOURCES.md)).
- The work set is every day in the window that is not `done`. With `-recheck N` (sync mode), it also holds the last N days of the window even when done. A recheck searches again and downloads only ids not yet held; a terminal rejection is counted again from its history and costs no download. Census mode skips done days. A rerun of a done window makes no calls.
- The one-day filter and the closed-day rule rest on Doffin's date bounds including their day at both ends. V1 checked that live on 2026-10-10, on four day pairs (see [SOURCES.md](SOURCES.md)).

### Completeness of a day

For a day with total `T` (`numHitsTotal`) and accessible `A` (`numHitsAccessible`):

1. Search page 1 with `numHitsPerPage = 100` and `sortBy = PUBLICATION_DATE_ASC`. The response bytes are stored before anything reads them.
2. If `T > A`, the day is `capped` with `saturated`: no further paging, no downloads, no notice rows.
3. If `T < A`, the day is `partial` with `count_mismatch`.
4. If `T = A`, the day is paged in sweeps. A sweep reads pages `1` to `ceil(A/N)`, where `N` is the page size: 100, unless `-page-size` says otherwise. Every page of every sweep must report the same `T` and `A` as the first page, or the day is `partial` with `count_changed`. An empty page before the last is `partial` with `count_mismatch`. The ids of all sweeps go into one set, in first-seen order. The day's ids are complete once at least two sweeps have run and the set holds exactly `T` ids. More than `T` distinct ids means the day changed under the sweeps: the sweep stops at the page that passes `T`, and the day is `partial` with `count_changed`. A day of one page cannot be reordered across a page boundary, so every sweep of it must hold the whole day by itself: a sweep with fewer than `T` distinct ids leaves the day `partial` with `count_mismatch` at once, as the two strict passes did. A set still below `T` after `maxSweeps` (8) sweeps leaves the day `partial` with `count_mismatch`, and the next run starts again. Downloads follow the set. Before any of this, an `A` above 1000, the cap Doffin documents, is `partial` with `count_mismatch` and nothing is paged: such counts are not a day the sync understands.
5. If `T = 0`, the day is `done` with zeros. Two sweeps still run.

Why at least two sweeps: comparing each page with the first page alone misses a notice that leaves while another arrives, because the total stays the same. A second sweep closes that gap, because a notice that arrived would push the set past `T`. Why a union and not two sweeps that each hold `T` and agree, which was the first version of this rule: Doffin does not keep tied hits in one order between requests. The live smoke test (V2, 2026-10-10) found one sweep with all 94 ids of a day and the next with 65 distinct ids and 29 repeats, at 25 per page, while the union of the two held all 94. Requiring every sweep to be perfect would leave such a day partial on most runs, and a longer day would fare worse. A set that reaches exactly `T` ids proves that every notice search reports for the day was seen, whichever sweep saw it, provided the day's membership holds still while it is swept. A withdrawal and an arrival in the same moments would leave `T` unchanged and one notice unseen, and a recheck would find it, because it downloads whatever is not yet held (no scheduler runs one yet). The rule proves completeness only against what search returns: a notice that search never returns is invisible to it. A day that fits on one page is not affected, and every day sampled so far did. How many days need several pages, and how many sweeps they need, stays open until the census (V5).

Cost: a day with `T = A` costs at least `2 × ceil(A/N)` searches and at most `8 × ceil(A/N)`, so a day of one page costs two. A census of the 94-hit day at 25 per page needed three sweeps, 12 searches. Each day line reports its own `searches`, so a census shows how many sweeps every day needed (searches divided by pages). Identical page bytes are stored once, because the unique key includes the body hash. A sweep whose page differs by a single byte adds a row, and `allTypes` listing its elements in another order does that (see [SOURCES.md](SOURCES.md)).

### Saturation (days over 1000 hits)

Doffin's `numHitsAccessible` caps at 1000 per query, while `numHitsTotal` can be far larger (159,833 in total against 1,000 accessible in the sample). The engine keys on `T > A`, not on `A = 1000`, so any day where the accessible count is below the total is flagged. Such a day is `capped` with `saturated`. It is flagged, not completed: no downloads and no notice rows for that day. A capped day is searched again on each run and stays capped. The rule rarely applies: the busiest day sampled had about 100 notices.

Rejected alternatives: downloading the 1000 accessible would fetch a subset chosen by the sort order, and cost about 125 minutes for one day. Splitting by estimated value fails because it is null on 53 of 100 sampled notices. Splitting by type fails because the list of types is undocumented. Splitting by status fails because only competition notices carry one. How to complete a capped day is an open owner decision.

### Downloads and the error policy

Candidates for download on a day, in first-seen order:

- **Held:** a raw row exists for the id. Counted `held`, and never downloaded again.
- **Rejected, terminal:** the id was refused for its content (`too_large` or `empty_body`) three times (`MaxRejections`), and its latest definitive attempt was one of those refusals. Counted `rejected`, in a bucket of its own, and never downloaded again. The day can be done.
- **Rejected, cooling:** fewer than three refusals, and the latest under 24 hours (`RejectCooloff`) old by the engine's clock. Counted unresolved with `item_rejected`. It is not downloaded, makes no attempt row, spends no budget and does not touch the consecutive-error count. The day stays `partial`.
- **Rejected, eligible:** fewer than three refusals, and the latest 24 hours old or older. Downloaded like any other candidate.
- **Malformed:** the id does not have Doffin's shape. It is never sent. It is counted unresolved with `item_rejected`, with no attempt row and no budget, because no attempt happened (D-A).
- **Not found, old day:** the id's latest definitive attempt was a 404 and the day is at least `NotFoundGrace` (7 days) old. Counted `not_found`, terminally.
- **Otherwise:** downloaded.

**Precedence.** `Resolve` reports facts and applies no policy. A held id (a raw row exists) beats everything, so it is never downloaded again, whatever else happened to it. Otherwise the most recent definitive attempt decides between not found and rejected. The definitive outcomes are `not_found`, `too_large` and `empty_body`, and the most recent is the one with the highest attempt row id, which is append order. The transient outcomes (`http_error`, `transport_error`, `rate_limited`, `unauthorized`, `invalid_id`) are ignored. So a 404 followed by a refusal is rejected, and a refusal followed by a 404 is not found. For a rejected id the store also reports how many refusals it has ever had and the instant of the latest. The engine applies the policy with its own clock (`Options.Now`), the clock that stamped those instants. This replaced the earlier fixed order held, then not found, then rejected. The rule is pinned by the database test `TestResolvePrecedenceHeldThenLatestDefinitive` in `internal/rawstore`, which passed on 2026-10-10 (see [Verification status](#verification-status)).

**Bounded retry (D-B2).** A notice refused for its content is asked for again, up to three refusals in all, each at least 24 hours after the one before. The third refusal makes it terminal, so a notice that Doffin keeps refusing completes its day no sooner than 48 hours after its first refusal, and only if the sync runs again then. The pure engine tests in `internal/doffinsync/rejection_policy_test.go` pin the policy. `TestRejectedNoticeIsRetriedThenTerminalThroughTheRealStore` (`internal/rawstore`) and `TestCLICountsTheThirdRefusalAsRejected` (`cmd/doffin-sync`) check it end to end with the real store and database. Terminal is permanent; see [Known gaps](#known-gaps).

Search outcomes:

| Search outcome | Day | Run |
|---|---|---|
| Run cancelled | `interrupted`, `cancelled` | `cancelled` (exit 5) |
| 401 or 403 | `failed`, `unauthorized` | `key_rejected` (exit 4) |

| Anything else (5xx, transport, too large, empty) | `failed`, `search_failed` | counted |

**Consecutive counter.** Five counted errors in a row end the day as `failed` with `consecutive_errors`, and the run as `failed` (exit 6). The counter resets on a successful search page and on a stored or duplicate download. A refused body (too large or empty) neither counts nor resets it. A 404, a 429, an authorisation failure, a malformed id, a cancelled call and a cooling or terminal rejected id (which makes no call) count nothing.

**Client retries.** The client absorbs a 429 itself: up to two retries, honouring `Retry-After` up to two minutes. Only longer waits reach the engine. Those internal retries are invisible to the engine's counters, so per-run request counts are lower bounds.

**Store failures.** A failed write of a search page, a notice or an attempt ends the day as `failed` with `store_failed`, and the run as `failed` (exit 6). A write that fails because the run was cancelled is recorded as cancelled instead (D-B8). The lost body is downloaded again on the next run. A write that the database's run guard refuses (see Write gating) is a store failure too.

**Retry instant.** A 429 stores `sync_runs.retry_after_until` as the process clock plus `Retry-After`. The next start reads the latest stored instant and makes no call while it is in the future (exit 3, run id 0). The store compares no times; the caller does, with its own clock (D-B4).

Attempt messages are fixed text or the client's sanitised message, clipped to 256 characters. Raw error text is never stored, because it can contain request URLs. Non-2xx bodies are not stored at all (P3).

### Budget lock, heartbeat and signals

- **Single writer.** A session advisory lock, `0x646F666673796E63` ("doffsync"), is taken with `pg_try_advisory_lock` on a connection removed from the pool (`Hijack`) and never returned to it, because a pooled connection would pass the lock to its next user. A second sync exits 7 without calling Doffin. The migration lock is separate (`0x616e6275646d6967`, transaction-scoped).
- **Recovery.** Once the lock is held, rows a dead process left `running` are marked `interrupted` (runs), and `interrupted` with `process_lost` (days). Finished rows are not touched.
- **Heartbeat.** A running sync checks the budget lock every second: its session must be alive and must hold the lock. Each check is bounded by a separate five-second ping timeout, so a healthy but slow ping is not read as a lost lock, and a hung ping is cut off within five seconds. A failed check cancels the run, and the CLI exits 5. Between a session death and the next failed check, the run can make at most one more call; the next call is refused once the flag is set (`lockGuard`).
- **Signals.** The first SIGINT or SIGTERM cancels the run. The run winds down, records the day as `interrupted` and the run as `cancelled`, and exits 5. A second signal exits at once with 5, without unlocking. The session then ends, and PostgreSQL frees the lock.
- **Killed process.** Its session ends, so PostgreSQL releases the lock. The next start recovers the rows.

**The probe.** `cmd/doffin-probe` takes the same lock whenever `ANBUD_DSN` is set and names the database the sync uses. It checks the DSN with the shared strict TLS rule (`db.CheckTLS` in `internal/db`, the rule the sync applies), opens a pool without applying any migration or writing a row, and takes the lock with `TryLock` before its first Doffin call. It holds the lock for its whole run and releases it on every exit path except a signal kill, where the closing of its database session frees it. If another sync holds the lock, the probe makes no Doffin call and exits 7, the code of the sync CLI. It has no lock-loss heartbeat, which the sync has. When `ANBUD_DSN` is unset the probe takes no lock, says `budget lock: not taken (ANBUD_DSN is not set); do not run this while a sync is running` in its header, and can spend the same key's budget while a sync runs.

### Budget arithmetic

Pacing: download, 8 per minute, is 7.5 s per call; search, 24 per minute, is 2.5 s per call. The two limiters are separate and the engine makes one call at a time, so their times add. Download capacity is 8 × 60 × 24 = 11,520 per day.

| Quantity | Calculation | Result |
|---|---|---|
| Typical day | 159,833 notices / 3,567 days = 44.8; 44.8 × 7.5 s = 336 s, plus two searches (5 s) | about 6 minutes (5.7) |
| Busy day | 100 × 7.5 s = 750 s, plus two searches | about 12.6 minutes |
| Saturated day | no downloads; one search | 2.5 s |
| Whole corpus, downloads | 159,833 × 7.5 s = 1,198,748 s | 333 hours, about 13.9 days of continuous downloads |
| Whole corpus, search, one pass (the plan's figure) | 3,567 to 5,165 searches × 2.5 s | 2.5 to 3.6 hours |
| Whole corpus, search, two sweeps (derived, not measured) | the one-pass counts, roughly doubled; more for any day that needs a third sweep or more | about 5.0 to 7.2 hours, plus the extra sweeps of multi-page days |
| Full serial backfill | 333 hours + 5.0 to 7.2 hours | 338 to 340 hours, about 14.1 days |
| Daily run with `-recheck 4` (not scheduled) | 4 rechecks × 2 searches × 2.5 s, plus about 45 new downloads (5.6 min) | about 6 minutes |

Storage: search pages were measured at about 2.8 KiB per hit on 2026-10-10 (a page of 19 hits was 54,881 bytes), against the sample's 2.45 KiB, so about 0.43 GiB for one copy of the corpus. A page that comes back with different bytes is stored again, so a torn sweep or a reordered `allTypes` adds copies; that overhead is not measured. Notice bodies are 8 KB to 540 KB each, about 1.3 GB to 86 GB for the corpus (the two the sync stored were 25 KB and 33 KB). Compression is not measured.

A partial day is searched again on every run until it resolves. A cooling rejected notice, or a 404 inside the grace period, keeps its day partial, so the day's searches recur on each run, though a cooling notice costs no download. A notice refused for its content costs at most three refused downloads, at least 24 hours apart, before it is terminal and lets its day complete.

### Decisions

Recorded after the design review. The labels are the ones the code comments use; the retry policy and the run guard appear in the code and its tests as R1 to R6. P1 to P3 are policy decisions the owner approved on 2026-10-10 and have no code label.

| Label | Decision |
|---|---|
| D-A | A malformed notice id is never sent to Doffin. It is counted unresolved with `item_rejected` and gets no attempt row, because no attempt happened. The database refuses such a row anyway. |
| D-B1 | The consecutive-error counter resets on any successful search page or download. Counted: search failures other than unauthorized, rate limit, invalid parameters, not found and cancel; download transport and HTTP errors of any status. Not counted: too large, empty body, malformed ids, 404, rate limit, unauthorized and cancel. |
| D-B2 | A notice whose download was refused for its content (too large, or an empty body) is retried a bounded number of times (R1 to R5). The store reports facts: how many refusals the id has had and when the latest was. The engine applies the policy with its own clock. Fewer than `MaxRejections` (3) refusals and the latest under `RejectCooloff` (24 hours) old: the id is cooling, unresolved with `item_rejected`, with no download and no attempt row. Fewer than 3 and the latest 24 hours old or older: it is downloaded again. The third refusal is terminal, in the same run: the id counts in `sync_days.rejected`, so its day can be done, and it is never downloaded again. Terminal is permanent. This replaced the earlier rule on 2026-10-10: never downloaded again, and its day stays partial. |
| D-B3 | A day with total equal to accessible is swept page by page at least twice, and its ids are the union of the sweeps. The day is complete when the union holds exactly the total. Revised on 2026-10-10 after V2: the first version needed two sweeps that each held the total and agreed with each other, and a single torn sweep broke it, because Doffin does not keep tied hits in one order between requests. At most 8 sweeps (`maxSweeps`). A union above the total is `count_changed`, noticed at the page that passes it. A one-page day must hold its whole day in every sweep: a shortfall is a mismatch at once, with no further sweep. Zero-hit days get two sweeps too. The union proves completeness only while the day's membership holds still during the sweeps (see Completeness of a day). |
| D-B10 | The search page size is an option: `-page-size`, 1 to 100, default 100 (`Options.PageSize`). It exists so that the multi-page path can be tried live on a day of fewer than 100 hits, and it costs more searches. It is part of the stored page's query key (`perPage=N`), so pages of different sizes never share a label. |
| D-B11 | An accessible count above 1000, the cap Doffin documents, is not trusted: the day is `partial` with `count_mismatch` and is not paged (`maxAccessible`). A total above the accessible count is still a `capped` day (saturation). The guard also keeps a bogus count from sending the paging loop on without a bound. |
| D-B4 | `LastRetryAfter` returns the stored instant. The caller compares it with its own clock. The host writes and reads the instant, so there is one clock domain. |
| D-B5 | Writes from a run that is no longer running are refused with `ErrStaleWrite`: ledger writes, by the SQL of the write, and evidence writes, by the database. Migration 0005 refuses an insert into `raw_search_pages`, `raw_documents` or `download_attempts` unless its `run_id` names a run in state `running` (R6). |
| D-B6 | Migration 0003 makes the id, mode, window and start of `sync_runs` immutable. |
| D-B7 | An HTTP status outside 100 to 599 is stored as NULL. |
| D-B8 | A cancellation during a store write is recorded as cancelled, not `store_failed`. The same holds for the day ledger: a cancel that cuts off `BeginDay` or the read of the day states is a cancelled run, not a ledger failure. The lost body is downloaded again next run. |
| D-B9 | `FinishRun` is tried three times, with 100 ms and 200 ms back-off. `FinishDay` is tried once. |
| H2 | A heartbeat checks the budget lock every second, and each check is bounded by a separate five-second ping timeout. Once a check fails, every Doffin call is refused. The run is cancelled and the CLI exits 5. |
| H3 | A non-loopback database must verify the server certificate, judged by what pgx verifies from the TLS configuration it builds, not the literal `sslmode` string: `sslmode=verify-ca` or `verify-full`; `sslmode=require` with an `sslrootcert` CA file (pgx verifies the chain as verify-ca); or `sslrootcert=system` (pgx verifies as verify-full). Plain `require`, `prefer`, `allow` and `disable` are refused. The DSN must name exactly one host with no plaintext fallback, so any multi-host DSN with a non-local host is refused. Unix socket directories count as local. The rule is `db.CheckTLS` in `internal/db`: `cmd/doffin-sync` always applies it, and `cmd/doffin-probe` applies it when `ANBUD_DSN` is set. |
| H4 | The first SIGINT or SIGTERM cancels the run. A second signal exits at once with 5. |
| H5 | With `ANBUD_REQUIRE_DB_TESTS=1`, a missing `ANBUD_TEST_DSN` fails the database test instead of skipping it. |
| H6 | The role model (O2, [ROLES.md](ROLES.md)). `scripts/roles.sql` creates `anbud_migrator` (owns the database and every object), `anbud_app` (the sync and the probe: select and insert on the evidence tables, also update on `sync_runs` and `sync_days`, nothing else, owns nothing) and `anbud_dba` (a NOLOGIN group: select, execute on the redaction function of 0006, and temporary tables for a DBA's own work). The three roles are members of no role, and the script takes back any membership they hold. The script also takes `CONNECT`, `TEMPORARY` and `CREATE` on the database from PUBLIC, and refuses a database that is not named `anbud*`: one anbud database per cluster, because the role names are cluster-wide. `ANBUD_MIGRATE_DSN` is optional: when set, the migrations run through it and the engine writes through `ANBUD_DSN`, and `db.CheckTLSFor` applies the strict TLS rule to both. The migration runner restates the application role's table privileges after every migration run (`internal/db/privileges.sql`), on the relations it may change. `db.CheckRuntimeRole` judges the engine's role by what it can use or become, not only by what it is: a superuser, or a role with CREATEROLE, CREATEDB or BYPASSRLS, itself or through any role it is a member of; a member of a predefined role that reaches files, programs or other sessions, of the owner role or of the DBA group; or an owner, directly or through a role it belongs to, of any relation, function, schema on its search path or of the database, is refused with exit 1 when the DSN names a non-loopback host and gets one warning line on a loopback host; a role that cannot be read is exit 6. `db.CheckOwnerRole` applies the attribute and predefined-role part of that to the role of `ANBUD_MIGRATE_DSN`, before it migrates anything (the owner owns everything by design). No credential is in the repository. |
| H7 | Erasure of a notice body (the mechanism for O1; the legal decision is not made). `raw_documents` stays append-only. The one change it admits is a redaction made by `anbud_redact_raw_document(id, reason, request)` (migration 0006): a SECURITY DEFINER function owned by the migrator, executable by `anbud_dba` only, with its search path pinned and every name schema-qualified. In one transaction it writes a tombstone to `raw_redactions` (original hash and size, a reason from a fixed list, a ticket-shaped reference, `session_user`, time), empties the body and sets `redacted_at`; the row, its id and the original `body_sha256` stay, so the same bytes can never be stored again. It checks that its UPDATE changed exactly one row and otherwise fails with `XX000`, rolling the tombstone back with it. The trigger admits exactly that transformation, only while a transaction-local door names the row and the transaction and a matching tombstone exists; the door is no secret and grants nothing: the privilege layer is the boundary. `raw_documents_live` is the contract for readers such as the parser. Search pages, backups, logs and Data Plane v2 are not reached; [PERSONAL-DATA.md](PERSONAL-DATA.md) is the runbook and lists what is open. |
| P1 | Layering and the CoreSystem rule. The raw layer (Doffin bodies, search pages, download attempts, the run and day ledger) is evidence. It lives in the Ingestion Plane's own database, which fits `CoreSystem/CLAUDE.md` ("captures evidence"). Parsed, validated tenders are knowledge: they are published to Data Plane v2 through its contracts. anbud-core keeps only a publication cursor for idempotency and must not become the authoritative home of procedure, notice or lot tables. Reading a public API is not a provider action in the sense of the actions surface. Acting on tenders later (drafting, notifying, submitting) goes through integration-corev2's actions surface and the Model Plane. Approved 2026-10-10; it settles the former open decision 1. |
| P2 | Zero Data Retention. ZDR does not apply to the shared public corpus: it holds public-source data with no tenant content, and the schema has no tenant column (`TestNoTenantColumns` enforces that). ZDR applies fully to every tenant-scoped derivative: watchlists, go/no-go assessments, bid drafts and persisted model output for a ZDR organisation. Each carries the organisation id and the organisation's retention posture. Personal data in notices is a separate question (O1). Approved 2026-10-10; it settles the former open decision 2. |
| P3 | Non-2xx response bodies are not stored. Only the status and the client's sanitised message are kept: such bodies are API-management error pages with no corpus value, and they could echo request details. Approved 2026-10-10; it closes the former open decision 4. |

Deviations from the design table:

- `ErrInvalidParams` on a download is no longer an upstream error. It is refused before any call (D-A), and it is never counted toward five in a row. On search, invalid parameters still stop the run.
- `TRUNCATE` of `raw_documents`: the design assumed the trigger fires first. PostgreSQL refuses the statement first, with SQLSTATE 0A000, and the row survives. The database test accepts either code (see Append-only).
- Search responses are evidence too. `SearchResponse` gained `ContentType` and `FetchedAt`, an additive client change. `Search` now keeps the `Content-Type` header it used to discard.
- The attempt outcome `invalid_id` is in the database list and in the store's list, but no path writes it (D-A).
- Non-2xx bodies are not stored (P3).

### Known gaps

- `FinishDay` is not retried. A failed write leaves the day `running` until the next start recovers it.
- The engine does not tell a stale evidence write from any other store failure. A write that the run guard refuses (SQLSTATE 55000, wrapping `ErrStaleWrite`; see Write gating) ends the day as `failed` with `store_failed` and the run as `failed` (exit 6), as any failed write does; a cancelled run is recorded as cancelled instead (D-B8). Nothing retries it. When the run has been recovered, the day's and the run's own final writes are refused as well, so their rows keep the state that recovery gave them, and only the process's report and exit code say `failed`.
- A terminal rejection is permanent. An id refused three times is never downloaded again, even if Doffin would now serve it. The verdict is read from the append-only attempt rows and nothing in the application resets it, so undoing it takes a DBA procedure or a new migration. A code change of `MaxRejections` would also move the line, because the engine compares the stored count with the constant.
- The 404 history hides earlier refusals. When an id's latest definitive attempt is a 404, `Resolve` reports it as not found and does not report the refusals before it. If such an id is retried (its day is younger than 7 days) and refused again, the engine counts that refusal as the id's first. A refusal that is in fact the third then becomes terminal one run later than it could: the run counts it unresolved, and the next run reads three refusals from the history and counts it `rejected` without a download. The refusals never exceed three in total.
- *Scheduled on this Mac since 2026-10-28:* `scripts/install-daily-sync.sh` runs `scripts/daily-sync.sh` through launchd at 06:15 and at login: the last 14 closed days with `-recheck 4`, Doffin and then TED, into the local stack's `anbud_core` on loopback (REQUIREMENTS.md section 9.8). There is still no scheduler in the service or in compose, and the CLI default is `-recheck 0`.
- *TED is a second source since 2026-10-28* (`-source ted`, migration 0008, `internal/sources/ted`): the same engine, ledger and budget lock, TED's own day ledger and identifier, buyer countries NOR, SWE, DNK, FIN and ISL by default. Both sources share `sync_runs`, so a 429 from one pauses the next run of either until its retry instant (at most an hour). Readers give a TED notice the public id `TED-<publication number>` (`internal/noticeid`). A notice published on both Doffin and TED is held once per source, as evidence, and shown once (2026-10-28, `internal/demo/twins.go`): copies from the two sources with the same eForms notice identifier are one notice, the higher version wins and on a tie Doffin's copy, under the Doffin id the app already knows. Copies within one source are left to the amendment tracking. The catalogue, the matches and the radar apply it before they count anything, so an award held twice is one award in the win history. Changing the country set does not re-search days that are done: run the TED sync once with `-recheck` over the held window.
- A census overwrites the state and counts of any day that is not `done` with `searched` and zero counts. Its raw and attempt rows are untouched, and the next sync searches the day again.
- A census does the same searches as a sync, without the downloads. It sweeps full days at least twice, as a sync does.
- The union rule (D-B3) has been tried live on one multi-page shape only: 94 hits at 25 per page. No day over 100 hits has been seen, so the production page size has not been tried on a multi-page day. A day whose sweeps never reach the total in 8 sweeps stays `partial` and costs up to eight sweeps of searches on every run.
- A `stored` download attempt has a NULL `http_status`. The status is recorded for failures only.
- A DSN that names several hosts is refused only when one of them is not local. A DSN that names only loopback hosts, several of them, is accepted; no test covers that case.
- `SERVICE_NAME` is loaded into the sync configuration, but the CLI never uses it.
- The probe has no lock-loss heartbeat, which the sync has. A probe whose database session ends mid-run does not notice, and goes on calling Doffin without the lock. Without `ANBUD_DSN` the probe takes no lock at all.
- The application role can UPDATE `sync_runs`, so it can reopen a finished run, and the run guard (D-B5) then accepts evidence under it. The guard protects against a stale process, not against a hostile one; the role cannot change the evidence itself.
- The runtime-role check (H6) reads the catalog as of the start. A privilege granted after the start, or a membership added while the process runs, is not seen until the next start. `roles.sql` takes back the memberships of the three roles when it is run again, and nothing runs it by itself.
- A process started with both `ANBUD_MIGRATE_DSN` and `ANBUD_DSN` holds the owner's credential in its environment for its whole life. A migrate-only mode would need its own flag, which is not built.
- `cmd/api` still migrates and runs through the one `ANBUD_DSN`. It needs the same split as `doffin-sync`. Compose, `init-databases.sql` and the plane's other cores are untouched, and `scripts/roles.sql` has been run on no real database.
- The role check runs after the migrations, because "owns tables" is only true once the tables exist, so a start against a remote host with a too privileged single DSN has applied its migrations before it is refused.

### Open owner decisions

Four of the six decisions that were open here are closed. On 2026-10-10 the owner decided the project rules (P1, was decision 1), Zero Data Retention (P2, was 2) and non-2xx bodies (P3, was 4); they are in [Decisions](#decisions). The budget lock scope (was 6) is closed by the code: the probe takes the lock when `ANBUD_DSN` is set (see [Budget lock, heartbeat and signals](#budget-lock-heartbeat-and-signals)). Two stayed open, each with the owner-approved recommended direction (a recommendation, not a decision). On 2026-10-10 the owner said to continue with the open items, and both were taken up from that direction: item 2 is built for this core, and item 1 has a mechanism and a runbook. Neither decision is closed; each item says what is left.

1. **Personal data in notices (O1, was 3).** Notices name contact persons. The lawful basis, retention and erasure for the shared corpus are undecided, and migration 0002 sets no expiry. Immutability conflicts with erasure, so erasure has to be a recorded DBA procedure, not application code. *Recommended:* legitimate interest as the basis (professional contact data that authorities publish under procurement law, processed for tender discovery); no automatic expiry while the source keeps the notice public; erasure as a documented, logged DBA procedure that redacts the body in one transaction and records a tombstone, with the parser honouring the redaction list; knowledge-layer erasure rides Data Plane v2's existing DSAR path. The procedure must be written before go-live. It needs a compliance check, and it is not decided. *Built on 2026-10-10, as the mechanism and the runbook only:* migration 0006 and [PERSONAL-DATA.md](PERSONAL-DATA.md), decision H7. What stays open, and is the owner's and compliance's to answer, is everything legal: the lawful basis and its balancing test, what data subjects are told, retention (the sync never re-checks a held notice), who authorises an erasure, standing requests, and the names in `raw_search_pages`, which the procedure finds but cannot erase. The runbook lists 16 open questions (the 16th, added 2026-10-10: winners who are sole traders). It has not been used on a real database. *Built on 2026-10-28:* `cmd/anbud-retention` applies a retention period with the same function (`internal/retention` decides from the contract end, deadline, award or issue day, else the fetch day; a contract with no end is kept), as a DBA's own login, dry run unless `-apply`; see [PERSONAL-DATA.md, section 4a](PERSONAL-DATA.md#4a-retention-runs). 2. **Least privilege (O2, was 5).** Built for this core on 2026-10-10 from the recommended direction. The DSN's role used to own the tables and be the container superuser, so the triggers did not stop it. Now a `NOSUPERUSER` application role (`anbud_app`: select and insert on the evidence tables, update on the ledger only), a separate owner role for migrations (`anbud_migrator`, reached through `ANBUD_MIGRATE_DSN`) and a read-only DBA group (`anbud_dba`) make the triggers a real boundary: see [ROLES.md](ROLES.md) and decision H6. What stays open is the plane-wide rollout. `init-databases.sql` and compose still create `ingestion_user` as the superuser of every core, `cmd/api` still migrates and runs through one DSN, and item 1 of [Hardening follow-ups](#hardening-follow-ups-plane-wide) is still to do for the other cores. The other cores of the plane are not covered.

Also open, and not decided here: how to complete a `capped` (saturated) day, and the backfill window. Whether to backfill the whole corpus, about 14 days of continuous downloads, depends on the V5 census.

## Model Plane integration

- **AI validation (stage 5):** anbud-core emits a work item; the Model Plane returns a structured verdict. Output must cite source spans, and canonical fields are never rewritten by the AI.

So "act" ends at analysis, drafts and deadlines, and reaching the documents is a Quarry job against those platforms, whose login and terms are not yet checked.

## Data Plane, events, Quarry

- **Data Plane v2:** publish through its contracts only, with a service principal `anbud-core` (audience `data-plane`, scope `documents:write`) registered in `PLANE_SERVICE_PRINCIPALS_JSON`. No direct database crossing.
- **Events:** none yet. A new NATS subject is silently inert unless the broker's ACL grants it, so subjects are designed together with their grants and verified against a real broker.
- **Quarry-v2:** executes scrape jobs; anbud-core orchestrates them and consumes the artifacts. A model may propose browser actions, Quarry executes or rejects them.

## Decisions

Made in this scaffold:

- anbud-core is an Ingestion Plane core in Go, next to finspo-core and shipping-core, with its own `.env`.
- The Doffin **Public API** is the primary feed; the year CSV is for backfill. *(Superseded in part, proposed 2026-10-10, not confirmed by the owner:)* the scraper was planned as a supplement; the link probe and the council review point to **no crawling** of login platforms (Mercell, EU-Supply, TendSign), and to tender documents arriving from the user instead (ZIP drop first, forwarded e-mail second). See [Product layer](#product-layer-proposed).
- One shared public corpus plus a tenant overlay; no LLM in-process.
- API responses use the monorepo envelopes (`{ data }`, `{ error: { code, message } }`).
- A missing source key degrades the service visibly; a malformed key stops it.
- The TED API is read anonymously; **no TED key is used or sent**. TED documents a key only for endpoints that touch unpublished notices.
- The format of a download is decided from its body, never from `Content-Type`.
- The Doffin subscription's second key is held for rotation and read only by the probe. The service never loads it, and compose blanks it in the container, so a leak from the running service cannot expose it. Both keys are sent only to the host in `DOFFIN_BASE_URL`, which must be `api.doffin.no` unless it is named in `DOFFIN_BASE_URL_ALLOW_HOST`.

Open (need confirmation):

## Product layer (proposed)

Agreed in discussion with the owner on 2026-10-10 and reviewed by a four-voice council (ML, procurement, go-to-market, legal). **Proposed, not decided;** nothing here is built beyond the parser and normaliser it needs.

- **Gate first, then score.** A passed deadline or an unmet mandatory requirement is a hard fail, never a low percentage. A requirement that can be obtained before the deadline is *conditional*, judged by a lead-time table (`required, held, obtainable, lead_time` → PASS / CONDITIONAL / FAIL): an ESPD or HMS declaration takes hours, StartBANK weeks, ISO 9001 months. "Equivalent documentation" is often accepted, so an ISO requirement is not a hard fail on its own.
- **Bands, not percentages.** Strong / Good / Stretch, each with a per-criterion breakdown cited to the notice text. A percentage needs outcome data to be calibrated, and there is none yet.
- **Strictness slider.** Strict / balanced / wide. Each step widens named dials (CPV ancestors, neighbouring NUTS regions, value range, synonyms) and shows "+N tenders if you widen X". `normalize.CPVAncestors` and `NUTSAncestors` are the first two dials.
- **Profile.** Prefilled from the organisation number (Brønnøysund: NACE, municipality, size) and the company's own past wins from award notices, then edited. A prefill, not a profile: NACE does not say what a company sells or which certificates it holds.
- **Incumbency and win prior.** From award notices: re-tender, incumbent, tender counts per buyer and CPV. This is a prior on winning, not a taste model: buyer criteria are published by law, and award notices name no losers. **Built 2026-10-12** as the incumbency panel and the re-tender radar of the demo API (see Demo API); a win-probability score is not built.
- **Learning.** Per tenant only: reason chips on "skip" adjust that tenant's own criterion weights. No collaborative filtering: a like is a bid intention, and sharing it across tenants leaks pipeline and raises competition-law and ZDR issues.
- **Triage.** A small daily list in a card stack. Success is measured as bids made and won, not clicks; outcomes (bid, won, lost) are captured from day one and joined to award notices by organisation number.
- **Documents.** User-supplied (ZIP drop, then forwarded e-mail), stored tenant-scoped, read through Data Plane v2 with citations. They hold contact persons and CVs, so retention, deletion and a processing agreement with the model vendor come before any upload. *Built so far (2026-10-10):* the ZIP drop, opt-in, which keeps only the manifest and the quoted sentences, tenant-scoped and expiring ([Tender documents](#tender-documents)). Not built: forwarded e-mail, and the Data Plane v2 route, which is where full text, embeddings and retrieval belong.
- **Pilot.** One real company, 12 months of its tenders: recall on what it actually bid, precision against a plain Doffin alert as the baseline.

## Demo API

A demo surface over the pieces above, so a person can see a company's profile matched against the stored tenders and check any one assessment. It is not a frozen contract: its shapes may change, and nothing should depend on them. Code: `internal/demo` (the logic), `internal/api/demo.go` (HTTP), `cmd/api` (wiring). The routes exist only when the service has a database.

| Route | What it does |
|---|---|
| `POST /api/v1/demo/matches` | Reads the newest stored notices (`scan`, default 300, at most 1000), parses and normalises each, assesses every contract notice against the profile, and returns the best `limit` (default 50, at most 200) with a funnel of what happened to every notice it read. |
| `POST /api/v1/demo/matches/{notice_id}` | The audit sheet of one stored tender for a profile: the assessment, what the notice states, the evidence (hash and fetch time of the stored bytes), what normalising changed, and what the parser read and did not read. Since 2026-10-12 it also holds the tender's **incumbency panel** (below). |
| `POST /api/v1/demo/company` | What Enhetsregisteret holds about an organisation, through org-core, to pre-fill a profile. 503 `not_configured` without `ANBUD_ORG_CORE_*`. |
| `POST /api/v1/demo/retenders` | The re-tender radar: from the award notices among the newest stored notices (`scan`, default and at most 1000), the contracts whose base period ends between today and `horizon_months` ahead (default 12, at most 36), nearest end first, at most 50, narrowed by the profile's CPV codes and regions when a profile is given, at the strictness step (`strictness`: `strict`, `balanced` (default) or `wide`). Exact matches come first, then near ones, each nearest end first; the list holds at most 50 rows, and `matching` is the total before that cap. Each row carries `reach`: `exact` when the strictest step reaches its codes, `near` when only a wider step does. |

All three are POST: a body holds a company's own business data and an organisation number, and none of it belongs in a URL, which ends up in access logs.

**Reached from the Verevon app (2026-10-28).** The gateway proxies four routes under `/api/v1/anbud/` (`matches`, `matches/{notice_id}`, `retenders`, `company`) to the demo routes below, and the app's tender pages at `/anbud` and `/anbud/radar` call them. The organisation comes from the browser's session and goes upstream as `X-Org-ID`. The gateway sends its own key (`ANBUD_API_KEY`, in the header `ANBUD_API_KEY_HEADER`, default `X-API-Key`) and nothing else from the browser. A 401 or 403 from this core becomes `503 tender_service_misconfigured`, because the browser reads a 401 as an expired session and signs the user out. A call that outlasts the gateway's timeout is `504 timeout`. Without a key the routes answer `503 not_configured`. Nothing is stored: the profile lives in the browser's memory for the session.

**Request** (`/matches`, and `/matches/{notice_id}` for its profile): `{ "profile": {...}, "strictness": "strict" | "balanced" | "wide", "show": "relevant" | "all", "limit": n, "scan": n }`. A profile has `org_number`, `cpv`, `excluded_cpv`, `nuts`, `value_range` (`currency`, `min`, `max`, whole currency units), `keywords`, and `held` and `lead_times` (the capabilities of `internal/match`). It needs a CPV code or a keyword. Unknown fields are refused, and every problem is reported at once (at most 20) as `{ field, reason }` with fixed text: a rejected value is never echoed.

**Response.** `data.funnel` says what happened to each notice read: `scanned`, `unreadable` (not an eForms notice, or over a limit), `unsupported` (a shape with no field map: refused, not guessed at), `awards` (result notices: parsed, not tenders to bid on; the incumbency panel will read them), `opportunities` (contract notices, which the gate judges), `gate` (pass, conditional, fail over the opportunities) and `matched` (those the `show` filter lets through, before `limit`). `show: "relevant"` (the default) keeps tenders the gate does not fail that fit at least a little; `"all"` keeps everything. `data.gained_by_widening` says, for each strictness wider than the requested one, how many more tenders a company could still bid on it would show: the "+N if you widen" figure. `data.company` says, when the profile names a company, whether the register was checked and why not if it was not; a lookup that cannot be made fails nothing. `data.results` is ordered: tenders a company can bid on before those it cannot (pass, conditional, fail), better fit first (strong, good, stretch, none), nearest open deadline first, then notice id, so the order is stable. Each result carries its gate and fit checks, cited to the field they come from, and `gate_counts` (pass, conditional, unknown, fail): a notice that is conditional only because its criteria are in documents nobody has read has unknown checks and no conditional ones. A notice that points to the tender documents once for each lot is one check, not one for each lot.

**Stateless.** Every request reads `raw_documents_live` and parses on the spot, and stores nothing: not the profile (tenant data) and not the parsed notice (knowledge, decision P1). A body that has been erased is never read again (checked end to end against a real database). The responses carry no contact person: the parser counts them and never copies them, and the tests look for the fixtures' invented person in every response.

**Limits and errors.** A body over 64 KiB is 413. At most two scans run at once; a third is 429 `rate_limited` with `Retry-After` and is not queued. A scan has 20 seconds: 504 `timeout`. The audit sheet clips free text at 2000 characters and lists at most 100 entries of each kind, with the totals. 400 `validation_failed` carries the field errors; 404 `not_found`; 422 `not_an_opportunity` (a result notice), `unreadable_notice`, `unsupported_notice` (details: root, SDK version, flavour); 502 `upstream_unavailable` and 503 `not_configured` for the organisation lookup. Anything unknown is 500 `internal`, and its cause is only in the log.

**Known gaps of the demo.**
- No pagination: the best `limit` of the newest `scan` stored rows. "Newest" is storage order (row id), not publication date, because the parser does not read the issue date.
- No cache: each request re-reads and re-parses its scan window. That is deliberate while the corpus is small; it also means an erasure takes effect on the next request.
- Not scoped to a tenant, except for uploaded documents. The API key is the plane's shared key and `X-Org-ID` is optional. A request that carries it is also judged by the tender documents that organisation uploaded ([Tender documents](#tender-documents)); one that does not is not. Nothing else is stored per tenant: profile storage, retention and ZDR for a stored profile are not designed.
- The requirement rules and the lead-time table are placeholders, and 14 of 20 captured notices point to tender documents that are read only when the company uploads them. Run over the 22 captured notices with a six-CPV profile (counts only, 2026-10-10): 16 opportunities, 4 result notices and 2 unsupported shapes in the funnel; **all 16 opportunities are conditional and none passes**, because the gate cannot confirm what it cannot read (the documents, 7 of 9 selection criteria no rule recognises, 2 notices that state no deadline). That is the honest top state until documents are read. 12 of the 16 fit strongly, and none of the 16 audit sheets contains an "@".
- A profile with no region, value range or keywords gets "unknown" for those checks, and unknown does not narrow the list.
- The routes are not registered as agent actions (reads follow the Leads precedent, and an action needs a gateway dispatcher), and compose does not yet pass `ANBUD_ORG_CORE_*` to `anbud-core`.

**Incumbency panel and re-tender radar (2026-10-12).** Code: `internal/incumbency` (pure) and `internal/demo/incumbency.go`. Each awarded lot of a result notice (winner chosen, at least one winner the parser could follow) is an award: buyer, CPV (the lot's, else the notice's), award day, signing day (BT-145), the lot's contract period (start and end, or a duration in DAY, WEEK, MONTH or YEAR, or open-ended) and renewals (BT-58), tenders received and the winning value.

- **Contract end.** The stated end; else the stated start, the signing day or the award day plus the duration, in that order (`end_basis` says which); `open` when the notice says the contract has no end; `unknown` otherwise. An estimate is never shown as a stated date. Renewals are reported and not added: a renewal's length is not stated.
- **Panel.** For the audited tender: the awards of the same buyer (organisation number) under another procedure whose CPV shares at least the group (3 digits) with the tender's, graded `same_cpv`, `same_class` (4 digits) or `same_group`. Sharing only a division says nothing and is left out. It lists up to 20, newest first, and gives the likely incumbent (the latest award of the closest relation), the organisations that won most (up to 5), the median tenders received (a decimal: for an even number of counts the mean of the two in the middle, so counts of 2 and 4 give 3), and how many winners were withheld.
- **Who is named.** A winner is named, and ranked, only when org-core says it is an organisation that is not an enkeltpersonforetak. A sole trader's name is a person's name, and a winner that cannot be checked (no register configured, a foreign identifier, no answer) is treated the same way: its entry stays, with `status` `sole_trader` or `unverified` and no name or number. At most 20 winners are looked up per request, four at a time, within 5 seconds; `incumbency_status.winners` (and `winners` on the radar) is `checked`, `partial` or `not_configured`. Only the winners of the related awards, or of the contracts on the radar, are looked up. This rule is a proposal awaiting a compliance check ([PERSONAL-DATA.md](PERSONAL-DATA.md), question 16).
- **Verified against a real database (2026-10-13).** `TestIncumbencyEndToEndAgainstARealDatabase` (`cmd/api`, `make test-db`) stores a tender and two awards of one buyer, checks the panel and the radar, erases one award body through `anbud_redact_raw_document`, and checks that it is gone from both at once. With no register configured it checks that no winner is named in any response. Writing it found a defect in the panel's median, which took the upper of the two middle counts for an even number of awards and so overstated competition; it is fixed and tested directly.
- **Advice, not a gate.** The panel does not change the assessment. A scan that cannot run costs the panel only: `incumbency_status.reason` is `busy`, `timeout` or `unavailable`.
- **Strictness (2026-10-13).** The radar takes `strictness` as the matches do, default `balanced`. At `strict` a contract's code is in scope when it lies inside a profile code or covers one. `balanced` also takes a code in the same CPV group (first three digits) or the same NUTS 2 region; `wide` also takes the same CPV division (first two digits) or the same NUTS 1 region. The gate and the radar call one rule, `match.CodeReaches`, and a test pins them together. `widening` lists each wider step with `adds`, how many more contracts it matches than the requested step in the same window, before the cap, and `dials`, the codes of what that step widens (`cpv_group` and `nuts2_region` at `balanced`, `cpv_division` and `nuts1_region` at `wide`); the app words them. Before 2026-10-13 the radar matched as `strict`; the default is now `balanced`, so a caller that wants the old list sends `"strictness": "strict"`.
- **Gaps.** Only award notices among the newest `scan` stored notices are read, so an older award, or one the sync has not stored, is missing, and the "likely" incumbent can be wrong; a parser only for SDK 1.14 award notices (4 captured). No dedupe across notice versions beyond the notice id and lot.

**Amendments (2026-10-13).** Code: `internal/lifecycle` (grouping and comparison, pure) and `internal/demo/amendments.go`. A notice that amends an earlier one has its own identifier and its own Doffin id, and its change section names the notice it changes by identifier and version. A TED publication number can also appear there; no stored body carries one, so it cannot be matched and is never confirmed. Contract notices with the same procedure identifier are one tender, ordered by issue time (BT-803, with its zone), then version number, then when the store took them, then Doffin id, so the order never depends on the store. The list shows the latest notice of each tender and counts the rest as `funnel.superseded`. A listed tender carries `amendment`: how many notices it has, the buyer's reason in its own words, whether the latest notice names the one before it (`confirmed`), and what has changed since the tender was first held. The audit sheet carries `amendments`: each notice of the procedure, oldest first, with what it changed from the one before, and where the audited notice sits. The comparison covers deadlines (Oslo calendar days moved), value, codes and places (without check digits), lots, documents, requirements, selection and award criteria (weights), procedure type and title. A description is compared by length, so no free text is repeated. A change is material when a bidder would act on it. A comparison holds at most 100 changes and counts the rest, and it is linear in the size of the notices.

Test coverage: unit tests of grouping, ordering, confirmation, the comparison and its bound, a timing test (60,000 links and codes compared in well under a second; the first version held a nested scan and took 20 seconds, found by that test), the demo's list and audit, and `TestAmendmentEndToEndAgainstARealDatabase` (`cmd/api`), which stores a tender and its change, checks the list and the history, erases the change through `anbud_redact_raw_document`, and checks that the tender is the original again.

Gaps: a superseded notice is seen only when it is in the newest `scan` window; the audited notice is always added, so the history of a notice outside the window is partial. The sync downloads each Doffin id once and never re-reads a held one, so a body that changes under the same id is still not detected (open question in [SOURCES.md](SOURCES.md)). Notices without a procedure identifier, such as planning notices, are never grouped.

## Tender documents

The documents a company already holds for a tender (the specification, the contract, the annexes), uploaded as a ZIP archive, so that the gate has something to read where a notice says "the selection criteria are in the tender documents". 14 of the 20 parsed notices say so. The documents are the company's own: downloaded by a person who is allowed to from Mercell or EU-Supply, and uploaded here. Nothing in this core logs in to a platform or fetches from one.

Code: `internal/ziputil` (the archive), `internal/docread` (the files), `internal/match` (`FindInPassages`, and the gate that reads the findings), `internal/docstore` (what is kept), `internal/tenderdocs` (the service), `internal/api/documents.go` (HTTP), `cmd/api` (wiring). **Opt-in:** off unless `ANBUD_TENDER_DOCS=true`, because the feature keeps a company's own documents. Off, the routes are not there.

| Route | What it does |
|---|---|
| `POST /api/v1/notices/{notice_id}/documents` | Upload an archive. The body is the ZIP itself, `Content-Type: application/zip`, optionally named in `X-Archive-Name` (percent-encoded). 201 with the upload; 200 when the same archive was uploaded before for the notice, which is not read or stored again. |
| `GET /api/v1/notices/{notice_id}/documents` | The organisation's live uploads for the notice, oldest first: the manifest of each and what was found. |
| `DELETE /api/v1/notices/{notice_id}/documents/{id}` | Delete an upload of the organisation's own, through the notice it belongs to. 204. |

All three need `X-Org-ID` (400 `organization_required` without it), and `X-User-ID` is recorded as who uploaded. An upload needs a notice the service holds (404 otherwise); a list or a delete is answered from what the organisation holds, and for a notice nobody has uploaded to the list is empty.

**What is kept.** One row in `tenant.tender_uploads` (migration 0007) for each upload: the archive's name, SHA-256 and size; the manifest, file by file (path, kind, size, SHA-256, status, reason, pages, characters); and the findings, each the one sentence of a document that names a certificate or registration the rules know, with its file, its page (PDF) or paragraph (other kinds) and its class. **Not kept:** the archive, the files, and the text of any document. A sentence that names nothing the rules know is in no table, no response and no log. The log says how many files, reads and findings an upload held and how long it took, and never a name or a sentence.

**How an archive is read.** In memory, while the request is open; nothing is written to disk by this code.

- `ziputil` treats the archive as hostile. It refuses an archive over the size limit before it opens it. It counts the file headers of the directory itself before the standard library allocates for any of them: the library reads headers until one is bad and goes neither by the end record's count (16 bits) nor by the size of the directory the record declares, so a record that says 3 entries can sit on a directory of 65 539, or of millions. It then gives the library a file that fails once more has been read than a directory of the allowed number of entries can hold, which stops a record that lies about the size however it lies (`ziputil.NewReader` is the one way in for every ZIP-based file, a DOCX too), and a ZIP64 marker in the size or the offset of the record counts only where there is a ZIP64 locator for it to point to (a count of 0xFFFF is refused with or without one). It enforces every size on what is actually read, whatever an entry declares, and charges a read that fails to the budget as well as one that succeeds. It judges the compression ratio of any entry over 1 MiB twice: by what the entry declares, before it is read, and by what it really took of the archive, after it, because the declared size is the author's word. It spends one budget of bytes on everything, nested archives included, and counts the entries of every directory it opens across the whole walk (four times the entries of one directory, 8000 by default), because a nested archive is opened for each entry that names it and entries may share their data: two thousand entries three deep would otherwise be eight billion. And it refuses a bomb whole. A `.zip` inside the archive is opened, to three levels. A file that is merely unusable is skipped and listed with its reason: a name that leaves its folder (`..`) or is too long, a link or device, an encrypted entry, an entry over the file limit, a duplicate name, an archive too deep. Names are brought to Unicode form C with control characters removed, and so is every character that is not drawn (`internal/textsafe`: the default ignorable code points and the other format characters of the Unicode standard, among them the marks and overrides of the direction, the zero-width and invisible characters, the tag characters, the variation selectors and the fillers). The same definition cleans the text of the documents and the name of the archive, so that no sentence or name that is stored says one thing to a person and another to what reads it; until 2026-10-12 three copies of a short list did it, and each missed most of them. `__MACOSX/`, `.DS_Store`, `Thumbs.db` and `desktop.ini` are ignored without a trace.
- `docread` detects what a file is from its bytes and not its name. **PDF** is read in a child process: the service binary run with `--pdf-extract-child`, an empty environment (so the database password and the API key are not there), a 30 second deadline, 32 MiB of output at most, two at a time, a soft memory limit of 768 MiB and a watchdog that ends the child at 1 GiB of heap, which the parent reads as a crash; on Linux the child also asks the kernel to choose it first when the host is out of memory. The library that reads PDFs panics on damaged files and can neither be stopped nor bounded inside the process. **DOCX** (tracked deletions left out; a main part that is not UTF-8, which Word never writes, is refused as damaged), **HTML** (UTF-8, or Windows-1252 when it is not valid UTF-8, since older Norwegian software writes æøå that way; what a page declares is not read) and **text** (UTF-8, UTF-16 with a BOM, Windows-1252) are read in process, with a limit on the XML a DOCX expands to and on how deep its elements nest (256). The XML decoder holds every attribute and every namespace declaration of the tag it is reading and of every element that is open, so a tag of millions of attributes costs far more than the file that holds it. The decoder is therefore fed through a meter that counts what the decoder itself takes of the input between one token and the next, and cuts a token off as it is read: a tag, a comment or a CDATA section at 64 KiB, the start tags of the elements that are open at one time at 256 KiB together, and a run of text at eight bytes for each character the file may yield. The meter does not read the markup, so nothing in it (a quote in a comment, a `>` in a value) can put it out of step with the decoder. Text, HTML and DOCX hand their paragraphs to one builder as they make them, and stop reading when the builder is full: at 3 million characters, or at 250 000 units (paragraphs, or the rows of a table, whatever their characters, because a unit costs a good deal more than the character it may hold); the pages of a PDF are cleaned one at a time, and a PDF has at most 500. A file that hit either limit says it is truncated. A paragraph, a table cell and a row are clipped to four bytes for each character the file may yield before they are cleaned (and each element of a cell or a row counts for 32 bytes besides its text), and a line of a text file, in UTF-8, Windows-1252 or UTF-16, is clipped before it is decoded, because cleaning costs a good many times the length of what it cleans, and the text is cleaned a line at a time. Cleaning can make text shorter, so a paragraph that is mostly blanks loses some of what the limit would have let through. Whenever text was left out because there was more than could be kept, and whenever an HTML token (a picture kept in a tag as a `data:` address, say) is larger than the tokenizer takes (16 MiB) and ends the reading, the file says it is truncated. Tables nest in a DOCX: each is read with its own row and cell, the text before and after an inner table stays in the outer cell, and the rows of the inner table are units of their own. Everything else is listed and not read: XLSX, PPTX, legacy Office files, RTF, images and other archives are `unsupported`; a PDF with no text is `empty` (a scan: there is no OCR here); one that asks for a password is `encrypted`; a damaged one is `failed` with reason `damaged`. A file with the same bytes as an earlier one is `duplicate` and is not read again. Limits: 64 MiB and 500 pages for a PDF, 3 million characters for a file.
- A reader that panics is recovered, and the file is listed as `failed`; what panicked is not logged, because the value of a panic can hold what was being read.

**How findings are made.** Deterministic, by keyword: `match.FindInPassages` splits the text of each page or paragraph into sentences and, for each capability the requirement rules know (ISO 9001 and 14001, Miljøfyrtårn, StartBANK, Achilles, skatteattest, HMS-egenerklæring, ESPD), classes each sentence that names one: **requirement** (asks for it), **award** (rewards it in the evaluation, which is not a condition for bidding), **negated** ("trenger ikke", "not required") or **mention**. Negation is judged first, then a qualification cue, then an award cue, then a requirement cue; an item of a list takes the class of the lead-in above it. The keywords and cues are placeholders for the owner's list to replace, and the class is a heuristic: it is evidence for a person to read, not a fact. An upload keeps at most 50 findings of each capability and 400 in all, requirements first and of equal weight the earliest, and says how many it left out (`findings_dropped`). They are also kept within 1 MB once encoded (`docstore.MaxEncodedBytes`): the longest path and the longest sentence, in characters that take many bytes, make the most findings an upload keeps come to more than the table holds, and the least important are left out and counted, the first that does not fit ending the list (until 2026-10-12 such an archive was answered with a 500 that the log called a bug). The cut is made after every page or paragraph, so a file that names a certificate in every sentence never holds more than one passage's findings beyond what an upload keeps, and a passage with nothing in it costs nothing.

**How the gate uses it.** As advice. For each capability the documents ask for (class requirement), unless the notice's own selection criteria already state it, the gate gets a `document_requirement` check, judged by the lead-time table like a criterion of the notice, **except that a fail is softened to conditional**: a sentence found by keyword is not a requirement proved. The check cites the first such sentence: file, page or paragraph, and the sentence. The check for "the criteria are in the tender documents" says how many uploaded documents were read and how many could not be, and that turnover, references, staff and the rest still need a person. Documents never fail a notice, so they cannot change what widening a search adds.

**In the demo.** A request that carries `X-Org-ID` is judged by that organisation's documents: `data.documents` says whether they were used and for how many tenders, each result has a `documents` summary, and the audit sheet lists every finding, of every class, with `documents_status`. If the store cannot be read the matching goes on without the documents and says `documents.reason: "unavailable"`. The organisation is read from the header, never from the body.

**Tenancy and retention.** The table is in schema `tenant`, not `public`: it is tenant data, not evidence, and the role model of [ROLES.md](ROLES.md) is built on `public` being append-only. Every query names the organisation, and row level security makes the database refuse a row of another organisation whatever a query forgets: a row is visible only when its `org_id` is the one the session set with `set_config('anbud.org_id', ..., true)` for the transaction, and with none set no row is. It binds a role that owns nothing, which `anbud_app` is; the owner and a superuser bypass it, which a development database with one DSN is. The setting is the application's own to make, so this is a guard against a query that forgets its `WHERE`, not against an application that is compromised: whoever can run arbitrary SQL as `anbud_app` can set it to any organisation, and keeping that from happening is the job of the role model and the gateway, not of this table. The application role may select and delete on the table, insert every column but `id` and `created_at` (the identity and the clock are the database's, so a session cannot take a future id or date a row into the future, which would carry its expiry past the bound below), and run `tenant.purge_expired_uploads()`. PUBLIC and the DBA group are granted nothing, and that is stated again at every start, so a grant made by hand does not last. An upload is kept for `ANBUD_TENDER_DOCS_RETENTION` (default 90 days, at most two years: the table refuses more than two years and two days, counted in hours so that the bound is the same in a leap year and in every time zone) and is then invisible to every read at once; an hourly purge removes the row, and an expired upload does not block uploading the same archive again. The same archive for the same notice by the same organisation is one upload, found before the archive is read: an organisation at its limit that sends what it already has is told it has it. An organisation holds at most 10 uploads for a notice and 200 in all, and the limit is counted twice. The service counts before it reads the archive, so that an archive that cannot be kept is not read: that count is passed by every upload that is under way at once, and was all there was until 2026-10-12 (a reviewer sent forty small archives a few milliseconds apart for a limit of ten, and fourteen were stored with a fast insert and twenty-nine with a slow one). The store counts again when it stores the upload (`docstore.Create`, given the limits in `NewUpload.MaxPerNotice` and `MaxPerOrg`), in the transaction that stores it: it first takes a transaction lock of the organisation (`pg_advisory_xact_lock(int, int)`, the organisation as the second key and a class of its own as the first, so it is never the same lock as the one-key locks of the sync and the migrations), so that the uploads of one organisation are counted one after another, each seeing what the one before it committed. The transaction asks for `READ COMMITTED` itself, whatever the role's sessions default to, because a snapshot taken before the wait for the lock would not see that. The same archive is looked for before anything is counted, so an organisation at its limit that sends what it has is told it has it; the notice is counted before the organisation; the upload that loses the race for the last place is refused (409 `limit_reached`) after its archive was read, which is the price of not holding a lock while an archive is read; and nothing is stored for it. An upload given no limits (0) takes no lock and is not counted. The lock is the transaction's, so it is gone when the transaction ends, however it ends, and uploads of other organisations never wait for it. Each call to the database has a deadline of its own (30 seconds), which the wait for the organisation's lock is under too, so a connection that hangs cannot hold a request, or one of the two slots, for ever, and the slot is given back before the upload is stored.

**Zero data retention.** An upload with `X-ZDR: true` (what the gateway sends for a request or an organisation in ZDR mode: `true` or `1`) is refused with 409 `zdr_persistence_forbidden` before anything is read or stored. List and delete keep working, so an organisation that turned ZDR on can still see and remove what it uploaded before. The gateway has no proxy route for these endpoints yet and must forward `x-zdr` when it gets one. The header is the gateway's to set from the organisation's own posture, and never a client's: a caller that reaches this core with the plane's key and leaves it out is stored, because absent means not in ZDR mode. A header sent as several lines, or as a list, is read as a whole: any item of any line of `X-ZDR` that says `true` or `1` marks the upload; a tenant (`X-Org-ID`) named twice is refused with 400 `invalid_organization`, and a user (`X-User-ID`) named twice is not recorded, because of two lines the server reads the first and which of them is the gateway's cannot be told. A trailer after a chunked body is merged by the server into the same list as the head, so the tenant and the user are read from the head only: a tenant named in a trailer is refused, a user named in a trailer is left out, and a trailer that asks for zero data retention is believed. The gateway must set these headers and never add to them.

**The HTTP edge.** The server's body limit is 1 MiB. A header hook gives `POST /api/v1/notices/{id}/documents`, and only that, the room of an archive (`ANBUD_TENDER_DOCS_MAX_MB`) and five minutes to arrive, and only when the request carries the API key: it decides from the headers, before any body is read, so a caller without the key is refused at 1 MiB whatever it goes on to send. It reads the request target as it was sent and the router reads the path, which ends at a fragment, so a target with a fragment before its query is no upload route to the hook: a client never sends one, and a spelling the router accepts that the hook does not (another case, a doubled slash, an absolute URL) gets the ordinary limit and is refused for it, which fails closed. A compressed request body (`Content-Encoding` other than `identity`) is refused with 415 on every route, because `Context.Body` inflates one without a limit and a small request would become a large allocation past every check made after it. Every `Content-Encoding` line counts, not the first (the framework goes by the last), and the upload reads the body with `BodyRaw`, which inflates nothing, whatever the check lets by. A multipart body is not parsed by the server (`DisablePreParseMultipartForm`), which would stream a large file into a temporary file on disk; it is refused by its content type.

**Limits and errors.** At most two archives are read at once; a third is 429 `rate_limited` with `Retry-After` and is not queued. An archive has three minutes: 504 `timeout`, and nothing is stored. 400 `bad_request` (an empty body, a notice id that is not one, or a request the HTTP parser refuses: the parser's own text of the error quotes the first and last 200 bytes of the head, which holds the key the gateway adds, so the answer says only that the request could not be read, and the server does not put the quote in the error at all, `SecureErrorLogMessage`), 400 `validation_failed` (`X-Archive-Name` that is not percent-encoded UTF-8 text), 404 `not_found` (a notice that is not held, an upload that is not there), 409 `zdr_persistence_forbidden`, 409 `limit_reached` (`details.scope`: notice or organisation), 413 `payload_too_large`, 415 `unsupported_media_type`, and 422 `invalid_archive` with `details.reason` one of `not_a_zip`, `too_many_entries` (over 2000 in one directory, or over 8000 in all the directories of the archive and the archives inside it), `too_many_files` (over 500 files, which is what a manifest lists, skipped ones included, or more skipped files than the report can list, 200: nothing is left out of the manifest without a number) and `expands_too_far` (a bomb). Anything unknown is 500 `internal`; its cause is only in the log.

**Configuration.** `ANBUD_TENDER_DOCS` (`true` or `false`, default off), `ANBUD_TENDER_DOCS_RETENTION` (a duration such as `2160h`, default 90 days, at least a second and at most two years: the database keeps the interval to the microsecond, and a shorter one is nothing, which made every upload expire as it was made and be refused) and `ANBUD_TENDER_DOCS_MAX_MB` (1 to 512, default 100). All three are checked at start-up whether or not the feature is on, and a rejected value is never echoed. Memory is the cost, in two parts. Reading: an upload holds the archive, one expanded file, the extracted text (at most 250 000 units and 3 million characters) and the working copies of the one paragraph being cleaned (clipped to four bytes for each character the file may yield), for each of two slots; on the worst shapes tried (millions of one-letter paragraphs or rows, a file of 64 MiB that is one line, runs of 20 MB of text in a DOCX, and text of characters that double in size when it is normalised, such as U+0F73) a reader needed up to about 200 MiB beyond the file itself, measured as the heap the process holds with the garbage not yet collected, which is what a container limit sees (the figure moves by half again from one run to the next with when the collector happens to run), and a PDF child may use 768 MiB softly, and 1 GiB before its watchdog ends it. Receiving: the HTTP server buffers a request's whole body before any handler runs, and allocates it from the declared `Content-Length` (rounded up to a power of two) as soon as the headers are accepted, so the peak is the archive limit, rounded up, for **every upload request in flight**, including those that will be refused with 429 and those that arrive slowly (up to five minutes), not for two. Nothing here bounds how many arrive at once: that is for the gateway's concurrency limit on the route and the container's memory limit. Size the container for the archive limit you set, and keep it as small as real packages allow. The demo is a third cost, and is bounded since 2026-10-13. A scan reads the live uploads of the organisation for the notices it looks at (`docstore.EvidenceFor`), at most 200 uploads, each with up to 1 MB of findings and a manifest of as much, and reads them one at a time: a file and a finding are counted by a hash of each and not held, so what is said of the documents is whole and the number of findings is exact. Of the findings only the best are held: cut the way an upload is (at most 50 of a capability and 400 for a notice, requirements first and of equal weight the earliest), and then to what is left of a budget of 8 MiB for the call (`docstore.MaxEvidenceBytes`), in the order the notices come, with the first requirement of every capability of a notice always held, so that the gate can always tell that a requirement is there and where. What is left out is counted (`Evidence.FindingsDropped`): `documents.findings` of a result and `findings_total` of the audit are all of the findings, the audit lists at most 100 of those held, and the gate says "at least" of the passages and documents it counts when something was left out. A scan reads at most 1000 notices, which is two calls to the store, each with a budget of its own. Measured on the part that holds them: 40 000 findings in letters of four bytes, which are 69 MiB when they are held whole, are held in 9 MiB. The rows themselves are still read and decoded, up to a megabyte of findings and as much of manifest each, one at a time, so the time is what it was and the memory is not: on a database of 200 uploads built to be as large as the store takes (71 MiB of manifests and 133 MiB of findings, with 350 findings of 2.7 KB in each) a scan peaked at 34 MiB of heap above what the process held before, against 255 MiB before the change, and took about nine seconds either way under the race detector, which is near the demo's ten seconds for the documents (the demo then reports them unavailable).

**Not built, and not verified.**
- **No OCR.** A scan, or a PDF that is only pictures, is listed as unread, and an image is `unsupported`. Reading them needs OCR, which belongs in a plane that already runs it.
- **XLSX, PPTX, legacy Office files and RTF are not read.** A price schedule or a requirements matrix in a workbook is invisible to the rules.
- **Not published to Data Plane v2.** Full text, embeddings and retrieval belong there (P1: this core keeps the manifest and the quoted sentences, tenant-scoped and expiring, and is not the home of documents). Publishing needs a service principal for this core in auth-core and ZDR propagation, which are shared infrastructure and not done.
- **No erasure by organisation.** When an organisation leaves, a DBA deletes its rows by `org_id` ([PERSONAL-DATA.md](PERSONAL-DATA.md), section 9). There is no hook from org-core.
- **No fairness between tenants.** The two slots for reading archives are shared by everyone: an organisation that uploads continuously can keep others at 429. Per-tenant rate limits belong to the gateway, like the plane's other edge limits (Hardening follow-ups, item 4).
- **Synchronous.** The request stays open while the archive is read. A package of hundreds of PDFs should be split; an asynchronous job is the next step if measurement says it is needed. Speed has been measured only on small synthetic files.
- **Not checked against real packages.** The PDF fixture is Chrome-made with invented text; no Mercell or EU-Supply package has been read, and none has been seen at the sizes the limits allow. A password-protected ZIP entry is skipped as `encrypted`, never opened.
- The gateway has no proxy route and the frontend no action contract for these endpoints, and compose does not pass the variables.

## Hardening follow-ups (plane-wide)

Found by the 2026-10-09 security review. They are shared with the sibling cores, so they are decisions for the plane rather than changes to make in this core alone.

1. **Database role.** Every Ingestion core connects as `ingestion_user`, which is the Postgres superuser (`init-databases.sql`). A bug that reaches SQL in any core would reach every database, and `COPY ... PROGRAM`. Proposed: a `NOSUPERUSER` role per core that owns only its own database, with `REVOKE CONNECT ... FROM PUBLIC`. Matters most now that this service can parse untrusted tender documents (opt-in; PDFs are read in a child process with an empty environment, so a bug in the reader does not hold the database password). The row level security of the `tenant` schema binds only a role that owns nothing, which is the point of the role model. For this core O2 is built: the application role owns no table, and a separate owner role runs the migrations (decision H6). The other cores and the compose setup still use `ingestion_user`.
2. **Inbound key.** Like finspo-core, anbud-core accepts the plane's shared `AUTH_CORE_INTERNAL_API_KEY`. A service that parses untrusted documents should not hold the plane's internal credential; a per-service key would need the gateway to be configured with it.
3. **Toolchain.** The Dockerfile builder is `golang:1.26.5`, which every Go core uses; the standard library advisories reported against it are fixed in 1.26.9. Locally Go 1.25.1 is also behind (fixes through 1.25.13). Bump both plane-wide, and run `govulncheck ./...` in CI.
4. **Edge limits.** The HTTP server has read, write and idle timeouts but no request rate limit; it is meant to sit behind the gateway.

## Known traps

- `go get golang.org/x/time@latest` raises the module's `go` line to 1.26 and downloads a toolchain; this module pins `v0.15.0` (go 1.25.0) to match the plane. Run Go commands with `GOTOOLCHAIN=local`.
- `docker compose up <service>` outside the runner can leave a container off `inter-plane-bus`.
- Postgres runs `init-databases.sql` only on a fresh volume.
- `cmd/doffin-probe` takes the budget lock only when `ANBUD_DSN` is set. Without it, run the probe only while no `doffin-sync` run is active, or it can spend the same key's budget. Even when the probe holds the lock, it has no lock-loss heartbeat.
