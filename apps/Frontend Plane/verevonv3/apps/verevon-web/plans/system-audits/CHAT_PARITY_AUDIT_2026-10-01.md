# Chat parity audit (2026-10-01)

**Question asked by the owner:** can we now say that the Verevon chat system has the same parity as the reference systems in the chat documents?

**Answer: no.** The core chat experience is strong and in places ahead of the references, but less than half of the chat documents' items and about one in six of the gap-matrix rows are at parity, and several things the plan marked "built" do not work end to end yet. Details below.

**How this was made:** workflow `chat-parity-audit-2026-10-01`, 12 sonnet agents, read-only. Six auditors (the connector rows, the Office rows, the research and agent rows, the browser and collaboration rows, the harness rows, and the chat parity documents) each cited code with file and line numbers. Six second readers then re-opened every cited file and downgraded any claim whose evidence was missing, stale or overstated. I re-checked three load-bearing citations myself (`sse.rs:8380` and `:8424`, `browser.rs:1235`, `grpc.rs:516`). **Everything here is by reading the code and the dated records. Nothing was run in this audit.**

Evidence: 142 rows with file and line references in `chat-parity-audit-2026-10-01.json`, next to this file. Some capabilities appear in both groups below because the gap matrix and the parity documents each list them.

"Live-proven" means the code exists and a dated record shows it running in the real app. Unit tests and mocked end-to-end tests do not count.

**The reading:**
- **The chat core is strong, but even the chat documents' own list is not at parity.** 33 of 75 items (44%) are at parity or ahead, 30 are partial and 12 are gaps; 28 of 80 are live-proven. The solid part is real and was exercised: durable resume, stop and continue, regenerate and edit-and-resubmit, attachments, markdown, compaction, memory disclosure, run receipts, the context inspector, the workspace layout and the Office exports (Word, Excel, PowerPoint). The partial and gap items are listed in section 3.
- **The connector and agentic items are mostly not at parity.** In the gap matrix only 10 of 62 rows are at parity or ahead, and only 5 are live-proven. That list is where the owner's Copilot priorities (connectors, Office documents, Excel on the web, controlling a browser) sit.
- **Data protection** is strong in code (server-enforced privacy tier, ZDR and residency, fail-closed) but has no third-party audit, so the claim of parity with an audited product (Microsoft's) cannot be made.

## 2. Corrections to the 2026-09-28 gap plan

The plan's wave status said these were built. They exist, but they are not end to end:

1. **Wide research does not scale through chat.** The subagent ceiling is configurable to 100 in code, but nothing sets it: the only run builder (`sse.rs:8380`, `:8424`) sends `max_rounds: 4` and `max_subagents: 0`. As read, a fan-out of N items gets at most 2 one-round researchers on round 1 and the rest are refused. It is also Do-mode only, and Do mode is off on the subscription route. It has never run live, and whether session-core accepts the child-run token is still untested.
2. **The editable plan gate is not connected from the chat page.** Propose, edit, approve and reject all exist and are unit-tested, but approving produces a grant and an edited plan that no turn from the web app consumes. The grant is in memory and lost on a gateway restart. Never run live.
3. **"Plan this" runs a very small job.** A scheduled run is a single call with no tools and a 1,024-token cap (`execution-core/src/grpc.rs:516`), on the paid balance, not the user's chosen model and without web, knowledge, connectors or code. No code was found that stores or delivers the generated text, and "Se resultater" is a disabled button. A "daily web briefing" cannot work.
4. **Agent-driven browser runs cannot start.** The gateway sends a grant id of the form `session:{id}` (`browser.rs:1235`, whose own comment calls real issuance "unbuilt"); the browser broker mints random ids, so the check fails closed with 403. Nothing issues a real grant. The manual hosted browser (live frames, human takeover) is live-proven; the agent-driven path and use from `/chat` are not reachable. The last live run of the agent loop is from July.
5. **Mail and files are listings, and only in Do mode.** The agent's Outlook and Gmail tools list headers (Gmail: bare ids), ignore the search text, and return no message bodies; the picker can read a picked message. The tools exist only in Do runs, which the composer disables on the subscription route, so none of this can run on the Terra route. The 2026-09-28 "live" for Wave 1 covers the Office export, not the connectors. No dated record shows a real Outlook, Gmail, OneDrive or Drive connection exercised.
6. **Delegated identity is activated but its agent read is unproven.** The token-exchange grant was put into the running registry on 2026-09-29 and auth-core recreated, but a delegated agent read has never been run (the agent's connector tools need Do mode), so it is unproven. Without a working delegation, an agent read of a personal connection sees none, now that personal connections are owner-only. The integration-corev2 `internal/api` test package also does not compile at HEAD, so its owner-only tests do not run.
7. **Stale rows.** The plan's matrix rows for the Outlook, Gmail and OneDrive catalog, editable plan, schedules, persona and rename and delete describe 2026-09-28 and are out of date in both directions.
