CORRECTIONS

1. BLOCKER: the org-ZDR resolver T1 reuses cannot read org-core.
   - Auth Core's resolver (CP/auth-core/src/auth/interactive-retention-policy.ts:94-129) calls org-core's `/api/v1/organizations/:id` and `/entitlements` with no credential.
   - org-core now enforces service auth (CP/org-core/internal/http/service_auth.go:545-600).
   - Live check: I ran the same two fetches from inside the auth-service container for the real org id. Both returned 401.
   - Even with a credential, Auth Core's own org-core principal holds only org:projection:write:any and org:projection:delete:any (live registry, and CP/docker-compose.yml:531-532). It lacks org:read:any.
   - The existing spec mocks global.fetch (interactive-retention-policy.spec.ts:36), so it never saw the 401.
   - Today the org-level ZDR flag therefore resolves to zdr:false for every org, including the user-token path used by documents-api.
   - Under the design's fail-closed tenant resolver, every org would mint zdr:true the moment T1 and the client ship. Contexts and graph extraction would stop for all orgs, and T1's own live proof ("zdr:false for the live non-ZDR org") would fail.
   - Fix, as a new T0:
     - Grant auth-core org:read:any in the org-core registry (CP docker-compose.yml and the launcher).
     - Send X-Service-Id and X-Service-Token from the resolver.
     - Better, add one org-core internal route returning {zdrIntent, entitled}. org-core has `/internal/orgs/:orgId` but no internal entitlements route (service_auth.go:~335-365).
   - Test with the real org-core middleware, for example a Go test that loads the compose registry and runs it against these routes. Also give Auth Core's fetch double a check that refuses calls without service headers.

2. BLOCKER: introducing 'tenant' fails open in one place and breaks the whole fleet in another.
   - `authorizePlaneServicePrincipal` returns `zdr: retentionPosture === 'zdr'` (plane-service-principal.ts:380,406). A 'tenant' value therefore yields zdr:false unless the caller overrides it.
   - A second caller exists that T1 does not list: CP/auth-core/src/auth/model-plane-token.controller.ts:224-254.
   - The registry is parsed as a whole, and `validAudienceRetentionMap` accepts only 'zdr' or 'persistent' (plane-service-principal.ts:266).
   - Flip the registry to 'tenant' with an auth-core image that lacks the change, and every principal on every plane gets a configuration error and a 503.
   - Fix:
     - Map 'tenant' to zdr:true by default in `authorizePlaneServicePrincipal`.
     - Resolve it explicitly in both controllers.
     - Require the auth-core image to be deployed before the registry file changes.
     - Add a spec that the old validator rejects 'tenant' and the new code never returns zdr:false without resolving.

3. "Fail closed to zdr:true" cannot carry the design's own deferral semantics.
   - A boolean claim cannot tell an org-core outage from a real ZDR org. Section 5 says unresolved posture becomes pending with a 5-minute retry. Section 3.2 says skipped_zdr is rechecked at most hourly. These conflict.
   - Fix: on resolution failure, auth-core returns 503 with reason `retention_posture_unavailable` and issues no token. The Data Plane maps that to pending.
   - "Negative results cached 5-10s, positive 45s" is ambiguous. State which outcome each TTL applies to.
   - Staleness window after an org turns ZDR on:
     - Bearer TTL up to 300s (inference_auth.rs:21).
     - Plus the design's 60s refresh margin.
     - Plus the 45s resolver cache.
     - Content can reach the persistent route for several minutes.
   - Fix: cap tenant-principal token TTL at 60s or key the bearer cache on a posture version, and disclose the window.

4. `stop_reason=end_turn` would reject every real answer.
   - The Azure/OpenAI adapter returns the raw finish_reason, which is "stop", "length" or "content_filter" (MP/rust/services/inference-core/src/provider/openai.rs:708-733, and the streaming path at :896).
   - The proto comment's "end_turn / max_tokens / stop_sequence" is the Anthropic vocabulary (inference.proto:259).
   - Under the design, all contexts become invalid_output.
   - Accept {stop, end_turn}. Treat {length, max_tokens} as truncated. Note that content_filter may also arrive as an HTTP error rather than a finish reason.
   - Test with a real captured Azure response, not a hand-written one.

5. Metering Event v2 needs verifier, envelope and consumer changes the design omits.
   - The Data Plane cost verifier pins one event_type per producer key: "embedding" for embedding-engine, "rerank" for retrieval-engine (DP/services/data-orchestrator-go/internal/cost/verifier.go:21-33,111-135,232-262).
   - It decodes strictly (DisallowUnknownFields). The payload has only count and estimated_tokens, and the consumer drops ZDR events (consumer.go:88-90).
   - The shared envelope crate has a closed subject-per-scope table (DP/services/event-envelope-rs/src/lib.rs:432-455). It does not allow `dataplane.knowledge.units.contextualized` and has no graph scope.
   - Required first: verifier, consumer, migration and envelope changes, deployed before any producer. Otherwise events are logged as invalid and lost, because the subscription is non-durable.
   - The design only states the cost-core ordering.
   - Separate existing bug, an inference from the code and not exercised: one embed.cost idempotency key is shared by all (org, user, zdr) groups in a batch (embedding-engine batch/mod.rs:185-216). The persist step prefixes only the org (consumer.go:149-164), so a second user in the same org is silently dropped.

6. Data Plane spend would count against the org's chat budget.
   - cost-core's org-wide budget check sums every row for the org, including producer-attributed ones (MP/go/services/cost-core/internal/postgres/store.go:241, and the "Budget scope" comment in internal/server/server.go).
   - inference-core's intent layer downgrades over-budget orgs to the cheap fallback model (MP/rust/services/inference-core/src/provider/intent.rs:176-234).
   - The design's stated reason for org-level rows (avoid eating one user's budget) only moves the problem to the org.
   - It also creates two budget systems, org_processing_policy.monthly_budget_usd and cost-core's.
   - Needs an owner decision, or a feature filter on the aggregate.

OWNER DECISIONS ALREADY ANSWERED BY THE OWNER RULES
- CR stays on.
- ZDR is respected per org that has it on and is never lowered org-wide. The design complies, subject to finding 18.
- BYO subscription or API ZDR prompts and per-run override belong to the connection design, per run and not org-wide. The only compliant mechanism is an issuer-selected per-run token, so the design's "must not weaken the issuer floor" note is consistent.
- Rerank may be paid and never uses a subscription.
- Quarry rerank is option B: a Data Plane endpoint accepting caller-supplied documents. Section 14's "open interaction" is therefore decided.
  - It needs a new data-plane scope for quarry-edge, which currently holds only data:read, documents:write and org:data:read_all.
  - It needs ZDR-org skipping, since the rerank provider is a retaining Foundry endpoint.
  - It meters as feature=rerank.
- The trust edits are in scope now. Do the non-pending ones immediately and re-verify the pending ones after the CR live proof.
