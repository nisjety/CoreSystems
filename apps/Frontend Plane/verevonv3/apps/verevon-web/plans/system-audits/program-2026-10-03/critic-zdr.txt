CORRECTIONS

1. BLOCKER: Auth Core cannot read org-core on the live stack, so org ZDR never reaches any signed token today. [FACT, verified live]
   - `auth-core/src/auth/interactive-retention-policy.ts:94-99` calls org-core with no auth headers.
   - org-core applies `router.Use(serviceAuthMiddleware(...))` to every route except `/health` (`org-core/internal/http/server.go:39`, `service_auth.go:545-576`).
   - From inside the auth-service container, the same unauthenticated GET returns `401 {"error":"service authentication required"}`. The deployed dist file (`/app/dist/src/auth/interactive-retention-policy.js:27`) also sends no headers.
   - `docker-compose.yml:531-532` gives principal `auth-core` only `org:projection:write:any` and `org:projection:delete:any`. It has no `org:read:any`, so adding headers alone still returns 403.
   - The `catch` at `interactive-retention-policy.ts:167` returns `zdr:false` for every org, always. The design calls this a transient outage fail-open, but it is permanent.
   - The resolver spec mocks `global.fetch` (`interactive-retention-policy.spec.ts:25-36`) and enforces no auth. Z-02 and Z-03 as written would pass their tests and still fail live.
   - The BFF's `org_zdr_enabled` works today only because `proxy_json` carries verevon-gateway delegated credentials.
   - Fix:
     - Send `X-Service-Id` and `X-Service-Token` from Auth Core (`ORG_CORE_SERVICE_TOKEN` is already set in the container).
     - Add a narrow scope such as `org:retention:read:any`, granted to `auth-core`.
     - Map the new `retention-posture` route in `serviceScopesForRequest` (its default branch returns nil, which gives 403).
     - Give the BFF its own scope for it.
     - Add a Go test that reads the real compose credential block and the real scope function.
     - Add a first free live probe: mint an interactive token for the ZDR test org and assert `zdr:true` before any model call.
   - Without this, Z2 could not produce a `zdr_waived` run. This must be task zero.

2. BLOCKER: Z-08 ("Quarry ORs the token claim in as a floor") would force ZDR on web search for every org. [FACT]
   - The live registry gives model-gateway to quarry and execution-core to quarry `retentionByAudience: "zdr"`.
   - Quarry reads the body flag only (`Quarry-v2/crates/quarry-edge/src/search_routes.rs:144,628`).
   - Reading the claim for service tokens would disable paid providers and bypass the cache for all turns.
   - Fix: apply the claim only for `principal_type=user`. For service principals, take the run's posture from the body flag. Test against the real registry rows.

3. Wrong premise on connection ownership. [FACT]
   - The design says integration-corev2 "already enforces owner and org via assertConnectionAccess". `personalProviderKeys` holds only microsoft and google (`providers/catalog.go:1863`).
   - For `openai-codex-subscription`, the generic routes `GET /api/v1/connections`, `/:id` and `/:id/consents` (`server.go:318-437`) check org only, so any org member can read another member's connection.
   - `scopedCodexSubscriptionConnection` skips the owner check for internal-key calls (`codex_subscription.go:455`).
   - Fix:
     - The ack and posture routes must be bearer-only, not `internalOrBearerAuth`.
     - Enforce `principal.UserID == connection.UserID` with no internal bypass, plus a test that sends `X-Internal-API-Key`.
     - Auth Core must compare the user itself.
     - The ZDR capability fields must not be writable through generic upsert or patch.

4. The waiver mints `zdr=false`, so any plane that is not waiver-aware silently treats the run as non-ZDR. [INFERENCE from the design plus code]
   - Planes ignore unknown claims (no `deny_unknown_fields` in model-gateway, inference-core, session-core or execution-core).
   - A rollback of the Model Plane while Auth Core stays up leaves an unbound `zdr=false` token for a ZDR org's content.
   - Required:
     - Ship enforcers first, then integration-corev2, then org-core, then Auth Core, then the BFF, then the SPA. Roll back in reverse order.
     - Put a kill switch on the Auth Core decision route.
     - Add a waiver version, with enforcers refusing unknown versions.
   - Add a test that every plane able to call a model with a user token rejects a waiver for an unbound route.
   - The BFF token set must be homogeneous. Execution-core and session-core compare `zdr` across delegated bearers and fail closed (`execution-core/src/auth.rs` ~420-515, `session-core/src/auth.rs:668`).
   - Every mint site needs the decision header: `chat/shared.rs:150-338,1389` and `json_handlers.rs:444`.

5. The live proof contradicts the org-switch gate. [FACT]
   - Section 11 needs ZDR switched on for a test org while no provider is attested.
   - Section 2.3 refuses to enable ZDR unless a ZDR model is advertised. These cannot both hold.
   - Fix: an operator-only seed path, or ordering the proof before the gate lands.
   - Also, the only holder of `org:settings:write:self` is verevon-gateway (compose line 532). So the gate belongs in the BFF, not "BFF and org-core". org-core cannot read the Model Plane catalogue without a Control-to-Model dependency.

6. Principal registry has two writers. [FACT, verified live]
   - `scripts/bootstrap_runtime_environment.sh:886,1056` writes a 14-principal registry without `verevon-gateway` or `model-gateway-mail-task-bridge`.
   - `apps/Control Plane/scripts/run-control-plane.sh:245-354` assembles from the committed JSON, which has 17 principals (live also shows 17).
   - A re-bootstrap silently removes the BFF's decision right. The design rates this "low"; it should be required.
   - `verevon-gateway`'s credential env is `MAIL_TASK_GATEWAY_BRIDGE_SERVICE_API_KEY`. Use a separate principal for retention decisions.

7. The `effective_zdr` site count is wrong. [FACT]

8. The unknown-posture policy is inconsistent and the 24 h figure is unsourced.

   - org-core emits an event only on false-to-true (`service_enhanced.go`). conversation-core's client comment says posture must be live-read with no cache, because no "off" event exists.
   - Fix:
     - Define one unknown-posture rule.
     - Emit revision-stamped events in both directions.
     - Persist last-known posture (controlplane-dragonfly exists) or refuse content-persisting audiences.

9. Restricted-classification documents under a waived run. [FACT plus INFERENCE]
