# Identity Flow Map — Execution-Core → Integration-CoreV2 and Mail-Task → Session-Core

Read-only investigation. All paths below are under `C:/dev/CoresSystem`. No files were modified.

## 1. How a chat turn's identity reaches execution-core, and what execution-core sends onward to integration-corev2

**Chat turn → model-gateway → execution-core (this path is sound and user-bound):**

- Browser session tokens are minted per-audience by auth-core from a live Better-Auth cookie: `apps/Frontend Plane/verevonv3/apps/gateway/src/audience_tokens.rs:87-117` (`get_audience_token`) calls `GET {auth_core_url}/api/{audience}/token` forwarding the request's `cookie` header. Server-side minting is `apps/Control Plane/auth-core/src/auth/plane-token.controller.ts:154-223` (`getToken`) — requires `auth.api.getSession(...)`, resolves the active org via `resolveCanonicalTokenContext`, and the returned JWT's `sub`/`userId` is the real user.
- model-gateway's gRPC ingress (`apps/Model Plane/rust/services/model-gateway/src/grpc_auth.rs:403-426`, `intercept()`) verifies the primary `aud=model-gateway` bearer, then independently re-verifies three delegated, audience-exact bearers carried as separate headers — `x-session-authorization` (aud=session-core), `x-inference-authorization` (aud=inference-core), `x-execution-authorization` (aud=execution-core) — via `verify_delegated_bearer` (lines 453-483), which additionally asserts each delegated token's `org_id`/`principal_id`/`user_id`/`kind` match the ingress token's own. `execution_request_with_session` (lines 188-206) then attaches both the verified execution-core bearer and the session-core bearer to the outbound `RunAgentRequest`/`ExecuteStepRequest`.
- execution-core's own gRPC ingress independently re-verifies the execution-core-audience JWT (`apps/Model Plane/rust/services/execution-core/src/auth.rs:57-88`, `Claims`/`AuthenticatedUser`, aud = `EXECUTION_CORE_AUTH_AUDIENCE`). `run_agent` (`.../src/grpc.rs:1172-1205`) then calls `caller.authorize(&req.org_id, Some(&req.user_id))` (`auth.rs:292-310`) — the wire-level `RunAgentRequest.user_id` must equal the verified JWT's own `user_id`, or it's `permission_denied`.
- The *durable run record* is separately checked: `authorize_run` → `authorize_durable_run_owner` (`grpc.rs:218-232`, `532-560`) first checks an in-process cache (`StateStore.authorizes`) and otherwise calls session-core's `RunService.ResolveRunOwner` RPC using the caller's own verified `session_bearer` (`SessionCoreRunOwnershipResolver::resolve`, `grpc.rs:85-115`), caching the verified result. So a chat turn's `(org_id, user_id)` is bound at three independent points: the execution-core-audience JWT, the RPC's own fields, and session-core's durable run ownership record.

**execution-core → integration-corev2 (this is where the identity is dropped):**

- `mint_ingestion_token` (`apps/Model Plane/rust/services/execution-core/src/integration_tools.rs:503-539`) calls `POST {auth_core_url}/api/ingestion/internal-token` with headers `x-service-id`/`x-service-api-key` (static env `INGESTION_SERVICE_ID`/`INGESTION_SERVICE_API_KEY`, default service id `"model-execution"` — set at `from_env`, lines 210-216) and body `{orgId, scopes:[scope], reason}` — **no `user_id`/`sub`/`acting_user` field exists anywhere in this request.** Every call site (`list_provider_actions` 234-262, `provider_key_for_connection` 269-307, `execute_action` 319-441, `read_action_json` 456-501) goes through this same function; the caller's own already-verified `caller.user_id` (available at the RPC layer, see above) is never threaded into it.
- Server side, `POST /api/ingestion/internal-token` is `apps/Control Plane/auth-core/src/auth/plane-token.controller.ts:230-333` (`issueInternalToken`). Its body type `PlaneInternalTokenBody` (lines 90-94) is `{orgId?, scopes?, reason?}` only. It authorizes via `authorizePlaneServicePrincipal` (`plane-service-principal.ts:330-372`) against a static deployment registry (`PLANE_SERVICE_PRINCIPALS_JSON`/`_FILE`), and mints the token with `userId: principal.subject` where `subject: 'service:${serviceId}'` (`plane-service-principal.ts:364-371`) — i.e. the token's `sub`/`user_id` claim is the **service's own** identity, never an end user.
- integration-corev2's `VerifyToken` (`apps/Ingestion Plane/integration-corev2/internal/controlplane/clients.go:145-196`) reads `principal_type`; when `"service"`, it sets `userID = service_id claim` and looks for an `acting_user_id` claim into `delegatedUserID` (lines 170-183) — but auth-core never issues that claim (confirmed above), so `delegatedUserID` is always `""` for this token.
- `Principal.EffectiveUserID(isInternalCall)` (`apps/Ingestion Plane/integration-corev2/internal/auth/middleware.go:90-101`) therefore returns `""` for execution-core's bearer. The new owner check — `assertConnectionAccess`/`assertPersonalConnectionOwner`/`filterPersonalConnectionsForCaller` (`internal/api/connection_access.go:53-116`) — fail-closes: `actingUserID == ""` on a personal (Microsoft/Google) connection → `personal_connection_no_delegated_user` (403) on a direct fetch, or silent omission from `list_provider_actions`' rendered connection list. This matches the task's problem statement (A) exactly and is directly confirmed in code, not just inferred from the report.

**Note on (b) vs. the task's framing:** execution-core's `mint_ingestion_token` uses mechanism (b), which is the one delegation shape in this table that has *no* end-user-binding field defined on the wire at all (`PlaneInternalTokenBody`), unlike (c)/(d)/(e)/(f) which each bind *something* about identity into their signed payload.

## 3. integration-corev2's `Principal.EffectiveUserID`/`DelegatedUserID` derivation

- `Principal` struct and doc: `apps/Ingestion Plane/integration-corev2/internal/auth/middleware.go:35-101`.
- `EffectiveUserID(isInternalCall bool)` (lines 90-101) branches on exactly the shape the security.md report describes, confirmed directly:
  - `isInternalCall == true` (legacy `x-internal-api-key` + `X-User-ID` path): `UserID` itself **is** the delegation (unless it's the `internal-service` sentinel).
  - `isInternalCall == false, PrincipalType=="user"`: `UserID` is the verified bearer's own subject.
  - `isInternalCall == false, PrincipalType=="service"`: only `DelegatedUserID` (never `UserID`, which here holds the service's own `service_id`).
- `DelegatedUserID` is populated only in `VerifyToken` (`controlplane/clients.go:167-196`) from a verified `acting_user_id` JWT claim, for `principal_type=="service"` only (lines 179-183) — currently always empty since nothing mints that claim (see §1/§2b).
- Consumers: `assertConnectionAccess`/`assertPersonalConnectionOwner`/`filterPersonalConnectionsForCaller` (`internal/api/connection_access.go:53-116`), wired into every connection-scoped route per `internal/api/server.go` (per security.md's file list, confirmed structurally by reading `connection_access.go`'s own doc comments naming each route family).

## 4. session-core's caller authentication: `PrepareScheduledRunThread` vs `PrepareUserOwnedThread`

Both RPCs first go through session-core's own general ingress identity (`apps/Model Plane/rust/services/session-core/src/auth.rs:189-195`, `identity()` — RS256, `aud=session-core`, same construction pattern as model-gateway/execution-core). The difference is entirely in what's layered on top:

- **`PrepareScheduledRunThread`** (`grpc.rs:4346-4429`): requires `caller.is_service() && caller.principal_id() == "service:capability-core"` (hard-coded single caller, line 4352) **and** `verify_scheduled_run_decision(&req)` (line 4359) — a Control-issued Ed25519 decision (mechanism e above) that cryptographically binds the exact `org_id`/`space_id`/`human_subject_id`/`schedule_id`/`fire_key`/`run_id`/`system_thread_key`/authority-revisions/`payload_digest`, checked against a `permissions` list containing `"schedule:run"`, non-ZDR, non-expired, with a non-empty nonce (`grpc.rs:736-804`). A retry additionally re-validates every stable authority binding against the existing thread row (lines 4389-4423).
- **`PrepareUserOwnedThread`** (`grpc.rs:4435-4487`): requires only `caller.is_service() && USER_OWNED_THREAD_CALLERS.contains(&caller.principal_id())` — an allow-list of exactly one entry, `"service:model-gateway"` (`grpc.rs:2146`) — **with no Control-issued decision at all**. It does validate that `req.user_id` isn't itself service-shaped (lines 4461-4465), that `origin` is a recognized non-`"space"` value (4466-4471), and `caller.authorize_org(&req.org_id)` (4447) — but nothing independently verifies that the caller's claimed `user_id` is one this specific service call was actually authorized to act for. Authority here is "trust the allow-listed service's own say-so", not "Control Plane attests this specific binding right now."

This confirms the task's framing precisely: **(B)'s underlying RPC exists and is tested, but its authorization model is a strict subset of every other authority-sensitive session-core RPC** (compare `CompleteStep`/`ReserveToolAction`/`FinalizeToolAction`, which all layer `authorize_run_owner` DB checks on top of caller identity, `grpc.rs:4489-4538`).

Additionally — and this is the concrete reason `MailTaskPipeline` is `None` in production — **model-gateway has no service-principal credential to session-core at all today.** `grpc_auth.rs`'s `VerifiedIdentity` (lines 49-61, 152-206) only ever carries a `session_bearer` forwarded from a **live user's own already-verified** ingress credential (`intercept()`, lines 403-426); there is no `mint_*`-style function anywhere in model-gateway analogous to execution-core's `mint_ingestion_token` that could mint a `service:model-gateway`-subject session-core token. So even though session-core's allow-list already names `service:model-gateway` (`grpc.rs:2146`), nothing in the codebase can currently present that identity — the allow-list entry is unreachable, exactly as documented in the gateway's own module doc (`apps/Frontend Plane/verevonv3/apps/gateway/src/domains/mail_task.rs:65-84`). Closing this requires three separate, unbuilt pieces: (i) an auth-core service-principal registry entry for `service:model-gateway` at `aud=session-core` plus new model-gateway client code to mint and hold it; (ii) a new internal HTTP route on model-gateway wrapping the gRPC RPC (this crate has no `tonic`/`mp_contracts` dependency); and arguably (iii) strengthening `PrepareUserOwnedThread`'s own authorization with something Control-issued (mechanism e-style), since today a bare allow-listed caller identity is sufficient to name *any* `user_id` in its own org as the thread's owner — a materially weaker bar than `PrepareScheduledRunThread`'s.

## Summary of the two gaps, restated precisely from evidence

- **(A)** execution-core's chat-turn identity is verified and durably bound at the execution-core/session-core boundary (§1), but is never threaded into `mint_ingestion_token`'s auth-core call, which mints a purely org+scope-bound service token with `sub = service:model-execution` and no end-user claim (§1, §2b). integration-corev2's new owner check therefore fail-closes every personal-connection read for the chat agent — correctly, given today's wiring, but the fix requires cross-plane work in execution-core (Rust, pass `caller.user_id` into the token request) **and** auth-core (NestJS, accept/authorize/issue an `acting_user_id` claim) — integration-corev2's consuming code (`clients.go:173-183`) already exists and needs no further change.
- **(B)** The `MailTaskPipeline` seam is fully specified and the session-core half (`PrepareUserOwnedThread`) is built and tested, but three things are still missing before it's safe/possible to wire up: a model-gateway→session-core service credential (doesn't exist), a model-gateway-side HTTP route to reach the RPC (doesn't exist, no gRPC client in this crate), and — unlike every comparable session-core RPC — `PrepareUserOwnedThread`'s authorization rests solely on caller-identity allow-listing with no Control-issued decision binding the specific `user_id` claimed, which the schedule.md review already flagged as a low-severity-but-real gap precisely because the RPC is currently unreachable.
