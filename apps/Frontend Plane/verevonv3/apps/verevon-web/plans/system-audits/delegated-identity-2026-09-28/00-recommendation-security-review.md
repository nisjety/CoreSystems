## 1. Attacks found in Design 1

### Part A (Ed25519 read-attestation, reusing the existing write-attestation shape)

**A-1. Read replay is a live, unauthenticated-by-anything-but-time bearer, and the design calls the fix "optional."** `attestation/verifier.go`'s `Verify()` **(confirmed)** does pure stateless claim validation — no JTI table, no nonce cache, nothing server-side that remembers a signature was already used. For writes this is safe because a replayed write attestation lands on the same `idempotency_key`/`ActionReceipt` row and becomes a no-op. Reads have no such row — the design says so itself ("reads have no `ActionReceipt` table"). So a captured `X-Access-Attestation` header is a live, fully self-contained proof of "I may read user U's personal Microsoft/Google connection" for up to 60 seconds, replayable from anywhere that can also present the static `INGESTION_SERVICE_API_KEY` bearer. Given this attestation is specifically the mechanism that gates *owner-ruling-5* protected data (personal mail/drive/calendar), a stolen header from a log line, an APM/tracing sidecar, or a misconfigured internal proxy is a real exposure. Design 1 defers the JTI-cache fix as "worth a follow-up, not required to close the gap." **Verdict: this should be mandatory before the mechanism ships**, not optional — the asymmetry between "writes are replay-safe by construction, reads are not" is exactly the kind of thing that gets forgotten once the design doc says "optional."

**A-2. `space_ref` is not the vulnerability here — that's Part B (see B-1) — but A does inherit one general risk from the shared runtime**: `actor_id` traces back to `caller.user_id`, which execution-core's `run_agent` handler already verifies equals the RPC-level `req.user_id` **(confirmed** via `auth.rs:292-310`'s `AuthenticatedUser::authorize`**)**. So on a single, correctly-isolated request this is sound — the attestation can only ever be signed for the run's own, cryptographically verified user. The residual risk is *not* in the crypto, it's in execution-core's own internal parameter threading: if two concurrent runs for two different users ever get their `user_id`/`session_bearer` crossed inside execution-core's tool-dispatch plumbing (shared client instances, a copy-paste bug threading the wrong closure variable, a future refactor), a syntactically perfect, correctly-signed attestation would be minted for the *wrong* human, and neither auth-core nor integration-corev2 has any way to detect that — they only ever see "a validly signed claim," never "the true call-site value." This risk is symmetric across Design 1 and Design 2 (both rely on the same execution-core internals being correct); it just means whichever design ships **needs a concurrency test that specifically proves two simultaneous runs for two different users never cross-contaminate the read credential** (see §4).

**A-3 (low).** The new `X-Access-Attestation` route change touches five handlers (`GET /connections/:id`, `.../status`, list, actions-read-branch, `filterPersonalConnectionsForCaller`). Design 1's own text says this is fail-closed and additive, which the code I read supports (`assertPersonalConnectionOwner`'s existing 403 path is untouched, the new path is a strict addition). No exploit found here beyond A-1.

### Part B (Ed25519 Control decision reused from the Space-decision family)

**B-1. The signed `space_ref` (and its ten Space-authority siblings) is decorative, not binding — confirmed by reading `decision.go`.** `Decision.Validate()` **(confirmed)** hard-requires `space_ref`, `recipient_audience_ref`, `recipient_audience_hash`, `privacy_policy_ref`, `resource_authorization_ref`, `purpose`, `lawful_basis`, `privacy_class`, `retention_class`, `residency`, `deletion_scope` all non-empty before it will even sign. `PrepareUserOwnedThreadRequest` **(confirmed** at `grpc.rs:4446-4471`**)** carries none of these — only `org_id`, `user_id`, `origin`, `session_key`. Design 1's own B.2 text admits its new verifier "deliberately does not compare `claims.space_ref`, since the request has no `space_id` to compare it to." That means: whatever value goes into ten mandatory fields on this decision is *never checked by the consumer at all*. This isn't directly exploitable (the token is still Ed25519-signed end to end, so nothing can be forged), but it is a real design-hygiene defect: reusing the full, heavyweight `Decision` struct for an RPC that structurally cannot use most of its fields means (a) the issuer has to synthesize/carry values that do nothing, and (b) a future maintainer skimming `VerifyDecision`'s call sites could reasonably assume "space_ref is checked everywhere this struct is used" and be wrong specifically here — a latent trap for the next person who touches this code, not a live vulnerability today.

**B-2. Same envelope version tag (`"v2"`) as five unrelated decision families, with no structural separation.** Design 1 reuses `decisionVersion = "v2"` **(confirmed)** — the identical tag scheduled-run, personal-thread-create, shared-thread, and thread-append decisions all use. The new mail-task verifier is safe *only* because it independently checks `action_id`, `service_audience`, `action_schema_hash`, and `permissions` all equal exact, unique strings — every one of those checks has to be written correctly, every time, forever, in a function sitting next to five near-identical sibling verifiers. One dropped `&&` clause in a future refactor (e.g. someone "simplifying" the six near-identical `verify_*_decision_with_keys` functions into a shared helper and forgetting one field) turns into a cross-family decision-confusion bug — e.g. a `model.schedule.run` decision satisfying `prepare_user_owned_thread`'s checks. Design 2's distinct `"mail-task-v1"` tag makes that class of bug structurally impossible instead of merely test-covered. Not exploitable as specified, but materially weaker defense-in-depth than Design 2's Part 2.

**B-3 (confirmed correctly scoped, not a flaw).** I verified the confused-deputy concern the task explicitly asks about — "can a forged inbound email create a thread for another user?" — by reading `mail_task.rs`'s `IngestRequest` **(confirmed)**: `user_id` is a bare JSON field with zero independent cryptographic binding beyond the existing HMAC covering body *integrity* (not content correctness). Both designs correctly close the *transport* confused-deputy gap: the new decision is minted from the *same* `resolveMailTaskAlias` call that already determines `org_id`/`user_id` server-side from the verified alias table (never from the email's own `From:` header), so a bug or compromise in any of the three pass-through hops after that point (integration-corev2's resolver, `gateway_client.go`, the gateway BFF, model-gateway) cannot silently swap the thread owner — session-core's final field-by-field comparison against the request would reject the mismatch. What neither design solves, and neither claims to: a bug *inside* `ResolveAlias` itself. That's out of scope per both designs and per `mail-task.md`, correctly.

**B-4 (operational gotcha found in both designs, not called out by either).** `authorize_operation` in session-core's `auth.rs` **(confirmed** lines 198-209**)** fails closed for any ZDR-flagged caller on a non-`:read` scope: `if caller.zdr() && !service_scope.ends_with(":read") { return Err(failed_precondition) }`. `session:user-owned-thread-prepare` does not end in `:read`. And `plane-service-principal.ts`'s `authorizePlaneServicePrincipal` **(confirmed)** defaults an unconfigured audience's retention posture to `'zdr'`: `principal?.retentionByAudience?.[request.audience] ?? 'zdr'`. So **unless the new `service:model-gateway`@`aud=session-core` registry row explicitly sets `retentionByAudience: {"session-core": "persistent"}`, `prepare_user_owned_thread` will refuse every call outright**, regardless of whether the Control decision is present and valid. Neither design's registry-row sketch mentions this field. This is a safe failure mode (fail-closed), not a vulnerability, but it will silently break the whole pipeline on first deploy if missed — worth stating explicitly in the implementation order.

## 2. Attacks found in Design 2

### Part 1 (RFC 8693 token exchange at auth-core)

**T-1 (inaccurate claim, doesn't break the design but changes the trust story).** Design 2 states the `x-session-authorization` subject token is "already independently re-verified at ingress against the SAME caller's `org_id`/`user_id`/`zdr` by every sibling `authenticate_delegated_*`." I checked `execution-core/src/auth.rs` line by line: there is **no** `authenticate_delegated_session` function. `delegated_session_bearer()` **(confirmed** `auth.rs:238-252`**)** does nothing but strip `"Bearer "` off the raw header and hand back an opaque string — its own doc comment says so explicitly: *"Execution Core never treats it as local authority; it only forwards it to session-core, which independently verifies."* The actual re-verification against the ingress identity happens one hop earlier, at **model-gateway's** `verify_delegated_bearer` **(confirmed** `grpc_auth.rs:453-483`**)**, before execution-core ever sees the token — not inside execution-core's own `authenticate_delegated_*` family (those exist only for the inference/browser/sandbox-manager/data-plane bearers, not session). This matters because the design's security narrative leans on "execution-core already checked this," when in fact execution-core has *never* checked it — it is pure pass-through. The actual safety net for Gap A is entirely the *new* `verifyPlaneSubjectToken` step at auth-core, which is fine (auth-core can validate its own JWT independently of what execution-core did or didn't do), but the design should say so accurately, because it changes where a future reviewer needs to look for the trust boundary.

**T-2. The exchanged token is a strictly more dangerous leak target than Design 1's layered attestation.** In Design 1, a stolen read-attestation is useless without *also* holding the long-lived `INGESTION_SERVICE_API_KEY` (the attestation only ever supplements the existing bearer check — `assertConnectionAccessOrAttestedRead` tries the ordinary bearer path first). In Design 2, the exchanged token *is* the complete, self-sufficient bearer — presented directly as `Authorization: Bearer <token>` to integration-corev2, no second secret required. A single captured token (log line, APM header capture, compromised HTTP client dependency) is immediately and fully usable by anyone, for the personal connections of exactly the user it was minted for, for up to 90 seconds, with — per the design's own §1.3 — no nonce/JTI defense either. This is a materially worse token-leak profile than the mechanism it's replacing/competing with, for the same TTL-only replay posture. If Design 2 is chosen, this needs a JTI or single-use marker at minimum (see §4), more so than Design 1's read-attestation needed one, because here the bearer alone is sufficient.

**T-3 (scope creep, low severity).** Design 2's `allowedAudiences: ["session-core", "execution-core"]` for the ingestion-target token exchange includes `execution-core` with no stated justification anywhere in the write-up — execution-core never needs to present its own execution-core-audience credential as proof of *end-user* identity (it already has that from the RPC layer directly); only the session-core-audience bearer carries anything new. Including a second, unexplained acceptable subject-audience widens what a compromised or buggy caller could hand auth-core as "proof." Should be `["session-core"]` only, unless a concrete need is named.

**T-4 (implementation-completeness gap, confirmed against code).** `plane-service-principal.ts`'s `parseRegistry` **(confirmed** lines 260-314**)** explicitly validates every known field on a principal config (`credential`, `audiences`, `orgIds`/`allowAnyOrg`, `scopes`, `scopesByAudience`, `retentionByAudience`) and throws `ServicePrincipalConfigurationError` on anything malformed. Design 2's new `tokenExchange` field is never added to this validator. Structurally this fails closed today (`principal.tokenExchange?.[audience]?.includes(subjectAud)` on `undefined` is just falsy), so it isn't exploitable, but a malformed `tokenExchange` entry in the deployment registry would silently do nothing forever rather than fail loudly at load time the way every other misconfiguration in this file does — worth closing for operability, not security.

**T-5 (real correctness risk, not yet a vuln).** The design explicitly calls out that `zdr` on the exchanged token must be "inherited from the subject token's own claim, NOT the registry default" and must "bypass `issuedTokenZdr`'s existing logic... on purpose." That's the right call, but it means the new endpoint **cannot** just call the existing `authorizePlaneServicePrincipal` + `issuePlaneToken(..., retentionPosture: {zdr: principal.zdr})` pipeline unchanged (that's exactly the path that defaults to the registry's `'zdr'`/`'persistent'` setting) — it needs a distinct code path that deliberately overrides that one field after computing scopes/orgId the normal way. This is easy to get backwards during implementation (reuse the whole existing function, forget the override) and would silently re-introduce a ZDR-inheritance bug the design itself flags as important. Needs an explicit test (§4).

### Part 2 (lean "mail-task-v1" decision family)

No new attacks found beyond what's shared with Design 1's Part B (B-3 applies identically and is correctly scoped in Design 2 too — same `resolveMailTaskAlias` reuse). The distinct version tag and the narrower, purpose-built claim struct are a genuine improvement over Design 1's B-1/B-2 findings, confirmed structurally sound against `decision.go`/`personal_thread_decision.go`.

**T-6 (shared with B-4, restated for Design 2's own credential-mint step).** Design 2's model-gateway `mint_session_gateway_token`/registry row for `aud=session-core` has exactly the same `authorize_operation` ZDR trap as B-4 — must set `retentionByAudience: {"session-core": "persistent"}` or the whole pipeline fails closed regardless of the decision token. Confirmed applies equally to both designs since it's a session-core-side check, independent of which decision family reaches it.

**Verified accurate (not a finding, a confirmation).** Design 2's B.4(ii) claim that model-gateway already has an HTTP-level `Claims`/`service_id` auth middleware separate from its gRPC ingress — **confirmed**, `model-gateway/src/auth.rs` exists with exactly that shape (`Claims { sub, service_id, principal_type, ... }`, JWKS-based RS256 verification). Also confirmed: model-gateway's `Cargo.toml` has `tonic`/`mp-contracts`; the Frontend-Plane gateway BFF's `Cargo.toml` has neither — so the BFF genuinely cannot call session-core's gRPC directly and does need the new HTTP bridge on model-gateway, exactly as both designs assume.

## 3. Recommendation: merge, favoring Design 2 for Gap A's shape and Design 2 for Gap B's decision family, with Design 1's layering discipline folded in

**Gap A → Design 2's token-exchange, but hardened to close T-2 and correct T-1's narrative:**
- Keep the RFC 8693 exchange at auth-core (cleaner than minting a fourth attestation-like primitive; it also fixes the `execute_action`-write-path's pre-existing free bug that Design 1 flagged: `provider_key_for_connection`'s GET currently 403s for personal connections even on writes).
- **Narrow `allowedAudiences` to `["session-core"]` only** (closes T-3).
- **Add a JTI/single-use marker, not just a TTL**, since the exchanged token is a complete standalone bearer (closes T-2): a small in-memory `(jti)` seen-set at auth-core with the same TTL as the token itself is enough — it doesn't need to be durable, it only needs to survive the token's own 90s window, mirroring the pattern `conversation-ingest-rs`'s `ReplayCache` already uses elsewhere in this codebase.
- **Correct the design doc's claim about where the session bearer is re-verified** (T-1) — state plainly that execution-core forwards it opaquely and the real re-verification is (a) at model-gateway's ingress when the bearer is first minted into the RunAgentRequest chain, and (b) at auth-core's new `verifyPlaneSubjectToken` step. This is a documentation fix, not a code fix, but it's the kind of inaccuracy that misleads the next reviewer into skipping the right place to look.
- **Add `tokenExchange` to `parseRegistry`'s validation** (closes T-4).
- Explicitly wire the `zdr` override on a code path distinct from the existing `/internal-token` handler's, with a dedicated test proving it (closes T-5).

**Gap B → Design 2's lean, distinctly-versioned `mail-task-v1` claim family, not Design 1's reuse of the full Space `Decision`** — closes B-1 and B-2 outright by construction (no Space-authority fields to leave unverified, no shared envelope tag with five sibling decision types).

**Both legs → explicitly document the session-core ZDR-scope trap (B-4/T-6)** in the deployment step that creates the `service:model-gateway` registry row: it must set persistent retention for `aud=session-core`, or the entire mail-task pipeline fails closed on the very first call regardless of every other piece being correct. This should be a named, tested precondition, not a thing someone discovers in production.

### Concrete changes needed to close every attack found

| Finding | Fix | Where |
|---|---|---|
| A-1 / T-2 (read/exchange replay) | Mandatory JTI/single-use cache, not optional follow-up | integration-corev2's `attestation.Verifier` (if any read-attestation path survives) **and** auth-core's new token-exchange endpoint |
| A-2 (concurrency cross-contamination) | Concurrency test, no code change identified as needed beyond existing threading | execution-core tool dispatch |
| B-1 / B-2 (Space-decision reuse for a non-Space RPC) | Use Design 2's lean `mail-task-v1` family instead of the full `Decision` struct | user-core `spaces` package, session-core `grpc.rs` |
| B-4 / T-6 (ZDR scope trap) | Explicit `retentionByAudience: {"session-core": "persistent"}` in the `service:model-gateway` registry row, with a startup/deploy check | auth-core deployment config |
| T-1 (inaccurate trust narrative) | Correct design documentation only | n/a |
| T-3 (audience scope creep) | `allowedAudiences: ["session-core"]` only | auth-core `verifyPlaneSubjectToken` |
| T-4 (unvalidated registry field) | Add `tokenExchange` shape validation to `parseRegistry` | auth-core `plane-service-principal.ts` |
| T-5 (zdr-inheritance implementation risk) | Distinct code path from `/internal-token`; explicit override test | auth-core `plane-token.controller.ts` |

### Implementation order across services

1. **auth-core**: add `tokenExchange` registry field + its `parseRegistry` validation; add `verifyPlaneSubjectToken` (audience allow-list = `["session-core"]` only); add the JTI cache; add the new `/api/:audience/token-exchange` endpoint with the `zdr`-override path proven distinct from `/internal-token`. Dead code until a registry row references it — zero behavior change to ship.
2. **user-core**: add the lean `mail_task_thread_decision.go` (distinct `"mail-task-v1"` envelope, distinct action/audience/schema constants), wire `resolveMailTaskAlias` to mint it, gated on non-ZDR + `ThreadCreateEntitled`.
3. **session-core**: add `control_decision_token` field to `PrepareUserOwnedThreadRequest` (proto, forces a model-gateway rebuild too per project precedent); add `verify_mail_task_thread_decision_with_keys` gated specifically on `origin == "mail_task"`, leaving every other `USER_OWNED_THREAD_CALLERS` origin untouched.
4. **execution-core**: thread the run's verified `user_id` into the existing `mint_ingestion_token` call sites via the new `mint_delegated_ingestion_token(session_bearer)`, replacing the four read call sites one at a time (`list_provider_actions`, `provider_key_for_connection`, `read_action_json`, `execute_action`'s read branch).
5. **model-gateway**: add the `service:model-gateway`@`aud=session-core` credential mint (verify the registry row sets persistent retention before wiring this up — B-4/T-6), and the new internal HTTP→gRPC bridge route to `PrepareUserOwnedThread`.
6. **gateway BFF**: mint its own `aud=model-gateway` credential, forward `thread_decision` opaquely through `IngestRequest`.
7. **Flip `MailTaskPipeline` from `None` to real, last**, only once steps 1-6 are deployed and tested — exactly as both designs already recommend, and consistent with `mail_task.rs`'s existing fail-closed `503` default.
8. Deploy-config-only additive registry rows throughout; no coordinated cutover required except step 7.

### Exact tests that prove the owner-only ruling still holds

**Gap A (execution-core → integration-corev2):**
- `token_exchange_rejects_a_subject_token_for_a_different_org_than_the_request_body` — auth-core.
- `token_exchange_rejects_an_expired_or_not-yet-valid_subject_token` — auth-core.
- `token_exchange_preserves_the_subject_tokens_own_zdr_even_when_the_registry_default_differs` — auth-core (closes T-5 directly).
- `token_exchange_replay_within_ttl_is_rejected_by_jti_cache` — auth-core (closes T-2/A-1).
- `list_provider_actions_and_read_action_json_succeed_for_the_runs_own_user_and_fail_for_a_different_users_personal_connection` — execution-core integration test against fake auth-core + integration-corev2.
- **`two_concurrent_runs_for_two_different_users_never_cross_contaminate_the_delegated_read_credential`** — execution-core, concurrency-specific (closes A-2; not present in either original design's test list).
- `VerifyToken_end_to_end_accepts_a_real_execution_core_shaped_token_carrying_acting_user_id` — integration-corev2 (closes the "inert until issued" gap security.md already flagged).
- Org-wide connector (Slack/GitHub) path is completely unaffected by any of the above — regression pin.

**Gap B (mail-task → session-core):**
- `mail_task_thread_decision_round_trips_through_the_mail-task-v1_verifier_and_is_rejected_by_the_space-decision_verifier_and_vice_versa` — cross-family confusion pin (closes B-2, the reason Design 2's distinct tag was chosen over Design 1's reuse).
- `issue_mail_task_thread_decision_refuses_for_a_zdr_org` — user-core.
- `prepare_user_owned_thread_rejects_a_missing_control_decision_token_for_mail_task_origin` — session-core.
- **`prepare_user_owned_thread_rejects_a_decision_minted_for_user_A_when_the_request_names_user_B`** — session-core, the single most important test for the owner-only ruling itself; must assert the field-by-field claim comparison actually fires (this is the test that would catch B-3's residual "did every hop wire the field through correctly" risk).
- `prepare_user_owned_thread_rejects_a_decision_whose_session_key_does_not_match_the_requests_session_key` — session-core (binds the decision to the specific inbound message, not just the user).
- `prepare_user_owned_thread_accepts_a_valid_mail_task_decision_and_is_idempotent_on_retry` — confirms the `(org_id, user_id, session_key)` advisory-lock idempotency (confirmed in code) holds even under decision-token replay within its window.
- `service_model_gateway_registry_row_sets_persistent_retention_for_session-core_or_every_prepare_user_owned_thread_call_fails_closed` — a deploy-config smoke test / startup assertion, not a unit test, but should exist somewhere in the rollout checklist (closes B-4/T-6, the gotcha neither original design's test list caught).
- gateway BFF: `thread_decision_forwarded_verbatim_and_unread_by_this_crate` (existing convention, extended).
- model-gateway: `wrong_or_missing_service_id_on_the_new_internal_route_is_rejected`; `control_decision_token_is_forwarded_unmodified_into_PrepareUserOwnedThreadRequest`.
