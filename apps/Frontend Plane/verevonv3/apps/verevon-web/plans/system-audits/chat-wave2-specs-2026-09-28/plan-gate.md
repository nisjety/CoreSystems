# Implementation spec: editable plan with a confirm-before-execute gate (Manus Plan Mode)

Repo root `C:/dev/CoresSystem`. Read-only investigation; no files were changed. All paths below are relative to that root unless given absolutely.

## 1. What exists today (file:line evidence)

Three separate "plan" mechanisms exist in this codebase, and they do not talk to each other. This is the central fact the design has to resolve.

**A. The autonomy-rung grant — the only one actually wired to chat.**
- Composer toggle "Ask"/"Do": `apps/Frontend Plane/verevonv3/src/features/dashboard/home/DashboardComposer.tsx:2725-2764` (`planMode` memo at :1123, `onPlanModeChange` at :2741). Sent as `planMode()` on the request.
- Client state: `ChatTurn.planMode?: boolean` and `ChatTurn.grantedRung?: AutonomyRung`, `apps/Frontend Plane/verevonv3/src/features/chat/components/chat-types.ts:335-357`. `planMode` is captured at send time, not read live from the toggle.
- Node derivation: only a **finished** plan-mode turn gets a `plan-approval` node — `apps/Frontend Plane/verevonv3/src/shared/chat-nodes/derive.ts:156-163`. Node shape: `{ kind: 'plan-approval', grantedRung?, pending, error? }` — `src/shared/chat-nodes/types.ts:119`, `onApprovePlan` contract at `:134`.
- UI: `PlanApprovalControl`, `apps/Frontend Plane/verevonv3/src/features/chat/components/ChatMessages.tsx:2038-2043` (rendered from the node registry at `:255-263`). It shows two fixed rungs (`GRANTABLE_RUNGS = ['workspace_write', 'danger_full_access']`, `:2123`) and a free-text justification box (`MIN_PLAN_JUSTIFICATION_CHARS = 12`, enforced client-side only, `chat-client.ts:1652`). **It has no concept of plan steps at all** — nothing here reads or edits what the model proposed to do; it only asks "how much authority, and why."
- Controller: `approveTurnPlan` in `use-chat-controller.ts:1992-2032`. On success it sets `turn.grantedRung` and turns the composer's plan-mode toggle off (`setPlanMode(false)`).
- Client call: `approvePlan(runId, rung, justification)` → `POST /api/v1/agents/runs/{runId}/plan-approval` with `{granted_rung, justification}` — `chat-client.ts:1676-1697`.
- BFF: route + thin proxy, `apps/gateway/src/domains/agents_runs.rs:41-46` (route) and `:221-238` (`approve_plan` handler) → `model-gateway`'s `/v1/runs/{run_id}/plan-approval`.
- model-gateway: `PlanApprovalRequest{granted_rung, justification}` (`Model Plane/rust/services/model-gateway/src/http_routes.rs:6846-6851`), handler `plan_approval` (`:6870-6965`). It (1) validates the escalation against `AutonomyEscalation::request(ReadOnly, requested, justification)`, (2) resolves the run's `thread_id`, (3) calls `coordinator::handle_exit_plan_mode` (`coordinator.rs:260-…`), which records the grant **thread-keyed** in an in-memory `PlanModeStore.grants` (`coordinator.rs:69-94`, `granted_rung()` reader at `:176-194`) and publishes a durable `RUN_PLAN_MODE_EXITED` event whose JSON payload today is only `{run_id, session_id, granted_rung, justification}` (`coordinator.rs` inside `handle_exit_plan_mode`), and (4) calls `session_client.set_run_mode` (`SetRunModeRequest{run_id, mode:"execute", granted_rung, justification}`, proto at `proto/model_plane/v1/sessions.proto:1069-1093`) for durability.
- Enforcement on the **next** run: `mark_run_plan_mode` marks a fresh run as planning (`model-gateway/src/sse.rs:5714`); the executing run's `autonomy_rung` is read back thread-scoped from `state.plan_mode.granted_rung(org_id, &run.thread_id)` when the next `RunAgentRequest` is built (`sse.rs:1058-1071`, specifically `:1058` `plan_mode` bool and `:1058-1071` the `autonomy_rung:` arm). execution-core enforces it per tool call in `runtime_loop/agent.rs:1225-1252` (rung check) and separately refuses risky tools outright while `req.plan_mode` is still true (`agent.rs:1320-1352`).
- **What is missing:** the model's plan is never captured as data — it is just the assistant turn's streamed markdown `content`. Nothing server-side parses it into steps, nothing is editable, and the executing run's context for "what was approved" is only the ordinary conversation history (the model re-reading its own earlier prose). There is no field anywhere in `PlanApprovalRequest`, `ExitPlanModeRequest`, or `SetRunModeRequest` for plan content.

**B. A structured `Plan`/`PlanStep` entity — built, but wired only as a retrospective execution log, and its approve/reject endpoints are dead from the browser's perspective.**
- Proto: `proto/model_plane/v1/orchestration.proto`. `PlanState` enum (`:146-166`) already has `DRAFT(1)`, `PROPOSED(2)`, `APPROVED(3)`, `REJECTED(4)`, `EXECUTING(5)`, `COMPLETED(6)`, `FAILED(7)`, `SUPERSEDED(8)`, `ARCHIVED(9)`. `PlanStepState` (`:170-183`): `PENDING/RUNNING/DONE/SKIPPED/FAILED`. `Plan` message (`:296-329`): `id, run_id, thread_id, author, state, summary, steps[], supersedes, metadata, created_at, updated_at`. `PlanStep` message (`:264-293`): `id, title, operation, state, created_at, updated_at, detail`. RPCs: `ListPlans`, `GetPlan`, `TransitionPlan` (`:24`), and a `PlanTransitioned` event (`:947-952`).
- Owner (durable store): `Model Plane/rust/services/session-core/src/orchestration_store.rs`. `create_plan` (`:29-52`) always inserts `status='draft'`; `append_plan_step` (`:96+`) appends one step at a time with auto ordinal.
- **How it's actually populated today:** a plan row is auto-created at run start with the run's `goal` as `summary` and **zero steps**, then immediately flipped to `executing` — `session-core/src/grpc.rs:2741-2755` (RunStarted path) and `session-core/src/terminalization.rs:730-748` (managed-run-start path, gated on `persisted.create_plan`). Steps are appended reactively, one per **completed tool call** (`operation: "tool_execution"`), inside `CompleteStep`'s handler — `session-core/src/grpc.rs:3021` (`complete_step_inner`) / `:3126` (`append_plan_step` call) with the state-mapping comment at `:3095-3120`. So `PLAN_STATE_PROPOSED` is **never reached** by any code path found, and `PLAN_STATE_REJECTED`/`SUPERSEDED` likewise.
- model-gateway read surface: `list_plans` (`http_routes.rs:836-850`), `get_plan` (`:857-872`), route table `:241-283` (`GET /v1/orchestration/runs/:run_id/plans`, `GET /v1/orchestration/plans/:plan_id`). Serializers `plan_value`/`plan_step_value` at `:5959` / `:5972`.
- model-gateway **mutation** surface, present but unused by the browser: `TransitionPlanBody{target_state, reason}` (`:1350-1354`), `approve_plan` (`:1356-1379`, distinct function from the rung-grant `plan_approval` at `:6870` — same English phrase, two unrelated handlers, a real naming collision), `reject_plan` (`:1383-1404`). Routes: `POST /v1/orchestration/plans/:plan_id/approve`, `POST /v1/orchestration/plans/:plan_id/reject` (route table `:270-273`).
- Frontend read client: `Plan`/`PlanStep`/`Todo` types and `normalizePlan` in `apps/Frontend Plane/verevonv3/src/shared/api/orchestration-client.ts:149-222`; `listPlans` (`:256-263`). **Confirmed by grep: nothing in `src/` calls the orchestration `.../plans/:id/approve` or `/reject` endpoints** — they are reachable only by hand-built HTTP calls today.
- Frontend render (read-only): the "Arbeidsplan" card in the run console panel, `apps/Frontend Plane/verevonv3/src/features/chat/components/ChatPanels.tsx:1080-1125` (steps) and `:1131-1146` (todos), hydrated by `Promise.allSettled([listPlans, listTodos, ...])` at `:948-957`.

**C. A generic HITL `Approval` with `ApprovalKind::APPROVAL_KIND_PLAN` (`orchestration.proto:186-190`).** Nothing found that creates an approval of this kind for plan mode; the plan-mode grant bypasses `CreateApproval` entirely and goes straight through `PlanModeStore`. This is a third, unconnected concept sharing the word "plan" — a trap for whoever implements this next without reading the proto comments.

**Todo tracking**, which the task description also names, is real and structurally sound (`Todo{id, state, title, description, priority, blockedBy}`, `TodoState` `PENDING/IN_PROGRESS/BLOCKED/COMPLETED/CANCELLED`) but is populated by the model calling actual todo-list tools mid-run (out of scope here) and rendered read-only at `ChatPanels.tsx:1131-1146`. It is not part of the pre-approval plan-editing gap and does not need to change for this item.

**Conclusion of the audit:** there is no structured, editable, pre-execution plan anywhere in the stack. Mechanism A is correctly wired but carries no content. Mechanism B has exactly the right shape (ordered steps, states, revision-via-`supersedes`) but is used for something else entirely (a post-hoc execution log) and its approve/reject transitions are unreachable. The correct design reuses B's schema for the plan's *content* and keeps A unchanged for the *authority grant*, joining them at the one moment both are decided: the approval click.

## 2. Design and exact change list

### 2.1 Model emits a structured plan, not just prose

Per this codebase's own stated principle (`chat-nodes/derive.ts`, the comment on why follow-up chips were deliberately **not** derived from free text: "inferring one from free text in the browser would be the fabrication this codebase forbids"), the edit surface must not be built by parsing the model's markdown numbered list client-side. The model must emit steps as data.

**New control tool**, same family and dispatch pattern as `subagent.task` (`Model Plane/rust/services/execution-core/src/runtime_loop/agent.rs:3172-3186` for the definition pattern, dispatch check at `:2090` for the `is_subagent_tool` prefix match):

- `plan.propose` — `pb::ToolDefinition` added to the same catalog list in `runtime_loop/agent.rs` (near the `subagent.task` entries, ~`:3186`).
  - Parameters: `{"summary": string, "steps": [{"title": string, "operation"?: string}], "supersedes"?: string}`.
  - Only meaningful/offered when `req.plan_mode == true`; add it to the tool catalog gated the same way plan mode already gates risky tools (`agent.rs:1320-1352`), i.e. offered unconditionally but the description states it is for plan-mode runs. Reuse `is_subagent_tool`-style classifier: add `crate::plan::is_plan_tool(name)` (new `execution-core/src/plan.rs`, mirroring `execution-core/src/subagent/mod.rs`'s `TOOL_PREFIX`/`is_subagent_tool` shape at `subagent/mod.rs:18-96`).
  - Dispatch: a new arm alongside the subagent dispatch check (`agent.rs:2090`) that, instead of spawning a subagent, calls a new `orchestration_client.propose_plan(...)` (new gRPC method, §2.2) and returns the created `plan_id`/state to the model as the tool result (so the model's own transcript records it proposed a plan, consistent with how `subagent.task` returns its conclusion).
  - This tool is **read-only from the run's own permission-ladder point of view** — it does not act, so it is never in `permission::is_risky_call`/`is_restricted_context_write`, matching `list_subagent_results`'s treatment.

- **New SSE event `plan_proposed`**, so the browser sees the steps live (same wiring pattern as `follow_ups`): a new `case 'plan_proposed'` in `dispatchFrame`, `apps/Frontend Plane/verevonv3/src/shared/api/chat-client.ts` (pattern at `:1483-1489`), payload `{ plan_id, summary, steps: [{id, title, operation?}], request_id }`, new handler `onPlanProposed?: (event: ChatPlanProposedEvent) => void` on `ChatStreamHandlers` (next to `onFollowUps` at `:582`). Emitted by model-gateway's SSE loop (`model-gateway/src/sse.rs`) when the `plan.propose` tool call round completes, mirroring how `follow_ups` is emitted after the model's answer.

### 2.2 Orchestration RPCs: light up `PROPOSED`, add step mutation

`proto/model_plane/v1/orchestration.proto`:
- New RPC `ProposePlan(ProposePlanRequest) returns (ProposePlanResponse)`: `{thread_id, run_id, org_id, user_id, author, summary, steps: [{title, operation}], supersedes?}` → creates the plan directly in `PLAN_STATE_PROPOSED` with real steps (unlike today's `create_plan`, which always starts `draft` with zero steps — `session-core/src/orchestration_store.rs:29-52`). Implementation: new `orchestration_store::create_proposed_plan` that inserts the plan row **and** its `plan_steps` rows in one transaction (reusing `append_plan_step`, `orchestration_store.rs:96+`, in a loop), then sets `status='proposed'`.
- Extend `TransitionPlanRequest` (`orchestration.proto:470-482`) with `repeated PlanStepEdit edited_steps = 5;` where `PlanStepEdit{string step_id (empty = new), string title, string operation, bool removed}` — carries the user's reorder/remove/add/edit-text result. The array's *order* is the new step order (removed steps included with `removed=true` so ordinals stay auditable and the removal itself is a chain-visible fact, not a silent drop).
- `session-core`'s `TransitionPlan` handler (implementor of `orchestration.proto:24`, in `session-core/src/orchestration_grpc.rs:1521` area) applies `edited_steps` before the state transition: diff against the existing `plan_steps` rows, apply title/operation edits, insert new rows, mark removed ones `SKIPPED` (never hard-delete — `plan_steps` is an audit trail; a "removed" step is a decided-against step, not an erased one), and reorder ordinals to match the array position. Only legal `target_state` transitions defined by `PlanState`'s natural flow are accepted: `PROPOSED → APPROVED` (with edits) or `PROPOSED → REJECTED` (no edits needed). Attempting to edit a plan not in `PROPOSED` is refused — this makes "edit window" and "plan state" the same fact, so the UI's `Show when={!props.grantedRung}` pattern (already used for gating `PlanApprovalControl`, `ChatMessages.tsx:2058`) generalizes naturally to "editable while proposed."

### 2.3 BFF and model-gateway: one approval call, two effects

Extend the **existing** `/v1/runs/{run_id}/plan-approval` request/response rather than adding a second endpoint — this is the one place the browser already asks "how much may this run do, and why," and the edited plan is inseparable from that decision (an edited plan *is* what the rung is being granted to run).

- `PlanApprovalRequest` (`model-gateway/src/http_routes.rs:6846-6851`) gains: `plan_id: String` (required — the proposed plan being approved/rejected), `edited_steps: Vec<PlanStepEditWire>` (mirrors §2.2's wire shape), `decision: "approve" | "reject"` (default `"approve"` for backward compatibility with today's callers, though today's callers never had a plan to reject).
- Handler `plan_approval` (`http_routes.rs:6870-6965`) sequence, extended:
  1. (unchanged) resolve `thread_id`, validate the rung escalation.
  2. **New:** call `orchestration_client.transition_plan(TransitionPlanRequest{plan_id, target_state: APPROVED (or REJECTED), actor: claims.user_id, reason: justification, edited_steps})`. Refuse the whole request (400) if this fails — an autonomy grant with no corresponding approved plan is exactly the "rubber stamp" this control exists to prevent.
  3. (unchanged) `coordinator::handle_exit_plan_mode` — **but** add `"plan_id": plan_id` to the published `RUN_PLAN_MODE_EXITED` envelope payload (`coordinator.rs`, the `serde_json::json!({...})` inside `handle_exit_plan_mode`) so the durable, correlation-id-bearing audit event names which plan (and therefore, via `GetPlan`, which exact edited steps) the grant was for. This is the receipt/lineage binding the task asks about: the `Plan` row (with its edited `PlanStep`s, each carrying `created_at`/`updated_at` and a full transition history via `PlanTransitioned` events, `orchestration.proto:947-952`) is the durable record; `RUN_PLAN_MODE_EXITED.plan_id` is the pointer from the rung grant to it; `GetRunProofBundle` (`proof_bundle.proto:30-49`) is extended with a `plan_id` field on `ApprovalProof` (or a new `PlanApprovalProof` message) so the run's own proof bundle can resolve "what was approved" without a second lookup by the reader.
  4. (unchanged) `session_client.set_run_mode`.
  5. Response gains `plan: {id, state, steps}` (the finalized, post-edit plan) alongside today's `granted_rung`/`was_in_plan_mode`/`persisted`.
- Reject path: `decision: "reject"` skips the rung-escalation/`set_run_mode` steps entirely (there is nothing to grant) and only calls `transition_plan(... REJECTED)`. The BFF route stays the single `POST /api/v1/agents/runs/{run_id}/plan-approval` (`apps/gateway/src/domains/agents_runs.rs:41-46`, `:221-238` — body forwarded unchanged, per its existing doc comment "The body is passed through unchanged").

### 2.4 Agent loop honours the edited plan on the executing run

The rung already reaches the next run thread-scoped (`sse.rs:1058-1071`, `coordinator.rs:176-194`). Add, in the same place the autonomy rung is resolved for a non-plan-mode run (`sse.rs:1058-1071`): when `state.plan_mode.granted_rung(org_id, thread_id)` returns `Some`, also fetch the thread's latest `APPROVED` plan (new `orchestration_client.get_latest_approved_plan(thread_id)`, or reuse `list_plans` + filter client-side in model-gateway) and, if present and not yet consumed by a run, inject its `summary` + ordered `steps` as a system-role context block prepended to the `RunAgentRequest.messages` — e.g. `"Approved plan (edited by the user; treat deviating from it as something to explain, not something to hide):\n1. ...\n2. ..."`. This is necessary because the model's original prose plan is immutable (the effectful-turn lock: `src/shared/chat/effect-class.ts:1-15` and its stated invariant that a turn "can't be silently edited or regenerated" — the edited plan must not be smuggled in by rewriting the original assistant message). Mark the plan `EXECUTING` at this point (reusing `orchestration_store::update_plan_status`, already used for exactly this transition at `session-core/src/grpc.rs` and `terminalization.rs:735-745`) so a stale/duplicate injection can't happen on a later run of the same thread.

### 2.5 Frontend: the edit surface

- `chat-nodes/types.ts:119` node shape becomes `{ kind: 'plan-approval'; planId?: string; summary?: string; steps?: PlanStep[]; grantedRung?: AutonomyRung; pending: boolean; error?: string }`. `chat-nodes/derive.ts:156-163`'s gate changes from "only a finished plan-mode turn" to "a finished plan-mode turn **that has a proposed plan**" — read the plan off the turn (new `ChatTurn.proposedPlan?: {planId, summary, steps}` field, populated by the new `onPlanProposed` SSE handler in `use-chat-controller.ts`, alongside the existing `onFollowUps` wiring).
- `PlanApprovalControl` (`ChatMessages.tsx:2038`) gains an editable step list above the existing rung/justification controls:
  - Local signal `const [steps, setSteps] = createSignal<EditableStep[]>(props.steps ?? [])`, seeded once from `props.steps` (not resynced on every render, so a mid-edit re-stream doesn't clobber the user's edits — same defensive pattern as the existing `reason` signal in the same component).
  - Per-step row: text edit (contenteditable or a plain `<input>`, matching this file's existing `<textarea>` styling convention), move-up/move-down buttons (no drag-and-drop library exists anywhere in `src/features/chat` or `src/features/dashboard` today — confirmed by grep — so up/down buttons keep this dependency-free and keyboard-operable, consistent with the Wave-1 reviewer fix that made the row-menu trigger keyboard-focusable), a remove (✕) button, and an "Add step" button appending a blank row.
  - Approve now calls `props.onApprove(rung, justification, steps())`; a parallel `props.onReject?.(reason)` covers the reject path.
  - `onApprovePlan` signature (`chat-nodes/types.ts:134`, `ChatMessages.tsx:152` and `:364`) gains the `steps` argument; `approveTurnPlan` (`use-chat-controller.ts:1992-2032`) forwards it into `approvePlan(runId, rung, justification, planId, steps)`.
- `chat-client.ts:1676-1697` `approvePlan` gains `planId` and `steps` parameters, serialized as `{granted_rung, justification, plan_id, edited_steps}`; response parsing adds `plan` alongside the existing three fields.
- `orchestration-client.ts` gains `proposePlan`/no client call needed for propose (server-driven via SSE) but gains a typed `PlanStepEdit` and reuses the existing `normalizePlan`/`PlanStep` types (`:149-186`) so the run-console panel (`ChatPanels.tsx:1080-1125`) and the new inline editor share one shape instead of drifting.

### 2.6 Norwegian-first UI

All new copy follows this file's existing `i18n.tr('norsk', 'English')` convention (seen throughout `ChatMessages.tsx`, e.g. `:2058` `i18n.tr('Godkjenn planen', 'Approve the plan')`): "Legg til steg" (add step), "Fjern" (remove), "Flytt opp/ned" (move up/down), "Avvis planen" (reject the plan).

## 4. Rollout

- **Proto change** (`proto/model_plane/v1/orchestration.proto`, `sessions.proto` untouched) requires regenerating the shared `mp_contracts`/generated-Rust bindings consumed by `model-gateway`, `execution-core`, and `session-core` — a workspace-wide `cargo` regen step, not a per-service edit. Per project memory, **build via the launcher**, not hand-built `docker compose build` (`project-build-images-via-launcher.md`): a hand-built compose misses the Control Plane env chain.
- **Services needing a rebuild:** `session-core` (new store functions, extended `TransitionPlan` handler, new `ProposePlan` RPC implementor), `model-gateway` (extended `PlanApprovalRequest`/response, new `propose_plan`/`get_latest_approved_plan` client calls, extended `RUN_PLAN_MODE_EXITED` payload, extended `RunAgentRequest` construction in `sse.rs`), `execution-core` (new `plan.propose` tool + dispatch, new context-injection of the approved plan). The frontend container per the Wave-1 rollout note only picks up source changes on a container **restart** (bind-mounted Vite dev with watching disabled) — restart it after any frontend change here, same as Wave 1.
- **No feature flag strictly required** for the backend (the new fields are additive and optional; `decision` defaults to `"approve"`, `edited_steps`/`plan_id` are additive on the wire), but ship the frontend edit UI behind the same kind of low-risk gate Wave 1 used (a rendering condition on `proposedPlan` being present) so a stale frontend talking to a rebuilt backend, or vice versa, degrades to today's rung-only control rather than breaking.
- **Migration:** none required for existing `plans`/`plan_steps` tables (schema already supports `PROPOSED`; no column additions needed beyond what `edited_steps`-driven writes already touch — title/operation/state/ordinal all exist). If a `plan_id` is added to `RunProofBundle`/`ApprovalProof` (proof_bundle.proto), that is a proto-only, additive change.

## 5. Risks and edge cases

- **Two "plan approve" functions collide by name** (`http_routes.rs:1356` orchestration `approve_plan`, `:6870` rung-grant `plan_approval`). Whoever implements this must not accidentally wire the browser to the wrong one; recommend renaming the orchestration one (e.g. `transition_plan_approve`) as part of this change to remove the trap.
- **Dead code becomes load-bearing:** `/v1/orchestration/plans/:plan_id/approve`/`reject` are currently unreachable from the browser and therefore effectively untested against real traffic. This design makes them (via the extended rung-grant handler calling `transition_plan` internally, not by exposing them directly) load-bearing for the first time — treat their existing inline tests as a starting point, not sufficient coverage.
- **Race: user edits while the model is still streaming its plan tool call's result, or the plan is superseded.** `plan.propose` could in principle be called more than once in one plan-mode turn (model changes its mind mid-response). Decide: does a second `plan.propose` call supersede the first (`Plan.supersedes`, already modeled) and does the UI swap to the newer one, warning if the user had already started editing the old one? Recommend: last-proposed-wins, `supersedes` chain recorded, client shows a "the agent revised its plan" notice if the user had unsaved edits (a genuinely new UI state, no existing precedent to copy).
- **Empty plan after edits.** A user who removes every step and clicks Approve is granting a rung to a run with nothing to do. Disable Approve at zero remaining (non-removed) steps, mirroring the existing "Approve disabled until justification is long enough" pattern (`ChatMessages.tsx:2038`, `tooShort()`).
- **ZDR runs.** `http_routes.rs` already refuses durable mutations for ZDR credentials elsewhere (`zdr_durable_mutation_forbidden`, seen just above the `TodosQuery` struct, `:790-800`). Plan proposal/approval writes a durable `plans`/`plan_steps` row — confirm (not verified in this pass, since it required executing code, which was out of scope for a read-only audit) that `plan.propose`'s new gRPC path is refused identically on a ZDR run, the same way `save_memory` already is (`agent.rs:3161-3168`'s tool description explicitly states "Unavailable on Zero-Data-Retention runs" as the existing convention to follow).
- **Cross-Space / foreign-origin threads.** `approveTurnPlan` already guards `isForeignOriginThread(state.threadId)` (`use-chat-controller.ts:1994`) — the same guard must cover the new edit-and-resubmit path; a continuity/replay view of another workspace's transcript must not be able to edit or approve its plan.
- **Effectful-turn lock interaction.** Confirm the plan-approval action itself is not classified as retroactively "editing" the assistant's own prior turn (`effect-class.ts`) — it should not be, since the edited plan is new data on a new record (`Plan`/`PlanStep`), not a mutation of `ChatTurn.content`, but this boundary is exactly where a careless implementation could accidentally violate the lock's stated invariant.
- **In-memory rung store is not durable across a gateway restart** (`PlanModeStore.grants`, `coordinator.rs:85` doc comment already states this as an accepted limitation). The newly durable `Plan` row (state `APPROVED`, in Postgres via session-core) is NOT subject to this limitation — worth stating explicitly to whoever reviews this, since it means the plan's content survives a gateway restart even though the rung grant currently does not; that asymmetry could confuse a debugging session later.

## 6. Genuine owner decisions

1. **Revision behavior when the model re-proposes a plan mid-turn** (superseding vs. append vs. refuse a second `plan.propose` call) — changes the state machine, not just the UI.
2. **Whether a rejected plan can be revised and resubmitted in the same turn**, or whether rejection ends the turn and the user must ask again in a fresh message. `PLAN_STATE_REJECTED` has no defined "revise" transition in the proto today (`orchestration.proto:146-166`); adding one is a design choice, not an implementation detail.
3. **Step granularity contract with the model** — should `plan.propose`'s steps be tied to concrete tool operations (`operation` field populated, steps become checkable against what actually ran later) or free-text intent lines (`operation` empty, purely descriptive)? This changes whether the executing run's steps can later be cross-checked against the retrospective `tool_execution` plan-step log (mechanism B in §1) for a "did it do what it said" comparison — a real capability if `operation` is populated, meaningless if not.

Everything else in this item (schema reuse, wire shapes, UI controls, event names) follows mechanically from the existing conventions cited above and does not need an owner call before an implementer starts.
