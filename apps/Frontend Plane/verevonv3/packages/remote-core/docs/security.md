# Security

## Nonce reuse in RustDesk's own peer-to-peer encryption (confirmed, not hypothetical)

This is significant enough to lead with, ahead of the general baseline requirements below.

RustDesk's own peer-to-peer session encryption (`hbb_common/src/tcp.rs`'s `Encrypt` struct — the layer that protects remote-control/video/input content between the browser and the Verevon Agent, independent of transport) has a **confirmed nonce-reuse weakness**, verified by reading the actual source directly (not inferred): both directions of a connection use the **same 32-byte secretbox key**, with **two independent `u64` counters that both start at 0** and increment by 1 per message, encoded as the low 8 bytes of an otherwise-zero 24-byte nonce — no role bit, no per-direction key derivation, nothing else distinguishing "client's Nth message" from "host's Nth message." That means, for every sequence number N that both sides reach in an active session (not just N=1 — this recurs for as long as the session runs), the client's Nth sent message and the host's Nth sent message use the identical (key, nonce) pair with different plaintext. For XSalsa20-Poly1305, that leaks the XOR of the two plaintexts to anyone observing both ciphertexts, and voids Poly1305's forgery-resistance guarantee for those messages.

**`@verevon/remote-core` replicates this exact mechanism** (`crypto/SessionCrypto.ts`'s `DirectionalCipher`/`SessionChannel`) rather than fixing it, because wire compatibility with an unmodified RustDesk-based Verevon Agent requires matching the real protocol byte-for-byte — deriving separate per-direction keys unilaterally on the browser side would simply desynchronize from what the host expects, breaking the session rather than securing it. This is a property of the protocol being reimplemented, not a defect introduced by this reimplementation.

**Why WSS to Support Plane does not fix this**: WSS protects the browser↔hbbs/hbbr transport hop only. The peer-to-peer secretbox layer described above is a *separate*, deliberately transport-independent layer, specifically meant to protect session content from a semi-trusted relay operator. It runs regardless of whether the underlying transport is raw TCP or WSS-tunneled WebSocket, and its weakness is unaffected by the transport choice.

**Practical exposure**: exploiting this requires an attacker positioned to observe *both* directions' ciphertext for the same connection — realistically, a compromised or malicious relay operator (a threat this layer exists specifically to defend against, and therefore fails to fully deliver on), or a network position downstream of the relay capable of correlating both flows. It is not exploitable by a passive observer of only the browser↔Support Plane WSS hop, since TLS already protects that leg independently. This should be treated as a real, disclosed limitation of the underlying protocol when evaluating Support Plane's threat model — not dismissed because `remote-core`'s own transport is TLS-protected.

**What Verevon can do about it**: nothing at the `remote-core` layer without breaking interoperability with real RustDesk-protocol hosts. If this residual risk is unacceptable for a given deployment, the mitigation has to happen at a different layer — e.g., running Support Plane's relay (`hbbr`) as infrastructure Verevon fully controls and trusts (already the plan — see `apps/Support Plane/README.md` — which at least removes the "malicious third-party relay operator" variant of this threat, leaving only "attacker who has compromised Verevon's own relay," a much higher bar), or by not treating this layer as sufficient defense-in-depth on its own and leaning more heavily on the WSS/TLS hop and short session lifetimes.

## Baseline requirements

- **TLS/WSS only in production.** hbbs/hbbr's native WebSocket listeners are plaintext (`rustdesk-protocol.md`); Support Plane must terminate TLS in front of ports 21118/21119 with a real reverse proxy before any browser session is allowed to reach them. `remote-core` should refuse to construct a `WebSocketTransport` against a plain `ws://` URL outside an explicit local-dev opt-in.
- **No remote password or session token in `localStorage`.** `ConnectOptions.auth.token` and any resolved `SessionAuthenticator` secret live only in memory for the duration of the connection attempt.
- **No session secret logged.** `RemoteError.metadata` is a closed, explicitly-typed bag (`string | number | boolean | undefined`) — there is no path for a raw password, token, key, or protocol payload to end up in it, and the injectable `Logger` interface has no default `console.*` implementation in production modules (enforced by an ESLint `no-console` rule on the package, not just a convention).
- **No protocol payload dumping in production.** Decrypted message contents never pass through `Logger` calls; only structural facts (`action.type`, error codes, state names) do.
- **Memory-clearing for sensitive temporary data** — best-effort only, and worth being explicit about the limit: JavaScript has no guaranteed secure-erase primitive (`Uint8Array` contents can be overwritten with zeros after use, but garbage-collected copies, JIT-retained values, and the underlying WASM heap for any future libsodium binding are outside this package's control). Session keys should be zeroed after use where the crypto library exposes a way to do so; this is defense-in-depth, not a guarantee.
- **Origin restrictions**: the Verevon SPA should pass an explicit `Origin`/`Referer` allowlist to whatever reverse proxy fronts Support Plane; `remote-core` itself has no way to enforce this from inside the browser and does not claim to.
- **Explicit remote consent**: out of scope for `remote-core` itself — the consent UI (the "small native Verevon support agent" the customer sees, per the top-level product vision) lives on the Verevon Agent running on the customer's machine, not in this browser library. `remote-core` only starts sending input/reading frames once the protocol layer reports the corresponding `RemotePermission` as granted.
- **Per-session permissions, enforced centrally**: every action goes through `ActionExecutor.execute()`, which checks the required `RemotePermission` (`requiredPermissionFor()`, `types/internal.ts`) *before* any middleware or protocol call runs — this cannot be bypassed by a middleware registered later, and it re-checks on every call rather than caching a single connect-time grant, because RustDesk pushes permission changes as discrete, live messages during an active session (`rustdesk-protocol.md`).
- **Action attribution**: every `RemoteAction` carries a mandatory `actor: "human" | "ai" | "system"`. There is no code path that executes an action without an actor.
- **Disconnect/revoke**: `session.disconnect()` tears down all subscriptions and closes the underlying protocol connection; a server-pushed `permission-change` that removes a permission takes effect on the *next* action attempt (permissions are re-checked per-call, not cached).

## Threat model

| Threat | Description | Mitigation in `remote-core` | Residual risk |
|---|---|---|---|
| **Malicious support agent** | A human operator with legitimate session access tries to exceed what was granted (e.g. read clipboard without `clipboard.read`, act after being told to stop). | Every action is permission-checked server-reported-state, not client-asserted; `ActionExecutor` enforces this centrally and cannot be bypassed by UI code that "forgets" to check. Actions are attributed (`actor`) for audit. | `remote-core` cannot enforce policies that require server-side context (e.g. "this agent has never handled this customer before") — that belongs in Verevon's backend, upstream of `remote-core`. |
| **Malicious remote machine** | A compromised or hostile "remote" endpoint sends malformed or oversized protocol messages to crash or exploit the browser tab. | The proto3 decoder never trusts a declared length blindly for control flow beyond slicing (`ProtoReader.readLengthDelimited` bounds to the actual buffer); unknown message types decode to a typed `unknown` result instead of throwing or attempting to interpret unfamiliar bytes as a known shape. | A hand-written parser is a larger attack surface than a battle-tested library; this is why it has dedicated round-trip and large-payload tests (`tests/protocol/rustdesk/wire/wire.test.ts`) and should get fuzz testing before production (not yet done in this version). |
| **MITM** | An attacker on the network path intercepts or alters traffic. | RustDesk's own end-to-end handshake (X25519 + XSalsa20-Poly1305, `rustdesk-protocol.md`) protects the peer-to-peer channel independently of transport security, so even a relay operator can't read session content *by default* — see the nonce-reuse caveat above for where that protection is weaker than intended. WSS protects the browser-to-server hop. | `remote-core` must actually verify the peer's signed identity key during the handshake (reject an unsigned or wrongly-signed `SignedId`) once the full handshake orchestration is wired up (`SessionCrypto`'s box/sign primitives exist and are tested; the orchestrating `RustDeskProtocol` does not yet — see `architecture.md`, Status) — a handshake that silently "falls back to plaintext P2P" when no signed key is available (a real native-client behavior noted in `rustdesk-protocol.md`) must **not** be the default for a production Verevon session; this should fail closed instead. Separately, the confirmed nonce-reuse weakness above is a residual risk this library cannot fix unilaterally without breaking interoperability. |
| **Stolen session token** | A Verevon-issued short-lived token is exfiltrated and replayed by someone else. | Tokens are used exactly like a RustDesk one-time password — never persisted to `localStorage`, held only in memory for the connect attempt. Short lifetime is a property of what Verevon's backend issues, not of this library. | `remote-core` has no built-in token-binding to a browser/device fingerprint; if that's needed, it belongs in the token issuance/verification contract between Verevon's backend and the Verevon Agent, not in this client library. |
| **Replay attack** | A captured login exchange is replayed to authenticate again. | The wire password is `SHA256(SHA256(secret ‖ salt) ‖ challenge)`, and `challenge` is fresh per connection attempt (server-generated) — a captured `wire` value cannot be replayed against a new `challenge`. | The freshness of `challenge` is a server-side guarantee (`rustdesk-protocol.md` notes this relies on `rand::thread_rng()` on the host side) that `remote-core` cannot itself verify beyond trusting the value differs each time. |
| **Cross-site attack** | A malicious page tries to drive a Verevon support session via `postMessage`, iframe embedding, or similar. | `remote-core` exposes no ambient global state and no `window.postMessage` listener of its own — every entry point requires an explicit, direct function call from the embedding page's own JavaScript. | Enforcing *which* pages may embed the Verevon SPA at all is a CSP/frame-ancestors concern for the SPA's own deployment, not something this library can control. |
| **Session fixation** | An attacker pre-establishes or pre-selects a session identifier that the victim then unknowingly uses. | Session IDs (`RemoteSession.id`) are generated locally via `crypto.randomUUID()` at connect time, never accepted as caller input. | If Verevon's backend later introduces its own durable session identifier that maps onto a `remote-core` session, that mapping's integrity is that system's responsibility, not this library's. |
| **AI performing an unauthorized action** | An AI agent (via `session.actions.execute({..., actor: "ai"})`) attempts an action beyond what was approved. | The action-middleware chain (`ActionMiddleware`) is the designed seam for approval gating — `ActionExecutor` runs registered middleware *before* the underlying protocol call, and any middleware can short-circuit with `{ ok: false }` without the action ever reaching the remote machine. The base permission check applies identically regardless of `actor`. | `remote-core` ships the *mechanism*, not a specific approval policy — Verevon's product code must actually register a middleware that gates `actor === "ai"` actions (per the top-level spec's own example); an integration that forgets to register one gets no AI-specific gating beyond the shared permission model. |
| **Clipboard exfiltration** | The remote machine pushes sensitive clipboard content, or a local clipboard read is used to exfiltrate data from the browser session. | Clipboard sync requires the `clipboard.read`/`clipboard.write` permission explicitly, checked per-call like every other action; nothing auto-syncs the clipboard without an explicit `ClipboardController.write()` call or an explicit `clipboard` event subscription. | Once content crosses into the embedding page's own clipboard-handling code, this library can no longer track where it goes — that's an application-level (Verevon UI) concern. |
| **Screen-data exfiltration** | Frames or AI-sampled screenshots leave the session in an uncontrolled way. | Frames are never sent to AI automatically — `session.ai.createObserver({ maxFramesPerSecond })` is opt-in, explicitly rate-limited (`FrameSampler`), and can be paused/closed; a bare `session.on('frame', ...)` subscriber only receives what it explicitly asked for. | What the embedding application *does* with a frame once delivered (e.g., actually calling an external AI API) is outside this library's control by design — `remote-core` controls the tap, not the destination. |

## Errors and safe metadata

Every error surfaced to Verevon's UI is a typed subclass of `RemoteError` (`RemoteConnectionError`, `AuthenticationError`, `PermissionDeniedError`, `ProtocolError`, `TransportError`, `CodecError`, `EncryptionError`, `RemoteDisconnectedError`) carrying a closed `metadata` bag. None of these types have a field capable of holding a password, key, or token — `metadata` values are constrained to `string | number | boolean | undefined` and populated only with structural facts (URLs, state names, field numbers) by the code that throws them, never with raw protocol payloads.

## Known gaps in this version

- **The nonce-reuse weakness described above is inherent to the protocol being reimplemented, not fixable here without breaking wire compatibility** — see the dedicated section at the top of this document. This is the single most important thing to communicate accurately to anyone reviewing this library's security posture; do not let the "we use real libsodium crypto" framing elsewhere in this document imply the handshake is flawless.
- **Peer identity verification is not yet wired into a working end-to-end handshake** — `SessionCrypto`'s box/sign/secretbox primitives exist and are tested in isolation (`tests/crypto/SessionCrypto.test.ts`), but the orchestrating code that actually verifies a peer's signed key during a real connection attempt (`RustDeskProtocol`) does not exist yet — see `architecture.md`, Status. Until it does, this library provides no working MITM protection in practice, isolated primitives notwithstanding.
- **No fuzz testing yet** on the proto3 decoder (`ProtoReader`) against adversarial input — only structured round-trip tests exist today.
- **2FA is detected but not completed** — a host requiring 2FA will surface as an `AuthenticationError`, not a working second-factor prompt.
