Reviewed 2026-10-05. Reference checkout: `C:/dev/references/polar`, shallow clone of `https://github.com/polarsource/polar`, commit `c063d7a9ad32ddae22a41cd33e47396cb78df969` (2026-10-03). Polar dependencies were not installed and its tests were read, not executed. No Polar code was copied or payment provider changed.

## Accepted product scope

The user explicitly includes recurring allowances, billing-cycle resets, credit grants, carry-over, expiry, overages, subscription changes and the wider billing/customer portal lifecycle. Today's reporting reset is a one-time clean starting point; it does not remove these capabilities from scope. Implementation status must remain separate from this accepted target.

Maintain three distinct operations:

1. **Reporting baseline:** choose the visible tracking start; retain ledger history. Does not change provider allowance, credits, invoices or money owed.
2. **Allowance renewal:** settle the previous usage period, carry forward eligible unused credits under the plan policy, grant the new allowance and advance the period once.
3. **Financial adjustment:** an authorized, auditable credit/refund/correction referencing the original entry. Never hide or delete an obligation by moving a reporting baseline.

## Late usage and reset boundaries

Polar's [customer meter test](https://github.com/polarsource/polar/blob/c063d7a9ad32ddae22a41cd33e47396cb78df969/server/tests/customer_meter/test_service.py), `test_historical_usage_ingested_after_reset_timestamp_is_included`, expects usage that occurred before a reset but arrived afterward to count. The service uses ingestion time for the reset window and event time for settlement cutoffs.

Verevon must preserve occurrence time, ingestion time and billing-period assignment explicitly. The existing reporting baseline is not a settlement policy. Late usage must be assigned or corrected under an explicit rule, without being dropped by a clean-start dashboard filter or charged in two periods. Unknown legacy billing classifications must not become invented metered charges.

The [meter cycle lifecycle test](https://github.com/polarsource/polar/blob/c063d7a9ad32ddae22a41cd33e47396cb78df969/server/tests/e2e/lifecycle/test_meter_cycle.py) exercises a yearly subscription with a monthly meter cycle using simulated Stripe and a controlled clock. This is a useful test pattern, not evidence that our lifecycle currently works.

## Ownership and integration

- **Model / Cost Core:** durable provider invocation usage, token counts, billing basis, provider estimates and Azure reconciliation evidence. Retain authenticated organization/user attribution through retries. Existing org-scoped idempotency is the starting point.
- **Control / Billing Core:** plans, meter/price versions, credit grants and consumption, rollover/expiry, period transitions, invoice adjustments, subscription/seat/trial/discount policy and payment-provider adapters. Extend the existing service and its idempotent account updates.
- **Application / Insight Core:** authorized reporting projections and freshness/coverage. Financial authority stays with Billing Core; provider usage authority stays with Cost Core.
- **Frontend / gateway:** action contracts and authenticated APIs for balances, period dates, remaining allowance, invoices and permitted account actions. Personal reports pin the actor; organization reports require the appropriate role. Never trust browser-supplied tenant headers.

Integration uses contracts/events, never direct database access across planes. Usage events need attribution and accounting metadata, not prompt/response content. ChatGPT's provider allowance remains a separate account-scoped snapshot and cannot be reset or apportioned as a tenant credit wallet merely from token totals.

## Implementation sequence and acceptance criteria

1. **Canonical usage delivery:** reconcile Cost-to-Billing delivery, stable IDs and tenant/user scope. Test duplicate, delayed and out-of-order events, unknown billing basis, missing tokens, restart/replay and cross-tenant denial.
2. **Credit ledger and policy:** add or extend grant, consume, expiry, rollover and reversal entries with exact units, stable operation keys and plan versions. Test concurrent consumption, duplicate grants, expiry boundaries, capped carry-over and adjustment lineage. Define whether units are tokens, requests or money; never mix them.
3. **Period state machine:** persist settlement, rollover, new grant and period advance with recoverable delivery. Test zero-usage renewal, monthly allowances on annual plans, leap/month-end boundaries, crashes between stages, double scheduler delivery and multiple missed periods. Plan configuration must explicitly specify rollover cap/expiry, consumption order and overage behavior; do not invent monetary defaults.
4. **Full subscription and portal lifecycle:** plan/seat changes, trials, discounts, cancellation/reactivation, invoices, payment methods, refunds, dunning and entitlement updates through configured providers. Test previews against resulting invoices, webhook duplication/reordering, failed payments and reconciliation. Checkout/tax/payout execution remains provider-backed; borrowing application code does not itself provide merchant-of-record operations.
5. **Insights and customer experience:** show used/included/carried/purchased/remaining balances, upcoming renewal/expiry, usage breakdowns and invoice links. Keep operational diagnostics in authorized support views; show concise user-actionable states without falsely calling missing data complete. Verify personal/org isolation, scope changes, auto-refresh, exports and exact reconciliation with backend ledgers.

This review itself does not implement or certify those five workstreams. The existing usage analytics and clean-start baseline are documented in [polar-inspired-usage.md](polar-inspired-usage.md). No additional production reset, charge, deployment or Git push was performed as part of this review.

Subsequent implementation on 2026-10-05 adds durable Cost-to-Billing delivery, integer allowances, recurring renewal/carry-over/expiry, scheduled policy revisions and an organization-only Insights view.
