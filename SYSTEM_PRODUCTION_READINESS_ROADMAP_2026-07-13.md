## How to read severities

- **P0 — release gate.** The system does not function correctly or safely for enterprise until these clear. Fix before *any* production deploy.
- **P1 — enterprise blocker.** Correctness, durability, security, or isolation gaps that will cause data loss, outages, or breaches under real multi-tenant load. Fix before onboarding external tenants.
- **P2 — hardening.** Reliability/perf/maintainability gaps that bite at scale or during incidents. Fix in the first hardening cycle.
- **P3 — polish.** Dead code, minor drift, observability nits, test-coverage gaps. Fix opportunistically / track as tech-debt.

## Phase 0 — P0 release gates (do first, in order)

1. **Restore Model Plane inference before redeploying MP.** Split the secure-MVP hardening from the server removal: re-serve inference-core's transport behind signed-audience auth, **or** migrate the model-gateway + execution-core + Data-Plane embedding/retrieval clients off the deleted `:9092` gRPC listener. This is a cross-plane cascade (chat + ingest embedding + query embedding), so treat DP-v2 retrieval as a co-dependent of the fix. *(A-Model P0, B-contract P0)*
2. **Ship the Bring shipping fix.** Commit the working-tree fix (`bring.go`/`wire.go`/`bring_test.go`), then rebuild shipping-core with `--no-cache` to bust the stale `go-build` cache layer. Requires host headroom from step 3. *(A-Ingestion P0)*
3. **Reclaim host capacity and remove the single-point-of-failure.** Prune ~16 GiB, relocate the Docker VM disk off the 99%-full host volume, cap the three uncapped stacks (Model Plane, zammad, DP-v2 app tier), and add host disk/RAM alerting. Do this *before* any rebuild in steps 1–2. *(B-host P0, B-resource-limits P1)*

## Phase 1 — P1 enterprise blockers (before external tenants)

Grouped by the systemic themes from the status doc; see Section A/B below for each item's evidence.

- **Messaging durability.** Migrate Control-Plane consumers (4/4) and the GDPR-erasure + session-cache-invalidation subscribers from ephemeral core-NATS to durable JetStream with backfill; make the DP indexing family (`index/embedding/graph-engine`) and autocomplete-core **nak on transient errors** with a DLQ; add supervised reconnect/backoff loops; bound the Model-Plane `natsx` dedup map. Fix the org→user membership projection (emit the member event on the reconcile path) as the first concrete instance.
- **Secret scoping.** Complete the per-caller token split for org-core + billing-core; stop sharing one `INTERNAL_API_KEY` across three planes; segment the Azure/Anthropic/Google keys per plane; move HS256 domains to asymmetric verification.
- **Close unauth/IDOR surfaces.** cost-core (auth + fail-*closed* budget), bridge-core, quarry-edge dev-bypass guard, `graph_preview` `org_id`, finspo-core org derivation, and the composer HITL gate off Plan mode.
- **Data-integrity / trust.** Stop information-core fabricating traffic metrics; gate mock carriers out of live quotes + AI recommendation.
- **Tenancy isolation.** Per-service DB roles + schema/RLS separation in the Application Plane (GDPR data segregation).
- **ZDR propagation.** Thread the ZDR flag through Data Plane + Ingestion content-persisting boundaries.
- **Consolidate the dangerous duplication.** One shared JWKS/auth module, one NATS client, one event publisher — so the reliability/security fixes above land once, not 7–8×.

## Phase 2 — P2 hardening (first hardening cycle)

Performance floor (benchmark harness + SLOs, DB pool sizing, parallelize retrieval fan-out, cache the visibility call, add gRPC timeouts/keepalive), healthcheck honesty (readiness must reflect worker/consumer liveness), observability (host + per-service resource alerting), and the remaining reliability/config-drift items in Section A/B.

## Phase 3 — P3 polish / tech-debt

Dead code, doc accuracy, minor config drift, test-coverage lifts on the untested seams (NATS handlers, membership projection, compaction). Track, don't block.

  The autocomplete-core 'health green while consumer dead' problem is not isolated: none of the ephemeral CP/MP consumers, nor the DP indexing consumers, expose their background consumer's liveness to their readiness probe. Because CP/MP consumers are fire-and-forget goroutines/tasks whose failure only logs, and DP consumers exit the process on error, the health endpoint (where present) is decoupled from whether events are actually being processed. Orchestrators and load balancers therefore keep routing to and trusting services whose event projections have silently stopped. This is a cross-cutting observability/honesty gap that masks every other finding in this report.  
  **Evidence:** autocomplete-core: src/ingest.rs:133-135 task death only logs; index-engine-rs/src/main.rs:96-100 admin/health router served independently of consumer_task state (:132-139); CP subscribers return from Start and the process health is unaffected by later handler/consumer death (e.g. org-core/internal/nats/subscriber.go:22-32).  
  **Recommendation:** Document that readiness must incorporate a consumer-heartbeat / last-processed-timestamp gauge and flip unhealthy when the consumer task/subscription is not live. Documentation only.
- **[P2] Shared durable-consumer scaffold's Stop() calls Unsubscribe() (not Drain) despite a 'drains' comment — in-flight handlers are interrupted at shutdown, relying on at-least-once redelivery + handler idempotency that not every handler guarantees** — `Application Plane (conversation-core-go, insight-core, notification-core) DurableConsumer scaffold` _(cat: graceful-shutdown-idempotency)_  
  The App Plane is the reliability exemplar (durable, manual-ack, nak-on-transient, and genuinely idempotent executors like AIActionExecutor with an atomic approved→executed claim guard). But the shared DurableConsumer.Stop drains via Unsubscribe(), which does not wait for an in-progress MsgHandler to finish; the doc-comment says it 'drains every bound subscription,' which is misleading. On shutdown a message mid-handler is left unacked and will be redelivered, so correctness depends entirely on each handler being idempotent. AIActionExecutor is idempotent; other bound handlers (identity_sync, metric/agent subscribers, webhook_received) should be audited for double-apply on redelivery. session-core's invalidator does use Drain() correctly, showing the intended API exists.  
  **Evidence:** apps/Application Plane/conversation-core/conversation-core-go/internal/consumers/consumer.go:54-68 (Stop uses sub.Unsubscribe(); comment line 4 says 'drain'); idempotent exemplar: ai_action_executor.go:100-161 (nak-on-transient, MarkAIActionExecuted claim); correct Drain usage: session-core upstream_invalidator.go:96-99.  
  **Recommendation:** Document that Stop should Drain() to let in-flight handlers ack before exit, and that all bound handlers need an explicit idempotency audit. Documentation only.
- **[P3] Cache-invalidation subscribers are ephemeral core NATS with no reconnect — self-documented as degrading only to TTL latency, but still die permanently on NATS disconnect** — `Data Plane v2 (retrieval-engine-rs grant/cache invalidators, quickwit-adapter-rs)` _(cat: missing-reconnect-loop)_  
  retrieval-engine-rs spawns grant/visibility cache invalidators over ephemeral core NATS (.subscribe); on subscribe error the task returns, and when the subscription stream ends (disconnect) the while-loop exits and the task is gone for the process lifetime with no reconnect. The code correctly documents that this degrades only to the 5-minute TTL backstop (the post-filter still resolves against canonical Postgres, so no wrong answer) — so the correctness blast radius is bounded, which is why this is P3 rather than higher. quickwit-adapter-rs stream.rs similarly uses an ephemeral .subscribe. Listing for completeness of the ephemeral-no-reconnect family; these are the lowest-impact instances because of the documented Postgres backstop.  
  **Evidence:** apps/Data Plane v2/services/retrieval-engine-rs/src/authz/visibility.rs:64-92 (spawn, subscribe, no reconnect; comment lines 52-57 note TTL-only degradation); retrieval-engine-rs/src/cache/invalidator.rs:32 nats.subscribe; quickwit-adapter-rs/src/stream.rs:31 .subscribe.  
  **Recommendation:** Document as accepted-risk-with-backstop but note a reconnect loop would remove the TTL-latency window on revocations. Documentation only.

### Fleet-wide security posture (cross-plane)

- **[P1] One Azure key backs ~10 Azure AI services across two planes** — `Model Plane + Data Plane v2 (Azure Cognitive Services)` _(cat: secret-reuse-blast-radius)_  
  A single Azure Cognitive Services key (AXO3fp...) is reused verbatim for AZURE_OPENAI_KEY/AZURE_OPENAI_API_KEY, AZURE_SPEECH_KEY, AZURE_TRANSLATOR_KEY, AZURE_CONTENT_SAFETY_KEY, AZURE_DOCUMENT_INTELLIGENCE_KEY and AZURE_AI_LANGUAGE_KEY, and the same value appears in BOTH the Model Plane and Data Plane v2 env files. Because Data Plane v2 was found (prior audits) to expose data with no credentials, a compromise of that lower-trust plane's env leaks the Model Plane's entire Azure AI account. One leak = full Azure AI takeover (uncapped spend, model abuse, content-safety bypass) across both planes with no per-service rotation possible.  
  **Evidence:** apps/Model Plane/.env: AZURE_OPENAI_KEY=AXO3fp***, AZURE_SPEECH_KEY=AXO3fp***, AZURE_TRANSLATOR_KEY=AXO3fp***, AZURE_CONTENT_SAFETY_KEY=AXO3fp***, AZURE_DOCUMENT_INTELLIGENCE_KEY=AXO3fp***, AZURE_AI_LANGUAGE_KEY=AXO3fp*** (all identical); apps/Data Plane v2/.env: AZURE_OPENAI_API_KEY=AXO3fp*** (same value); duplicated again in apps/Model Plane/deploy/.env  
  **Recommendation:** Document requirement: issue a distinct Azure key per service (or per plane) via separate Cognitive Services resources / Key Vault references so a single leak cannot pivot across services and planes; never place Model Plane provider keys in Data Plane env.
- **[P1] Anthropic and Google API keys shared across 3-4 services/planes** — `auth-core + Data Plane v2 + integration-corev2 + Model Plane (Anthropic/Google)` _(cat: secret-reuse-blast-radius)_  
  ANTHROPIC_API_KEY (sk-ant...) is identical in Data Plane v2 and Model Plane; GOOGLE_API_KEY (AIzaSy...) is identical across Control Plane auth-core, Data Plane v2, Ingestion integration-corev2 and Model Plane. The lowest-trust holder (Data Plane v2, no-cred data reads) governs the rotation of a key also used for paid Anthropic inference in the Model Plane. A leak anywhere forces fleet-wide rotation and exposes premium billing.  
  **Evidence:** apps/Data Plane v2/.env: ANTHROPIC_API_KEY=sk-ant***, GOOGLE_API_KEY=AIzaSy***; apps/Model Plane/.env + deploy/.env: ANTHROPIC_API_KEY=sk-ant***, GOOGLE_API_KEY=AIzaSy***; apps/Control Plane/auth-core/.env(.docker/.production): GOOGLE_API_KEY=AIzaSy***; apps/Ingestion Plane/integration-corev2/.env: GOOGLE_API_KEY=AIzaSy***  
  **Recommendation:** Document requirement: separate provider keys per plane with independent billing/rotation; keep inference provider keys out of Data/Ingestion planes entirely (route through Model Plane).
- **[P1] Shared INTERNAL_API_KEY blast radius spans three planes, not just Control+Data** — `Control + Data + Ingestion planes (INTERNAL_API_KEY)` _(cat: shared-internal-key)_  
  The prior audit scoped the shared 7647e1c6... key to auth/user/org/billing-core + Data Plane. Confirmed it is ALSO the INTERNAL_API_KEY in the Ingestion Plane root env, imports-core, integration-corev2 and services/support-worker, and is reused as AUTH_CORE_INTERNAL_API_KEY, DATA_PLANE_INTERNAL_API_KEY and NOTIFICATION_CORE_INTERNAL_KEY. One leak grants an attacker service-to-service impersonation across Control, Data AND Ingestion planes plus notification-delivery injection — a single static string with no rotation, no per-caller scoping, and no expiry.  
  **Evidence:** INTERNAL_API_KEY=7647e1c6*** in: apps/Control Plane/.env, auth-core/.env.docker, user-core/.env.docker, org-core/.env, billing-core/.env.docker; apps/Data Plane v2/.env; apps/Ingestion Plane/.env (also AUTH_CORE_INTERNAL_API_KEY=7647e1c6***, NOTIFICATION_CORE_INTERNAL_KEY=7647e1c6***), imports-core/.env, integration-corev2/.env (also DATA_PLANE_INTERNAL_API_KEY=7647e1c6***), services/support-worker/.env  
  **Recommendation:** Document requirement: replace the single shared static key with per-service credentials (mTLS or scoped signed tokens) and per-plane rotation; at minimum give each plane a distinct internal key so the trust radius stops at plane boundaries.
- **[P1] quarry-edge auth dev-bypass shipped ON with no ENVIRONMENT guard, accepts any bearer** — `Ingestion Plane / Quarry-v2 quarry-edge` _(cat: unauthenticated-surface)_  
  quarry-edge (the crawl/browser execution surface that runs pages on tenants' behalf) has a start-time safety net that ONLY refuses to boot when ENVIRONMENT (or APP_ENV) equals 'prod'/'production'. The shipped Ingestion Plane env sets QUARRY_EDGE_AUTH_DEV_BYPASS=1 and sets NO ENVIRONMENT variable, so env_name is empty, the guard does not trip, and the service logs a warning but starts with bypass active. With bypass on, every bearer is accepted without JWKS verification, so anyone with network reach can drive arbitrary page runs / change-monitor internal routes against any org. The control (JWKS verification) exists in code but is disabled by the default config plus a fail-open guard that keys off an unset env var.  
  **Evidence:** apps/Ingestion Plane/.env: QUARRY_EDGE_AUTH_DEV_BYPASS=1 with no ENVIRONMENT/APP_ENV set; apps/Ingestion Plane/Quarry-v2/crates/quarry-edge/src/main.rs:69 guard triggers only for env_name=='prod'|'production'; change_routes.rs:210-263 internal_dev_bypass() honors the same var to skip check_internal_token  
  **Recommendation:** Document requirement: make the guard fail-closed — refuse to start (or force verification) unless ENVIRONMENT is explicitly a recognized dev value; never ship QUARRY_EDGE_AUTH_DEV_BYPASS=1 in a deployable env file; set ENVIRONMENT=production in the Ingestion stack.
- **[P1] ZDR flag is Model-Plane-only; never propagates to content-persisting boundaries in Data/Ingestion** — `Cross-plane: Model -> Data / Ingestion` _(cat: zdr-propagation)_  
  The architecture rule requires Zero Data Retention to propagate through any content-persisting boundary. The zdr bool is defined and threaded throughout Model Plane protos (gateway, inference, execution, events) but there are ZERO zdr references anywhere in Data Plane v2 or Ingestion Plane code. So a ZDR-flagged run that persists documents/chunks/embeddings via Data Plane contracts, or captures evidence through Ingestion/Quarry, has no field to honor and retains content durably despite ZDR. Additionally, within the Model Plane the embedding path itself notes the EU/ZDR embedding provider is an unmet 'Phase-4 prerequisite,' so ZDR content may still egress to a retaining embedding provider.  
  **Evidence:** zdr present in apps/Model Plane/go/gen/model_plane/v1/{gateway,inference,execution,events}.pb.go and rust mp-contracts; grep for zdr/zero-data-retention/no_retention across apps/Data Plane v2 and apps/Ingestion Plane (*.go/*.rs) returns nothing; apps/Model Plane/go/gen/model_plane/v1/inference.pb.go:558-563 comment: 'An EU/ZDR embedding provider is a Phase-4 prerequisite'  
  **Recommendation:** Document requirement: add an explicit no-persist/ZDR field to the Data Plane document/chunk/embedding write contracts and the Ingestion evidence-capture contract, and thread the Model Plane zdr flag through every cross-plane call that can persist content; block ZDR runs from any retaining embedding provider.
- **[P1] Two disjoint HS256 JWT_SECRET domains; symmetric secret = token-mint capability at rest** — `Control Plane (user-core) + Application Plane (convex-core)` _(cat: jwt-symmetric-secret)_  
  Alongside the correct RS256/JWKS path used for Data Plane tokens, there are two independent symmetric HS256 JWT domains: Control Plane user-core signs/verifies with JWT_SECRET=40e8f7..., while the Application Plane and convex-core use JWT_SECRET=a2db55.... They do not share a trust root. Two consequences: (1) any Application-Plane service expecting to verify a Control-Plane user token cannot (secret mismatch) — pushing toward header-trust fallbacks; (2) because the secret is symmetric, any actor who can read a plane's .env can MINT fully valid user JWTs for that plane (no asymmetric public/private separation like the auth-core RS256 issuance). Combined with the broad .env sharing above, the mint capability travels with the secret.  
  **Evidence:** apps/Control Plane/.env + user-core/.env(.docker): JWT_SECRET=40e8f7***; apps/Application Plane/.env + convex-core/.env(.local): JWT_SECRET=a2db55*** (distinct value); auth-core issues RS256 via convex-auth/jwks (apps/Data Plane v2/services/documents-api-go/pkg/authctx/authctx.go:31-34)  
  **Recommendation:** Document requirement: converge all cross-service token verification on the asymmetric auth-core RS256/JWKS path (private key only in the issuer); if HS256 must stay, isolate the secret to the single signing service and never replicate it into verifier envs.
- **[P2] authctx verification confirmed only for documents-api-go; sibling services' wiring unverified** — `Data Plane v2 (data-quality-go, data-orchestrator-go, wiki-store-go, graph-index-rs, quickwit-adapter)` _(cat: authz-middleware-coverage)_  
  documents-api-go's authctx now verifies RS256/JWKS correctly and its compose sets AUTHCTX_ENFORCE=1 (good). authctx packages also exist under data-orchestrator-go, data-quality-go and wiki-store-go, but package presence is not proof the middleware is actually mounted on their data routes with enforce on — and the prior per-plane audit reported those exact services (plus graph-index-rs / quickwit-adapter) as readable with zero credentials. The observe-mode fallback (AUTHCTX_ENFORCE=0 + ALLOW_INSECURE_DEV_DEFAULTS=1, as set in tests/e2e/isolated/docker-compose.yml) trusts the X-Org-ID header outright, so any service left in observe mode remains a cross-tenant read.  
  **Evidence:** authctx pkgs: apps/Data Plane v2/services/{data-orchestrator-go,data-quality-go,wiki-store-go}/internal/authctx/authctx.go; enforce set only for documents-api-go in apps/Data Plane v2/docker-compose.yml:661 (AUTHCTX_ENFORCE: "1"); observe fallback path authctx.go:202-241; apps/Data Plane v2/tests/e2e/isolated/docker-compose.yml:23 ALLOW_INSECURE_DEV_DEFAULTS: "1"  
  **Recommendation:** Document requirement: verify each Data Plane service mounts authctx.Middleware with Enforce on for every data route (not just documents-api-go), set AUTHCTX_ENFORCE=1 for all of them in the shipped compose, and add a startup assertion that fails closed if any guarded router is missing the middleware.
- **[P2] No live secrets committed to git; .env gitignore coverage is complete** — `Fleet (git tracking)` _(cat: secret-hygiene-positive)_  
  Positive control worth recording so remediation does not waste effort on git-history scrubbing for these files. Every runtime secret file (root .env per plane, plus nested .env/.env.docker/.env.production/.env.local/lago.env/.env.bak.*) is matched by .gitignore and none are tracked. Only non-secret templates are committed. The residual secret risk is entirely runtime/at-rest sharing (findings above), not source control.  
  **Evidence:** git check-ignore returns IGNORED for all root and nested .env variants tested; git ls-files env/secret patterns yields only .github/workflows/secret-scan.yml, apps/Application Plane/.env.zammad.example, apps/Control Plane/.env.sso.template, scripts/generate_external_services_credentials.sh  
  **Recommendation:** Document as a maintained control; keep the secret-scan workflow as a merge gate and add a pre-commit gitleaks hook so newly added planes cannot regress this.
